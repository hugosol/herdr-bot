# 规划交付契约

## 共同身份

概要方案与能力建设需求分别自包含，通过方案标识、修订标记及稳定缺口编号关联；接收者无需读取其他 Chat 历史才能理解本次工作。

修订说明替代版本、受影响内容及仍有效的确认范围。业务取舍变化须重新取得用户确认，旧版本确认不自动覆盖新内容。

草案和待补能力方案是中间材料；只有当前版本经用户确认并满足转换条件，才能正式交给转换者。业务确认、成果批准、管理者接受交接和实际业务验证分别判断。

## 共同写入规则

默认避免覆盖，写入前查看目标现状，保存后读回核对。用户明确调整保存方式、覆盖范围、冲突处理或检查范围时，按其指示执行，不反复要求同一授权。

使用系统支持的接口，遵守代码校验与并发控制；接口拒绝时说明原因，不规避系统约束。交付时如实说明实际效果、已执行和省略的检查及剩余不确定性。

调用要求交付文件时，授权在本次明确的交付位置，或流程提供的内部材料位置，新建该项工作所需的交付文件；覆盖既有文件仍须明确授权。

## 规划文档保存与交接

独立使用且未要求文件时，可交付完整 Markdown 正文；要求文件时，保存完整、自包含的文档。流程内按命名输出交付，消费者直接读取实际绑定的文件，不从其他 Chat、报告摘要或同目录文件名推测材料。

正式交付位置以本次明确要求为准；流程内部材料使用运行上下文提供的位置。按「共同写入规则」处理保存方式、授权及检查范围。

交接说明当前修订、有效确认范围及正文或真实文件位置。流程中的文件登记、批准与报告遵循适用流程说明和工具指引；保存文件本身不代表成果已批准或交接已完成。

## 创建 Map 的整图交接

「创建map」各节点在准备交付本阶段成果时，读取本节对应阶段并按当前有效的交付与检查约定核对实际材料；不要求管理者读取本节或执行专属业务验收。用户明确省略某项默认检查，不自动构成阻塞，也不表示该检查已通过。

**概要规划**

当前版本已经用户确认，满足「概要方案」规定的转换条件。草案、待补能力方案和阻塞说明不能代替正式方案；不满足条件时，概要规划节点不将其报告为可交接成果。

**Map 转换**

完整 Map 已保存，已完成本次约定的检查；实际核验结果和待配置项有明确说明。转换节点核对满足条件后交接给后续优化，不将此阶段配置作为最终交付。

**整图优化**

获准修改已全部保存，已完成本次约定的检查；交接说明包含实际修改范围、共享影响、用户确定的边界和未验证事项。有阻塞或未完成修改时，优化节点不将其报告为可交接的最终成果。

最终成果以优化后的实际配置为准，内部 Map 文件与其一致。用户通过界面查看配置，本流程不要求公开成果文件，也不启动生成的业务。优化节点核对上述最终成果并按公共报告协议交接；管理者依据通用交接条件收束流程，不再次执行本节的业务检查。

## 能力建设需求

有能力缺口、需要用户另行衔接补齐时，按以下内容交付自包含的 Markdown 文档。无缺口时省略。

1. **身份与确认**：方案标识、修订、对应缺口编号及用户已确认的范围。
2. **所需能力**：目标、职责与非目标，能够接收的业务输入、预期成果及完成标准。
3. **复用调查**：已调查的相关能力、不能直接复用的原因，以及事实依据；不把名称相似或配置存在当作能力满足。
4. **缺口与已有条件**：区分仅缺 Task/Bot 等定义配置，还是缺少实际实现、工具、数据、资源或权限。说明已有条件、尚缺条件和未验证事项。
5. **操作边界**：已获授权、需要另行确认的操作，以及用户指定的宿主、模型和资源限制。
6. **补齐后需要返回的信息**：真实 Bot 身份及目标引用、使用条件、补齐结果、已验证与未验证事项、剩余阻塞或部分失败。返回信息须足以让规划者核实原缺口是否解决。

完成条件：每个缺口都有明确的所需结果、现有依据、操作边界和返回要求。本文不替代整体概要方案，也不授权接收者执行原始业务；补齐入口由用户决定。

## 概要方案

概要方案是转换者的完整业务依据。按以下内容组织，不依赖其他 Chat 历史补全。

1. **身份与确认**：方案标识、修订、替代版本，以及用户确认的内容和范围。
2. **目标与边界**：业务目标、验收标准、非目标、约束及操作授权。
3. **工作划分**：各项工作的稳定编号、职责、输入材料用途、预期成果及完成条件。
4. **能力选用**：所选真实 Bot、适用依据及关键限制。未解决的能力缺口使用稳定编号标识，不以假设能力代替。
5. **依赖与材料交接**：各项工作的前置关系、材料提供方、接收方及用途。保留已明确的接口 ID、文件格式和正式交付要求；未来成果不预造实际地址，依赖关系不代替材料接线。
6. **执行条件**：已核实的资源、执行位置及调用条件。Map 型调用所需的管理者配置、输入和材料关系必须明确；被调用 Map 的内部节点不展开。外层根 Run 的启动配置仅记录用户明确提供的值，不沿用规划 Run 的配置。
7. **证据与未决项**：区分事实、推断、未验证条件及阻塞，注明依据；缺口已补齐不等于实际业务已验证。
8. **转换要求**：本次允许新增或覆盖的范围、受保护对象及额外验收要求。转换者依据真实实现落实配置；业务选择缺失或需要改变已确认方案时，返回确认。
9. **能力建设索引（按需）**：关联建设需求的位置、修订和缺口编号，仅用于追踪，不代替正文中的必要信息。

**转换条件**

当前方案已获用户确认；影响转换的能力绑定、业务输入、依赖、材料关系、执行位置和权限均已明确且无矛盾，Map 型调用自身的管理者配置也已核实。

仅缺外层根 Run 的启动配置不阻止方案交付，须列为待配置；未解决的业务选择或能力缺口仍阻止正式交接。真实业务效果未经验证时如实注明，不以配置存在或方案确认代替验证。

## 能力选用与调用

**能力选用**

通过真实 Bot 目录发现候选，读取其适用条件、能力描述及输入输出摘要，判断能否满足本项工作、承接上游成果并支持下游需要。

摘要不证明实现存在或可运行。按概要方案的转换条件核实必要事实，记录缺口及未验证事项；不凭相似名称替换目标，也不自动补建能力。

**读取实现**

转换者解析 Bot 的实际目标，并读取：

- Task：完整工作设定及其引用资料，核实稳定职责、输入要求和交付方式。
- Map：完整定义及公开输入输出规则，核实本次调用条件，不展开内部节点生成父图。
- script：实际代码与调用接口，按真实参数和文件要求接线，不假定脚本理解自然语言委托。

Bot 与实现不一致时明确指出；涉及业务方案变化，返回用户确认。

**落实本次调用**

实现已有的稳定职责不复制进 node.input。材料来源、依赖、执行位置及成果策略使用结构化字段；本次目标、材料用途和特殊限制才写入节点委托，没有差异时可为空。

按系统定义文档中 Bot 与执行上下文的分工，逐项核对“实现及引用资料＋本次委托＋实际材料＋适用运行上下文”是否完整；稳定能力缺失应修复实现，而不是藏进节点委托。系统原则见 `${herdr-bot-path}/docs/scheduler.md`「定义职责与唯一格式」。

**Map 接口对接**

父节点输入 ID 与子 Map 公开输入 ID 同名，材料来源由父节点输入规则声明。必需材料在确认子 Run 输入就绪前备齐，不要求启动管理者前全部到位。

父节点所需输出只能取自子 Map 声明的公开输出，可要求其子集；不通过委托文字指定内部节点寻址。未声明公开文件输出的 Map，可以完成操作或交付系统配置，但不能据此提供命名文件成果。

实际路径由本次运行登记，不写进静态输出声明。具体字段形状及机械校验规则查询系统定义文档，不在本文重复维护。

## 保存与证据边界

**保存方式**

默认通过系统支持的方式新增 Map，优先采用用户指定的名称和位置。按「共同写入规则」处理保存、覆盖、冲突及检查范围；按需要执行定义检查和启动预检。

用户可以明确指定保存方式或调整检查范围，默认建议不是继续工作的额外门槛。具体配置接口和机械校验以目标平台文档及实际返回为准。

**结果说明**

如实说明实际保存结果、执行或省略的检查及剩余不确定性。失败或效果不明时先核实现场，再按用户指示处理；不把未验证、部分成功或结果未知说成成功。
