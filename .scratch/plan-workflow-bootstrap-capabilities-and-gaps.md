# plan_workflow：自举设计、能力范围与当前缺口

日期：2026-10-30  
状态：讨论整理与后续设计依据，不是已实施规格或开发票据。

## 1. 本轮目标与证据范围

本轮收窄为两项交付：

1. 设计一张用于构建新 Map 的 Map，即 plan_workflow。
2. 设计四种可复用 Bot：创建概要计划、概要计划转换为 Map、创建 Task、创建 Bot。

用户报告已实现根据 Map 调度工作流的基本框架。本文件依据本次讨论及当前长期文档进行静态核对；没有重新运行产品、核验外部 toolkit 部署、审计全部代码或读取全部实际 Bot/Task 配置。因此，“未确认”不等于“底层完全不存在”，文档中的接口事实也不代替真实运行证据。

本文不修改产品代码、实际配置或现有运行。未确定的工具名、交付格式和界面交互不作为已批准实现。

## 2. 核心思想：工作流生产工作流

以前的路线是：已有 Bot → 从现有能力中选择组合 → 生成 Map。

现在的路线是：用户目标 → 概要规划 → 复用已有能力／构建缺失能力 → 生成业务 Map。

已有能力仓库是复用起点，而不是规划的永久上限。创建能力、验证假设、整理交付、生成定义，都可以成为工作流组织的工作，不必由用户在多个会话和配置页面之间手工搬运。

需要区分两张 Map：

- **自举 Map**：组织规划与能力建设的既有定义。
- **业务 Map**：本次规划产生的新定义，负责之后的业务执行。

生成业务 Map 不等于自动发起它。规划交付与正式业务执行分别授权、分别观察。

第一张自举 Map、四个 Bot 及其绑定 Task 可以人工配置；不要求系统在能力尚不存在时先创建自己。之后可以用这些能力生成、维护下一批 Task、Bot 和 Map。

## 3. 这套设计能够承载什么

### 3.1 从自然语言到可执行定义

用户表达目标，规划会话读取能力说明与项目规范，通过讨论形成方案，再交给独立会话落实为符合格式的 Map。用户不用首先手写 JSON，但仍能查看与理解生成的对象。

### 3.2 复用能力并补齐缺口

规划先搜索已有 Bot；已有能力适用则复用，缺失则形成明确的能力需求，交给创建 Task、创建 Bot 的能力处理。

必须区分两类缺口：

- **配置缺口**：底层工具、数据和权限已经具备，只缺执行预设或能力说明，创建 Task/Bot 可能足以解决。
- **真实能力缺口**：缺少代码、工具、数据、凭据或外部条件，仅生成配置并不能补齐。工作流可以组织建设或请求人工提供条件，但必须如实说明尚未具备的能力。

因此，本设计提供可扩展的工作流生产方式，不保证“任何问题都能解决”。

### 3.3 将上下文切分变成工作流设计

用户不必手工完成“讨论 → 整理结论 → 新建会话 → 搬运背景”。可以把有独立交付的工作设计成不同节点，由系统创建不同 Chat。

拆分标准不是动作数量，而是目标与交付是否稳定：

- 搜索 Bot 与组合流程保留在同一设计会话，用户否定当前方案后可以继续搜索、重新组合。
- 能力需求明确后，可以交给独立会话创建 Task、创建 Bot。
- 方案准备好后，交给独立会话生成严格 Map，避免被大量已放弃方案干扰。

这里的“单向门”表示下游能够凭交付独立工作，不表示业务上永远不能返工。上下文隔离有助于减少目标混淆，但不是正确性保证。

### 3.4 在讨论中按需验证

概要规划会话应保留调用 subagent 调查、验证的能力；需要额外权限时，申请明确授权后做小范围试验，再根据结果修改计划。

验证是讨论中可随时插入的能力，不必固定为每张规划图都经过的阶段。主会话保留目标、方案和取舍；子会话接收窄范围问题、必要材料、操作范围和预期观察，返回事实、结论及限制。

已有授权内的只读调查不必全部新增审批；需要写入、外部调用或其他新增权限的试验，要说明对象、影响和授权范围。不能因委派而扩大权限。

试验验证的是明确假设，不是提前完成全部正式业务。一次样例成功不证明所有输入都可靠。

### 3.5 减少长尾 UI，并保留可理解性

不为每种复杂情形设计专用表单或向导：常用动作保留直接 UI，长尾需求由对话与工作流组织。

- Task、scheduler 发起等位置保留直接入口。
- 流程图呈现工作结构和进度，相关详情提供结果、配置与 Chat 的定位。
- 用户通过文字描述目标、调整方案、处理非标准情况。
- 用户仍需理解 Task、Bot、Map/Workflow、Run 等基础概念；配置可按需查看，复杂机制渐进展开，而不是完全隐藏。

这是交互方向，不表示现有只读 workflow 图已经支持自然语言修改、直接停止或任意操作。底层规则与校验不因增加聊天入口而被绕过。

### 3.6 用系统自身能力教用户上手

可以另外配置一个教学 Task，介绍基础概念，带用户查看真实对象并完成小范围上手体验。它是可扩展应用，不是上述四个核心 Bot 之外强行新增的首轮阻塞项。

目标是让用户知道当前操作对象、定义与运行的区别、配置和结果的位置，以及怎样进入相关会话纠正；不要求第一次使用就学会全部配置字段。教学 Task 是提案，未实现或验证教学效果。

## 4. 四个核心 Bot 的职责

| Bot | 主要输入 | 主要工作 | 独立交付 |
| --- | --- | --- | --- |
| 创建概要计划 | 用户目标、约束、Bot 目录、背景材料 | 搜索与组合往返、必要澄清、委派验证、识别能力缺口 | 当前方案、复用 Bot、缺口、依赖与交接、验证事实及未决项 |
| 概要计划转换为 Map | 当前方案、能力准备结果、node_guide、Map 规范 | 落实 node.input、引用、zone 和依赖，生成并校验定义 | Map 位置、结构校验结果、启动条件及缺项 |
| 创建 Task | 明确的能力需求、可用宿主与配置规范 | 配置固定职能、合法执行环境及必要工具，不虚构依赖 | Task 身份、配置、使用条件和必要验证结果 |
| 创建 Bot | 业务能力说明、已创建或已有 Task | 编写 when、plan_guide、node_guide，并明确绑定 | Bot 身份、能力说明、Task 绑定与限制 |

按现行结构，Map node 引用 Bot，Bot 通过 task_id 引用 Task；不是 Map 直接引用 Task。四个 Bot 自身也需要执行 Task。作为节点执行时使用 normal Task；管理者使用 manager Task。

这些 Bot 应能独立使用，不仅是自举 Map 内的私有提示词。当前没有必要仅因为出现规划角色，就预设必须新增底层 plan Task 类型；是否需要新类型，取决于确实不同的权限或生命周期，尚未确定。

## 5. 建议的协作关系与交付边界

```text
用户需求
   ↓
概要规划：理解 ↔ 搜索 ↔ 组合 ↔ 用户反馈
   │             ↕
   │        subagent 验证／授权试验
   ↓
明确方案与能力缺口
   ├─ 已有 Bot：复用
   └─ 缺失能力：创建 Task → 创建并绑定 Bot
   ↓
将当前方案落实为 Map
   ↓
交付定义、校验结果与限制
   ↓（另行选择并授权）
发起业务 Run
```

该图表示业务协作，不宣称现有调度器已实现条件跳过、循环、嵌套 Run 或运行时动态改图。

### 5.1 概要计划不应模糊

概要计划无需采用最终 JSON，但至少应保留：用户目标与限制、工作划分、每项交付、选定 Bot、能力缺口、依赖与材料交接、已验证事实和未解决问题。

下游接收的是当前方案，不是所有聊天记录。放弃方案的历史通常不必搬运；仍约束实施的结论必须保留。

### 5.2 材料必须显式交接

当前 blocked_by 仅表示前置约束，不自动传递产物；节点也不会自动继承用户给管理者的要求或完整规划对话。应约定可读材料位置、报告读取方式和交付内容，并明确写入输入或由节点按约定读取。

初期可使用有清楚章节的 Markdown 交付，不必预先建设通用类型化产物系统。但具体格式、保存位置和“当前方案”的识别方式仍需设计。

### 5.3 分开反馈三种结论

1. 业务方案是否合理：依赖用户目标、Agent 判断与必要验证。
2. 定义是否结构合法：依赖现有结构与依赖检查。
3. 当前是否可启动：依赖真实 Bot/Task/zone 及管理者启动配置。

可保存不等于可启动；预检通过不等于已启动，更不等于业务结果正确。input 当前是原文字符串，无模板插值；可重复发起的 Map 不自动等于参数化模板。

## 7. 当前缺口与需确认项

### G1. 自举资产尚未在本轮交付

四个 Bot、各自 Task、管理者指引与首张 plan_workflow 需要形成真实可用配置。本轮仅确认设计方向，未核实实际仓库是否已有部分资产，不能把讨论当成部署完成。

### G2. Agent 可用的配置读写闭环尚需落实

需要使 Agent 能发现真实配置、创建 Task、创建 Bot、生成整张 Map、读取保存结果与错误，并遵循现有冲突及路径规则。

现有文档列出了 Bot 保存和 node 编辑接口；所核对的接口表没有提供完整的新 Map 创建接口，也没有证明上述能力已封装为 Agent 工具。这里是接入和核实缺口，不据此断言产品完全没有相关代码。

应优先复用真实写入与校验能力，避免维护 UI 和 Agent 两套不同规则。采用现有接口还是受控文件写入需核实后决定，不能靠直接改文件绕过并发、校验或状态维护。

### G3. Bot 发现与按需读取机制需验证

已有 Bot 目录与说明；面向规划者的 when 搜索、返回身份及适用依据、继续读取 plan_guide/node_guide 的具体机制尚未确认。UI 按名称／ID 筛选不等同语义能力搜索。搜索未命中也不能直接认定能力不存在，应允许改写检索或浏览目录。

### G4. 阶段交付与本次需求传播尚未定义

需要确定概要计划、缺口、能力创建结果和验证结果怎样交接。当前管理者 user_input 不自动注入节点，必须显式解决本次需求与材料位置如何到达规划节点，而不是指望共享聊天上下文。

### G5. 可变数量能力缺口的承载方式尚未选择

一次规划可能没有缺口，也可能有多个缺口。现有依赖图、状态和动作没有据此自动提供条件跳过或动态扩图。

可研究固定建设节点处理缺口清单，或由会话内委派完成多项建设；二者只是候选，不是已批准方案。需说明零缺口时如何诚实完成交付、多个缺口怎样定位失败，以及何时可以进入 Map 生成。不要为此默认建设通用循环／动态改图系统。

### G6. 规划中 subagent、试验及授权接入需确认

需要核实目标宿主及实际 Task 暴露哪些委派、调查、试验工具，以及权限申请发生在哪里。具备 omp/pi 执行能力不自动证明每个 Task 都能调用这些工具。

尚需约定试验范围、权限传递、观察证据、产生的资源及必要清理；不默认所有只读动作都审批，也不将规划授权扩大为正式业务执行授权。

### G7. 新能力的真实就绪条件需明确

Task/Bot 保存成功不证明工具、权限和业务行为可用。根据具体缺口采取必要的样例或小范围试验，记录尚未具备的条件；不为所有能力强制加入统一严格验收，也不假装未验证就是验证通过。

### G8. 业务生成与运行前配置需要衔接

生成者需要读取真实绑定和登记 zone。现有 preflight 还需要 managerTaskId、zone、userInput；不能凭空选择管理者或默认目录来宣布可启动。应明确缺配置时怎样交付合法草稿并提示缺项，条件齐全时怎样运行预检。

### G9. 返工的用户路径需明确

搜索与组合留在同一 Chat，天然支持讨论往返。进入后续阶段才发现设计问题时，仍需明确返回哪个会话、更新哪份方案、哪些产物需要重新生成。不要将任意修改运行中定义作为返工方式，也不要将格式修正与业务重设计混在一起。

### G10. 交互与教学属于后续可落实能力

常用入口、配置可查、图与对话相互定位有现有基础；“引导式创建新工作流”与教学 Task 的内容、入口和体验尚待设计及实测。无需先做一个覆盖所有情形的复杂 UI，也不能声称聊天入口已经实现全部操作。

## 8. 与当前运行约束的关键衔接

现有 Run 在启动前检查全部节点，运行期间要求定义与 Task 配置保持不变。因此：

- 自举 Map 的四类执行能力必须预先存在，并满足自身启动配置。
- 本次新建的 Task/Bot 是供新业务 Map 使用的产物，不应通过修改当前自举图来临时替换正在执行的能力。
- 不要把尚不存在的业务 Bot 直接放入自举 Map 的待执行节点，指望前一步创建后再绕过启动预检。
- 生成业务 Map 后再独立预检和发起，是两张 Map、两次运行的自然分离，不要求嵌套 Run 协议。
- 当前后端重启后旧 Run 只读，普通 Chat Resume 不恢复运行管理权；本设计不自动解决长规划跨重启的接管问题。

这些约束不否定自举，而是帮助选取与已有底座相容的首轮实现。

## 9. 建议的首轮闭环与验收

以下是后续实施建议，不是已完成测试或用户逐项批准的票据。

选一个小业务需求，包含一个可复用 Bot、一项能通过真实现有工具补齐的能力，以及一个需要验证的疑问。

应实际观察：

1. 用户在概要规划 Chat 里讨论，并至少完成一次“重新搜索／组合”，未被固定单向步骤阻断。
2. 对一个明确疑问完成调查或经授权的小试验，返回依据与限制，并影响方案。
3. 创建真实 Task 与 Bot，绑定正确，能在现有界面查看；不伪造底层能力。
4. 独立生成 Chat 凭交付落实业务 Map，不依赖完整规划聊天历史。
5. 结构校验通过；有完整启动配置时预检通过；缺项时明确报告而非补默认绑定。
6. 用户另行授权后，实际运行生成的业务 Map，确认交接路径和最终业务结果。
7. 用户能从图或相关详情找到配置、产物及执行 Chat，不需要理解全部内部协议。

同时检查零能力缺口不会迫使创建重复 Task/Bot，多缺口不会丢失部分失败或提前宣称全部就绪。教学 Task 可随后独立验证，不作为本轮四 Bot 自举的必经依赖。

## 10. 本轮不应顺带扩张的范围

不自动引入：通用动态改图、循环调度、任意条件表达式、参数化模板语言、通用权限审批平台、统一严格业务验收系统、自动执行所有生成 Map、复杂配置向导或新 Task 类型。

若真实案例证明某项是必要条件，再单独决策；不要用扩展潜力替代首轮真实闭环。

## 11. 后续讨论确认：首轮人工衔接能力建设

以下决定更新本文前述候选方案的首轮范围，不表示已完成配置或实现。

- 创建 Task 与创建 Bot 合并在一个 Chat 中完成，交付真实的 Bot、对应 Task 及绑定结果；不要求分成两个执行会话。对象职责仍保持分离。
- 概要规划 Chat 发现现有 Bot 无法覆盖需求时，首轮由用户手动在 zone 中使用能力创建 Task 发起 Chat，创建所需 Bot＋Task，再由用户将结果交回概要规划 Chat，继续讨论。
- 首轮不要求概要规划节点调用能力创建 Bot，不增加 executor 的调度权限，不引入运行中动态新增 node、自动委派或自动返工循环。
- 自举 Map 的主链保持“概要规划 → 将概要计划转换为 Map”；能力补齐通过上述人工衔接推进，不要求加入固定的能力建设节点。
- 下一阶段再讨论：当现有 Bot 能力不足以覆盖概要规划 Chat 中发现的需求时，系统应通过什么机制解决，包括是否需要能力调用、委派或其他组织方式。本轮不预选技术方案。
- 人工衔接不改变真实性边界：创建配置不能替代缺失的工具、数据、凭据或权限；创建结果应说明真实身份、绑定及尚未满足的条件。
