# Node 成果批准与交接门禁

Status: ready-for-agent

Contract: [已批准的成果批准与交接门禁契约](contract.md) — Full automation。后续批准的约束以 contract 为准：不兼容旧 Run；approve 不新增 manager 通知；批准工具不要求交接说明；清理旧报告发送审批专属测试。

## Problem Statement

用户需要把人工控制放在“当前 node 的成果已经足够，可以交接”这一业务边界，而不是文件写入、输入整理或报告发送上。

当前 node 的 report_policy 控制报告发送是否需要原生批准，但允许发送报告不等于成果可以交接。创建 Bot V1 的材料协议又要求 authorization.create_blank、write_materials、save_guides 等业务授权声明。脚本校验这些字段，上游生产者为了生成合法输入而询问下游授权，导致通用提示词优化节点也因下游创建或材料写入授权而停止。

write_materials 当前实际表示写材料授权，并不是通用成果批准状态。文件可以在讨论中持续落盘；写入完成既不表示成果审核通过，也不应要求用户先批准最终成果。将两者混同使设计交流、节点解耦及自动流转都受到影响。

用户希望普通 node 在自己的 Chat 内完成业务讨论与成果确认，manager 自动整理输入、核对交接并推进流程；脚本型 Bot 仅执行脚本，不增加人类执行前审批。创建 Bot V1 与 V2 需要保持独立并行，不以本次改造替换或移除其中之一。

## Solution

以可选人工确认的“成果批准”替换 node 的报告发送确认机制。

普通工作 node 使用 auto_approved 配置。每次执行有持久的 approved 事实，初始为 false。auto_approved=true 允许 node-chat 在判断工作已经足够交接时直接调用成果批准工具；它不表示派发时自动获批。auto_approved=false 时，同一工具必须展示原生用户确认，只有用户显式选择 Yes 才能记录批准。

report 始终可以发送进度、失败、问题或成果，不再要求报告发送批准，也不会隐式批准成果。成果批准不要求先产生报告、文件或其他产物。manager 只有在该次执行已批准并满足原有其他完成条件时，才能 complete；现有依赖完成规则继续控制下游派发。批准不自动 complete、dispatch 或 finish。

approved 表示成果已经足够，不冻结成果。批准后允许继续修改，不自动撤销批准，不承诺后续优化一定被已推进的下游消费。批准记录与本次执行关联，但调用者不需要填写 execution ID、报告 ID 或正文版本。

脚本节点固定自动批准，成功执行并通过现有结果校验后由运行时记录；失败不批准。结束节点保持成功发起即可交给用户继续的特殊职责，不受 approved 限制。嵌套 Map 的子 manager 按父节点配置提交整体成果批准。

删除 V1 创建脚本的整个 authorization 对象及其生产、消费要求，精简为执行必需材料。批准事实属于通用执行交接机制，不属于创建业务 request，不以 approved 替换 authorization 下的某个字段来保留旧授权链。

## User Stories

1. As a workflow 用户, I want 人工确认发生在成果交接时, so that 不必为材料整理或脚本执行反复批准。
2. As a Map 设计者, I want 为普通 node 选择 auto_approved, so that 可以按业务需要决定是否由人类把关。
3. As a Map 设计者, I want 默认采用自动批准模式, so that 无需人工审核的工作不会引入新的等待。
4. As a node 执行者, I want 在自动模式下自主调用成果批准工具, so that 可以在判断成果足够时推进交接。
5. As a workflow 用户, I want 人工模式展示原生 Yes/No 确认, so that 只有我的显式操作才能批准交接。
6. As a workflow 用户, I want 拒绝批准后仍能继续讨论和修改, so that 拒绝不会被误判为执行失败。
7. As a workflow 用户, I want 取消或超时后保持未批准, so that 未作决定不会被解释为同意。
8. As a node 执行者, I want 确认界面不可用时保持未批准并收到明确反馈, so that 不会伪造用户批准。
9. As a node 执行者, I want 在准备好后主动再次请求批准, so that 修改后的工作仍可继续交接。
10. As a workflow 用户, I want 系统不自动重试批准请求, so that 不会被重复确认打扰。
11. As a node 执行者, I want 随时发送进展、问题和失败报告, so that manager 不必等待人工批准才得知真实状态。
12. As a manager, I want 报告发送和成果批准相互独立, so that 收到报告不被误认为成果已批准。
13. As a node 执行者, I want 在没有文件产物或成果报告时也能请求批准, so that 无产物任务不必制造占位材料。
14. As a node 执行者, I want 工具从当前执行角色定位批准对象, so that 无需手填 execution ID 或其他运行身份。
15. As a workflow 用户, I want 普通聊天中的同意不能绕过人工模式的原生确认, so that 批准规则清晰稳定。
16. As a manager, I want 后端拒绝完成尚未批准的普通工作节点, so that 流转不依赖模型是否记得检查批准。
17. As a manager, I want 批准后仍需核对原有完成条件, so that approved 不掩盖失败或缺失交付。
18. As a manager, I want 批准不自动派发下游, so that 仍由我负责工作安排与交接验收。
19. As a workflow 用户, I want 无依赖的其他分支不受某节点等待批准影响, so that 审核不会阻塞整个 Run。
20. As a node 执行者, I want 批准前即可持续写材料, so that 可以一边讨论一边修改成果。
21. As a node 执行者, I want 批准后仍能继续优化, so that 批准不是停止工作的命令。
22. As a workflow 用户, I want 清楚知道批准后的优化不保证传给下游, so that 不会误以为存在自动同步承诺。
23. As a workflow 用户, I want 批准状态在会话恢复和服务重启后保留, so that 不必为同次执行重复批准。
24. As a manager, I want retry 的新执行不继承旧批准, so that 上一次执行的结论不会错误应用到新工作。
25. As a workflow 用户, I want 不同 Run 和不同执行的批准相互隔离, so that 批准不会串用。
26. As a 脚本型 Bot 使用者, I want 脚本不出现人工执行前批准, so that 固定业务能直接执行。
27. As a 脚本型 Bot 使用者, I want 成功脚本自动记录批准而失败脚本不获批, so that 自动流转仍反映真实结果。
28. As a Map 设计者, I want 脚本节点不能配置人工批准模式, so that 不会生成没有 Chat 可以处理的确认等待。
29. As a 子 Run manager, I want 按父节点配置批准子流程的整体成果, so that 内部完成和父层交接保持清晰边界。
30. As a 父 Run manager, I want 子节点批准不自动替代父节点整体批准, so that 嵌套工作得到独立交接验收。
31. As a 结束节点使用者, I want 成功发起后仍可按原规则结束 Run, so that 不必等待交给用户的后续工作完成。
32. As a V1 创建流程使用者, I want 上游不再填写创建、材料写入和脚本保存的授权凭据, so that 通用节点不会为下游申请进入许可。
33. As a V1 创建流程使用者, I want 普通编写节点保留其成果讨论与人工审核, so that 删除脚本授权不会删掉真正需要的业务把关。
34. As a V1 创建流程使用者, I want 保存脚本仅消费执行必需材料, so that 不再维护用于脚本验权的交接书。
35. As a V1 与 V2 使用者, I want 两套创建流程独立并行并使用同一通用批准机制, so that 可以逐步比较而不被强制替换。
36. As a Map 维护者, I want 迁移按节点实际成果审核职责决定配置, so that 旧字段不会造成误放行或额外人工门禁。
37. As a workflow 页面使用者, I want 看见批准模式和本次执行的批准状态, so that 能区分正在工作、等待批准和等待 manager 验收。
38. As a chief 使用者, I want chief 委派与 chief 报告确认维持现状, so that node 机制改造不会误改其他批准边界。

## Implementation Decisions

- 使用现有领域词汇：Task 是预设，Bot 是能力定义，node 是 Map 中的一项工作，Run 是 Map 的一次运行，节点执行角色由当前执行关联决定。脚本型 Bot 不是一种 Task 类型，也不创建 Chat。
- 新增通用成果批准概念。auto_approved 是 node 配置；approved 是本次执行的运行事实，两者不得共用一个字段或通过材料写入状态推导。
- 普通节点默认 auto_approved=true。它代表允许执行者自主提交批准，不代表运行开始即 approved=true。
- node 的 report_policy auto/manual 及对应发送批准机制由新机制替代，不保留两套并行的 node 审批开关。报告继续保留现有保存、归属、通知与失败事实，不因移除确认而弱化身份检查。
- 人工模式必须通过成果批准工具的原生 UI 显式 Yes；普通文字、报告内容、LLM 声明或旧报告发送批准不能代替。拒绝、取消、超时、UI 不可用均不能写入批准。
- 自动模式允许当前合法 node-chat 直接调用批准工具。工具不要求先有报告、成果文件或非空输出，不引入 report ID、正文摘要或严格成果版本绑定。
- 批准对象由当前会话的真实执行角色解析；LLM 不负责提交 execution ID。运行事实仍需隔离不同 Run、node 与执行，不能允许任意 Chat 批准别人的执行。
- approved 由后端持久记录，普通工作节点的 complete 必须同时满足批准和原有完成条件。现有报告要求、输出约定及依赖规则不因批准工具不要求产物而被取消。
- 成果批准不意味着 manager 已接受交接，不自动 complete、dispatch、finish，也不代表目标业务效果已被独立验证。
- 同次执行批准后可以继续修改、继续报告，批准不自动撤销；不保证后续修改被已派发的下游接收，不增加自动同步、追赶或重新派发。
- 恢复同一 Chat、同次执行或重启服务保留批准事实。明确 retry 创建新执行时 approved 从 false 开始，不继承旧批准。
- 拒绝批准不是执行失败。节点继续工作后可主动再次请求；无自动重试、弹窗循环或隐式批准。
- 脚本节点固定自动模式，不能选择人工批准；成功执行并通过现有输出／结果校验后由运行时记录批准，失败不批准。仍由 manager 验收并显式 complete，不伪造节点 Chat 或用户批准。
- 嵌套 Map 的子 manager 同时承担父节点执行角色，在子流程完成后按父节点配置提交整体成果批准。子流程内部的批准不自动批准父节点；父 manager 另行 complete。
- 结束节点保持成功发起即可交给用户继续的特殊职责，不配置成果批准门禁，不通过伪造 approved=true 来实现豁免。
- V1 创建脚本 request 中整个 authorization 对象及生产者、消费者要求删除，包括 create_blank、write_materials、save_guides。不把它改名为 authorization.approved，也不让 LLM 自动填写批准布尔值以绕过旧机制。
- 删除 V1 脚本材料中的批准凭据门禁和供脚本验权的确认要求；保存脚本只要求实际执行需要的基线、目标、明确绑定正文等材料。不再强制消费三份业务批准交接书。普通节点的业务说明与批准历史可以保留供 manager 了解，但不转化为脚本许可证。
- 保留执行正确性约束：材料形状、目标与字段归属、必要内容一致性、真实 revision、并发冲突、合法保存、完整读回及部分失败事实。当前把摘要匹配和授权混在一起的检查应拆分职责，不能整段删除导致数据正确性退化。
- 发布节点迁移先以 write_materials 和旧 manual report 查找候选，再核对实际 Task 与 node 业务职责。明确需要用户确认本节点成果后交接的普通节点采用人工模式，其余采用自动模式；脚本始终自动。不能机械地把旧 manual 或 write_materials 映射为人工成果批准。
- 创建 Bot V1 与 V2 保持独立并行；通用 node 批准替换适用于二者及其他 Map。V1 脚本材料协议清理不扩展为 V2 业务材料协议重写。
- 不兼容旧版本 V1 业务材料，不增加旧字段别名、双解析器或旧协议自动转换。不删除旧历史及产物，不自动重跑已有副作用。
- 涉及后端运行模型、公开操作、持久化与门禁，前端节点配置与状态呈现，以及配套 OMP／Pi 的 node 工具、原生确认和角色指引。具体模块划分、工具参数、存储形式及测试 seam 留给 /to-contract，不在此预选。
- 现有 ADR 0019 关于脚本不创建 Chat、自动报告及 manager 显式完成的边界继续成立；其“两个业务脚本保留授权检查”的决定由本需求明确改为纯执行输入与正确性校验，实施时同步修订。通用 approved 不以该旧决定为由恢复脚本审批。

## Testing Decisions

- 现有后端 workflow 回归已有真实公开操作、执行隔离、报告保存／通知、完成门禁、脚本生命周期及嵌套运行的先例；沿用既有测试组织与独占资源规则，不以配置存在或接线快照证明业务成立。
- 现有创建脚本验证通过真实 HTTP、Bun 子进程、实际文件和完整读回验证创建与保存；纯 Schema 通过不能代替这些执行事实。
- 现有前端交互与浏览器验收区分受控外部宿主和真实原生宿主证据。批准配置及状态呈现需要观察真实页面，不能仅以类型检查代替。
- 人工批准沿用真实安装 OMP／Pi 原生确认的验证方式，需要区分 Yes、拒绝、取消、超时、UI 不可用与普通聊天同意；受控 provider 的协议证据不能被称为真实模型业务决策证据。
- 持久批准、恢复、retry 隔离及后台门禁不能仅靠模型复述证明。自动模式也不能因为字段设为 true 就声称工具已调用或执行已获批。
- 无成果文件或尚无报告时调用批准的行为不得被新增测试前提排除；批准工具的宽松前提不用于放宽已有 complete 业务条件。
- 独占定义、数据目录、原生会话、端口与进程；不使用用户历史 Chat 或生产 Run 做破坏性验证。不读取未授权凭据、不执行真实关机；结束时确认所属进程退出，保留原错误与清理失败。
- 沿用仓库现有后端、前端、浏览器及配套工具集检查入口。精确 seam、承诺、覆盖分配和验收矩阵由 /to-contract 决定；本 spec 不预定测试边界或以已有测试通过代替新行为验证。

## Out of Scope

- 修改 chief 委派确认或 chief 报告确认。
- 移除 V1、合并 V1 与 V2，或将其中一套流程自动改为调用另一套。
- 重写 V2 专用业务材料协议；其现有字段不因通用批准新增而被自动当作 approved。
- 为脚本新增人工审批、审批 Chat、外层业务授权系统或审批凭据验证。
- 成果冻结、严格批准版本绑定、正文哈希批准锁、批准后自动失效或自动撤销机制。
- 保证批准后修改自动传播给已派发下游，或自动重跑、同步和返工调度。
- 用 approved 替代 manager 的交接验收、现有报告／输出条件、节点完成或 Run 结束。
- 取消节点内部业务讨论、候选审核、用户明确限制、合法保存或并发保护。
- 旧 V1 业务材料兼容层、批量改写用户历史、删除旧产物或自动部署并重跑用户正在进行的工作。
- 在本阶段决定接口 seam、精确 API 路由、工具形状或实现票据拆分。

## Further Notes

- 本 spec 来自已完成的设计讨论，不表示代码、部署或原生宿主行为已经实现或验收。本轮仅发布需求规格。
- 最初的问题来自一个 W2 普通优化 Chat：其 prompt 保存已授权，但为生成下游创建 v1 request 被迫补齐空白创建及材料写入授权。这证明的是业务协议把下游授权责任倒灌给上游，不是所有脚本运行时天然要求用户审批。
- 用户最终选择从通用报告发送确认切换为通用成果批准，范围因此从最初 V1 脚本材料清理扩大到所有普通 workflow node 的交接控制。脚本和结束节点有明确特殊规则。
- approved 的领域含义为“用户或按配置获准自主判断的执行者认为当前成果已经足够交接”；人工与自动来源必须可区分，不能把自动批准表述为用户批准。
- write_materials 是旧业务授权字段，不是既有 approved 的别名。新机制与旧材料字段分离是本次消除概念混乱的必要条件。
- 下一步对本 spec 执行 /to-contract，选择承诺承载边界并批准承诺；该阶段需核实两仓实际能力和当前代码，不能把本 spec 中的模块范围当作已选定 seam。
