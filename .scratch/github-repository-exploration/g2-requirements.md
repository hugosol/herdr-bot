# G2：克隆仓库登记 zone 脚本与 Bot——详细需求

## 1. 身份、目标与确认范围

- 方案标识：`github-repository-exploration`；缺口编号：`G2`；对应工作：`W2 登记 zone`。
- 文档修订：`g2-r1`。本文件细化此前 requirements-r1 中的 G2，独立完整描述所需上游接口；接收者无需读取其他 Chat。
- 用户已确认：zone ID 直接为 `<owner>/<repo>`，不加 github 前缀；同 ID 已登记则停止，不复用；目标本地仓库由前一步浅克隆得到；所有业务参数及上游交付用命名文件传递。
- 本次授权仅编写文档。本文是待建设需求，不是配置保存、登记实际 zone、实现代码或试运行授权，也不表示当前缺口已补齐。
- 完整业务背景：W1 脚本浅克隆 → W2 脚本登记 zone → W3 在该 zone 发起“开源项目仓库探索”Task 的结束节点 Chat。W3 成功发起后，管理者可显式 finish，用户继续探索 Chat。
- G2 的完成边界：真实登记与独立读回，以及可交给管理者/W3 的 zone 文件；不启动 Chat，不直接派发第三节点。

## 2. 能力与接口要求

### 2.1 执行形态与配置

交付预先实现的 TypeScript 脚本与脚本型 Bot，复用现有 Bun 宿主，不新增 Task、Chat、后端执行器或调度器。Bot 只绑定合法相对 `.ts` 的 `script`，不混用 task_id/map_file。

节点使用 `report_policy=auto`、`auto_close=false`，不设置 manager_task_id，不是结束节点。脚本正常退出、报告成功、manager complete 是不同事实；不得自动推进 W3。

业务服务为 `http://127.0.0.1:18787`。服务地址来自明确部署配置，不从被克隆项目或上游任意字符串推导。隔离验收可明确配置另一个回环服务，不准失败后回退生产。

脚本运行 zone 应是事先已登记且可用的工作位置；G2 的作用是登记新仓库，不能依赖“新仓库已登记”作为自身派发前提。具体工作 zone 在总体方案中落实，本需求不借用当前规划 Run 的配置。

### 2.2 唯一输入与上游接口

从 `context.inputs` 取得本地输入 ID `repository` 的实际文件地址，完整读取 UTF-8 JSON。它由 G1 成功输出 `repository` 提供；blocked_by 仅表达依赖，不自动传材料。不得扫描报告、运行记录、相邻文件或其他 Chat 寻找参数。

G1 必需交付字段如下，G2 依此消费：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| repository_url | string | G1 实际使用的 GitHub 仓库 URL，保留 HTTPS/SSH 形式 |
| owner | string | 仓库 owner |
| repo | string | 去掉末尾 `.git` 的仓库名 |
| zone_id | string | 必须等于 owner + `/` + repo，不得添加前缀/后缀 |
| parent_directory | string | G1 实际使用的规范化绝对父目录 |
| repository_path | string | G1 实际克隆仓库根的绝对路径 |
| clone_status | string | 必须为 `succeeded` |

输入中三项身份（URL、owner/repo、zone_id）必须一致；repository_path 必须对应 parent_directory 下的 repo，且真实目录可读取、未被链接重定向到越界位置。不能信任成功标记就跳过实际目录检查。读取 Git 根时须确认是该目录本身，不是其祖先目录的仓库。

G2 可以执行必要的本地只读 Git 检查，不运行远端查询、clone、pull、checkout 或仓库代码。不得用工作树没有改动作为登记前提，不自行重置、清理或切分支。发现来源/路径冲突应失败，不在 G2 修复 G1 的输出。

JSON 缺字段、错类型、重复键或语义矛盾在写接口前拒绝。不得对材料里的 `${...}` 作插值，不把任意文本当命令。可兼容明确的额外诊断字段，但必需字段不能被自由文本替代。

### 2.3 zone 身份与重复规则

以服务登记的稳定 ID 为准。例如：

- `https://github.com/caddyserver/caddy` → `caddyserver/caddy`。
- `git@github.com:caddyserver/caddy.git` → `caddyserver/caddy`。

保存前查询 `GET /api/zones`，精确查找 ID：存在则立即失败，即使现有路径与输入完全相同也不能按幂等成功处理；不得复用、改绑、删除旧登记或自动改名。

本业务不要求根据路径、Git remote 或仓库显示名判断“重复”。产品允许不同 zone ID 指向同一路径；不得另加“路径相同就自动选一个 zone”的分支。GitHub 大小写别名不是产品已有的 ID 别名规则；如欲新增折叠或别名兼容，必须显式返回规划讨论，不暗中改变用户给定身份。

G1 在克隆前已经检查过 ID，但 G2 仍必须重查，因为两节点间可能有人工或并发登记。最终保存冲突须以服务响应为准，不能用前一次 GET 授予覆盖权。

### 2.4 登记与读回流程

1. 校验本次声明的输出、输入材料、真实目录、仓库根与身份关系；记录可确认的前置事实。
2. 读取 zone 目录，确认目标 ID 尚未登记；查询失败或正文无法解析时停止，不当作空列表。
3. 通过当前公开“登记已有目录”接口提交 ID 与实际本机路径。现有调用形态为 `POST /api/zones`，请求 `{"id":"owner/repo","path":"绝对仓库目录"}`；实施前须对当前路由/契约再次核实，不扩展接口、不直接写 `.data/zones.json`。
4. 不调用“新建 Zone”接口，不额外创建目录，不套用服务 `create_parent_directory` 替代已克隆目录。
5. 保存成功后独立 `GET /api/zones`，核对同一 ID 和实际路径，路径按服务规范化/Windows 路径语义比较，不以分隔符或盘符大小写差异误报冲突，也不靠简单小写字符串掩盖不同真实路径。
6. 生成 zone 输出文件并完整读回。仅当保存成功、独立读回匹配和输出文件完整时返回 success。

服务的现有注册实现会校验 ID、规范化候选路径，在服务的登记变更边界检查重复 ID；业务脚本不能直接覆盖存储绕过这些检查。HTTP 成功本身不替代独立读回。保存与读回不是跨请求事务，不承诺返回后绑定永远不变。

### 2.5 输出与下游消费

唯一成功输出 ID 为 `zone`，UTF-8 JSON 必需字段：

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| repository_url | string | 经过上游一致性核实的来源 URL |
| owner | string | 仓库 owner |
| repo | string | 仓库名 |
| zone_id | string | 实际登记的 owner/repo |
| repository_path | string | 独立服务读回并核实的实际绝对目录 |
| registration_status | string | 正常成功固定为 `succeeded` |
| read_back_status | string | 正常成功固定为 `succeeded` |

脚本在 `context.outputDirectory` 中选择不覆盖已有产物的地址，安全保存并完整读回后，返回 `{status:"success",outputs:[{id:"zone",path:"真实绝对路径"}]}`。不预造未来地址、不仅打印 JSON、不只在报告中写路径。不复制探索方向；W3 另从原 request 消费。

管理者读取 zone 文件，根据其中真实 zone_id，为 W3 动态 zone 派发显式指定位置；系统不会自动从报告提取或自动派发。W3 可将该输出作为本地命名输入 zone，同时绑定原 request。G2 不写 Map，不代调管理者工具，不创建/关闭 Chat。

## 4. 失败、权限与部分效果

### 4.1 权限与非目标

脚本只允许读取声明材料、必要的本地仓库事实、公开 zone 目录，登记本次唯一 ID/路径并写本次输出文件。不修改仓库内容、不拉取远端、不删除目录、不改已有 zone、不修改 Task/Bot/Map 或运行记录、不启动业务 Chat/Run、不安装工具、不读写凭据、不提权、不停止服务。

实现与配置保存须由用户在另一个 Chat 明确授权。本次文档保存不授予生产 zone 写入或试运行权限。脚本没有沙箱，权限范围需要调用方与可信实现共同遵守，不能以输入校验声称具备系统隔离。

### 4.2 错误分类与现场保留

诊断至少区分：材料不可读/无效、仓库身份不一致、目录不可用、zone 已登记、服务查询失败、登记明确拒绝、登记效果未知、独立读回失败/不匹配、材料保存/读回失败。诊断名称由实现自行定义，不冒充新增产品错误码。

- 前置失败：不得调用登记写接口，保留原仓库。
- 服务明确拒绝：返回 failure，保留原错误，不重发、不改 ID、不改绑。
- POST 超时、断连或响应无法理解：不得直接声称“未登记”。仅做只读查询，记录可确认事实；即使看到同 ID 同路径，也不能证明由本次请求写入。返回 failure 并标明效果未知/当前绑定观察，留给人工处理，不自动把未知变成功。
- POST 已明确成功，但 GET 失败或路径不匹配：返回 failure，注明可能或已经登记，不能以先前成功响应代替读回。
- 登记与 GET 均成功，材料失败：仍返回 failure，明确“登记已生效、交付文件失败”。不得注销 zone 或删除仓库以伪造回滚。
- 本次失败后再次执行，若 ID 已存在，仍按重复规则停止；不提供自动接管、幂等复用或恢复分支。需要处理现场时用户另行明确授权。

成功材料只在完整正常成功路径生成/登记。失败诊断至少保留操作阶段、目标 ID、目标路径、写入和读回的已成功/未尝试/失败/未知事实；不要求额外建立持久状态系统。报告由现有脚本宿主生成，不伪造 Session 或调用节点报告接口。

## 5. 验收要求

以下为待执行的实现验收清单，不是已验证结果。

| 场景 | 必须可观察的结果 |
| --- | --- |
| 合法上游材料与有效仓库 | 仅登记指定 ID/目录，独立 GET 匹配，zone 文件完整可读 |
| 同 ID 同路径已登记 | 明确重复失败，不以已有结果报成功，不发送登记写请求 |
| 同 ID 不同路径已登记 | 失败，旧绑定不变，不改绑 |
| G1 后、G2 前出现同 ID 登记 | G2 重查拒绝，不继续 W3 |
| 预查后并发抢占 ID | 尊重服务最终拒绝，既有绑定不覆盖 |
| 缺字段/错类型/重复键/clone_status 非成功 | 写接口零调用，无新登记 |
| URL、owner/repo、zone_id 或路径矛盾 | 失败，不自动修正成另一身份 |
| 目录缺失/不可读/不是仓库根/链接越界 | 无登记，不修复上游现场 |
| GET 不可达或返回损坏正文 | 不当作空目录，不写入 |
| POST 明确失败或返回效果未知 | 无自动重发；未知时只读核实并保留不确定性 |
| 保存成功、读回失败或路径变化 | failure，明确保存事实及冲突，不注销回滚 |
| 登记成功、输出失败 | failure，保留真实 zone 和仓库，不输出假成功材料 |
| 路径分隔符或盘符形式不同 | 按真实规范化路径核对，不因纯表现差异误判 |
| workflow 集成 | 真实脚本派发自动报告、无 Chat；manager complete 后才允许下游安排 |

验收使用测试拥有的仓库、zone registry、定义和独占回环服务；受控 HTTP 只能证明错误处理，成功登记与读回至少要通过真实隔离服务。不得把测试 zone 写入用户生产 registry 后再擅自删除。运行验收前读取仓库测试约定，不为测试安装工具或扩大权限。

完整 G1→G2 验证需要真实上游文件和公开派发；只调用函数或使用合成 repository 文件时，报告相应证据边界。任何真实生产登记或第三节点 Chat 启动均须另获授权，不把配置读回当作端到端业务成功。
