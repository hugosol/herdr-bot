# 第二阶段曳光弹：由管理 Bot 驱动的 Map 运行系统

整理日期：2026-10-27。状态：教学讨论形成的开发交接计划；不是已完成实现、正式批准的逐字段 schema 或已执行的验收报告。

## 1. 定位、优先级与唯一交付目标

> 用户选择已有 Map，创建一次运行；系统启动管理 Bot 的 Chat。管理 Bot 使用运行工具派发节点、收取反馈、作出放行决定并结束流程。节点复用现有 Task → Chat 执行链。运行事实集中持久化，用户在只读运行图中观察进度、交付和关联 Chat。

这次要验证的是“Bot 作为运行系统的使用者，能够推动 Map 走完”，而不是先写一个自动执行 DAG 的代码调度器。

### 1.1 与历史计划的关系

- 第一阶段的 Map/Bot 定义管理、校验、可视化已由用户报告完成；当前仓库说明与源码具备这套静态底座。本次没有重新运行产品验收。
- [上一阶段计划](workflow-map-and-plan-implementation-plan.md)中“第二阶段先做 LLM Plan”的顺序，由本文替代。LLM 规划不是本阶段前置条件。
- [早期总体设计](llm-driven-workflow-definition-design.md)继续作为历史背景；与本次范围冲突时，以本文为准。
- 本次讨论中曾提出“首版确定性策略自动补满空闲槽”，用户随后明确改为**首版直接由管理 Bot 控制**。不要实现两个管理者，也不要把代码自动选路作为隐藏默认行为。
- 早期教学材料中的完整人工接管、自动恢复与较大生命周期设计，不是本轮交付要求。

### 1.2 如何阅读本文

- **确定方向**：用户明确认可的职责和阶段范围，不能在实现中悄悄替换。
- **建议落点**：用于指导编码的最小实现建议，可按仓库惯例调整命名、组织、路由和字段，但必须保留语义。
- **开发前选择项**：尚无最终决定的宿主接入、字段及配置方式，见第 14 节。不得把候选名字当作既有接口。

## 2. 核心原则

1. **流程管理者是运行系统的使用者，而不是运行系统本身。** 管理者作决定，运行系统落实动作并保存事实。
2. **决策 seam 与 Map 解耦。** Map 表达工作、依赖和预期交付；执行策略决定谁判断是否放行，不把质量验收算法嵌入 Map。
3. **首版使用管理 Bot 策略。** 后续代码策略、人工方式使用相同的观察／操作 Interface；本轮只留清晰 seam，不建设插件平台或未使用的通用抽象。
4. **只有一份逻辑运行态。** 运行文件是持久表示，内存是工作表示。不要维护“状态机内部真相”和“文件真相”两套可独立修改的数据。
5. **单一写入主体。** Bot、页面、执行者均通过运行系统操作或报告，不直接编辑共享运行 JSON。
6. **执行结束、交付存在、决策放行是不同事实。** 可以在执行尚未结束时放行；有输出不代表已被验收，允许使用不代表严格验证正确。
7. **Map 层与 node 内部分层。** Map 记录外层状态和执行引用；Chat/subagent/脚本管理内部现场。不要在 Map 中复制完整聊天或内部执行状态。
8. **先完成可保留的端到端薄切片。** 不先建设恢复平台、通用消息总线或复杂状态机。不能把未启动、仅提交 prompt、或状态未知伪报成业务完成。
9. **接受适度不确定性。** 首版管理 Bot 可以宽松判断；代码保证归属、状态和操作约束，不重做业务质量判断。后续修正是能力与机会，不是必然保证。

## 3. 范围

### 3.1 本轮必需

- 复用已有静态 Map/Bot 管理和依赖图。
- 补齐 Bot 到现有 Task/Chat 的执行绑定及本次实际环境配置。
- 启动一次 Run，固定所用定义和配置，关联管理 Bot 的真实 Chat。
- 管理 Bot 可读取运行、派发节点、等待反馈、发送指示、提交决策、结束 Run。
- 节点执行 Bot 可接收指定输入、报告交付与结束／失败、提出问题并获得管理者回应。
- 简单运行信箱和交付引用，形成真正可继续对话的闭环。
- 持久化运行文件，保存状态、执行关联、交付、决策和消息。
- 节点放行决策经过 seam，首版仅实现 manager 策略。
- 只读运行列表／运行详情与运行时图；展示状态、交付、错误、管理者和节点 Chat 入口。
- 基本操作拒绝：未知身份、重复派发、前置未放行、无权提交决定、引用错误、运行已经结束等。

### 3.2 明确不做

- 代码版自动选路／自动派发管理者。
- LLM Plan、运行中改图、循环、定时、多轮重跑和自动重试。
- subagent、脚本执行 Adapter；长期 Bot 概念允许这些类型，但本轮真实实现仅 Chat。
- 人工审批页面、人工接管、策略热切换、交互式暂停／恢复产品功能。
- 自动故障恢复、重启自动续跑、统一恢复 node 内部会话或进程。
- 任意 JSON patch、直接 setStatus 的万能修复后门。
- 通用聊天总线、复杂审计平台、完整事件溯源、分布式调度、多进程并发写同一运行文件。
- extension SDK／策略市场／任意脚本条件表达式。

暂停、恢复、人工判断、故障修正可以在数据和操作 seam 上预留语义位置，但不能为了这些未来能力扩大本轮验收；不支持的策略／动作必须明确拒绝，不提供假实现。

## 4. 六个 Module 的落点

这些是职责划分，不要求六个服务或固定六个源码文件。

| Module | 本轮职责 | 不属于它的职责 |
|---|---|---|
| 定义管理 | 复用 Map/Bot 的读写校验；增加执行必需配置；创建 Run 时固定定义 | 不存本次运行进度，不负责自动推进 |
| Bot 执行 | Bot → Task → 已有 Chat 创建；组织输入；保存实际执行引用；接收或传递外层消息 | 不选择后继，不用 Chat 创建成功冒充业务完成 |
| 协作与交付 | 保存简单消息、交付、关联和来源；提供等待／读取与发送 | 不因普通消息隐式放行，不自行派发节点 |
| 流程控制 | 管理者使用运行工具作决定；内核实施操作、依赖准入和状态变更 | 不将管理策略散入各 HTTP handler，不预编全部业务路线 |
| 运行状态与恢复 | 仅实现运行态持久记录、查询和中断事实表达 | 不实现自动恢复或 Bot 内部 checkpoint |
| 观察与人工控制 | 只读运行图、详情、消息／交付和 Chat 导航 | 人工审批和接管 UI 延后 |

### 4.1 总体协作

```text
管理 Bot                          节点执行 Bot
   | read / collect / operate        | report / deliver / message
   +-------------------+-------------+
                       v
                    运行系统
          +------------+--------------+
          |                           |
    操作与状态更新               既有 Task / Chat 能力
          |
       逻辑运行态
          +---- 持久化 ---- 本次运行文件
          +---- 查询 ------ 只读运行图
          +---- 变化通知 -- collect 返回给管理 Bot
```

管理者的决策实现使用与未来代码／人工方式一致的运行 Interface，不允许管理 Bot 特权地直接改文件。执行者只能提交自己负责的执行反馈，不能仅通过伪造 node_id 修改其他节点或放行决定。

## 5. 既有定义与执行配置

### 5.1 保留当前语义

当前 Map 为 `schema_version/title/description/nodes`；node 为 `title/bot_id/parameters/blocked_by`。Bot 是共享业务调用模板，当前 `implementation` 仅有 `{ "type": "chat" }`。

- Map 是数据，定义管理 Module 是处理数据的代码。
- Bot 不是 Task。Bot 的执行配置引用或绑定现有 Task；复用 Task 的环境、模型、Skill 和启动能力。
- `inputs`／`outputs` 当前是说明文字，不是可执行 JSON Schema，也不是实际结果。
- `blocked_by` 当前为硬前置关系，定义校验拒绝自依赖、未知依赖和环。不要以实现循环为名在本轮改写它。

### 5.2 必须补齐的绑定

开发时明确：

1. Bot 如何引用 Task；建议放在 Bot 的执行配置中，不把 Task 内容复制一份到每个 node。
2. zone、Workspace、本次输入等从启动参数或运行默认值取得的规则。
3. node.parameters 如何与 Bot 说明、Task 初始指示、上游交付组合；保留原始参数和输入引用，不只存最终 prompt。
4. 管理 Bot 在启动 Run 时如何选择。它属于 Run 的管理配置，不是 Map 中伪造的业务节点。
5. 管理者与各 node 的 Chat 如何保证本轮上下文隔离。现有启动代码允许 agent 原生自动续接，不能假定“新 Tab = 新会话”。应选定明确的隔离策略，防止不相关 node 共用上下文。
6. 实际解析出的配置保存在本次运行记录；不要恢复查询时重新读取已变化的默认配置来猜测过去用了什么。

当前严格 JSON 校验拒绝未知字段。新增 Bot 执行字段时，须同步更新解析、编辑校验、预览、样例、文档和相关契约；不能只在运行器里偷偷读取一套额外字段。是否升级 schema_version，以及旧定义缺失执行配置时如何显示不可运行，需显式选择。不得静默选择一个不相干 Task 作为兜底。

## 6. 运行时文件与数据结构

### 6.1 存储组织

建议一份 Run 对应一个文件，例如 `.data/workflow-runs/<run-id>.json`。目录名是建议值，应与项目配置方式一致，和 Map/Bot 定义目录分离。同一 Map 多次启动产生不同 Run，不覆盖旧记录。

运行系统是唯一写入者。前端通过后端查询；Agent 通过工具调用后端；不得由多个 Chat 各自 read-modify-write JSON。

文件固定本次 Map 和引用 Bot 的内容、所选管理配置；大产物可以放在外部文件中并保存引用，不必把二进制或整个 transcript 塞入 JSON。

### 6.2 最小逻辑对象

以下是语义清单，不强制最终字段命名或枚举名称。

| 对象 | 本轮至少保存 |
|---|---|
| Run | 格式版本、run_id、Map 来源及快照、引用 Bot 快照、实际运行配置、管理者执行引用、状态、结束结果／说明、更新时间或修订号 |
| NodeRun | node_id、独立 execution_id、启动／执行状态、实际输入绑定、执行引用、交付引用、错误／未确定原因 |
| Decision | decision_id、node／流转点、本次 execution 和被判断交付的引用、策略绑定、等待／允许／不允许结果、提交者、原因 |
| Delivery | delivery_id、run/node/execution 归属、命名输出的文本或稳定产物引用、发布时间、必要说明 |
| Message | message_id、归属、发送者、接收者、类型、内容／引用、关联问题的标识和时间 |

执行引用可包含类型、Chat 创建句柄、Herdr 控制别名／Tab／Pane、原生 session ID 等已知值。未知值明确为空或尚未取得，不把显示名或 node_id 假装成原生 session ID。业务运行身份独立于这些宿主句柄。

首版同一 Run 中每个 node 只派发一次，但仍保留 execution_id。暂不建立通用 attempt 树或自动重试队列；未来重跑应产生新执行，不擦掉旧事实。

### 6.3 执行、放行、运行结束分开

候选外层状态可采用：Run 的 starting/running/finished/interrupted；NodeRun 的 pending/starting/running/succeeded/failed/interrupted。名称可调整。

- 等待验收由 Decision 的 pending 表达，不把一个已结束 node 改成模糊的 paused。
- 发布 Delivery 不自动意味着执行结束。
- 对具体 Delivery 的允许决定形成该 node 本次放行事实；可以派生查询字段，不要额外维护一个无人能解释的独立布尔值。
- 同一 node 可以 running 且已有允许决定；可以 succeeded 但 Decision 仍 pending。
- Run 的结束与结果分开表达：结束不必意味着成功。不要把失败节点或未决事项抹去后显示“全部成功”。

成功结束的最小机械条件建议：所需节点均明确成功结束、所需放行决定允许、无本轮未决事项；内容是否足够由管理 Bot 判断。发生无法处理的失败时允许明确以失败／中断结果停止本轮，不自动重跑。结束运行本身不等于强制终止外部 Chat；若还有活动执行，应拒绝伪报成功并说明现场。

### 6.4 输入与交付绑定

依赖关系不是数据传递。派发 C 时，需明确 C 消费 A、B 哪些 delivery_id，以及哪些命名输出。可由管理 Bot 指定引用，运行系统读取后组装输入；不要求模型复制整段结果充当唯一传递方式。

同一已发布交付应保持稳定；更正产生新交付引用，不悄悄修改已经被下游消费的内容。放行决定针对具体交付，后续消息不能自动替换它。

本轮可用文本交付完成闭环，不要求通用 artifact 服务；若使用路径引用，必须保证接收者能通过已有读取能力访问，不把发送方不可见的本地路径当作完成传递。

## 7. 决策 seam：管理者身份不等于每个判断的决定权

### 7.1 本轮实现

首版仅支持 node 的 `release` 决策点，默认 manager 策略。交付后创建或定位待决事项，管理 Bot 经操作入口提交决定。不要将“管理者收到了报告”直接等同放行。

决策 Interface 至少能表达：

- 输入：run/node/execution、决策点、具体交付、策略绑定。
- 输出：等待处理、允许继续、不允许继续，以及说明。

不允许继续不天然等于自动循环。管理者可以发送补充要求或明确结束失败；本轮不支持重新派发同一 node。正在同一 Chat 中继续沟通与创建第二次执行是两回事。

### 7.2 为未来保留的位置

未来可按运行默认值和 node 覆盖绑定 human/code/manager。Map 本体不需增加“及格分数”“审批者姓名”等控制规则。

- human：保存待处理决策，人提交后产生状态变化。
- code：调用选定检查，以其结果形成决定。
- manager：管理 Bot 提交决定。

本轮不实现前两种处理者及 UI。若配置选择未支持类型，启动前明确拒绝，不默默退回 manager。

门禁只检查决定是否来自当前绑定的合法处理者，不重新判断业务质量。未来 human 策略不能被普通 manager 的直接 release 绕过；显式人工覆盖另行设计。

### 7.3 与总管理者的关系

管理 Bot 负责全局协调，可以委派局部判断。未来代码管理者也应通过同样的决策和运行 Interface；不是为了换管理者而替换执行存储。不要把整个六个 Module 都实现成 Bot。

## 8. 工具闭环：读取、collect 与 operate

工具名和 HTTP 路由待实现选择。可提供少量工具，也可一个入口以 action 区分；不要因表格行数就建同样数量的公开接口。所有入口共用一个运行操作实现。

### 8.1 管理者能力

| 动作语义 | 行为与约束 |
|---|---|
| read/status | 返回定义、节点、决策、交付、消息和派发不可用原因；只读 |
| dispatch | 申请一个或多个节点；检查身份、未重复启动、前置已放行、运行仍可推进、容量；先保留执行位置再调用 Chat |
| collect | 有变化即返回，没变化则等待；不自动选路或派发 |
| send | 向已关联执行者发送补充信息，或回复关联问题；不隐式改变放行 |
| decide | 对具体 release 决策提交允许／不允许；检查策略归属与交付引用 |
| finish | 管理者提出结束及结果，系统检查结构性条件并落盘；不能把活跃执行伪报全部成功 |

### 8.2 执行者能力

- 读取本次输入和指定交付。
- 报告普通消息／问题。
- 提交命名交付及必要限制说明。
- 明确报告本次工作结束或失败。
- 接收管理者回复／指示；首版选择一种与实际宿主兼容的机制。

报告必须绑定 run_id/node_id/execution_id，并核对调用者归属。系统分配和注入可信执行上下文，不只相信模型提交的任意字符串。管理者和执行者的能力范围应分开，具体会话绑定或凭据方式沿用项目可用机制；不要把运行文件中的可展示配置暴露为敏感凭据。

### 8.3 collect 的确切角色

```text
管理 Bot 调用 collect
  -> 已有未观察变化：返回快照和相关消息
  -> 无变化：工具等待，不反复要求模型推理
执行者报告 / 决策变化
  -> 运行系统提交状态
  -> 唤醒等待
collect 返回
  -> 管理 Bot 决定下一步
  -> 调用 operate
```

- collect 不是自动调度器，也不是 node 完成判定器。
- 通知与等待不是审批意义的 paused；底层 node 可继续执行和提交结果。
- 必须保留“无人等待时已经发生的变化”，不能只提供一次性易丢通知。
- 建议以 Run revision／消息位置为游标返回新变化；也可沿用 hyper 的保留通知＋当前快照思路，但要保证独立页面读取不消费管理者的消息。
- collect 不持有阻止报告／派发的全局锁。持久状态和交付才是事实，通知只是提醒重新读取。
- 宿主不支持长期工具等待时，使用有界等待，返回是否超时和当前位置，再由 Agent 续接等待；不能默默依赖无限工具时长。
- 没有活动执行、没有可等待事件且无法推进时，返回可解释的空闲／阻塞现场，不让管理者永远卡在等待。

### 8.4 实际工具接入是本轮必需工作

仅写 HTTP endpoints 或 prompt 文案不足以交付。管理者和节点 Chat 必须实际加载可调用的运行工具，并能从报告继续执行。

开发时选定一个现有支持的 agent/Task 组合作为真实验收载体，接入其工具／extension 机制；不要求同时支持全部宿主。应复用现有 Task 配置入口，不借用本教学会话的工具权限冒充产品 Chat 已具备能力。

消息发出不等于对方已处理；若执行者等回应，使用可实际等待回应的入口或已核实的宿主投递方式。若 Chat 已空闲，必须选择已有可用唤醒／继续输入路径，不能只写信箱并假设它会自己回来。

## 9. 派发、依赖与并发

- `blocked_by` 保持静态，不因运行删除边。满足状态由本次运行的放行决定得出。
- 本轮采用 AND：A、B 都放行，C 才允许派发。首版不实现分支选择和可选前置。
- ready 可以由代码计算并返回作为便利事实，但不因此自动启动。管理 Bot 明确申请派发。
- 一次申请可包含多个独立节点，支持 A、B 实际并行。
- 保留简单执行容量限制，防止 Bot 一次启动无限 Chat。容量按仍在执行的 node 统计，不因为已放行就释放；若未来按阶段计槽，另定策略。
- 管理者可在 A 已放行但未结束时派发依赖 A 的工作，只要其他依赖与容量允许。
- 发起相同 node 的并发或重复派发请求，不得启动两个实际 Chat；操作占位和检查应由同一运行系统串行完成。
- 交付放行后普通消息不会自动撤回。若后续发现失败，保留真实历史并向管理者报告；不实现级联撤销、自动补偿或重算，不因此假报成功。

## 10. 持久化与故障范围

### 10.1 一份状态的更新路径

```text
可信操作 / 执行反馈
 -> 检查当前运行态
 -> 串行提交变更并可靠写盘
 -> 对外返回结果、通知 collect / 页面
```

建议复用当前历史存储的“锁保护读改写＋临时文件＋flush/sync＋替换”惯例，并验证 Windows 文件替换语义。不要直接截断正在使用的运行文件，不忽略读盘／写盘错误。

外部 Chat 启动不与文件写入天然原子：先记录 execution 身份与 starting，再调用已有启动链，返回后记录真实结果。不要持有运行锁等待长时间启动或 collect。提交失败应明确暴露，不允许内存里成功、落盘失败却仍静默向下游放行。

### 10.2 本轮只保证记录，不承诺自动续跑

- 浏览器刷新／断开不取消已接受的后台 Run；重新打开可查询已有状态。
- 后端重启后仍能读取历史文件；此前活动 Run 明确标为中断或需要确认，不自动重复派发。
- 不将 session 暂时离线、register 消失、awaiting-input 当作业务完成。
- prompt 超时可能已投递，不能默认再次提交；报告结果未知或启动异常，保留执行引用供人工查找。
- node 内部恢复由 Bot 执行层负责。运行文件不包含它的全部内存／对话现场。

### 10.3 未来统一操作入口，而非本轮万能修复后门

operate 将来可以增加 pause/resume、关联已有执行、采用已有交付、明确重跑等语义。但不能用任意字段 patch 假装发生外部动作：改成 finished 不会杀死 Chat，改成 running 不会恢复进程。

未来 Map 暂停首先可以定义为禁止新派发；要求 node 内部暂停是另一条消息／控制请求。当前保留操作分层即可，不提前实现完整暂停恢复系统。

## 11. 管理 Bot 与执行 Bot 的指导内容

指导是管理策略实现的一部分，不属于运行内核硬编码业务条件。

### 管理 Bot 至少知道

1. 目标、本次 Map 和运行身份；工具可发现且可调用。
2. 先读当前事实，只使用所属运行的执行／交付引用。
3. 可并行派发独立节点，不靠聊天声称已派发。
4. 无需忙等；调用 collect 收集反馈。
5. 按本次策略作出放行决定，允许说明不确定性，不将放行写成严格正确保证。
6. 需要补充时使用通信入口；不得直接修改运行文件。
7. 结束前读取当前事实，明确成功／失败／中断结果，不把创建成功当业务完成。
8. 不支持的重试、动态改图、恢复等动作不得用改状态绕过。

### 执行 Bot 至少知道

1. 本次 run/node/execution 归属、目标、参数、所需上游交付及报告工具。
2. 普通进度、问题、交付和结束的差别。
3. 可以先交付后继续收尾，但必须明确报告；结束报告不能省略。
4. 不得代替管理者放行其他节点，不直接写运行文件。
5. 如需要回应，使用可收取回复的路径，而不是发完问题就永久退出。

管理者上下文只包含协调所需信息和引用；节点拥有自己的任务上下文。不要把所有节点 transcript 拼接给管理者作为运行数据库。

## 12. 页面交付

复用已有静态图布局和节点选择，不重建另一份 Map。

### 启动入口

- 选择 Map 与管理 Bot，补齐运行环境配置。
- 启动前验证引用／执行配置可用；不能因为静态编辑允许缺失 Bot，就在运行时静默忽略节点。
- 创建独立 Run 后进入运行详情；同一 Map 旧 Run 仍可查看。

### 只读运行图

- 使用本次定义快照显示图结构，叠加同一运行记录的事实。
- 显示 Run 状态和管理 Chat 入口。
- 节点展示执行状态、放行状态、错误／等待原因。
- 点击节点查看本次参数／输入引用、交付、决定说明、消息和关联 Chat 入口。
- 普通执行结束与仍待放行区分；已放行但仍运行也能表达。
- 页面不解析 Agent 聊天猜进度，不持有自己的调度状态机。
- 首版轮询或手动刷新均可，后端是权威；不以 SSE 重构作为前置条件。
- 页面只读，不做批准、暂停、接管、编辑运行态。通过现有 Chat 入口人工对话不等于本轮交付人工审批系统。

## 13. 曳光弹验收与实现顺序

### 13.1 主场景

使用人工固定 Map：A 整理材料甲，B 整理材料乙，C 结合两者形成结论。材料随验收输入提供，不依赖实时天气等外部不稳定服务。

```text
A --+
    +--> C
B --+
```

应观察到：

1. 用户实际启动 Run，真实管理 Chat 创建并关联。
2. 管理 Bot 调用运行工具派发 A、B，两个执行 Chat 实际运行且相互隔离。
3. A、B 通过产品报告入口产生交付，不由测试或人工直接改运行 JSON 代替。
4. 管理 Bot 的 collect 收到反馈并恢复推理，提交针对交付的允许决定。
5. 管理 Bot 派发 C；C 确实获得指定的 A、B 结果，而非只看见两个依赖 ID。
6. C 报告结论；管理 Bot 通过操作入口结束 Run，状态落盘。
7. 只读图显示实际执行过程、决定与交付；可打开管理者和节点 Chat。
8. 刷新页面后仍可读取同一 Run，无重复启动。

### 13.2 必须覆盖的语义切片

- 一次真实问题／回应：执行者询问，管理者回复，执行者继续并交付。
- 提前发布与结束分离：至少一个 node 发布后仍有收尾；有空闲容量且其他前置满足时，下游可由管理者启动，Run 不提前伪报结束。
- 未放行时尝试派发 C，被拒绝且未创建 C Chat。
- 同一 node 重复或并发派发，不产生第二次真实执行。
- 普通消息、Chat 创建 succeeded、awaiting-input 均不自动放行。
- 放行决定关联具体交付；错误归属或无权决定被拒绝。
- 失败／超时不会伪造交付、自动重试或显示整体成功。
- 服务重启后历史记录可读，未完成运行不自动续跑；这不是恢复功能验收。
- 未支持的 human/code 策略明确不可用，不静默降级。

真实 Agent 验收可能需要配置、凭据和费用，实施时先确认可用环境。单元测试／HTTP 测试可以验证状态规则，但不能代替至少一次真实管理 Chat → 执行 Chat → 反馈 → 后继派发的端到端 smoke。

### 13.3 建议纵向实现顺序

1. **单节点真实闭环**：运行文件＋管理 Chat＋执行 Chat＋报告＋管理决定＋结束＋最小可读状态。先证明工具注入和 collect 能真实工作，不先完成所有 UI。
2. **并行与汇合**：A、B → C，补输入引用、并发准入、提前交付和重复派发保护。
3. **最小双向协作**：真实问题／回应，确保执行者可以继续，不仅是写一行消息。
4. **运行图与历史查看**：复用静态图并投影同一状态，完整查看决定／交付／Chat。
5. **补齐失败可见性并完成验收**：中断记录、不支持策略、错误配置和持久失败，更新文档及样例。

每一步保留并成为下一步底座，不制作一次性模拟执行器作为最终交付。顺序可按已有代码调整，但第 13.1 节端到端目标不得缩水。

## 14. 开发前需要落定的具体选择

这些不是要求重新讨论总体架构，而是落地前的有限选择：

1. Bot 的 Task 绑定字段和版本迁移方式；zone／Workspace 的来源与覆盖规则。
2. 首个真实验收使用哪种现有 agent 宿主、如何加载运行工具；运行工具入口放在何处，如何复用已有 Task 扩展配置。
3. 管理者／执行者可信归属如何绑定；不要依赖任意可伪造 ID。
4. Chat 输入隔离方式、已有 Chat 的继续输入／消息接收方式；采集原生身份的确认路径。
5. 运行目录配置、最终 schema 和状态名称；按项目现有存储惯例选择。
6. collect 的等待时长、游标及宿主超时适配；必须保证报告后管理者实际继续。
7. 文本交付还是文件引用作为首条 smoke 的载体；引用必须可读取。
8. 本轮并发容量、成功结束的明确结构条件、失败时如何留在可解释的终态／中断态。

选择完成后记录到开发 spec/contract，再细分实现票据。不要让后续开发者自行把管理 Bot 换成自动 DAG 调度器来降低实现难度。

## 16. 交付完成的定义

完成不是“有运行 JSON”“有几个 HTTP 接口”或“页面会变色”。完成是：真实管理 Bot 能通过产品工具控制真实节点 Chat，节点反馈能让管理者继续，依赖和交付确实影响后继执行，结果持久保存并在只读运行图中可见。

本文件是实现计划。本次仅创建和校验交接文档，没有修改产品代码、创建实现票据、运行 Agent 工作流或验证模型调度可靠性。
