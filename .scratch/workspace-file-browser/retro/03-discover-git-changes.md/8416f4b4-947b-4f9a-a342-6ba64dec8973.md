## Retrospective

# 复盘：03-discover-git-changes 的 TDD 执行轮

## 结论摘要

本票的代码、测试和真实浏览器证据已完成；最大的环境改进空间不在实现本身，而在**可重复的全量检查**和**机械规则的确定性拦截**：

1. 全量后端检查依赖已构建的前端静态页，且既有 `connection_drop` 用例在全量运行时会出现夹具宽限抖动；这两点让一次“全绿”验证变得昂贵且不可靠。
2. 项目已有若干 TypeScript 机械规则，但只在写入后以提醒形式出现；本轮的 `gitApi.ts` 因此返工了一次。应优先把这类规则接到确定性检查，而不是依赖提醒。
3. `cargo fmt --check` 当前包含大量与本票无关的既有差异，无法作为通过/失败门槛；前端也没有 lint 脚本。
4. TDD 的后半段多为“实现已具备后补测试 + 末尾突变”，事实充分性尚可，但红/绿证据没有按验收项系统记录。
5. 真实浏览器证据流程是临时的：截图返回值形态、截图取景和说明文字都出现过一次返工。

以下按严重度展开。标注“事实”的是本轮对话中实际观察到的结果；“推断”是可能原因；“未验证”是本轮没有检查或没有执行的事项。

## 高优先级

### 1. 建立唯一、可重复的全量检查入口，并消除静态页前置条件

**事实**

- 第一次 `cargo test` 失败于 `mdns_conflict`：`/` 返回 404，因为本 worktree 的 `backend/static` 尚未构建。执行 `npm run build` 后，该测试立即通过。
- 之后两次全量 `cargo test` 在 `connection_drop` 失败：`stop_record[0].detail` 期望 `long-running=ended-by-stop-marker`，实际得到 `force-killed`；单独运行该测试通过，最终 `cargo test --no-fail-fast` 全部通过（`218 passed / 29 suites`）。
- 本轮为验证这一点多次运行了约 4 分钟的全量后端套件，并一度与前端测试/构建并行执行。

**建议**

- 在 README 或新增的 `docs/agents/testing.md` 中给出唯一命令，例如：安装前端依赖 → 构建前端静态页 → 运行后端全量检查；并让 CI/pre-commit 使用同一命令。示例顺序：`npm --prefix frontend ci`、`npm --prefix frontend run build`、`cargo test --manifest-path backend/Cargo.toml --no-fail-fast`。
- 让依赖页面产物的测试在静态页缺失时**明确失败并说明需要先构建**，或在测试夹具启动前自动构建；不要把 404 伪装成断言失败。
- 对 `connection_drop` 的停止路径使用已有的 `stop_fixtures_with_grace`（或增大停止脚本的兜底宽限），使停止标记有确定机会被夹具观察到。当前“通过/失败”受调度影响，作为全量闸门不可靠。

**推断**

- 两次抖动发生在全量套件运行期间；并行执行前端测试/构建可能加剧了夹具轮询的延迟，但没有证据证明这是唯一原因。

**未验证**

- 本轮没有检查仓库的 CI 或 pre-commit 配置，因此不能断言当前是否存在同类闸门；建议先确认，再决定是新增还是修现有检查。

### 2. 把 TypeScript 机械规则接到 lint/检查，而不是只依赖写入后的提醒

**事实**

- 新增 `gitApi.ts` 时先写了一个 JSX 中的立即调用函数和一处内联类型断言；随后收到 `ts-no-tiny-functions` 与 `ts-no-inline-cast-access` 两条规则提醒，并进行了重写。
- `frontend/package.json` 只有 `dev`、`build`、`preview`、`test`、`test:watch`，没有 lint 脚本。

**建议**

- 为这类机械模式增加确定性检查：ESLint + typescript-eslint 规则，或一个轻量的 `scripts/check-frontend`（在 `tsc --noEmit` 之外检查内联断言、单表达式包装等明确模式），并纳入 pre-commit/CI。
- 若暂时不引入 ESLint，至少在 review 阶段的 `CODING_STANDARDS.md` 中列出这些模式，并让 review agent 在合并前检查。机械规则优先用检查，判断类规则才留给 review。
- 保持现有规则提醒作为最后一道安全网，但不要把它当作唯一防线。

**推断**

- 若没有这层检查，同类内联断言可能进入提交；本轮只是碰巧在写入后立即被提醒。

## 中优先级

### 3. 明确格式化/lint 的权威基线

**事实**

- `cargo fmt --check` 报告了 `examples/safe_shutdown_shell.rs`、`config.rs`、`tests/common/mod.rs` 等本票未修改文件的格式差异；本票新增文件也有格式化差异，最后逐个手工对齐。
- 本轮没有运行前端 formatter/linter（仓库没有对应脚本）。

**建议**

- 决定 rustfmt 是否权威：如果是，做一次仓库级 `cargo fmt --all`，并把 `cargo fmt --check` 接入 CI/pre-commit；如果不是，明确“格式化属于 review 判断”，并提供只检查变更文件的轻量脚本，避免全仓既有差异淹没真实问题。
- 前端若要强制格式/风格，增加 eslint/prettier 脚本并在 CI 中运行；否则在 review 标准中写明哪些是判断项。

**未验证**

- 现有构建流程是否在其他环境运行过 fmt/lint；本轮只观察到本 worktree 的结果。

### 4. 为 TDD 增加按验收项的“红/绿或突变”记录

**事实**

- 第一个后端切片的测试是先失败（端点 404）再实现；但重命名、冲突、分支、概览等后续测试多数在实现已具备后一次通过。
- 末尾做了三次针对性突变：后端把 `A` 分类改为 `modified`；前端把祖先提示收窄为精确路径；前端把冲突色合并为普通修改蓝。三处都被新增测试抓住并已还原。
- 并非每个验收项都做了突变，例如 pending set 的忽略规则、角标固定期望、分支刷新和错误状态主要依赖首次通过的测试。

**建议**

- 在实现票模板或 `docs/agents/testing.md` 中增加一张“验收项 → 测试 → 红证据/突变结果”的短表，要求每项至少满足其一：首次运行确实失败，或做一次针对该行为的临时故障注入。
- 对难以制造红的“已存在行为”项，记录“为什么无需新增红”的理由即可，避免为制造失败而制造失败。
- 可以为高风险变更提供一个小型突变脚本（只改一行、运行指定测试、还原），但不必引入完整 mutation testing 工具。

**推断**

- 这种记录不会直接改变代码质量，但能让 review 和集成阶段更快判断测试是否真正约束了行为。

### 5. 把真实浏览器证据流程做成可重复配方

**事实**

- `tab.screenshot` 返回的是保存后的路径字符串，而不是图像字节；本轮先按字节写入，生成了一个 66 字节的无效 PNG，之后改用 `page.screenshot({ path })`。
- 第一次浏览树截图取景在展开的 `.git` 上，没有显示彩色文件；证据说明最初还写了截图中并不存在的冲突色，随后重拍并修正说明。
- 最终证据同时保存了计算颜色（`getComputedStyle` 结果）和截图，这使颜色断言比只看截图更可靠。

**建议**

- 新增 `docs/agents/browser-evidence.md`（由 `AGENTS.md` 用一行指针指向），记录可复用步骤：创建隔离 Git 仓库、写隔离登记/配置、启动后端、用 `page.screenshot({ path })` 保存、同时保存 `colors.json`、最后人工查看每张截图再写说明。
- 在证据 README 中要求引用 `colors.json` 或等价的计算值；截图只作为视觉佐证，不作为唯一断言来源。
- 若未来重复做同类证据，可把上述步骤固化为脚本，但先确认不把浏览器驱动变成新的维护负担。

**推断**

- 流程固化后，类似“截图没有拍到目标内容”的问题可以在写说明前被检查出来。

## 低优先级

### 6. 为测试夹具与检查命令增加导航指针

**事实**

- 本轮通过目录列表和阅读才发现 `backend/tests/common/mod.rs` 的 `TempDir`、`TestServer`、`get_over_tcp`、`post_json_over_tcp` 等夹具，以及后端测试依赖前端构建产物这一隐藏条件。
- `AGENTS.md` 目前只指向 issue tracker、triage labels 和 domain 文档，没有测试/检查入口的指针。

**建议**

- 新增 `docs/agents/testing.md`，集中说明：唯一全量检查命令、真实 Git/浏览器证据流程、HTTP 与临时目录夹具位置、前端构建前置条件。`AGENTS.md` 只增加一行指针，保持其轻量。
- 不要把这些细节直接堆进 `AGENTS.md`；当前它的简短结构是有效的。

### 7. 关注 API 客户端模板的重复，但不要过早抽象

**事实**

- 新增 `gitApi.ts` 与既有 `browseApi.ts` 在“fetch → JSON → 形状校验 → ok/rejected/unreachable”这一段上高度相似；本轮选择复制既有模式以保持一致。

**建议**

- 在 review 标准中把“复用既有请求/错误归一化模式”列为检查项；等出现第三个 API 客户端时，再评估抽取一个 `requestJson` 或结果类型 helper。当前不因重复而立即引入抽象。

## 本轮无需改动的做法

- 用 codebase-memory 的文件大纲先看大文件、再按范围阅读，降低了阅读成本和遗漏风险；可以保留。
- 在真实浏览器中同时记录计算颜色和截图，是比“只断言 class”更强的证据；应保留。
- 对关键行为做临时突变并还原，确实发现了测试对语义的约束；应保留并扩展到更多验收项。
- `AGENTS.md` 当前只承载少量高价值指针，没有明显膨胀；不建议为了“更完整”而增加常驻说明。

## 未验证与已知限制

- 本轮未验证真实手机触摸与软键盘体验（H1）；浏览器证据来自无头 Chromium 和窄屏仿真。
- `git` 可执行文件缺失这一错误分支已实现，但没有自动化用例覆盖；已验证的是目录消失、未登记和损坏的 Git 元数据。
- 本轮没有检查 CI、pre-commit 或仓库级格式化基线，因此上述“接入检查”的建议需要先确认现有设施，再决定实现方式。
