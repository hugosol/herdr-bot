## Retrospective

# 复盘：02-browse-workspace-files 的 TDD 执行

## 结论

本票实现与验收证据基本完整，但执行过程中反复出现**验证基础设施**造成的浪费：后台测试残留进程导致后续构建失败、缺少串行验证入口、Rustfmt 与 TypeScript 机械规则没有仓库级 guardrail、Windows 标准符号链接能力缺失。以下按严重度排列，均为对环境的改进建议，不代表本次实现未完成。

## 高严重度

### 1. 后台测试进程泄漏 + 并发 cargo，造成假失败和重复全量运行

**事实**
- 最终全量 `cargo test` 在 bg_13 通过（`250.78s`，全部目标通过）。
- 在此之前，bg_12 以 `LNK1104: cannot open file '...\no_auto_termination-ae431854552d1ce2.exe'` 失败；`Get-Process` 确认 PID 7840 仍持有该测试 exe；执行 `Stop-Process -Id 7840 -Force` 后重跑才通过。
- bg_13 运行期间，另一条 `cargo test --test workspace_browse --test workspace_registry` 遇到 `Blocking waiting for file lock on build directory`，并因 `omp-bot.exe` 被占用而无法删除。
- 泄漏进程属于既有 `no_auto_termination` 测试；后台 job 被取消/超时后，其子进程没有随之清理。

**影响**
- 构建失败看起来像代码问题，实际是环境残留；实现代理需要额外花一轮排查进程。
- 并发 cargo 命令触发文件锁和 exe 占用，增加了不可复现失败的风险。

**建议**
- 增加唯一的验证入口 `scripts/verify.ps1`（或 `just verify`）：使用命名锁禁止重叠运行；按顺序执行后端、前端与构建；在 `finally` 中只清理本 worktree `backend/target/debug` 下仍存活的测试进程。
- 在测试/CI 文档中明确「同一仓库同一时刻只运行一条 cargo 测试/构建命令」。
- 增加 `scripts/cleanup-test-processes.ps1`：按 worktree 路径筛选进程并安全终止，替代每次手写 PowerShell。
- 长期考虑用 Windows Job Object 包裹测试子进程，使取消父任务时能级联终止（推断：可解决现有泄漏；未在本轮验证）。

### 2. 仓库没有 CI / pre-commit 验证 guardrail

**事实**
- 跟踪文件中没有 CI 工作流（`git ls-files` 未见 `.github` 等 CI 配置）。
- `frontend/package.json` 只有 `dev`、`build`、`preview`、`test`、`test:watch`，没有 lint/typecheck 独立脚本；仓库中也没有 ESLint 配置。
- 本次全量测试、前端测试与构建都由实现代理在对话中手动执行；最后一次小的后端改动后只重跑了受影响的 `workspace_browse` 与 `workspace_registry`，没有再次全量运行。

**影响**
- 验证依赖代理记忆，容易漏跑或在不同代码状态上运行；本次就出现了「全量通过后又有改动」的时效缺口。
- Rustfmt 基线不干净，没有「只检查改动文件」的固定入口，格式噪声容易混入提交。

**建议**
- 增加 `scripts/check.ps1`：`cargo test`（或 fast lane）、`npm --prefix frontend test`、`npm --prefix frontend run build`、`git diff --check`，以及只针对改动 `.rs` 文件的 rustfmt 检查。
- 把同一脚本接入 CI（push/PR）和 pre-commit；全量 `cargo test` 约 250 秒，适合 CI；pre-commit 可只跑 fast lane。
- 在预提交中加入 `git status --porcelain` 检查，发现未预期的未暂存文件时明确失败。

### 3. 缺少标准 Windows 符号链接的创建能力，验收证据被迫降级

**事实**
- PowerShell 创建符号链接返回「此操作需要管理员权限」；本机未启用开发者模式。
- 测试改用真实 Windows 目录联接 + WSL 在 NTFS 上创建的 reparse point 符号链接；测试输出为 `native=false`，并明确打印了 WSL 链接路径。
- 目录联接的目标显示已验证；WSL 符号链接的 `read_link` 目标无法被 Windows 读取，页面显示「目标不可读取」，因此标准 Windows 符号链接的目标文本没有单独验证。

**影响**
- P14 要求真实 Windows 链接/联接证据；WSL LX 符号链接是真实 reparse point，但不是标准 Windows 符号链接，目标显示这一项证据不完整。
- 后续票据若继续依赖链接测试，会再次遇到同样环境阻塞。

**建议**
- 增加 `scripts/create-windows-links.ps1`：优先创建标准 `mklink` 符号链接；失败时明确提示需要开发者模式/管理员权限，并记录当前使用的是 junction 还是 WSL reparse point。
- 在 CI 或本地测试准备中提供一个具备 `SeCreateSymbolicLinkPrivilege` 的运行方式（开发者模式或提权 job），让标准符号链接的「显示目标 + 拒绝进入」成为可稳定运行的断言。
- 对无法创建标准链接的环境，让测试输出明确的 `SKIP` 原因和缺失的验收项，而不是只打印一行提示后继续通过。

## 中严重度

### 4. 浏览器证据工具行为不明确，截图路径会静默丢失

**事实**
- `tab.screenshot({ path })` 返回了截图图像，但磁盘文件的修改时间没有更新；改用 `tab.run` 内的 `page.screenshot({ path })` 后文件才真正写入。
- `tab.run` 的函数回调没有注入 `document`；使用 `document` 会抛 `ReferenceError`，需要 `page.evaluate`。
- 多个浏览器操作放在同一个 `tab.run` 单元格时超过默认 30 秒超时；拆开并显式传 `timeout: 120` 后成功。
- 请求的视口为 `1280×900`，实际截图/观测到 `1258×802`；最终 README 需要按实际尺寸修正。

**影响**
- 截图可能停留在旧构建，本次曾出现截图文件未更新的情况；需要人工检查时间戳并重拍。
- 最终截图与最后一次前端构建（内容滚动复位改动）不是同一时刻，证据与 bundle 的对应关系靠人工维护。
- 取证步骤重复且容易遗漏。

**建议**
- 修复或明确文档化 `BrowserTab.screenshot` 的 `path` 语义；如果 `path` 不受支持，只推荐 `page.screenshot({ path })` 并附可复制示例。
- 在浏览器工具文档中补充：`tab.run` 回调参数、`document` 不可用、默认超时与显式 `timeout`、截图尺寸与视口的关系。
- 增加一个可复用的 `scripts/capture-browse-evidence` 脚本：创建隔离目录、启动真实后端、执行桌面/窄屏导航并落盘截图；截图后校验文件存在与时间戳，避免旧图被提交。
- 对需要精确视口的证据，使用 `page.setViewport` 并在截图元数据中记录 `window.innerWidth/innerHeight`。

### 5. TypeScript 机械规则只靠系统提示，没有仓库级 lint

**事实**
- 首版 `frontend/src/browseApi.ts` 定义了本地 `isRecord`，触发 `ts-no-local-is-record`；测试中使用 `(window as unknown as { __pwned?: unknown }).__pwned`，触发 `ts-no-inline-cast-access`。实现代理随后改为内联 `in`/`typeof` 检查和 `'__pwned' in window`。
- 仓库没有 ESLint 配置或 `npm run lint`。

**影响**
- 这类**机械性**规则本应在实现阶段被确定性检查挡住，却由系统提示/宿主规则在提交前拦截，增加往返。
- 人工 review 需要重复检查同一类模式，分散对行为正确性的注意力。

**建议**
- 增加 ESLint（或基于 TypeScript compiler API 的小检查脚本），用 `no-restricted-syntax` 覆盖至少三类本仓库反复出现的规则：本地 shape guard、内联 cast 成员访问、单表达式包装函数。
- 增加 `npm run lint`，并接入 CI/pre-commit 与 `scripts/check.ps1`。这是机械模式，默认应该用检查而不是文档规则。

### 6. Rustfmt 基线未清理，且 `rustfmt file.rs` 会顺着 `mod` 改写无关文件

**事实**
- `cargo fmt --check` 在既有 `backend/tests/common/mod.rs`、`backend/tests/common/sse.rs` 等文件报告差异，说明基线并非 rustfmt-clean。
- 对新增测试执行 `rustfmt tests/workspace_browse.rs` 时，它跟随 `mod common;` 改写了 `common/mod.rs` 与 `common/sse.rs`；提交后 `git status` 出现这两个未预期的修改，随后用 `git restore` 还原。

**影响**
- 无关文件被格式化，容易混入提交或制造 review 噪声；全局 `cargo fmt` 会放大这个问题。
- 实现代理需要额外判断哪些修改是自己造成的。

**建议**
- 增加只检查改动文件的脚本，例如 `rustfmt --edition 2024 --check --config skip_children=true <changed files>`（以固定工具链支持为准），不要运行全局 `cargo fmt`。
- 在测试/贡献文档中写明「不要对既有文件运行 rustfmt；新增文件按仓库目标风格格式化」。
- 把 rustfmt 基线清理作为独立变更，而不是夹在功能票中；或者明确接受基线现状，只阻止新增偏差。

### 7. TDD 的 red-first 与 vertical slice 没有可检查证据

**事实**
- 从对话顺序看，先创建了 `backend/src/browse.rs` 与配置字段，之后才创建 `backend/tests/workspace_browse.rs` 和配置测试；前端同样先实现 `WorkspaceBrowser.tsx`/`browseApi.ts`，后写 `workspaceBrowser.test.tsx`。
- 没有记录第一次运行新测试时的失败输出；8 个后端测试和 9 个前端测试是成批写入的，而不是一次一个 tracer bullet。

**推断**
- 本次实际是「实现后补测试」而非严格的 red → green；测试可能已经受实现结构影响。

**影响**
- 这是 TDD skill 的流程偏差；验收测试仍通过，但 red 阶段没有证据，无法证明测试在实现前能因行为缺失而失败。

**建议**
- 在票据模板或 TDD 执行契约中加入 `red` 检查点：实现前先运行新测试并记录失败命令与断言输出（可放在票据的临时字段或 `red.log`），review agent 检查 red/green 两侧证据，而不只看最终绿色。
- 在 skill/模板中强调垂直切片：每个 cycle 只写一个测试、一个最小实现；禁止一次写入全部测试。
- 如果要把这条变成自动化检查，可在 harness 层记录「第一次测试运行」与「第一次源码编辑」的时序，至少对「从未运行过失败测试」给出警告。
