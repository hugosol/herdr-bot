# 05: 同一 Chat 的并发 Resume 不重复执行

**What to build:** 同一 herdr-bot 实例内，同一历史 Chat 同时最多一个 Resume 持有执行资格。来自不同页面或独立请求者的重复操作不能形成后续启动队列，浏览器依据后端权威结果反馈忙碌。

**Delivers:** P16。

**Blocked by:** 02: 无匹配时恢复 Pi 历史 Chat。

**Status:** ready-for-agent

- [ ] 执行资格在实例级按所选历史 Chat 约束，不仅依赖单页按钮禁用；并发进入查找及启动阶段时都不能让同一 Chat 同时执行多个 Resume。
- [ ] 独立 HTTP 请求者同时操作同一 Chat，配合受控查询及启动延迟，观察最多一次创建和启动；重复请求不等待后排入下一次执行。
- [ ] 首个操作完成后，先前被拒绝的请求不会自动执行；不存在延迟启动副本。
- [ ] 正常定位、恢复成功和明确失败后正确释放执行资格，后续由用户新发起的请求可以执行；同一 Chat 不会因失败永久忙碌。
- [ ] 不同 Chat 不因本票新增不必要的全局串行限制；执行资格不扩大为多实例分布式锁。
- [ ] 实际浏览器交互呈现后端接受或拒绝的结果，不乐观宣称成功；以独立请求者和副作用记录证明约束，而不是以按钮状态证明。
- [ ] 本票拥有正常和明确失败路径的并发、非排队及资格释放检查；启动超时、后续重试与并发交错用例由 06 唯一拥有。
- [ ] 更新现有 Resume 说明中的实例内并发边界及忙碌语义，不改变会话登记生命周期。

## 覆盖分区

本票拥有 P16 的基础实例级执行资格、独立请求并发、拒绝排队、正常与明确失败后释放的自动检查。06 在 P17–P19 的超时场景中验证与该资格的组合行为，不重复认领本票基础用例。
