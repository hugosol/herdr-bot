这次最有价值的发现来自真实外部边界：自动检查已能通过，但 Herdr 自身返回的结构化启动超时仍被归为普通失败。执行者随后补出了有辨别力的 red，再完成修复和 green。最终记录为后端 439 通过、5 项既有人工网络检查忽略，前端 205 通过，相关浏览器检查 12 通过；H-Pi／H-OMP 保持未验收，没有用自动测试或准备材料代签用户确认。

以下按严重度排列，均为后续环境改进建议，不表示本轮仍有同名产品缺陷未修复。

## 1. 高：让原生验收夹具先证明隔离生效，再启动验收路径

**事实**：最初虽创建了专用目录、命名 Herdr session 和启动 wrappers，实际 Pi 终端仍出现用户环境中的 Skills／Prompts，以及 `Could not restore model storage-local/storage-probe. Using openai-codex/gpt-5.6-sol`。OMP 初次启动又因 PowerShell 的 `Start-Process omp` 报“不是有效的 Win32 应用程序”而超时。之后改为专用 `cmd.exe`，并在专用 Herdr server 环境中设置共享的 `PI_CODING_AGENT_DIR`、HOME／USERPROFILE，最终才得到隔离配置下的证据。

**推断**：只检查 wrapper 文件或父进程环境，不能证明实际终端里的命令解析与 agent 有效配置一致。记录没有证明发生了向用户现有 Chat 提交输入的行为，也不应将这次配置串入扩大解释为用户对话被改动。

**建议**：给现有原生验收设施补一个可重复的 **隔离预检**，完成条件是从实际专用进程或终端观测到：

- Herdr session、Workspace、cwd 和原生配置目录均属于本次隔离根目录；
- 实际 CLI 解析结果、版本和启动参数符合本次验收配置；
- 专用模型配置可识别，没有非预期回退或继承的嵌套 agent 标记。

预检未满足时，只记录环境前提和失败目标，暂不把该次运行纳入最终原生证明。把这段流程放在原生验收入口附近，而不是增加全局 `AGENTS.md` 禁令；CLI 语法仍以当次 `--help` 为准。

## 2. 高：把真实外部错误信封变成版本化的 adapter 回归资产

**事实**：实机 Herdr 0.9.5 返回的是 CLI 非零退出及结构化 `error.code: "timeout"`，消息为 `timed out waiting for agent startup`。原 adapter 将它转换为 `CommandFailed`，页面／HTTP 因而报告 `failed`。此前的超时自动覆盖没有暴露这一分支。

本轮处理正确：先从专用目标捕获原生错误信封，再让夹具重现该响应；新增测试实际失败于“预期 `unconfirmed`、实际 `failed`”，生产分类修复后通过。该问题已经修复，不建议再新增一份同名回归。

**建议**：复用现有 Herdr fixture，把本次捕获进一步作为 **外部协议样例** 管理：记录 CLI 版本、退出码、stdout／stderr 位置及错误 code，再由公开 HTTP／页面测试消费。后续补样例时优先覆盖不同协议分支，例如普通拒绝、CLI 自身超时、adapter 等待超时，而不是仅增加 `fail_*` 布尔开关数量。

这类机械分类由确定性回归守住，不宜写成“reviewer 注意超时”的宽泛标准。真实加载、实际客户端焦点和任务是否继续，仍保留原有 H-Pi／H-OMP 确认边界；协议样例不能替代它们。

## 3. 中：将已有网络策略检查接到浏览器测试的实际入口

**事实**：`frontend/package.json` 已有 `pretest`、`pretest:browser` 等钩子，运行现成的 `check-test-network-policy.mjs`。本轮 `npm test` 确实执行并通过了该检查；但浏览器验收使用的是多次直接 `npx playwright test ...`，该入口本身不会触发 npm 的 `pretest:browser`。当前 Playwright 配置也没有承担同一前置检查。

只读查找未发现 `.github/workflows/`、`.husky/` 或 `.githooks/` 下的仓库级入口。未检查外部 CI、`core.hooksPath` 或本地 Git hooks，因此不能断言所有环境都没有 guardrail。

**建议**：复用已有网络策略检查，而非另写一套规则：

1. 将其接到 Playwright 的统一启动生命周期，使直接调用 Playwright 也经过检查；或统一通过现有 npm 测试入口执行。
2. 在仓库级 CI／提交检查中调用同一现有检查入口；先确认外部已有接线情况，再补缺失部分。

完成条件应是：同一违规样例从 npm 入口和直接浏览器 runner 入口都会被拒绝。规则已有确定的语法和文件位置约束，适合自动化，不需要扩大 `CODING_STANDARDS.md` 或常驻代理指令。

## 4. 中：原生 seed 的完成条件应是“目标历史状态已持久化”

**事实**：首次准备 OMP 中断样例时，在第一条真实模型请求到达后终止专用 seed 进程，但预期原生 session 文件尚未落盘，身份查找断言失败。后续改为让真实 OMP 完成一次 Read 工具调用，在下一条模型请求期间中断，才得到包含旧 user、assistant toolUse 和 toolResult 的持久历史。该原生文件首行还是 title 元数据，而不是 session header。

**建议**：在现有 `scripts/test-native-session-storage.py` 的原生样例能力附近，提供明确的中断样例分支或可复用 seed 边界。其完成标准应由可观察状态决定：

- 用独立、已知的历史标记找到唯一原生文件；
- 核实完整 session ID、cwd 和目标消息／工具记录已经持久化；
- 确认任务仍处于待继续的历史状态后，再中断专用进程；
- 记录恢复前基线，供恢复后比较。

“模型请求已经出现”不足以作为持久化完成条件。这条知识属于 native seed 分支，不应成为所有实现任务都要加载的全局规则。失败的准备尝试可保留为诊断，但与最终验收样例分开标注。

## 5. 中：将浏览器 setup 失败与行为 red 分开，并让 setup 快速失败

**事实**：新增身份集合组合用例最初按完整 session ID 定位历史行，但页面在存在名称时显示名称而不显示 ID。Pi、OMP 两例都耗尽 90 秒测试时限；随后读取错误上下文，改用独立预写的公开时间字段定位，两个组合用例通过。

这两次失败是定位器／setup 失败，不能证明 P21 或 P22 的行为断言具有辨别力。本轮后面的结构化超时失败才是明确的行为 red。已有行为直接验证通过，不人为制造失败，也符合本次 TDD 要求。

**建议**：在现有 `frontend/browser-tests/ui.ts` 中复用或补充语义化的历史行操作辅助能力。在创建响应等待之前，先以较短、明确的断言确认目标行唯一且按钮可操作；再执行点击和响应观察。必要时在同名样例中使用公开可见字段组合，不依赖页面并未展示的身份。

辅助能力的完成条件是：错误选择器在定位阶段快速给出页面上下文；产品缺陷仍失败于行为断言。不要用统一延长超时、添加休眠或新增测试专用恢复接口处理这个问题。

## 6. 低：让导航工具显式识别“当前 worktree 未覆盖”和“服务不可用”

**事实**：首次 `find` 的 24 个判断请求全部因区域限制 HTTP 451 失败；随后项目列表没有当前 worktree 的索引，执行者借用了 `chat-resume-06` 的声明大纲，再读当前 worktree 文件。部分索引查询返回空结果。

**风险推断**：相邻 worktree 的大纲即使看起来相同，也不能证明当前路径和版本被覆盖。工具空结果与无索引、服务不可用之间若没有明确区分，会诱导额外探索或错误的“未找到”结论；本轮记录没有证明因此误改了文件。

**建议**：由工具／宿主提供一次轻量的 root-aware 索引选择与能力检测：当前 worktree 精确覆盖、可复用但未确认的新鲜度、不可用三种状态分别返回。区域限制应尽早触发受支持的本地搜索回退，而不是继续走需要同一不可用服务的判断链。

这个改进放在工具路由层比再加一条“优先使用 MCP”的常驻指令更有效。对 repo 文档，只在原生验收分支需要时提供现有验收入口指针，避免缓存整个 CLI 帮助或反复抄写路径清单。
