## 1. 高：为 Herdr 夹具建立独立的操作级协议校验

### 事实

- 第一轮 HTTP 测试通过时，夹具的 `agent focus` 返回通用 `ok`，生产适配器也按 `ok` 接受聚焦确认。随后交付页面测试同样通过。
- 后期才从外部 Herdr 的 `handle_agent_focus` 源码确认：该操作返回的是 `agent_info`，包含实际 agent 信息。
- 只把夹具改成官方响应形状后，原先通过的测试立即失败，结果为 HTTP 502，错误包含 `missing focus acknowledgement`；修正适配器后才恢复通过。原始日志约 04:09:48—04:10:06 明确记录了这次红绿转换。

### 判断

这是已被本轮工具结果证明的**夹具与实现共享错误假设**，不是推测出的潜在问题。HTTP、真实子进程和真实浏览器都没有自动提供独立预期：如果外部替身的协议本身错误，多层测试仍可一起变绿。

### 建议

- 为新增 Herdr 操作准备**操作级协议样例及独立校验**，预期来自官方操作处理器或专用测试环境采样，而不是从 herdr-bot 的解析逻辑反向生成。
- 校验 `agent focus` 的命令与响应对应关系：正常返回 `agent_info`，位置字段和 `focused` 可用于确认导航。通用 JSON schema 校验不足以替代这一点，因为 `ok` 本身可能是其他操作的合法响应。
- 将这类检查接入现有 Cargo 测试入口。`frontend/package.json` 已有类型检查及测试网络护栏，但它们不覆盖这种外部操作语义。
- 在现有 Herdr 集成文档中集中记录协议事实的查证入口和适用版本；触发指针只需表达：“新增或修改 Herdr 操作时，先核对该操作的请求与响应。”不把完整 schema、机器绝对路径或每个操作的字段抄进常驻代理上下文。

**完成判据：** 将受控 `agent focus` 的正常响应替换成通用 `ok` 时，独立协议检查失败；官方响应样例通过，且无需接触用户现有 Chat。

## 2. 中：把“缺接口红”与“行为红”分开，收紧纵向切片的完成门槛

### 事实

- 首个 `native_path_matches_saved_id_and_focuses_actual_location_without_input` 测试先因 HTTP **405** 失败。这证明入口缺失，但尚未检验身份匹配或焦点行为。
- 随后的实现已经包含多目标排序和相关身份资料核实等分支；相应测试是在这些实现之后才补写的。
- 浏览器红灯运行期间，一个身份可读性测试因可执行文件占用而未能运行；在取得该测试行为结果之前，又加入了稳定排序测试。
- 本轮也有有效的行为红绿证据：JSON 错误信封的错误分类被测试暴露并修正；官方聚焦响应纠正后，已有测试重新变红并推动修正。

### 判断

本轮不是没有 TDD，而是部分切片从“入口不存在”直接跨到多个行为已实现，再补充覆盖。最终的反例与排序测试有价值；但它们不能反过来证明每个新增分支都经历过当时所要求的纵向红绿过程。

### 建议

- 在 TDD 执行器的当前切片记录中，区分**缺接口、环境失败、行为失败、已有行为已覆盖**，不要把四者都压成一个“red 已完成”。
- 首次失败若只是路由、导入或夹具能力缺失，先补足使行为可达的最小接线，再检查当前行为断言；随后才进入下一个新行为分支。
- 新实现的排序、身份核实等承诺分别完成当前切片后再推进。已满足的行为可以直接验证，不必为了制造红灯改坏代码；但应说明为何现有反例能排除具体错误。
- 对“错误实现是否仍可能通过”无法由检查场景直接判断的情况，使用局部临时变异验证敏感性。不要把变异测试变成每个已绿用例的强制仪式。

**完成判据：** 每个新实现的行为都有可追溯的独立预期、具体反例与观测结果；环境失败不被计作行为红灯，缺接口红灯也不单独承担整条行为的验证责任。

## 3. 中：隔离浏览器运行产物，避免 Windows 可执行文件占用打断验证

### 事实

- 浏览器测试从 `backend/target/debug/herdr-bot.exe` 启动服务。
- 页面缺少 Resume 按钮时，`locator.click` 等到了 **90 秒整项测试超时**。
- 该测试仍运行期间，另一次 `cargo test` 尝试重建同一个可执行文件，得到 `failed to remove file ... herdr-bot.exe`、`os error 5`。
- 浏览器任务结束后，后续测试正常通过。因此这次失败是运行环境冲突，不是身份核实断言检出了缺陷。

### 建议

- 优先在现有浏览器测试 helper 中，把已构建服务复制到每次测试的隔离运行目录，再启动副本；清理由 helper 负责。浏览器运行与 Cargo 输出目录由此不再争用同一 exe。
- 若暂时不做产物隔离，则由测试运行器串行管理“占用该 exe 的浏览器测试”和“会重建该 exe 的 Cargo 命令”。浏览器任务运行期间仍可做阅读等不争用产物的工作。
- 对页面操作前置条件先使用合理时限的可见性断言，再执行点击。页面启动就绪时限和按钮缺失的失败时限应分开，避免一个明确缺失的控件拖到整项测试超时。

**完成判据：** 浏览器服务运行时，重新构建原 Cargo 目标不再出现这类文件占用错误；缺失按钮能以明确的界面断言结束，而不是等待整项 90 秒超时。

## 4. 中低：让搜索工具快速降级，并按操作提取 Herdr schema

### 事实

- 首次 `find` 的 **26 个 judge 请求全部因 HTTP 451 地区限制失败**；工具明确说明这不能作为代码不存在的证据。
- 后续在外部 Herdr 源码中再次使用 `find`，又有 **24 个 judge 请求因同一原因全部失败**，之后才改用字面检索。
- `herdr api schema --json` 一次返回 **10,760 行**，输出中间省略了 8,886 行。代理随后再次搜索、定段读取，最终仍需查看具体操作处理器才能确认聚焦返回类型。
- 本轮通过代码图搜索、声明大纲和后备字面检索找到了所需位置；不存在“完全无法访问资料”的阻塞。

### 建议

- 在工具层对地区不可用等稳定故障建立**本会话能力熔断**：首次确认后，直接降级到代码图或字面搜索，并保留“未完成语义搜索”的说明。恢复探测由工具层处理，不让每次代码导航都重新触发一批失败请求。
- 为 Herdr schema 查询提供按操作或定义提取的只读入口，返回所需类型、关联定义及版本即可。原始完整 schema 保留为按需展开的底层材料。
- 将“操作对应哪种响应”的导航与大 schema 定义分开；只有类型定义、没有操作映射，仍不足以防止本轮的 `ok` 假设。

**完成判据：** 同一会话中的已知不可用搜索服务不再重复扇出；查询聚焦协议时，无需把万行 schema 注入上下文，且能直接到达该操作的响应依据。

### 建议

先核实外部触发机制。若没有覆盖提交或集成的自动入口，再增加一个仓库级触发点，调用现有检查命令，并纳入第 1 项的协议校验。沿用现有 Windows、回环网络和人工 LAN 用例隔离要求，不为普通流水线开启真实网卡或原生 Chat 操作。

**完成判据：** 无需依赖代理记得手工运行命令，正常提交或集成流程就能给出明确的检查结果；已有外部入口若足够，只补导航，不另建重复流水线。
