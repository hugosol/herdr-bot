# Ticket 05 TDD 执行复盘建议

## 范围与结论

本复盘仅依据指定 ticket 执行会话的 JSONL、其中的工具结果，以及只读查看的项目检查入口；未使用父 session 或其他 ticket 的执行历史。复盘阶段未修改文件、未重跑验收。

**本轮有有效的行为 red，也完成了对应 green。** 首个独立 HTTP 并发用例在未加执行资格时，因为重复请求不能即时返回而失败；完成实现后，相关 HTTP 回归为 **17 passed**，真实浏览器回归为 **4 passed**，并已提交 `f6fd6b6`。受控查询／启动屏障、外部副作用记录和真实页面交互值得保留，不能退化为只验证按钮禁用。

主要改进空间在测试环境的诊断能力与复用、自动检查接线和工具失败降级，而不是再增加“认真检查”“遵守 TDD”之类常驻指令。以下按优先级排列。

## 1. 较高优先级：让屏障等待同时观察操作是否已结束

**类别：信息访问／测试基础设施。**

### 已观察事实

- 增加 guard 后，两次测试都等待启动屏障约 10 秒，最后只报 `external CLI must reach the controlled gate: Elapsed(())`。
- 这期间代理先给 catalog 增加了 `extensions = []`，仍未解决问题。
- 后来把等待改成 `tokio::select!`，同时观察首个 HTTP 请求是否结束，才直接得到 `502 / invalid-agent-settings / agent pi 缺少固定扩展`。该次失败在测试运行约 0.07 秒时即被识别。
- 随后补齐固定 Pi 集成 fixture，同一行为预期保持不变，用例通过。

### 建议

将这次有效的诊断方式下沉到现有测试支撑层：屏障等待同时观察**目标外部调用、所属操作结果和有界超时**。操作提前结束时直接输出 HTTP 状态、响应体及已记录的外部调用；超时时输出等待的阶段和已有记录。

适合落点是 `backend/tests/common/mod.rs` 的测试辅助能力，而不是新增一条要求代理“超时后多看日志”的全局规则。辅助能力只提供调度与诊断，行为断言仍留在公开 HTTP／Herdr seams。

**预期收益［推断］：** 将本次两次完整等待和一次猜测性 fixture 修补，缩短为首次失败即可定位的环境问题；同时更容易区分行为 red 与未到达行为条件的 setup failure。

**建议验收边界：** 人为提供缺少固定集成的 catalog 时，等待启动的用例应直接报告实际 settings 失败，而不是耗尽屏障等待时间。本轮未执行该建议的验收。

## 2. 中优先级：为 Resume 测试提供一份最小有效环境构造器

**类别：导航／测试环境复用。**

### 已观察事实

执行中已经阅读了 `backend/tests/chat_resume_pi.rs` 的有效 setup，其中包含真实固定集成文件及 catalog 条目；新建并发测试时仍另外手写了一份缺少必需内容的 catalog，导致前述失败。

这不是完全找不到示例，而是**已找到的环境约束没有通过可复用接口承载**。仅增加一个指向旧测试的导航指针，收益可能有限。

### 建议

在现有 `common` 测试支撑中提取最小有效 Pi Resume 环境的构造能力，负责真实临时路径、有效 catalog 和固定集成文件；历史记录、原生身份、外部故障及预期结果继续由各用例独立提供。

复用的对象应是**有效环境**，不是完整场景，更不是测试期望值。这样既减少 catalog schema 的重复缓存，也保留独立字面样例和不同测试的辨别力。

**建议验收边界：** 新并发用例无需复制 catalog TOML 即可到达预定外部屏障；无效配置测试仍能显式替换对应文件，验证公开接口的失败反馈。

## 3. 中优先级：把已有检查接入仓库可见的自动门禁，并由启动流程准备依赖

**类别：自动检查／执行环境。**

### 已观察事实

- `frontend/package.json` 已有 `build`、`test`、`test:browser`；`build` 包含 `tsc --noEmit`，测试入口已有网络策略前置检查。这些能力应复用，而不是重新发明另一套检查。
- 本轮第一次前端构建因找不到 `tsc` 失败。执行锁定依赖安装后，约两秒完成安装，构建及浏览器验证随即成功。
- 本次只读检查未发现 `.github/workflows/*`、`.githooks/*` 或 `.husky/*` 中的入口。**这不能证明完全不存在自动门禁**：外部 CI、全局 hooks 及自定义 hooks 路径未核实。

### 建议

先确认现有外部门禁；若没有覆盖，则接入仓库可见的 Windows CI，调用已有 Cargo 与 npm 检查入口，并明确真实浏览器检查所需的前后端构建顺序。现成的网络策略检查继续由 npm 生命周期触发，无需复制规则。

同时由 worktree 启动流程按锁文件准备前端依赖，或在进入浏览器构建前提供可执行的依赖缺失提示。将安装状态交给工具判断，比在 AGENTS.md 中再写一句“记得安装依赖”稳定。

**预期收益［推断］：** 降低验收是否运行对单个实现代理记忆的依赖，减少新 worktree 的无意义构建失败。

**未验证项：** 现有外部 CI 是否已完成这些工作、完整套件在 CI 的运行成本及 Chrome 可用性。本轮没有执行新增门禁或检查全仓结果。

## 4. 中低优先级：语义查找后端不可用时立即降级

**类别：工具经济性。**

### 已观察事实

首个 `find` 调用内部发出了 26 次判断请求，全部因 `451 / Typesafe is not available in your region` 失败，没有产生任何判断结果。之后代理通过字面搜索、文件发现和 codebase-memory 索引／声明大纲继续完成了定位。

这是一次调用内部的批量失败，不能描述成代理连续重试了 26 次。

### 建议

在工具实现层对区域限制、授权不可用等稳定错误设置快速失败或短期熔断：首次确认后直接返回明确状态及可用降级入口，避免继续分发整批判断请求。保留工具当前“失败不是不存在的证据”的说明。

若需要调整导航指令，应统一放在工具选择规则的单一来源中，明确不可用时的下一步；不宜在每个项目 AGENTS.md 重复增加异常处理段落。当前 worktree 的索引建立和大纲读取满足已有约束，不应仅为减少调用而绕开它们。

**建议验收边界：** 模拟该稳定 451 时，工具无需完成整批远端请求即可返回可操作的降级信息。本轮未验证工具改造。
