# LLM 驱动工作流：Definition 设计共识与原则

> 整理日期：2026-10-25。
> 来源：本次关于工作流 Definition 的连续教学讨论，以及对 oh-my-wayfinder / oh-my-pi 和 Pi workflow 方案的核对。
> 用途：作为后续设计与实现的上下文，保存已经确认的方向、关键推导、设计原则及未决问题。
> 状态：**设计共识记录，不是最终 schema、实施规格或已实现功能说明。**

## 1. 原始需求与本次讨论范围

希望设计一个类似 Claude Code 使用体验的 workflow 功能：

- 用简单、可保存的数据结构记录工作流，能够反复复用。
- 用户通过自然语言生成、修改和复用工作流。
- 不要求在界面上拖拽编辑；只需要通过可视化验证调整结果。
- 支持人工参与与自动执行，用户可以逐步把实际工作中的环节自动化。
- 最初以 session / subagent 理解节点，讨论后确认节点可以封装更复杂的执行过程，不必与一个会话一一对应。

**执行系统已经有承接方：herdr-bot。**当前可以把节点执行简化为使用“发起 chat”触发 session，交付可以是文件、消息或通知。本次不以执行 Interface、adapter、消息桥接或宿主接线为设计重点，也没有要求修改这些系统。

当前的核心是两件事：

1. 从 hyper-auto-coding 抽取与业务无关的编排内核。
2. 设计 LLM 能够生成、引擎能够约束、用户能够通过流程图验证的 Definition。

## 2. 核心结论

> **LLM 理解业务、提取工作结构并选择动作；引擎实施通用门禁、管理执行并保存事实；节点完成具体工作。**

Definition 是三者之间可保存、可复用的工作约定：

- 给 LLM：目标、工作说明与必要上下文。
- 给引擎：节点身份、输入来源、依赖与完成约束等明确结构。
- 给用户与可视化：可检查的任务关系、交付关系及参与方式。

Definition 不应默认成为一个穷举所有业务分支的调度程序，也不能退化成只靠模型自觉遵守的 prompt。

## 3. 关键决策及其形成过程

### D1：不预设代码必须决定所有业务流转

早期讨论过显式状态机、固定 next / switch、DAG 等方案。但用户指出：这可能带有先入为主的偏见，把本可以由 LLM 判断的流转编码成大量分支。

已确认的方向是：

- LLM 根据工作目标、Definition 和当前执行事实选择下一步动作。
- 引擎检查该动作当前是否允许，并可靠地启动执行、记录结果。
- 不要求代码预先决定每一种业务情况下应该走哪一步。

这不是取消状态或门禁，而是将“选择动作的策略”与“动作是否合法及如何执行”分开。

**仍然成立的补充：**不必让每一项确定性后续处理都增加一次模型决策。例如，记录结果、产生通知、执行已确定的收尾，可以继续由代码直接推进。

### D2：优先从 hyper-auto-coding 抽取内核，不另起一套框架

用户主动发现：hyper-auto-coding 已有的依赖登记、派发、收集与收尾协议，本身就接近可泛化的流程引擎模型；TDD、integration 等更像具体节点。

已确认：后续以现有实现为起点，去掉与编码流程强耦合的部分，保留已经有效的编排协议与执行语义。

**不能过度解读：**当前实现仍直接依赖编码领域结构，并非今天替换一组任务文本就已经能执行任意领域流程。“可抽取通用内核”是设计判断，不是泛化已完成的事实。

### D3：节点不等于一个 session / subagent

节点是对编排层承担一项工作的执行模块，可以是：

- 一个自动 subagent；
- 一个人与 agent 多轮协作的 session；
- 一段确定性代码；
- 包含实现、集成、复盘及多个会话的组合过程。

外层引擎只应掌握必要的输入、交付、等待和最终执行事实，不要求了解节点内部所有步骤。

因此，session / subagent 是执行资源或参与方式，不应成为限制整个节点模型表达能力的唯一顶层分类。

### D4：释放下游与本节点最终结束必须解耦

这是从实际优化中提炼出的已确认原则：

> **某项产物已经可供下游使用，不等于本节点的全部工作已经完成。**

现有编码流程中，首次合并成功即可解锁依赖，后续集成处理结束才达到最终集成状态。

通用模型必须能保留这种差异，不能无条件压缩成唯一的 completed 状态。

可能的表达方式包括：命名交付、里程碑、输出端口，或者将相关过程拆为不同节点。**具体选哪一种尚未定稿。**

### D5：Definition 由代码构造，保留结构元数据以直接复用

用户明确修正过最初“独立 JSON 是默认权威”的设想：希望 Definition 由代码控制，可以类似状态机的代码，并保留元数据；以后直接复用，不重新推导流程图。

后续讨论进一步明确：代码式 Definition 不等于必须编码完整业务转移表。

期望方向：

```text
代码构造 / 组合 Definition
             ↓
规范化、可保存的定义描述
   ├─ 引擎使用
   ├─ LLM 理解与执行已有流程
   └─ 可视化展示
```

代码与元数据不应分别维护两套流程逻辑。节点关系等关键结构需要显式存在于最终描述中，而不是依靠每次分析任意代码重新发现。

尚未决定：采用怎样的 TS builder、哪些内容保存为引用、元数据是否自身足以解释执行，以及代码版本与定义快照的具体关联方式。

### D6：自然语言到 Definition 是核心能力，不只是附加入口

用户强调的价值是：LLM 能够理解业务文本，智能生成一个工作流结构。

两个阶段分别是：

```text
设计时：业务文本 → LLM 提取结构 → Definition → 流程图

运行时：已有 Definition + 当前事实 → LLM 选择动作 → 引擎执行
```

生成的结构应保存下来。复用既定工作流时，不应要求模型每次重新识别已确定的任务关系。

### D7：先划分判断职责，再形成框架和字段

用户最后归纳的设计方法是：

> 关键在于判断什么交给 LLM、什么可以固化为引擎逻辑；让这套分工适配不同任务，框架自然形成。

因此不先追求“完整流程功能清单”，而是逐项判断某个概念属于模型指导、通用约束，还是领域节点内部工作。

## 4. 如何划分 LLM、引擎与节点的职责

### 4.1 交给 LLM 的判断

需要理解目标、语义、上下文或领域知识的内容，例如：

- 应将工作拆成哪些任务。
- 两项任务是否存在真实业务依赖。
- 哪些材料足以支持下一步。
- 当前失败意味着重试、补充调查还是调整方案。
- 多个合法动作中，哪一个最值得执行。
- 如何组织任务说明和有用的上下文。

引擎提供事实，但不内置这些问题的业务答案。

### 4.2 固化为引擎的逻辑

已经明确表达、可以机械检查和执行的规则，例如：

- 节点与交付引用是否存在。
- 指定交付是否已经发布。
- 当前执行是否拥有提交权。
- 并发与重复执行约束是否满足。
- 暂停后是否禁止新工作进入。
- 结束运行前是否满足定义中的条件。

核心判断标准：

> **规则明确表达之后，执行它是否还需要重新理解业务？**

例如“报告必须等待三份材料”是业务判断；当它被写成依赖关系后，检查三份材料是否已交付，可以由引擎完成。

### 4.3 不属于引擎，也不一定必须交给 LLM

Git 操作、文件转换、调用已有系统等确定性业务工作，可以保留在节点内部。

从引擎中移除业务逻辑，不意味着将业务代码一律改成模型推理。

### 4.4 固定能力，配置具体关系

| 引擎固定实现 | Definition 声明具体内容 |
|---|---|
| 检查依赖 | 哪项工作依赖哪项交付 |
| 限制并发 | 本流程或节点的限制 |
| 等待交付 | 等待哪个命名交付 |
| 检查完成条件 | 本流程要求什么条件 |
| 解析输入来源 | 哪个节点消费哪个结果 |

这使得同一套引擎不必为每个业务修改代码，也不必将所有约束放进 prompt。

## 5. 已有通用能力与需要移出的领域耦合

### 5.1 可保留为内核的能力

| 能力 | 通用含义 |
|---|---|
| 加载 / 登记结构 | 获取本次运行使用的任务及约束 |
| 查询状态 | 提供 ready、active、waiting、交付、失败等事实 |
| 准入检查 | 检查依赖、权限、并发、重复执行及暂停状态 |
| 启动工作 | 调用既有执行能力，不嵌入具体业务过程 |
| 收集进展 | 保留变化、等待变化、提供一致快照 |
| 执行记账 | 区分节点身份、具体执行及尝试，保存证据 |
| 暂停 / 恢复 | 管理明确支持的运行生命周期 |
| 结束检查 | 只有完成约束满足后才接受 finish |

现有 plan / dispatch / collect / finish 是重要参考，而不是要求未来 Interface 必须原样命名。

特别是 plan：已有 Definition 时，应直接加载既定结构；只有本次确实需要动态规划的部分，才让模型生成运行计划。

### 5.2 应移出通用内核的编码领域内容

- 固定读取 implementation 票据目录。
- 固定的 implement / integrate 角色。
- integrating / integrated 这类领域状态名称。
- worktree、Git 合并及集成分支处理。
- TDD、integration、retro 的特定组合与提示内容。

移出后，这些能力仍可作为节点或节点内部流程复用，不是删除其价值。

## 6. Definition 的候选结构：讨论起点，不是最终 schema

最后提出的概念主体是五部分：

```text
Definition
  ├─ identity       标识与版本
  ├─ inputs         每次运行需要传入什么
  ├─ instructions   目标与控制者工作说明
  ├─ nodes          工作节点及其约束
  └─ completion     什么情况下允许结束
```

一个节点需要描述的概念：

```text
做什么？
交给谁或哪种执行模块？
人怎样参与？
需要什么输入与前置事实？
承诺交付什么？
```

这些是待设计内容，不表示字段命名、必填性、默认值或嵌套结构已经确认。

### 6.1 工作指导与门禁必须区分

| 内容 | 性质 |
|---|---|
| 优先并行处理相互独立的调查 | LLM 工作指导 |
| 撰写前必须取得调查交付 | 引擎可检查的门禁 |
| 证据不足时补充调查 | LLM 语义判断与策略 |
| 尚无审阅结论不能 finish | 引擎可检查的门禁 |

不能因为一句约束出现在 instructions 中，就声称引擎已经强制执行它。

### 6.2 输入绑定可以同时表达数据来源与执行依赖

讨论中使用过以下概念写法：

```ts
inputs: {
  evidence: delivery("research", "evidence")
}
```

含义是：消费 research 节点已发布的 evidence 交付，并等待该交付可用。

倾向：从明确引用推导依赖，避免同时维护 inputs、dependsOn、edges 三份可能冲突的事实。

纯顺序约束、但不读取结果的情况，应有单独表达方式。其形式和等待的是发布还是最终结算，仍需确定。

### 6.3 不默认加入 next

在当前方向下，下一动作由 LLM 选择；Definition 提供约束和事实结构，不必预写每个状态的唯一下一个节点。

这不排除个别工作内部使用确定状态机，也不排除日后确有需求时声明路由。只是不能把完整跳转表作为所有工作流的先决条件。

### 6.4 完成条件独立于目标描述

- 目标帮助模型判断如何工作。
- 完成条件约束引擎何时允许结束。

需要分别考虑：

1. 某项交付已发布。
2. 某个节点最终结算。
3. 某项业务验收条件满足。
4. 整个运行允许结束。

例如“审阅结论存在”不等于“审阅通过”。业务判断可以由节点产生；如果必须强制通过才能结束，判断结果需要成为明确的完成约束输入。

并未决定所有节点都必须成功或所有交付都必须存在；可选节点、失败结算与分支完成语义尚待设计。

## 7. 元数据、运行记录与可视化的关系

### 7.1 三种内容各自承担职责

| 内容 | 回答的问题 |
|---|---|
| Definition | 已保存的工作结构及约束是什么？ |
| Run | 本次实际发生了什么？ |
| LLM 控制策略 | 面对当前事实，下一步选择什么？ |

不将 sessionId、当前状态、具体结果等运行数据写回可复用模板。

节点定义、节点实例、执行尝试、宿主 session 是不同身份。概念分离不意味着现在就要实现复杂数据库或拆成多张表。

### 7.2 流程图是 Definition 的直接投影

推荐：

```text
                   ┌→ 引擎执行约束
LLM → Definition ──┤
                   └→ 确定性渲染流程图
```

不推荐：模型写一份说明，再让模型独立画另一张图。两次理解可能产生两份不一致的结构。

静态定义图与实际运行图也应区别：定义展示工作约定，运行展示具体执行、等待和尝试历史。静态结构不能伪装成对所有未来动态行为的完整预测。

### 7.3 可视化应展示语义，而非仅展示连线

至少应能检查节点、依赖 / 交付关系和人工参与方式。自然语言修改后，拓扑可能不变，但参与策略、完成权或交付约束已经改变，因此还需要语义差异展示。

结构校验不能证明模型无误理解了业务；图和差异展示用于帮助用户发现理解偏差。

### 7.4 复用与版本

保存后的结构应可直接复用；不要依赖原始聊天里未保存的隐含理解。

讨论中提出过：修改形成新版本，新运行锁定对应版本，旧运行保留旧定义事实；这是合理候选策略，代码、引用配置与快照的精确版本契约尚未定稿。

## 8. 重要设计原则

### P1：先划职责，再定字段

不从功能大全或框架惯例出发，而从真实工作中的判断与不变量抽取结构。

### P2：业务含义由模型理解，明确约束由引擎落实

模型发现依赖，不代表运行时必须重复推理依赖是否满足。

### P3：策略与事实分离

模型可以建议下一步，不能靠自然语言改写权威执行状态或绕过门禁。

### P4：单一事实来源

执行关系和图形关系来自同一份 Definition；布局不改变执行语义。

### P5：局部修改

例如把某节点改为人工参与，不应要求重新设计整个流程，也不应隐式修改其他依赖。

### P6：保留必要语义，不做表面改名式泛化

不能仅把 ticket 改名为 task 就宣称通用化；也不能删掉提前释放下游等真实能力来换取表面简洁。

### P7：确定后续不必再次模型化

无歧义的记录、通知和固定执行步骤可以由代码完成；把流转决策交给 LLM 不意味着每个回调都要请求模型。

### P8：门禁保证合法性，不自动保证决策质量与推进

模型可能反复选择合法但无收益的动作，或生成结构合法但业务错误的计划。应区分安全准入、语义质量、持续进展，不能互相冒充。

### P9：既有节点执行能力先视为前提

当前不继续设计 herdr-bot chat 的调用、输出媒介和 adapter；优先完成 Definition 与通用内核的职责划分。

### P10：为每个新概念提出三个问题

1. 没有它，模型是否不得不反复猜测已经确定的事实？
2. 有了它，引擎能否执行一项清楚的约束？
3. 换成其他领域任务，它是否仍然成立？

仅帮助思考的内容可能属于工作说明；具有稳定执行语义的内容才值得成为结构化字段；仅对某领域有意义的内容留在节点配置或内部流程。

## 9. 尚未决定的问题

以下不能当成已确认需求或接口：

1. **最终 schema 与代码构造方式**：builder、对象结构、引用格式、必填字段及默认值。
2. **交付 / 里程碑表示**：命名输出、端口、里程碑还是拆节点；是否需要多次发布。
3. **交付版本与重跑**：如何绑定明确版本，重新执行后哪些下游需要重新判断，避免隐含 latest 覆盖历史事实。
4. **提前释放后的失败**：已经发布交付并启动下游后，上游收尾失败如何处理；不能默认撤销已经发生的副作用。
5. **循环、返工与动态任务**：固定定义中如何表达允许的重做与结构扩展，不能把 retry、resume、业务下一轮混同。
6. **图模型**：依赖图、状态机、显式循环或混合方式，尚未选定最终形式；不应继续将早期 DAG 示例当成用户已选定限制。
7. **互动与完成权**：此前提出 interaction / completion 两维区分，是候选模型，最终字段与控制方式未定。
8. **结束语义**：可选节点、失败终态、必须收尾的后台工作、业务通过条件如何组合。
9. **修改运行中流程**：修改 Definition 与本次运行干预如何区分，是否允许热修改，当前未作承诺。
10. **指导与门禁的对应**：如何避免文本要求与结构化约束不一致，哪些条件允许模型判断，哪些必须有可检查事实。

## 10. 建议的后续设计方法

不先扩展功能，先用少量不同领域的例子推导最小结构，例如：

- 多来源调查 → 汇总 → 人工审阅。
- 人工澄清 → 自动执行 → 交付通知。
- 当前编码流程，保留首次交付释放与最终收尾的差异。

对每个例子标出：

- 哪些内容需要 LLM 理解或选择。
- 哪些事实和关系必须保存，不能每次重推。
- 哪些约束引擎可以机械执行。
- 哪些领域行为应留在节点内部。

再从共同部分形成 Definition。以上为建议的设计推进方式，尚未完成跨领域运行验证。

## 11. 参考方案提供的启发与边界

| 方案 | 本次借鉴点 | 不应混同的内容 |
|---|---|---|
| oh-my-pi 原生 task / session | 子 session、寻址、消息、人工聚焦、执行生命周期 | 任务生命周期不是完整业务 workflow；聚焦会话不等于已有持久化批准协议 |
| pi-subagents 父模型编排 | 模型根据指引组织工作 | prompt 指导不是严格流程门禁 |
| pi-subagents 脚本工作流 | 程序保存编排与显式传参，宿主管 keyed child | 脚本最初由模型生成，不代表每一步由主模型在线调度；运行图不等于完整静态定义 |
| AgwaB/pi-workflow | 定义、编译 / 展开、运行分层；数据与纯顺序依赖；显式轮次 | 普通声明流程与 dynamic controller 不是同一控制模式 |
| osolmaz/pi-workflows | 代码声明合法路线，模型在合法集合中决策，执行器推进 | 固定 Definition 不等于固定每次执行路径 |
| pi-flows | agent / code / user 等决策方式显式区分 | 不能由事件可重建视图推断执行可恢复 |
| pi-tasks / pi-review-loop | 轻量依赖协调、最小反馈循环 | 不应自动视为完整通用图引擎 |

这组案例主要用于澄清控制权，而非要求复制某个框架的 schema。

### 12.3 实际运行过什么

实际通过 bun 导入现有纯逻辑模块进行了无外部副作用的 smoke：

- 后续回合已有票据时，planTurn 返回 phase2，judge 调用次数为 0。

- 自动干预最多 15 次，再次申请被拒绝。
