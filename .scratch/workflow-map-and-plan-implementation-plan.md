# Workflow Map 与 Plan：两阶段实现计划

整理日期：2026-10-26。

## 1. 文档定位与优先级

本文整理本次教学讨论中确认的开发方向、两个阶段的产物及验收标准，供 herdr-bot 后续实现使用。本轮只生成交接文档，不实施系统。

- 第一阶段是当前实施范围：人工编写 map，程序读取、校验并可视化，供人检查工作结构。
- 第二阶段是在第一阶段底座上实现 Plan：LLM 渐进式生成和修改同一份定义。
- 本文中的 JSON 是候选格式，用于说明语义，不表示字段命名、执行器登记方式或完整 schema 已定稿。
- 既有 `llm-driven-workflow-definition-design.md` 保留前次讨论的总体共识；涉及本次迭代范围与顺序时，以本文为准。前次教学课件中更大的执行与审批闭环，不是第一阶段的验收要求。
- 不替换既有执行系统，不在本次实现计划中重新设计 session/subagent 的宿主接入 Interface。

## 2. 核心拆分原则

> 每个阶段都是下一阶段直接复用的底座，而不是一次性演示，也不是必须等最后拼装才能验收的孤立零件。

每个阶段都应回答：

1. 结束后，人能实际使用和验收什么？
2. 下一阶段直接复用哪些成果？
3. 下一阶段新增什么，而不是重做什么？

当前选择：

```text
第一阶段：人工 map → 读取与校验 → 可视化 → 人核对
                         ↑
第二阶段：业务描述 → LLM 渐进式规划与修改 → 同一份 map
```

第一阶段不是完整 scheduler，也不是一次性画图 Demo；它是未来 scheduler 的定义载体、加载校验与可视化切片。真实节点执行和运行调度留给后续另行规划。

## 3. 长期目标与当前边界

### 3.1 长期目标

工作流不仅承载程序任务，也能承载人和 agent 的计划讨论、分析与决策过程。节点可以由 session、subagent、固定程序或它们的组合承接。

希望复用的是得到结论的方法，而不只是上次的答案。抽象 skill 提供分析原则，LLM 结合具体问题自主生成分析内容和工作结构。其价值可以是减少人组织讨论、维护上下文、记录结论和推进工作的心智负担，不以完全自动化为前提。

用户对未来模型能力的期待，不作为已经验证的产品效果。

### 3.2 本次不解决运行中改图

当前讨论限定于生成一张地图，之后按已确定地图执行；不引入执行过程中自动增删节点、重绘依赖或定义热更新。

Plan 阶段的草稿修改，与运行中的地图变更是两件事。第二阶段允许在最终确认前修订草稿，不因此要求实现动态执行图。

### 3.3 不限制 LLM 思考的基本分工

- 人提供目标、背景、不可突破的约束，并参与需要人的判断。
- LLM 负责理解业务，自主设计节点、依赖与必要推进约束，不从固定业务节点菜单中机械拼装。
- 程序负责结构校验，以及未来执行时的事实记录、权限与动作准入；不预先穷举业务推理路径。

第一阶段仅实现上述分工中的定义与展示部分，不实现未来运行时门禁。

## 4. Map 的最小表达范围

### 4.1 数据语义

Map 使用 JSON 表达一张工作依赖图。每个节点至少能描述以下概念：

| 概念 | 要表达什么 |
|---|---|
| 稳定身份 | 节点引用使用的 ID，可使用 nodes map 的 key，不重复维护第二份身份 |
| 标题与任务 | 让人知道节点要解决什么问题；任务可以给出目标与原则，不必穷举分析步骤 |
| 依赖 | 哪些前置工作或交付满足后，才允许本节点开始 |
| 输入 | 节点实际使用的材料或前置交付；不等于复制前置节点整段聊天 |
| 输出 | 本节点应形成的交付及可读说明，不限于代码或文件 |
| 执行方式引用 | 指向 session、subagent、固定程序或组合执行定义的描述性引用 |
| 完成约定 | 必需交付、是否需要人工确认等声明性要求 |

第一阶段应能表达、读取和展示这些内容；不要求创建实际会话、调用程序、收集交付或实施批准。

### 4.2 候选 JSON 示例

下例用于建立共同理解。开发时可按仓库现有约定收束字段，但必须保留上述语义，不借机扩大执行范围。

```json
{
  "nodes": {
    "requirements": {
      "title": "整理需求",
      "task": "与用户澄清目标和范围，形成需求说明",
      "blockedBy": [],
      "inputs": {},
      "outputs": {
        "document": {
          "format": "markdown",
          "description": "目标、范围、验收标准和待确认问题"
        }
      },
      "executor": {
        "ref": "requirements-session"
      },
      "completion": {
        "requires": ["document"],
        "approval": "human"
      }
    },
    "plan": {
      "title": "制定实施计划",
      "task": "根据需求比较验证路径，提出小而可验收的迭代计划，不修改业务代码",
      "blockedBy": ["requirements"],
      "inputs": {
        "requirements": {
          "from": "requirements",
          "output": "document"
        }
      },
      "outputs": {
        "document": {
          "format": "markdown",
          "description": "迭代目标、非目标、产物、验收方式及阶段间的复用关系"
        }
      },
      "executor": {
        "ref": "planning-session"
      },
      "completion": {
        "requires": ["document"],
        "approval": "human"
      }
    }
  }
}
```

示例中的 executor 引用名不是当前已存在执行器的声明。第一阶段不解析为真实执行资源。

### 4.3 依赖与流转的语义约定

- `B.blockedBy: ["A"]` 显示为 `A → B`，箭头表示 A 是 B 的前置，不表示“信息自动复制”或“无条件立即启动 B”。
- 连线从定义中的依赖推导，不另维护一份手写 edges。
- 输入引用与依赖是不同概念；同一项工作的“需要材料”和“必须等待”不能互相含糊替代。若开发时增加自动推导依赖，须明确唯一规则，不能让图和未来调度各自解释。
- 依赖当前采用无环图。此处的环是非法的前置依赖，不作为业务循环执行。
- 交付可供下游使用，与节点全部收尾结束，在语义上不应永久混为一谈。
- 先前讨论过用 `released` / `completed` 区分等待事实，这是后续表达依赖细节的候选方案，不强制第一阶段实现完整端口、里程碑或运行状态系统。
- 第一阶段展示完成约定即可，不把“human”解释为已经实现审批机制，也不凭一个展示标签承诺运行时行为。

### 4.4 定义与运行事实分开

可复用 map 不写入具体运行中的 `sessionId`、当前状态、尝试结果和审批记录。执行方式引用是定义内容，实际 session 与 attempt 的关联属于未来运行数据。

JSON 是本轮的交换与保存格式，不意味着必须放弃此前代码构造 Definition、保留元数据的方向。未来代码构造和 LLM 生成都应有机会收束到同一份可检查的定义描述；本轮不实现 builder 或代码生成。

## 5. 第一阶段：人工 Map 的加载、校验与可视化

### 5.1 目标

证明一份人工编写的 map 能准确表达并展示工作流，允许人发现和修正结构问题，为第二阶段提供可复用底座。

### 5.2 交付产物

1. **最小格式约定**：明确字段、依赖方向、引用和允许的声明内容；采用仓库现有文档方式说明。
2. **Map 读取与结构校验能力**：将 JSON 处理为展示所用的统一定义，不维护第二份人工图数据。
3. **可视化入口**：加载或选择 map，显示节点和依赖，支持重新加载修改后的文件。
4. **节点详情**：展示任务、输入输出、执行方式引用和完成约定。
5. **错误呈现**：让人知道文件为什么不能被作为有效定义展示，不能静默丢节点、丢边。

界面优先只读预览；不要求拖拽编辑、图形化连线编辑器或独立审批按钮。人发现错误后修改文件并重新加载，已构成这一阶段的反馈闭环。

具体使用既有页面、路由或其他宿主入口，按 herdr-bot 当前约定选择；本文不指定未经检查的技术栈或新增前端框架。

### 5.3 验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 加载一个小型有效 map | 全部节点显示，标题与 ID 可辨认，节点详情与文件一致 |
| 多前置与独立节点 | 多条前置边正确显示，无依赖节点不被错误连接 |
| 检查方向 | `B` 依赖 `A` 时显示 `A → B` |
| 查看丰富节点内容 | 不同工作内容、执行方式引用和完成约定都可查看；不局限于固定业务模板 |
| 修改依赖并重新加载 | 图同步改变，不残留旧连线或旧详情 |
| JSON 无法解析 | 明确提示加载失败，不伪装成有效空图 |
| 未知依赖、未知交付引用、自依赖或依赖环 | 对应结构错误被指出，不能作为通过校验的定义呈现 |
| 有效图之后加载错误文件 | 明确区分当前错误与上一份有效图；不能让用户误以为旧图是新文件加载成功的结果 |

人工验收的问题是：“这张图和节点详情，是否准确表达了我写下的工作约定？”不是“这些节点是否能实际完成工作”。

### 5.4 明确不做

- LLM 生成或修改 map。
- 自动推导业务节点和依赖。
- 启动 session、subagent、程序或组合流程。
- 运行状态流转、真实 Dispatch / Collect / Finish。
- 实际产物提交、人工审批、版本失效传播、重试、取消后迟到提交处理。
- 并发调度、恢复、定义热更新和运行中改图。
- 任意业务分支表达式或复杂 DSL。

不得因考虑未来适配而把这些能力变成第一阶段完成的前置条件。

## 6. 第二阶段：LLM 渐进式 Plan

### 6.1 目标

让 LLM 根据业务描述自主形成工作结构，分阶段完善同一份 map；人利用第一阶段的界面检查与纠正，最终保存完整定义。

这里的 Plan 是广义的设计时规划。现有 hyper-auto-coding 的 `plan` 更窄：已有票据后登记依赖，不能直接等同于完整业务规划。

### 6.2 三步生成

| 步骤 | 本步作出的决定 | 人或系统重点检查 |
|---|---|---|
| ① 节点 | 需要哪些工作，各自目标与交付是什么 | 遗漏、冗余、职责不清；不能只有标题没有交付说明 |
| ② 依赖 | 哪些节点必须等哪些节点，理由是什么 | 是否存在真实前置，而不是照抄习惯顺序 |
| ③ 推进约束 | 哪些交付需确认、依赖等待什么事实等必要约束 | 规则能否明确表达；是否把业务推理错误地写死 |

三步不是三份独立权威数据，而是同一份定义的逐步完善。允许后一步发现问题后回到前一步修订；最终地图确认前的修改，不是运行中动态改图。

步骤不必各自增加强制审批按钮。人可以按需介入；最终确认与保存方式在本阶段实现时收束。

### 6.3 自主性的要求

- 输入应提供目标、背景、限制和必要判断原则，而不是预设所有节点名称、数量和顺序。
- 三步固定的是设计方法，不是流程答案。
- LLM 可根据问题识别需要澄清、调查、实验、比较或讨论的工作；不强制每次套“需求—设计—审查”模板。
- 第三步优先选择明确的推进规则，而非为每条边生成任意代码或长篇条件 prompt。
- JSON schema 约束表达方式，不借结构校验之名限定业务思考路径。
- 高级思考质量属于第二阶段 Plan 的行为验证，不追加为第一阶段可视化交付要求。

### 6.4 交付产物

1. 从业务描述启动 Plan 的入口。
2. 三步骤渐进式生成、草稿状态维护及按需修订能力。
3. 第一阶段校验与可视化的接入，不另造第二套定义或图模型。
4. 完整定义的确认、保存与重载能力；已保存关系复用时不重新推导。
5. 对尚未完成、存在结构错误或业务待确认问题的清晰呈现。

### 6.5 草稿与完整定义

- 字段尚未填写，不等于显式为空。例如未设计依赖与确认 `blockedBy: []` 必须能够区分。
- 中间草稿允许不完整；不能把第一步输出误当成可执行定义。
- 第一阶段的完整定义校验仍需复用；第二阶段可增加针对草稿的分步检查，不靠放松完整定义要求让一切“通过”。
- 最终完整格式必须兼容第一阶段建立的载体；需要调整时做有意识的小步迭代，不静默替换整个模型。

### 6.6 验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 一条真实业务诉求 | 逐步形成节点、依赖和必要推进约束，最终图与定义一致 |
| 中间发现遗漏或错误依赖 | 人能指出问题，LLM 修订相应内容，不无故重写已确认部分 |
| 后一步暴露前一步问题 | 可回到对应步骤修正，引用与图保持一致 |
| 草稿不完整 | 界面不把尚未决定的字段误呈现为已确定结论 |
| 最终保存后重载 | 同一份完整定义可以由第一阶段能力读取和展示，不依赖重新推理图结构 |
| 不同目标和不确定性 | 检查节点是否体现任务差异，而非只替换固定模板的标题；合理相似结构不因相似而被机械判错 |

第二阶段仍不包含真实节点执行，也不以几次生成成功证明所有领域规划可靠。

## 7. 后续调度协议的位置：只作背景，不列入本轮任务

上一课参考的核心动作是：

```text
Plan → Dispatch ⇄ Collect → Finish
          Status 查询当前事实
```

- Plan：形成或加载工作约定。
- Dispatch：请求启动允许执行的工作。
- Collect：收集结果、更新事实并继续判断。
- Finish：满足整体结束约束后收尾。

它们不是只能各经过一次的线性阶段。当前两阶段实现计划只覆盖定义载体和设计时 Plan，不承诺实现其余动作。

现有 hyper-auto-coding 可作为策略与硬门禁结合的参考：模型登记依赖并选择派发，程序检查图、依赖、并发和暂停；下游准入检查首次合并事实，不单凭模型声称完成。后续泛化不应把 Git 集成事实硬编码为所有领域的完成语义。

## 8. 尚未定稿，但不应阻塞第一阶段的问题

- 候选字段的最终命名，以及是否增加格式版本号。
- 执行方式引用登记与解析的具体实现。
- released / completed 等依赖等待事实的最终表达。
- 输出格式声明的精度、未来的结构化输出校验方式。
- 第二阶段交互入口、草稿保存方式与提示设计。
- 后续运行协议、收尾、恢复与执行过程中的版本语义。

第一阶段只需对实际采用的格式作出明确、一致的约定，正确读取、校验与展示；不必一次解决所有后续问题，也不宣称格式永远无需调整。
