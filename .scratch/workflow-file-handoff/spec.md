# Workflow 文件交接与 report 完成声明：曳光弹规格

Status: ready-for-agent
Labels: ready-for-agent
Type: spec
Date: 2026-11-01
Contract: [已批准契约 — Full automation](contract.md)

## Problem Statement

现有 Map 的 node.input 重复承担机械交接协议：读取运行记录、确定 Run/node/execution 身份、推导材料路径、筛选上游报告、排除旧执行，以及在报告正文中反复填写地址与身份。plan_workflow、创建 Task＋Bot、优化既有 Bot 的工作流都存在这类负担。

这些约定依赖模型逐次理解和遵守，既增加上下文，也使业务目标与框架协议混杂。下游为了找到一份输入，需要理解运行记录和报告格式；manager 为交接搬运信息、阅读详细成果，也承担了超出编排的内容验收责任。

系统已经持久化 Run 当前状态、执行关联、完成事实、报告与历史，workflow 界面也已展示节点状态。本次不需要第二套运行状态、资料索引或产物管理平台。用户要求一个事实只有一个来源，在现有机制上实现最原始的文件输入输出交接，将重复机械逻辑固化到代码。

## Solution

Map 在运行前声明 node 的命名输入来源：直接文件，或另一 node 的命名输出。派发时，框架把本次背景、业务 input 和解析后的输入文件路径注入节点初始化信息。node 不再自行解析运行日志、猜测身份或搜索最新文件。

node 自行通过业务工具、程序或其他方法完成工作。现有 report 工具扩展为同时提交简短报告、必填的 can_complete 和可选的 outputs。outputs 登记命名输出与实际文件地址；工具与后端自动确定真实执行归属。登记不生成、复制、发布、验证或验收文件。

manager 阅读报告正文，了解结论、阻塞、部分效果及需要干预的事项，但原则上不读取输出正文进行业务验收。manager 显式调用 complete；后端以当前 execution 最新报告的 can_complete 为完成门禁。门禁拒绝后，manager 沿用 collect 等待新的报告，而不是反复尝试完成。

背景和运行事实复用现有来源，输出登记保存在报告记录中，不新增结果注册表。Run 内中间产物沿用已确定的 manager zone 下按 Run ID 隔离的位置方向，但不增加每节点目录、预分配输出位置或临时发布协议。首条迁移链路是 plan_workflow 的 outline → generate_map。

## User Stories

1. As a Map 规划者, I want 在 Map 中声明节点输入文件, so that 不必在 node.input 中重复文件定位算法。
2. As a Map 规划者, I want 输入能够直接引用业务文件, so that 已有材料无需先登记成上游产物。
3. As a Map 规划者, I want 输入能够引用另一个 node 的命名输出, so that 运行前无需知道上游最终生成的文件地址。
4. As a Map 规划者, I want 文件输入关系与 blocked_by 的前置依赖含义分开, so that 不把依赖箭头误当成材料传递。
5. As a Map 规划者, I want 多个节点可以引用同一上游输出, so that 并行转换无需各自编写材料筛选协议。
6. As a Map 规划者, I want 汇总由一个业务 node 承担, so that 具体合并算法不会进入框架内核。
7. As a Map 规划者, I want 必要的业务验收由独立 node 承担, so that manager 不需要成为内容审查者。
8. As a 节点执行者, I want 初始化时获得本次背景和业务 input, so that 不必读取完整运行记录才能知道任务要求。
9. As a 节点执行者, I want 初始化时获得已解析的输入文件地址, so that 不必解析报告日志或寻找最新文件。
10. As a 节点执行者, I want 缺少上游登记时收到明确的未解析输入信息, so that 可以自行处理交接问题而不是使用猜测路径。
11. As a 节点执行者, I want 输入未登记也不被框架禁止派发, so that 交接问题仍可在节点侧调查和处理。
12. As a 节点执行者, I want 自由选择生成结果的业务程序, so that 框架不会把结果生成限定成聊天或文件写入工具。
13. As a 节点执行者, I want 用现有 report 一次登记结果并报告情况, so that 不需要额外的产物登记工具或重复调用。
14. As a 节点执行者, I want 只提供输出名和文件地址而不手填运行身份, so that 身份绑定不依赖提示词或模型推断。
15. As a 节点执行者, I want outputs 可以省略, so that 无文件成果的任务和纯情况报告也能使用同一工具。
16. As a 节点执行者, I want 同一执行的输出按名称逐项更新, so that 补充一个输出不会清除此前登记的其他输出。
17. As a 节点执行者, I want 通过必填 can_complete 明确表达可交接性, so that manager 不必从正文措辞猜测完成意图。
18. As a 节点执行者, I want 报告正文只携带必要编排情报, so that 详细成果不用重复进入 manager 上下文。
19. As a 节点执行者, I want 能明确报告阻塞、失败和部分生效, so that manager 不把不完整结果误认为可推进。
20. As a manager, I want 阅读报告摘要与完成声明而不默认阅读输出正文, so that 上下文集中于编排。
21. As a manager, I want can_complete 为 true 时仍由我显式决定 complete, so that 报告不会自动推进流程。
22. As a manager, I want 后端拒绝在最新声明不是 true 时完成当前执行, so that 编排错误不会绕过节点自己的交接判断。
23. As a manager, I want 完成拒绝返回明确原因及相关报告信息, so that 可以回到等待而不是不断重试。
24. As a manager, I want 复用 collect 的通知等待机制, so that 不需要新的等待状态、去重存储或轮询协议。
25. As a manager, I want 旧 execution 的可完成声明不放行新 execution, so that 重试不会误用历史交接事实。
26. As a manager, I want 最新 false 声明覆盖此前 true 对完成资格的影响, so that 节点撤回可交接判断后不会继续放行。
27. As a workflow 使用者, I want 已 completed 的节点保留既有幂等语义, so that 后续补充报告不会自动撤销已发生的完成。
28. As a workflow 使用者, I want 继续使用现有 Run 状态和 workflow 展示, so that 不出现两份可能矛盾的最新状态。
29. As a workflow 使用者, I want 中间产物按 manager zone 和 Run ID 区分, so that 不同 Run 的材料位置有明确归属。
30. As a 维护者, I want 输出登记只有报告记录这一个权威来源, so that 不必同步报告、注册表和状态副本。
31. As a 维护者, I want 工具注册复用 my-agent-toolkit 的角色工具和身份传递机制, so that 不建立另一套会话关联。
32. As a 维护者, I want 公共角色指引统一解释报告与编排职责, so that 不再把这些协议复制进每个 node.input。
33. As a plan_workflow 使用者, I want 删除两节点中的日志解析和交接身份提示词后仍可完成大纲到 Map 的交接, so that 曳光弹能证明实际减少了重复工作。
34. As a plan_workflow 使用者, I want 保留人工确认、真实业务格式和能力边界, so that 协议简化不会改变业务目标或伪造确认。
35. As a 维护者, I want 未声明文件输入输出的现有流程不被强迫生成文件成果, so that 这次改造不把所有工作都变成文件生产。

## Implementation Decisions

### 1. 保留模型与单一事实来源

- 沿用 Map、node、Run、execution、Task、Chat 的现有领域模型。node 是工作定义，当前由 Chat 执行；未来脚本执行是扩展方向，不在本次实现。
- Map 保存静态业务定义、前置依赖和输入来源。Run 保存本次要求、运行状态与执行关联。运行期间不修改 node 定义。
- 最新状态继续以现有 Run 当前事实为准，不新增索引、第二套状态或持久化上下文摘要。manager 可以整体读取当前运行信息。
- 本次背景复用 Run 的 userInput，不建立另一份可独立修改的背景文件。
- 输出登记随报告保存。当前输出映射从报告事实解析，不另存权威注册表。历史记录与当前状态各自保留既有职责。
- 遵守节点执行角色来自实际执行上下文的既有决策，不根据 Task 用途猜测角色。遵守统一文件持久化决策，业务状态与引用规则仍由 workflow 业务拥有，不增加数据库或持久化抽象平台。

### 2. 输入声明与初始化

- 节点输入是命名输入，来源只支持直接文件路径，以及来源 node ID 加输出名。具体字段布局在后续契约阶段确定。
- 上游来源解析使用该 node 当前 execution 的登记结果，不跨执行回退，不搜索目录时间或从正文猜地址。
- 输入材料关系不改变 blocked_by 的前置依赖含义，不隐式引入自动派发。
- 派发初始化注入本次背景、原业务 input、解析后的输入文件地址；不注入上游完整聊天或文件正文，不新增节点上下文查询工具。
- 未登记的输入明确标为未解析，不伪造文件地址，不阻止创建节点 Chat。交接问题由 node 自行处理和汇报。
- manager zone 是本 Run 中间资料的位置基础，按 Run ID 隔离。该方向不要求建立状态索引、背景副本、每个 node 的独立目录、输出预分配或强制搬运已有文件。

### 3. report 同时承担报告与结果登记

- 扩展现有 report，不增加独立登记工具。保留报告正文参数 body，新增必填 boolean can_complete 和可选 outputs。
- outputs 表达逻辑输出名到实际文件地址的映射。文件由业务过程自行生成；框架登记不负责生成、复制、移动、临时替换或发布。
- 同一 execution 的 outputs 按名称逐项更新；省略 outputs 或未提供某个名字不清除已有登记。本次不增加撤销输出的专门协议。
- 不增加输出存在、可读性、格式、数量或完整性检查。无输出的工作可以声明 can_complete 为 true。基本参数类型检查和已有调用者归属检查继续保留。
- can_complete 是 node 的交接声明，不是内容质量证明、人工批准凭证或节点状态。
- 工具自动携带真实 Session 身份，后端确定 Run、Map、node 和 execution；模型不填写这些身份参数。复用现有旧执行报告归属规则，旧报告不能伪装为当前执行报告。
- 沿用报告先保存后通知的行为与部分失败反馈。不因为新增登记而增加通知重试、自动回滚或额外存储系统。
- body 用于结论、阻塞、部分效果、限制和必要干预；不要求重复完整文件内容、输出地址或框架已知身份。

### 4. complete 完成门禁

- manager 显式调用 complete 时，后端检查该 node 当前 execution 的最新一条 report。只有 can_complete 严格为 true，才通过新增的完成前置条件；仍需通过原有身份和状态规则。
- 当前执行没有报告、最新报告缺少字段或值为 false，均拒绝首次完成。旧执行的 true 不可代用。
- 最新 false 阻止完成，即使更早有 true；不回退旧成功报告。此规则与 outputs 逐项累积是两种不同语义。
- 拒绝不改变节点状态，返回明确原因及相关最新报告信息。manager 阅读报告判断，调用失败后回到等待。
- 最新报告检查与完成状态转换需在现有运行操作协调机制下保持一致，不能只在 toolkit 做一次有竞争窗口的预检。具体协调实现由后续契约与实施确定，不新增本 spec 的验证 seam。
- 已 completed 节点重复 complete 保留既有幂等行为；后续补充报告不自动撤销完成。
- 不新增人工绕过门禁或强制 complete 入口。此前允许在无可完成报告时人工完成的路径需要按这一新规则调整。
- 完成表示流程交接，不等于 Chat 退出；auto_close 保留既有独立语义。

### 5. manager 与 node 的公共职责

- node 自行判断是否可交接；缺材料、业务失败和必要限制须在报告中说清楚，不能把输出存在当完成证明。
- manager 阅读报告正文并判断编排动作，不默认读取输出内容做语义验收。true 是允许 complete，不强迫 manager complete。
- 需要业务验收时，规划者安排专门 node。合并和验收逻辑不成为框架内置能力。
- manager 被完成门禁拒绝后复用 collect。现有 generation / checked 判断新通知；pendingReports 仅是返回的待办信息，不因同一报告仍在待办就反复唤醒。无新通知且仍有 running 节点时，下一次 collect 等待。
- 不增加等待状态、collect 游标或新的通知协议。公共角色指引解释职责，不在每个 node.input 重复。

### 6. 已确定的实施归属与迁移范围

- my-agent-toolkit 中现有 node-chat 工具注册、参数处理与公共请求机制承接 report 扩展；manager-chat 与 node-chat 公共指引同步职责。
- herdr-bot 的 Map 定义处理、节点启动输入、报告持久化及完成动作承接对应行为。不要求 toolkit 直接改运行记录，不另建身份映射。
- 上述归属是会话中已确定的事实；本 spec 不额外选择模块拆分或验证 seam。
- 第一条真实迁移链路为 plan_workflow 的 outline → generate_map。减少输入中的身份推导、报告筛选和地址交接协议，保持业务目标、权限、人工确认以及真实大纲格式。既有大纲要求引用 Task 的九章节约定，不照搬早期草案的示例四标题。
- 其他 Map 本次不批量迁移，但工具的新报告调用必须明确给出 can_complete。历史报告缺字段保持可读，不据此放行新的完成。
- 现行 workflow 契约中 node 不自动获得 userInput、report 仅正文、manager 内容验收及无报告人工完成等相关规则需窄范围更新。不能借此次变更扩大到旧 Run 接管或配置版本管理。

## Testing Decisions

- 现有代码已包含 Run 启动、节点派发、报告、完成、重试与 collect 的检查基础，并有真实宿主与材料汇合的验收先例。后续优先复用既有测试和隔离设施；本节不决定 seam、覆盖映射或测试数量。
- 会话确定的实际目标是：plan_workflow 删除机械交接提示词后，outline 与 generate_map 仍可完成真实输入输出交接。单独字段存在、编译通过或提示词变短不能代替行为证据。
- 完成门禁需考虑当前执行与旧执行、无报告、缺字段、最新 true/false、补充报告和已完成幂等；输出登记需考虑省略和逐项更新。具体承诺与验证位置由 /to-contract 审批。
- 保留 collect 的 generation / checked 行为，不以 pendingReports 非空编造重复唤醒问题，不为这一不存在的问题新增测试或机制。
- 运行验证遵守仓库测试指引：使用独占临时目录、动态数值回环端口、隔离存储和所属进程；不连接或修改用户正在使用的 Chat、Run 或文件。
- 真实宿主验证不能被替身结果冒充；安全替身与真实依赖的使用遵循现有规则。真实关机、LAN/mDNS 与符号链接等显式授权约束保持不变。
- toolkit 部分沿用该仓库既有工具、身份与请求取消的验证规范；本次 spec 未声称跨仓实现或验证已经完成。
- 本次交付仅发布规格，不运行产品测试，也不将设计确认表述为实现验收通过。

## Out of Scope

- 自动完成、自动派发、自动选路、自动重试、自动修复或重启接管。
- 框架生成业务结果、文本合并、格式转换、业务质量验收或通用人工审批。
- 输出文件存在、可读性、格式、数量、完整性校验，以及缺少输入登记时的派发门禁。
- 文件快照、哈希、不可变版本、产物版本库、整组验收和回滚。
- 同路径并发写入、覆盖前后版本一致性、上下游文件冲突的自动检查；可作为未来 Map 检查增强。
- 框架临时输出后替换原文件、发布到外部目标、覆盖授权和发布冲突检测。当前只登记文件，不实施这些文件操作。
- 第二套 Run 状态、状态索引、背景副本、持久化上下文清单或独立产物注册表。
- 输入模板语言、自动目录搜索、运行中修改 node，以及运行前规则变换机制。
- 脚本执行器及非 Chat 宿主接入；仅保持文件交接不依赖聊天正文作为未来可复用方向。
- 新增 collect 等待协议、通知重试、可靠消息队列或 exactly-once 保证。
- 新增数据库、存储适配平台、跨文件事务、强认证或操作系统文件沙箱。
- 所有现有 Map 的批量迁移或与首条链路无关的界面改造。

## Further Notes

- 本规格以本轮最终确认的最小方案为准。早期交付物草案提出的提交验收、固定版本、发布、快照等方案不自动进入本次范围。
- 接受的风险：node 可以错误声明 can_complete、登记不存在的文件或遗漏必要输出；框架不做业务兜底，后续 node 可以遇到交接问题并报告。并发节点对同一路径操作也不由本版检测。
- 完成门禁只保证“当前执行最新报告声明可完成”，不证明成果正确、用户已批准或文件内容稳定。
- 直接文件与上游命名输出的具体 schema、路径表示、返回错误形式及物理目录名称在 /to-contract 中按现有约定确定，不另造产品能力。
- 本 spec 的 ready-for-agent 标签按 to-spec 发布要求设置，表示无需另做 triage；不表示后续契约、实施或真实运行已经获验收。
- 下一步：对本规格执行 /to-contract，选择尽可能少且复用既有的 seams，并批准其承诺与覆盖；本规格没有预先替代该步骤。
