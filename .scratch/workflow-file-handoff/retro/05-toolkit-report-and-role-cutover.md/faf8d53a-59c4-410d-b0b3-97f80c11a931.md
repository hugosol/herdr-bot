## 1. 高：把公开 wire 契约放到跨仓 tracer bullet 的入口

### 事实

- 模型参数要求使用 `can_complete`。实现最初把同名字段直接发送到 HTTP，受控 HTTP 测试也按这个预期断言。
- 第一轮完整 workflow-chat 分区得到 **24 pass / 0 fail**，其中尚不能证明新字段被真实后端接受。
- 随后的配套 dock 明确返回：`unknown field can_complete, expected one of sessionId, body, canComplete, outputs`，多个调用因此失败。
- 读取配套后端 `docs/workflow-runtime.md` 后，找到了已经明确写出的规则：toolkit 将模型 `can_complete` 映射为 HTTP `canComplete`，报告记录也使用 `canComplete`。
- 之后先修改独立预期并运行红测试，观察到实际 snake_case 与预期 camelCase 的差异，再修改实现并得到绿测试；最终真实 dock 全部通过。

### 判断

这是一次**公开协议事实查阅过晚**，不是需要新增编码风格规则的判断题。最初的受控 HTTP 测试把实现假设和预期绑在了一起，形成了“测试通过但配套服务拒绝”的空隙。后续真实联调和红绿循环有效修复了这个空隙。

### 建议

在现有跨仓测试指引中加入一个按条件触发的入口，而不是给全局 `AGENTS.md` 增加常驻细则：

> **跨仓 wire 变更**：先读取配套服务的公开请求与响应契约，写明模型参数、HTTP 字段和持久记录字段的映射；第一条 tracer bullet 须经真实配套路由成功，再扩展受控响应矩阵。

完成标准应是：**真实角色工具发送请求，配套服务接受，返回或公开记录包含独立预期的字段和值。** schema 存在、HTTP echo 和类型检查只作为补充证据。

不建议另建一份字段清单长期维护；后端公开协议已经是事实来源，工具测试应指向它。

## 2. 高：给配套 worktree 增加明确的占用与释放边界

### 事实

- 实现代理多次协调配套后端路径、版本与 dock 窗口。
- 获得 `hyper-ticket-yMjvdc` 的只读构建许可后启动了独立 target 构建；构建过程中该 worktree 被清理，Cargo 报告无法读取 `safe_shutdown_shell.rs` 和 `herdr-fixture.rs`。
- 后续协调改用 `hyper-ticket-xyfvcs`，由其 owner 合并并冻结包含 01、02、04 的源码，给出准确 HEAD `63d7007d923d7cee102ee0620a7ef53a57f05bb1`。
- 在稳定源码上构建成功，验收结束后实现代理向 owner 明确释放路径。

### 判断

“源码冻结”与“worktree 生命周期受保护”是两个不同条件。此次前者的口头确认没有阻止后者被清理。独立 `CARGO_TARGET_DIR` 隔离了构建产物，但不能保护编译所需的源文件。

### 建议

由现有工作流调度层提供一个**配套资源占用**事实：仓库路径、固定 HEAD、使用者及释放状态。只要仍有依赖消费者占用，清理动作就应延后；消费者在完成或失败退出时释放。

这应优先是调度工具可检查的生命周期约束，而不是要求每个实现代理记住“再次确认目录还在”。验收标准是：消费者完成编译和约定检查前，调度层不会删除其配套源码。

同时区分两类协调：

- **产品依赖**决定票据是否可执行；
- **验证资源组合**决定某次检查需要哪些已集成行为。

本票确实需要更新 node `userInput` 的既有回归，但不应因此把执行资源协调误写成新的票据产品门禁。

## 3. 中：让原生宿主参数矩阵固定覆盖“显式值变成省略”的路径

### 事实

- 新增的实际 OMP 工具测试覆盖了 `outputs: null`。
- 该用例发现宿主会在业务校验前删去可选 null，使请求按“省略 outputs”执行。
- 仅放宽开放映射的 schema，并未解决这个问题；对话中两次运行仍观察到 null 用例未被拒绝。
- 查阅宿主验证逻辑后，确认存在 optional-null normalization；最终使用等价的 singleton object type union 避开该修复，再由共享业务逻辑严格拒绝错误值。
- 最终原生测试还覆盖了缺声明、字符串布尔值、null、数字、错误 body/outputs 类型和额外身份字段；Pi 原生检查也通过。

### 判断

这是本次 TDD 做得好的部分：测试保留了**真实宿主 → adapter → 业务校验 → HTTP** 路径，因而发现了共享逻辑单测和 schema 检查都容易漏掉的错误。

风险在于：该修复依赖宿主的具体 normalization 行为。如果未来仅保留业务逻辑测试，宿主升级可能重新引入静默修复。

### 建议

把下列条件作为现有原生工具兼容性检查的稳定测试类别，而不是新增审查口号：

- **省略**：可选字段未提供时可执行；
- **显式非法值**：null、空串、字符串 `"null"`、错误集合类型须被拒绝；
- **归属额外字段**：包括值为 null 的身份字段，整次调用不得被删字段后执行；
- **观察点**：非法调用没有实际 HTTP 请求，合法调用的值未经类型修复。

这些检查应接入宿主版本升级时已有的兼容性入口。本轮没有检查其在 CI 或升级流程中是否已被强制执行，因此这里只建议核实接线，不能认定仓库缺少该 guardrail。

## 4. 中：工具包装层应裁剪结构化返回，而不是把编辑快照全部展开

### 事实

- 一次批量 `eval` 编辑循环直接 `print(r)`，展开了 edit 返回中的 `oldText`、`newText` 等内部详情，输出达到 **3185 行**并溢出为 artifact。
- 其中两个针对 `toEqual(["body"])` 的替换没有生效，代理随后重新读取相应范围才发现并补改。
- 后续循环改用 `print(r.text)`，返回内容明显收敛。

### 判断

批量编辑本身不是问题；问题是成功、失败和大体量快照混在同一输出中，降低了错误的可见性。上下文载荷增加，也没有换来更清晰的编辑状态。

### 建议

在工具包装层提供紧凑的批量结果：每项只返回路径、成功/失败、简短 diff；完整旧新快照保存在 artifact，按需读取。

批量调用还应在任一编辑失败时显式汇总失败项，或停止依赖该编辑的后续操作。**失败是可见结果，不应藏在大对象中。** 这属于确定性工具改进，不需要给实现代理增加一条长期写作规则。

## 5. 中：区分测试进程等待与代理协调等待

### 事实

- `find` 的 28 个 judge 请求全部因区域限制返回 451；工具明确说明结果不是“没有文件”。代理随后转用 grep 和目录读取，继续完成定位。
- 后续一次 `wait` 返回“没有可等待的后台任务或欠回复代理”，但配套源码的协调通知随后仍正常到达。
- 在等待配套源码期间，代理运行了共享 adapter/framework 与 authoring 检查；这些检查实际得到 762 个通过结果，不能据此认定它们没有价值。

### 推断

当前运行时对“已回复，但承诺稍后发送资源就绪通知”的协调状态缺少可等待表示。它可能促使代理额外寻找工作或调用一个不能表示该等待的工具。仅凭本次记录，不能量化这带来的时间浪费，也不能把较大检查范围直接判为无效。

### 建议

- 对 `find` 这类已知区域不可用的能力，工具应在首次明确失败后暴露不可用状态，并直接给出可用的定位路径，避免每轮重复支付 judge 请求。
- 调度层为“等待配套源码冻结/等待资源释放”提供具名状态，使 `wait` 能等待该状态；不要求代理用轮询或无关检查填满等待。
- 保留代理在真正独立、相关的检查上继续工作的能力，但不要把“每次响应都要有工具调用”解释为需要制造额外工作。
