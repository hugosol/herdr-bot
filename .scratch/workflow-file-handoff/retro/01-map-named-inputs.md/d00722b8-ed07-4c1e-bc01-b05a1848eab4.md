本轮表现较好的部分应保留：测试从批准的 S1 HTTP interface 进入，保留真实文件保存和生产宿主调用包装层，仅在外部 Herdr 边界使用记录型进程；四个新增行为切片均观察到具体红灯后才实现。存储故障与无输入兼容行为已存在，直接验证，没有为满足形式要求制造失败。最终定向测试 105 项通过，完整后端及 doctest 通过，前端构建、6 项相关测试和文档链接检查也通过。真实 Chat 验证与上游输出解析明确留给其他票据，没有以受控宿主证据冒充实际模型执行。

## 1. 高：让交付验证入口完整表达依赖与推荐并发，降低迟到失败

**事实**

- 首次前端构建因缺少依赖而失败：`'tsc' 不是内部或外部命令`；执行 `npm --prefix frontend ci` 后构建成功。
- 首次运行 `workflow_dispatch` 未限制内部测试线程，93 项中有两项在既有 5 秒宿主夹具等待处失败。之后使用 `--test-threads 2` 的定向与完整回归均通过。
- 第一次完整后端检查在运行约 262 秒后，因 manager 初始化的旧字面预期未包含新增资料位置而失败；另有 8 个二进制未派发，doctest 未执行。
- 现有 `scripts/test-backend.mjs` 已提供 `--binary-jobs`、`--test-threads`、分目标日志和汇总文件；现有测试文档也说明了这些选项。这里不是缺少测试工具，而是现有入口没有一次性表达本票需要的准备与执行顺序。

**推断**

默认测试线程下的两个等待失败可能与负载有关；对话中的证据不足以证明根因，也不能据此扩大超时或修改产品逻辑。可以确认的是，受限并发下的测试路径更稳定，且此次已实际通过。

**建议**

优先复用现有 runner，在 ticket 验证说明中给出一个明确的、适合独立 worktree 的交付顺序：前端依赖准备与构建 → 受影响的 Map／Run 定向检查 → 完整后端入口。针对会启动大量外部进程的 workflow 目标，采用有明确来源的并发配置，而不是让每次执行代理自行试出参数。

如果增加包装入口，应组合现有命令和参数，不复制测试发现逻辑；完成条件是缺少依赖、前端类型错误或初始化预期不一致能在完整后端长检查之前显式失败。固定参数是否应成为全仓默认，需要独立测量，本次对话不能支持直接修改默认值。

## 2. 高：把“初始化变更”导航到正反角色的预期测试，而不只到生产入口

**事实**

- 实现较早定位到了 `backend/src/runs/startup.rs`，并新增了节点初始化的 HTTP 派发测试。
- 新增 manager 中间资料位置后，已有 `workflow_start.rs::manager_trigger_and_status_follow_committed_identity` 的完整输入字面预期没有同步更新，直到完整后端检查才暴露。
- 修正该预期后，包含 `workflow_dispatch` 与 `workflow_start` 的定向检查共 105 项通过。

**建议**

在已有 workflow 参考文档或测试入口说明中，加入一个窄导航指针：**变更 Chat 初始化或组合输入时，同时检查 manager 启动、node 派发和 retry 的公开行为预期。** 指针应直接指向现有测试位置，不复制初始化文本或重新建立字段清单。

这属于跨角色变更面的导航问题，不适合新增全局“记得更新测试”口号。若要自动化，应优先提供现有相关测试目标的快捷入口；不要用静态关键字检查替代真正的宿主初始化断言。

**未验证项**

零项大纲的原因未确定，可能是索引覆盖、项目选择或索引状态问题；不能把它视为源文件没有声明的证明。

**建议**

工具环境应对当前 worktree 提供明确的项目身份、覆盖状态和可用性信号。描述式搜索发生已知区域不可用错误后，允许在该执行内直接转向已有的精确搜索工具；图查询返回空时，先区分“确实无结果”和“当前路径未覆盖”。

这应尽量落在工具路由与错误反馈，而不是不断扩充仓库 `AGENTS.md`。目标是减少无效查询，同时保留图优先探索的价值，不以永久绕过索引作为修复。

## 4. 中：把实现期验证权限收敛成一个明确指针，减少流程冲突

**事实**

- 常驻协作指令多次要求实现代理完成变更后直接交接，不自行验证。
- 本 ticket 的专属指令与加载的 TDD 流程又明确要求红绿循环、定向测试和完整后端验收。
- 代理本次按专属任务执行了必要验证，未观察到因冲突而停工或漏验收。

**推断**

本次没有产生权限判断错误，但重复且方向相反的常驻指令增加了每次选择执行路径的负担，未来可能导致该运行测试时不运行，或不该运行时重复检查。

**建议**

在宿主的任务模式配置中明确区分“实现后由主代理验证”和“本票代理承担 TDD 验收”，由模式决定验证责任。常驻指令只保留责任路由；红绿循环、最终测试和报告要求由对应技能作为单一来源维护。

这项建议面向宿主环境，不需要把规则再抄入项目文档。完成标准是实施代理只需读取一个明确的责任声明，就能知道本轮应运行哪些检查、由谁承担最终验收。

## 5. 低：输出应保留证据定位，但减少重载长日志

**事实**

- 默认线程定向运行输出了大量业务快照、宿主参数及实际初始化内容，工具结果超过展示上限。
- 为定位两个失败，后续又搜索完整 artifact；搜索模式较宽，同时命中了大量含 `timeout` 的宿主调用参数，形成了额外长输出。
- 现有完整后端 runner 已输出分目标 stdout／stderr 和 `summary.json`，成功用于区分已通过、失败、未派发与 doctest 未执行。

**建议**

开发反馈默认保留完整原始日志，但优先返回失败测试名、断言位置和相关错误片段；只有审查初始化证据时再加载对应的完整输入。优先使用现有 runner 的分目标日志，不引入第二套日志协议。

失败检索应先用精确测试名、`panicked at` 或失败区段，而不是把 `timeout` 等正常调用参数也作为主要搜索词。该优化不应删掉原始请求、结果或宿主输入证据。

- **不建议宣称仓库缺少 CI 或 pre-commit。** 本轮没有检查这些配置；已有构建和测试脚本确实运行过，但是否存在自动接线仍未验证。
- **不建议把两次 5 秒等待失败当作产品缺陷修复。** 根因未证实；应保留失败记录与后续受限并发通过的事实。
- **不建议为本票新增真实 Chat 验收。** 该覆盖已明确归属 07；本票正确保留了受控宿主证据的边界。
