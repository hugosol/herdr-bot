# Ticket 08 执行复盘建议

## 复盘范围与证据边界

本复盘仅依据 `08-cross-repository-file-fan-in-acceptancemd-f9d` 本次执行对话及其工具返回，不延伸评判父 session 或其他实现代理。

本轮属于**交付恢复**，不是新的 TDD 实现：用户要求处理未跟踪的 `.scratch/workflow-file-handoff/evidence/`，保留既有实现及有效验收结果。代理读取了本票、两个 worktree 的项目指令、前次报告及验收 manifest；确认已有提交后，将证据目录原子迁移至本次真实运行所属的独占 Temp 根。最终两个 worktree 的 `git status --porcelain=v1 --untracked-files=all` 均退出 0、无输出。

本轮没有修改测试或产品代码，也没有运行 red→green、故障注入或验收套件。前次报告中的 TDD 与测试结果属于本轮读取的历史材料，不能表述成本轮重新观察到的测试执行。

## 1. 高优先级：让证据落盘与 worktree 交付形成一个可检查的闭环

**事实**：本轮启动原因是前次交付被工作流拒收：实现已经提交，但专属 evidence 目录仍未跟踪。项目测试指引又要求将运行日志和验收资料保存到 `.scratch/<feature>/evidence/`。现有做法满足了证据保存要求，却没有同时满足工作流的清洁交付要求。

**建议**：在工作流现有交付入口中增加确定性的证据交接步骤，而不是给实现代理增加一条泛化的“保持干净”规则：

1. 将本票拥有的运行证据归档至工作流管理的独立证据根；
2. 返回稳定的 manifest 地址及归档结果；
3. 在释放 worktree 前检查完整的 tracked、staged 和 untracked 状态；
4. 对本票证据执行明确归档，对其他遗留变更返回具体阻塞项。

**完成判据**：模拟“实现已提交、仅剩本票未跟踪 evidence”的交付，能够保留证据并通过清洁检查；存在其他变更时仍明确拒绝释放。

**未验证项**：本轮未读取工作流实现、提交钩子或 CI 配置，因此不能断言这些检查完全不存在。已观察到的缺口是：拒收发生在交付之后，证据归档没有在此前闭环。优先接入已有交付检查，不另建重复检查入口。

## 2. 中优先级：证据迁移时一并发布路径映射

**事实**：代理通过同卷目录重命名保留了完整证据，没有改写内容。但 `verification.json` 内的日志、依赖配置及 completion wire 绝对路径仍指向原 worktree。新旧前缀映射只写在本轮最终报告中。

**推断**：仅取得归档 manifest 的后续验收者，可能遇到失效路径；能否完整定位材料，取决于其是否同时获得本轮报告。

**建议**：由证据归档器在归档根发布独立的索引或 relocation manifest，记录原根、新根和文件清单。保留历史 manifest 原样，不回写历史命令。证据读取工具通过归档索引解析旧路径，而不是要求每个消费者手工替换前缀。

**完成判据**：只提供归档入口即可定位 manifest 所引用的全部已保留材料，无需查阅执行对话；无法定位的材料明确列出。

这是路径管理的机械问题，适合工具解决，不宜变成 reviewer 的人工核对规则。

## 3. 中优先级：把历史验收复用条件做成机器可核对的凭据

**事实**：本轮读取了两个 worktree 的 HEAD 和状态，确认其与前次报告、provenance 一致；读取的 manifest 也记录了源码文件哈希、隔离参数及各检查退出码。代理因此复用了历史验收，没有重新运行测试，符合用户“不要重复已完成且无需重跑的工作”的要求。

**证据边界**：本轮没有独立检查依赖安装树、真实依赖二进制或模型配置是否变化。最终报告以“源码、夹具、依赖或验收环境未变”解释复用条件，其中源码状态有直接工具证据；依赖与环境连续性主要来自既有记录和本轮未执行修改操作，证明力度不同。

**建议**：扩展现有 verification manifest，而不是新增一套状态文档：为每类检查记录其适用的源码状态、锁文件、相关构建产物和外部依赖身份。恢复执行时由交付工具比较这些凭据，并输出“可复用”“需要重跑”或“未能确认”。

报告措辞也应分层：

- 本轮直接核对了什么；
- 哪些结果来自前次日志；
- 哪些环境条件尚未独立核对。

**完成判据**：依赖或环境凭据缺失时，复用判断显示不确定性，而不是把相同 HEAD 自动提升为完整环境相同。本建议不要求本轮补跑验收。

## 4. 低优先级：为交付恢复提供紧凑的证据入口

**事实**：代理先读取了前次完整报告，再读取长期场景说明和 provenance。第一次读取 `verification.json` 返回折叠内容，之后才用字段查询取得所需信息；另一次业务证据查询返回了两轮完整的 read/toolResult 与原始字节，明显多于处理清洁交付阻塞所必需的内容。

**建议**：在现有 manifest 中提供可直接查询的恢复摘要：实现提交、参与 worktree、最终有效检查、真实业务证据入口、未解决项和归档位置。交付恢复先读该摘要，只有结果冲突或缺项时再展开原生轨迹。

导航指针可采用明确的分支触发语义：**“恢复已验收票据的交付时，先读取其 verification manifest；身份、结果或适用状态冲突时再展开原始日志。”** 将该指针放在工作流恢复入口附近，无需扩充两个仓库的全局 `AGENTS.md`。

**完成判据**：仅处理未跟踪证据阻塞时，能够凭紧凑摘要和 worktree 状态完成判断；验收细节仍可按需追溯。

## TDD 结论

本轮没有新的行为切片，因此不需要为了展示 red→green 而制造失败或重复添加测试。代理保留既有实现、没有重跑用户要求复用的验收，是本次恢复执行中应保留的做法。

对前次 TDD 的判断应保持有限：读取到的报告提到 CLI 缺依赖回归的 red→green，但本轮可见执行没有展示该循环的原始断言与命令过程，不能据此进一步评价其测试敏感性。此次最明确的改进点不是增加 TDD 步骤，而是将**证据归档、验收复用和清洁交付**接到现有工作流中，避免已完成的实现因交付资料管理再次启动恢复轮。
