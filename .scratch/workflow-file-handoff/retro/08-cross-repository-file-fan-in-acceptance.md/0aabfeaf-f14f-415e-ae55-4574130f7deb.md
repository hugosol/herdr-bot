## 1. 高：让真实模型传输的授权上下文按调用绑定，提前暴露失效

### 观察

- 首次运行的 completion 能实际返回模型决策。
- 下一次 eval 复用了上一调用捕获的 `contextvars` 上下文。传输记录出现明确错误：`No active Python tool bridge session`。
- 该错误已发生在模型传输层，但场景最终仍以约 300 秒的“manager 未完成”超时结束。
- 在实际运行所在 eval 中重新捕获上下文后，传输恢复；后续真实模型场景最终通过。

这证明了一项本次实际环境约束：**持久的 Python 变量不等于仍有效的宿主授权上下文。**它不证明产品角色逻辑有故障，也不证明所有宿主都具有相同生命周期。

### 建议

优先在现有公开 completion 传输入口及其运行说明中建立一个明确的“调用上下文”边界：

1. 将上下文捕获和 `CompletionTransport` 生命周期放在同一个可调用入口内，供每次宿主调用执行，避免依赖此前 eval 留下的闭包。
2. 对这一已观察到的传输错误保留原始异常，并使验收入口及时报告“真实模型传输不可用”；不要只等待业务完成超时。实现时须同时维持所属进程清理及原始错误保留。
3. 在既有传输回归中覆盖“completion 抛错时明确失败且不产生替代业务动作”。若宿主允许，再单独验证调用上下文过期；普通 HTTP 回归不能冒充宿主生命周期证据。

**完成判据：**上下文失效能被归类为传输失败，证据指向原始异常；无需等满业务观察窗口，也不会生成伪造工具决定。

不建议把这条约束加入全局 `AGENTS.md`：它只适用于使用公开 completion 薄传输的分支，应与现有传输示例共置。

## 2. 高：给跨仓临时 worktree 提供一个快速的依赖前置检查

### 观察

toolkit 的第一次完整运行得到 `1782 pass / 8 fail`，失败指向默认 sibling 路径下缺失的 `safe_shutdown_shell`。设置现有 `HERDR_BOT_BINARY` 后，第二次完整运行仍为 `1782 pass / 8 fail`，这次指向默认 sibling 路径下缺失的 `meta-data/task-options.toml`。

对话还显示一次不必要的源码修改计划：执行者先把问题判断为 helper 不支持跨仓根，向另一 owner 宣告将修改源码；继续读取后才发现已有覆盖项，并及时撤回了这一判断。最终没有修改 toolkit 源码。

3. 排查配置失败时，先读完整的路径解析函数及紧邻配置函数，再提出新增环境变量或源码修正。这里应使用局部导航，而不是新增全局禁止规则。

**完成判据：**缺失安全壳或元数据的临时 worktree 在启动完整套件前给出明确路径与现有覆盖方式；修复配置后仍执行规范完整入口，而不是把前置检查当作测试通过。

**边界：**本次会话已读取 toolkit 的 `package.json` 和测试指引；没有读取 CI 或 hook 配置。因此不能据此断言仓库“没有 CI/提交护栏”，也不建议臆造一套新的全量检查机制。

## 3. 中：真实业务 fixture 优先采用宿主已经证明可用的原生文件 seam

### 观察

最初的 source fixture 要求 Pi 原生 `bash` 执行 Windows Python 路径。两种实际尝试分别得到：

- 反斜杠路径：`command not found`；
- 正斜杠路径：`No such file or directory`。

source 如实报告 `canComplete=false`，manager 没有强行完成或派发下游；验收器则等待到业务超时。之后 fixture 改为真实 source Chat 原生 `read` 种子、`write` 新业务文件、实际 `report` 登记。两个消费者仍从登记的同一源地址读取，summary 仍读取两份独立结果。固定输入和独立预期字节没有改变，最终场景通过。

可确认的是这些可执行路径在本次原生 Bash 环境中不可用；**不能从现有结果进一步断言该 Bash 必然是 WSL、Git Bash 或某个特定实现。**

### 建议

- 此类以文件交接为目标的验收，默认使用已批准、实际可观察的原生文件工具完成 fixture；只有验收对象本身包含外部程序执行时，才把 shell 和可执行文件兼容性引入关键路径。
- 对必须使用外部程序的分支，先做一个不含业务答案的最小原生宿主执行探针，再开始完整 Run；探针失败应明确归类为依赖阻塞，不使用猜测性的路径格式修改代替环境确认。
- 保持本次成功做法：fixture 修改须说明为什么不改变验收含义，并保留此前失败。源文件的真实创建、两个消费者实际读取和独立预期校验都应继续留在场景中。

**完成判据：**文件交接验收不会被与目标无关的 shell 假设阻塞；若 shell 本身是必需依赖，则其可用性有独立原生证据。

执行者先加入了相当完整的新业务验收类，再运行真实场景；这不是逐个业务断言展开的 red→green。另一方面，本票主要补充对既有产品行为的真实验收覆盖，并没有观察到为制造 red 而故意破坏产品逻辑。这两点应同时保留，不能简单评价为“没有 red”或“所有条件都经历了 TDD”。

### 建议

在现有 TDD 执行记录中明确分为两层：

- **设施层：**CLI、依赖检查、证据输出和宿主连接是否可达；记录其 red→green。
- **行为层：**对既有产品行为补覆盖时，说明行为是否已经实现，并为每项承诺记录“违规实现会在哪里被观察到”。本次最有价值的区分是：即使最终文件碰巧正确，缺少指定地址的原生读取及成功结果仍会失败。

下一次新增复杂真实场景时，可先建立一条 source→consumer 的最小追踪链，证明原生读取与登记的观察机制确实成立，再增加第二消费者、summary 和第二 Run。每个阶段都保留同一最终验收含义，不以缩小验收来换通过。

**完成判据：**最终报告能区分设施测试、既有行为验证和新实现的 red→green；每项业务承诺都有具体观察面，而不是仅以“运行失败过”作为 TDD 证据。

没有证据表明本票必须新增产品内部单元测试；强行制造内部 seam 会削弱已批准的真实外部验收边界。
