# Ticket 07 TDD 执行复盘建议

## 范围与结论

本复盘仅依据当前 ticket 的执行对话及其工具结果，不使用父 session 或其他票据的执行历史补全事实。本轮未重新运行验收、修改源码或保存文档。

本次交付的可达部分包括隔离验收入口、OMP/Pi report contract dock、CLI 前置失败回归及两仓运行说明。后端完整检查、toolkit 类型检查、workflow 分区及新增原生宿主 dock 通过；真实模型 S2 因缺少授权配置而未执行，canonical toolkit 全仓检查仍有五例启动超时。因此，最终保留“未关闭”而非宣称完成，是正确的证据边界。

主要改进机会不是增加“更认真测试”的泛化指令，而是让环境更早暴露前置依赖、让 TDD 的行为红灯更明确，并缩短跨代理重型检查的协调路径。

## 1. 高：把真实验收依赖做成调度前可检查的能力清单

**事实**

- 票据要求真实 Herdr、原生角色及实际模型链路，明确排除受控 provider 作为通过证据。
- 执行初期发现机器根配置没有专用模型配置，环境也没有可直接使用的模型 API key；代理向 Main 请求明确授权的隔离配置。
- Main 随后确认本对话没有额外授权的模型配置或凭据，并禁止读取用户 Session、全局私有配置或使用 bridge token 替代。
- 新入口最终以 `Missing isolated actual-model configuration` 非零退出，未启动服务，`cleanupErrors=[]`。真实 S2 承诺没有被标为通过。

**影响**

这是决定能否关闭票据的前提，但直到实施和多轮检查期间才得到明确确认。该缺口不是增加测试重试或继续搜索用户目录可以解决的。

**建议**

在调度真实依赖票据前，提供一份验收能力清单：参与 worktree、宿主可执行文件、官方扩展来源、专用模型配置路径、凭据环境变量名称及授权范围。只检查路径、必要字段和凭据是否存在，不输出密钥，也不自动读取用户状态。

完成条件应是“每项必需能力均可用，或有明确的不可用项及其允许继续的交付范围”。能力清单不可用时，应在开始实现前明确：可以交付 runner 和技术组件覆盖，但票据保持未关闭。不要将这种情况记作业务验收失败或模型行为失败。

**未验证项**：本对话没有证明现有调度器已具备这类检查；建议复用已有调度能力，而不是先建立另一套配置来源。

## 2. 高：为跨仓检查提供统一的前置检查入口，保留现有检查命令

**事实**

- 已阅读的项目说明要求独立 `CARGO_TARGET_DIR`、正确定位参与源码，并使用仓库脚本入口执行全量检查。
- 第一次后端完整检查在缺少本 worktree 的 `backend/static/index.html` 时停止；补做前端安装和构建后，完整后端检查通过。
- toolkit 的 workflow helper 使用 `HERDR_BOT_REPO`，而 connect-bot/panel helper 另有既存的 `HERDR_BOT_BINARY` 和 `HERDR_BOT_METADATA` 参数。
- 首轮 serial dock 和全仓检查落到了不存在的默认同级后端路径。显式设置后两个参数后，相关前置路径错误才消除。
- 这些参数和检查入口已经存在；问题是跨仓运行前没有一次性核对它们。

**建议**

在现有检查脚本之前增加轻量前置检查，统一验证：

1. 所有跨仓 helper 的实际源码根、二进制、元数据和 Cargo target 是否关联同一参与 worktree；
2. 后端进程检查所需的前端静态产物是否存在；
3. Bun 版本及 frozen-baseline 外部依赖定位是否符合现有规范。

输出一份简短的“解析后的依赖表”，然后调用原有脚本。缺少前置产物时，在启动测试进程前给出对应构建命令。无需新增另一套全仓测试命令，也不应自动改用同级旧仓或已安装后端。

这是适合自动化的路径和产物一致性检查，不宜只追加到 `AGENTS.md` 或留给 reviewer 记忆。

## 3. 高：把 TDD 红灯锚定到行为，而不是入口缺失或夹具启动失败

**事实**

- 新 runner 的最初红灯是 Python 找不到脚本；这能证明交付入口尚不存在，但不能证明后续行为断言能捕获违规。
- 新增宿主 dock 的首轮结果为 OMP 通过、Pi 失败。Pi 失败发生在受控 manager 的身份类型与 Task agent 不匹配，尚未到达 report 行为断言；修正夹具后 Pi 用例通过。
- 后续工具结果证明：两宿主最终均覆盖非法调用无报告保存、严格声明和原生 Session 归属；新增 dock 为两例、40 次断言。
- CLI fail-closed 回归通过，但真实角色链路没有实际模型证据。

**建议**

在测试输出或测试旁的短说明中，把证据分为三个层次：

- **入口红灯**：接口尚不存在；
- **夹具红灯**：场景未到达被验收条件；
- **行为红灯**：场景已到达条件，断言识别了指定违规。

对“已存在实现、票据补覆盖”的情况，按现有 TDD 规则验证覆盖即可，不制造失败。对新行为，在具备真实依赖时，至少选择一个关键判据做针对性的故障注入，例如宿主删掉额外字段后非法调用变成合法调用，测试必须因新增报告而失败。恢复后再确认通过。

真实依赖缺失时，应保留“行为判据已实现、红绿敏感性未验证”，而不是把入口红灯接上组件绿灯后概括为完整 S2 红绿循环。

**边界**：本对话没有观察到真实模型场景的针对性故障注入；不能据此推断其断言已经证实有效，也不能推断断言必然无效。

## 4. 中高：用宿主级资源预约替代代理之间的重型检查排队消息

**事实**

- 已阅读的 toolkit 测试规范明确要求协调 real-host 和全仓检查窗口。
- 本次为避免与其他代理的浏览器检查竞争，多次通过消息申请、延后并释放窗口。
- 一次 canonical toolkit 全仓运行从此前约 108 秒变成约 509 秒，包含五个 OMP ready-frame 90 秒超时；独立运行对应文件随后八例通过。
- 完整日志被保留，独立诊断没有被冒充为 canonical 全仓通过。

**推断**

检查结果对运行环境或并发条件敏感，但本次证据不足以确定超时根因。不能仅凭独立通过就断言是 CPU 竞争。

**建议**

给重型检查增加宿主级、可释放的预约机制：声明 `native-host`、`browser` 或 `build` 资源，记录持有者、实际子进程和结束状态；进程退出时释放预约，并向等待者推送结果。预计耗时只用于提示，不作为自动抢占或放行依据。

这比要求每个代理维护一串“现在能否运行”的消息更可靠，也能使超时证据包含当时实际存在的并行任务。诊断应继续使用现有 serial/定向入口，保留 canonical 失败，不通过延长 deadline 或自动重试抹平结果。

## 5. 中：把 Windows 进程启动与构建环境查询的惯例封装到现有工具层

**事实**

- 一次 Python `subprocess` 调用使用短名称 `npm`，在启动任何构建前得到 `WinError 2`；改用 `shutil.which('npm')` 定位到 `.CMD` 后成功。
- 新 runner 起初在隔离 HOME 下执行 `cargo --version`，rustup 因隔离目录没有默认 toolchain 配置而失败。
- 后续将 Cargo 版本查询放回源码构建环境，而原生 Chat 继续使用隔离 HOME，入口才到达真正缺失的模型配置门禁。

**建议**

在现有脚本公共设施中提供两个清晰操作：

- **执行依赖命令**：按平台解析可执行文件或 shim，再启动进程；
- **查询构建工具链**：在源码构建环境记录版本，与隔离运行时环境分开。

可用小型确定性回归检查 Windows shim 解析与环境分离。不要把构建工具链配置复制进原生 Chat HOME，也无需增加“遇到 WinError 再试另一种写法”的通用重试规则。

## 6. 中：将已被识别的机械错误变成确定性检查，而非增加风格禁令

**事实**

- 新 dock 一度通过 `Awaited<ReturnType<typeof roleContractDock>>` 暴露具体 helper 的契约，宿主风格提醒要求改用模块拥有的命名类型；代理随后修改。
- 新命名契约的 `state()` 返回类型与现有 RPC frame 的索引签名不兼容，现有 `bun run typecheck` 明确报错；修正后类型检查通过。
- 当前仓库已有类型检查及 authoring 检查入口；这些检查确实捕获了问题。

**建议**

保留现有 typecheck 作为交付门禁。对于“具体函数的 `ReturnType<typeof ...>` 被用来发布契约”这类固定语法规则，若仓库决定长期采用，适合加入现有 linter/authoring 检查，而不是继续向始终加载的指令追加禁令。泛型工具类型的例外也应由检查规则表达。

**未验证项**：本轮没有检查 CI 或 pre-commit 配置，不能据此断言仓库缺少自动执行这些检查的 guardrail。应先核对现有 wiring，再决定是否补接。

## 7. 中：把跨平台提示词比较的换行差异纳入公共边界测试

**事实**

- 代理在实现后确认，两个角色指引文件实际都使用 CRLF。
- runner 通过 Python 读取期望文本，而宿主通过文本导入加载指引；两条路径可能保留不同换行形式。
- 最终修改为对实际模型消息做 CRLF→LF 归一化后比较。修改后 CLI 前置回归通过，但真实模型指引注入仍未执行。

**建议**

在可运行的 prompt/provider 观察边界增加换行等价用例：相同指引的 LF 与 CRLF 都应被识别为已注入，缺段或改词仍应失败。比较应只归一化换行，不扩大到会掩盖内容变化的任意空白折叠。

这是适合自动化的跨平台差异。无需通过增加自然语言提示，要求每次实现者手动检查文件换行。

## 8. 中低：让验证文档只维护前置条件和分支，减少检查清单缓存

**事实**

- 执行早期已读取两仓 `AGENTS.md` 指向的测试规范；导航指针本身可达，并非主要障碍。
- 新增长期说明同时涉及依赖安装、源码定位、模型授权、原生宿主边界、检查命令、观察窗口和证据要求。
- 关键参数分散在不同 helper，部分查找最终仍依赖测试失败信息。

**建议**

保留现有简短测试导航指针，把本次新发现的内容按分支共置：

- **跨仓技术检查**：解析后的源码/二进制/元数据定位及现有脚本入口；
- **真实模型验收**：授权依赖、隔离边界、通过判据及阻塞处理；
- **失败诊断**：日志位置、canonical 与诊断结果的区别。

将 `package.json`、`--help` 或前置检查可以直接给出的参数清单留在环境中；文档重点解释不能由一次查询得到的 gotcha，例如不同 helper 使用不同后端定位变量、隔离 HOME 不适合 rustup 默认选择、技术 dock 不等于模型职责证据。避免在两仓长期说明中维护两份完整协议和检查清单。

不建议仅为本次发现继续扩充全局 `AGENTS.md`：本次问题主要是前置检查和资源协调缺少机械支持，而不是导航指针不够强。

## 应保留的做法

- 缺少模型授权时明确询问 Main，随后遵守边界，没有转向读取用户状态或使用 bridge token。
- 保存全量日志，区分环境前置错误、技术组件通过、canonical 失败和独立诊断通过。
- 两仓使用独立 worktree 与 Cargo target，最终以各自提交交接，没有自行合入集成分支。
- 对未执行的真实 S2 保持未验证；没有从提示词存在、受控 provider 或最终状态推断角色行为通过。

这些做法应由能力清单、检查结果结构和资源预约机制稳定承载，而不必再增加一层泛化的“务必谨慎”指令。
