# Ticket 07 TDD 执行复盘建议

## 范围与结论

本复盘仅依据 `07-cross-repository-role-acceptancemd-dfb638a7-2` 本次执行对话及其中实际读取的工具结果。上一轮实现报告和 `verification.json` 仅作为本轮读取到的历史证据，不视为本轮重新执行的验证；未审阅父 session 或其他票据执行。

本轮没有修改产品源码，也没有新增 TDD 红→绿循环：主要工作是保留已有提交、核实真实模型验收前提、调查既有全仓失败，并执行一次限定并发的鉴别实验。最终明确报告阻塞而未宣称关闭票据，这是正确的验收边界。环境改进应优先解决前提可达性、失败证据留存和执行协议，而不是补充泛泛的“更彻底”指令。

## 1. 高：将真实验收依赖变成可判定的调度前提

**事实**

- 本轮开始时，上一轮报告已经明确缺少专用真实模型配置和授权凭据。
- 本轮读取的隔离配置仍将 `workflow_model` 指向 `authorized-model-not-provided`；检查到的显式验收配置和默认验收密钥环境变量均不存在。
- Main 随后明确确认没有新增授权配置或凭据信息，且当前会话不支持交互式 `ask`。
- 票据要求真实模型角色链路实际通过后才可关闭，因此已有 runner 和受控宿主 dock 不能消除此阻塞。

**建议**

在执行环境的现有准备流程中增加**依赖就绪判定**，沿用现有 runner 的配置解析和校验逻辑：显式模型配置可读、必要字段齐全、声明的凭据变量存在、所选宿主与依赖路径可用。输出只记录路径、配置身份、变量名及缺失项，不记录凭据值，也不自动读取用户全局认证或 Session。

缺失前提应产生机器可识别的 `blocked-prerequisite` 结果，并由宿主保留已完成的实现提交。恢复执行应由“前提已补齐”触发，而不是仅重新发出相同实现任务。这是前提状态的表达，不是为本票额外增加终局验收门禁。

**预期收益**

避免同一缺项驱动重复接手和重复核实；真实验收仍保持 fail-closed，不以替身降低承诺。

**未验证**

本轮未读取调度器实现，不能断言现有系统没有类似能力；能确认的是，本次恢复调用没有获得足以解除已知阻塞的新信息。

## 2. 高：在删除失败临时目录前保留最小诊断包

**事实**

- 上一轮 canonical `bun run test` 的 5 项失败均发生于 `model-cost-modes.test.ts`，表现为原生 OMP 子进程等待 ready frame 达到 90000ms。
- 原始日志中子进程仍运行，但没有 Session 文件、stderr 或 RPC 帧。
- 本轮尝试读取其中一个失败 runRoot 时，目录已不存在；读到的 `startRun` 错误路径会停止 capture 并调用 `runRoot.dispose()`。
- 因此，本轮能核对失败表象，却无法再检查失败时的隔离配置和启动现场。

**建议**

在现有 dock 清理边界保存**最小失败诊断包**，再照常清理所属进程和临时目录。诊断包应包括：启动参数、宿主/依赖版本、源码归属、启动阶段时间点、子进程退出或清理结果，以及经过脱敏的测试生成配置。现有 stdout/stderr/RPC 记录继续复用，不另建一套运行事实。

对凭据或运行态访问记录采用明确白名单，而非复制整个 HOME、环境或源码运行目录。失败证据保留与进程回收应是两个独立动作，避免为了留现场而泄漏服务。

**预期收益**

让“无输出、ready 超时”具备可继续调查的原始材料，而不是只能重新施加载荷猜测原因。

**未验证**

现有日志不足以确定卡点属于 Bun、宿主初始化、文件访问还是并发资源；本轮没有根因修复证据。

## 3. 中：区分诊断实验、验收通过与未解决失败

**事实**

- 本轮实际运行了：`bun test --parallel=2 tests/harness-dock/model-cost-modes.test.ts tests/harness-dock/node-report-contract.test.ts`。
- 结果为退出 0，10 passed、111 assertions，约 28.55 秒。
- 该实验改变了 canonical 全仓运行的文件集合和并发条件，因此只能说明这两个文件在该条件下可共存。
- 本轮最终报告正确保留了原 canonical 的 5 项失败，没有用局部绿覆盖全仓红。

**建议**

在现有验证摘要结构中明确记录实验的**判别问题**和**适用范围**：源码归属、命令、相对原失败改变的变量、实际观测，以及仍未排除的情况。此类结果标为 `diagnostic`，与 `acceptance` 分开聚合。

若此问题需要继续调查，应先获得一个能够捕获原症状的反馈循环或保留现场，再决定是否调整代码。当前不宜仅凭两 worker 通过就修改 canonical 并发数、延长 deadline，或把失败归因为资源竞争。

**推断**

本次两文件实验降低了“新增 report dock 必然直接破坏该文件”的可信度，但单次通过无法排除间歇性相互影响，更不能证明 12-worker 全仓条件没有问题。

## 4. 中：为不可用的发现工具提供确定性降级路径

**事实**

- 本轮两次 `find` 均返回判定服务 HTTP 451，明确说明没有候选得到判定，不能据此认定代码不存在。
- 后续一次宽泛日志 `grep` 产生大量通过项，达到匹配和输出上限；收窄到 `(fail)`、90000ms 和文件名后才得到可用证据。
- 为满足读取较长源码前查看大纲的要求，本轮分页查询项目列表并建立 fast 索引；目标测试文件随后仍返回空大纲。

**建议**

给工具环境增加会话级的**能力降级状态**：发现服务因固定区域限制不可用后，后续定位直接走确定性的文件名/符号搜索，保留原错误，不反复请求相同不可用依赖。

对已知文件，优先使用精确路径和已知失败签名；对源码大纲，提供与当前 worktree 关联的轻量文件级声明提取。MCP 返回空大纲时，应同时区分“未覆盖”和“确无声明”，让代理能够直接选择有界源码读取，而不是为单文件调查建立全仓索引。

**预期收益**

减少与本票实际问题无关的项目枚举、重复失败请求和日志噪声，同时保持“未知不当作不存在”的边界。

## 5. 中：按阶段提供互斥的完成契约和缺省工具能力

**事实**

- 实现轮上下文要求用 `yield` 返回结果，但运行时接受的完成形式与最初展示的单项工具说明并不一致；实际 `{error: ...}` 返回被宿主标记为 `Task aborted`。
- 本轮同时出现通用“不自行验证”、票据要求自行验收以及 TDD 要求运行测试等规则，需要代理自行判断特定任务优先。
- 本轮复盘由宿主另外声明独立的单项完成契约，明确替代实现轮参数，并要求只返回建议正文。

**建议**

由宿主为每个阶段只提供一份当前生效的工具 schema 和完成契约。实现、阻塞交接、复盘应有明确且可解析的不同结果；已识别的外部前提缺失应能表达为“实现保留、验收阻塞”，而不是只有正常完成或异常中止两种含义。

验证权限也宜在阶段入口统一：例如本票明确授权验收，则宿主不再同时加载默认禁止自行验证的执行分支。工具缺失时直接暴露能力状态，避免代理走到需要交互才发现 `ask` 不可用。

**未验证**

本轮没有查看宿主协议实现，无法判断 `Task aborted` 是否必然触发重调度。建议针对这次可见的协议歧义改进，不推断内部故障机制。
