# herdr-bot 分层原则

## 目的与适用范围

herdr-bot 要抽象的是**提示词之外反复出现的系统能力**，而不是把优秀的工作方法全部固化成代码。每次运行中得到的经验，都可以由人类审查后进入 Task、Bot、Map 的提示词字段、AGENTS.md 等持久化记忆或 skill，继续随实践演进。框架则承担不应依赖模型记忆与临场发挥的机械性保证。

本文记录分层判断原则，不规定包结构、接口清单或实施顺序。目标、责任分工与人类控制边界是已确认方向；统一消息、产物契约和复盘支持等是据此提出的设计方向，不代表当前已经实现或验收。

## 一 按责任分层而非按文件分层

| 责任范围 | 应当承担什么 | 不应代替什么 |
| --- | --- | --- |
| 人类目标与决策 | 明确目标、取舍、授权范围，审查结果与经验变更 | 不替框架手填会话身份、搬运协议字段 |
| 提示词与经验 | Task 指示、Bot 能力说明、Map 中的业务描述、记忆与 skill；指导理解、方法、质量判断 | 不以文字约定冒充权限、身份或持久化保证 |
| 工作流编排 | 通过 Map 组织工作，由 manager 结合 Run 现场调用工具，作派发、交接与恢复判断 | 不把语义决策藏进后端自动调度器 |
| 框架原语与契约 | 身份关联、运行事实、状态合法性、存储，以及经确认后抽象的消息与产物机制 | 不包办业务方案、质量结论或人的批准 |
| 宿主适配 | 对接 OMP、pi、Herdr 的会话、工具、输入与生命周期能力 | 不把某个宿主的进程模型当成通用领域模型 |

这些是责任视角，不是必须逐级调用的五层架构。身份、授权、可观察性会横跨多处；业务工具、脚本和普通代码也可以复用，不必因此晋升为框架内核。

## 二 保持定义与运行事实的边界

- **Task** 是可复用发起预设，用途分类为 normal / manager；节点执行者是某次 Chat 在 Run 中的角色，不是第三种 Task。
- **Bot** 是跨 Map 共享的能力说明，服务于选用、规划和执行理解。说明写得完整，不等于能力已经实现，也不等于后端验收规则。
- **Map** 是静态工作定义，同时包含结构化字段和提示词性质的描述；不能把整张 Map 都叫作提示词。`blocked_by` 表示前置依赖，不是材料流、消息路由或自动启动连线。
- **Run** 保存一次运行的要求、关联和事实；**Chat** 是实际原生对话，不等于 Task、进程、Tab 或在线登记。

`node.input` 应描述这项业务工作要做什么、使用什么材料、有什么业务约束。系统能够可靠取得的 Run 身份、Chat 归属、运行目录和通用交接协议，不应在每个节点中重复手写。业务确实需要的材料地址仍可出现，不能为了“纯净输入”删掉必要信息。

## 三 用判断性质决定经验落在哪里

**需要理解目的、权衡语境、选择方法的内容，优先留在提示词或 skill。** 例如怎样拆分研究问题、何时追问、如何设计有判别力的实验、怎样判断报告可用。这类判断即使反复发生，也不因此变成确定性规则。

**跨任务不变、输入输出清楚、失败可观察、能机械验证的能力，才是框架候选。** 例如从真实会话取得身份、拒绝跨 Run 写入、记录提交结果、定位关联 Chat、区分投递失败与保存失败。抽象应减少重复协议与错误机会，而不只是把调用包一层。

评估一个候选时，要能回答：它保护哪个不变量？谁调用、谁拥有事实？失败后哪些副作用已经发生？哪些结论仍需 agent 或人类判断？不能回答时，先保留为局部工具或经验，不急于增加概念。

存储就是例子：统一常用文件操作和协调范围有价值，但业务仍拥有状态转换与引用规则。不需要为了“架构完整”先设计多个存储 adapter，更不预设 SQLite、跨文件事务或自动修复。

## 四 框架保证动作可靠 不接管语义决策

manager 读取事实与材料，显式选择合法工具动作；后端验证身份、依赖与转换条件并如实记录。后端能判定“允许 complete”，不意味着它能判定“这份结果值得接受”。不要用一个自动遍历 DAG 的调度器替代 manager，也不要为了增加协作能力就直接套用另一项目的 Ticket 模型。

worker 应拥有自己的技术闭环：理解任务、选择方法、实施、验证并报告。可以借鉴 DSH 的这种分工，以及“授权范围与工作方法分开、观察到的消息不自动扩大权限”的原则；不照搬其领域与恢复策略。`ready` 的质量要求可以由提示词指导，但报告一个状态并不能证明质量已经达标。

## 五 将反复讨论的问题拆成两种责任

下表中的框架项是抽象方向，不是现有功能清单。

| 遇到的问题 | 提示词或 skill 承担 | 框架候选原语 | 保留给人或 agent 的判断 |
| --- | --- | --- | --- |
| 每个节点重复路径和交接说明 | 业务目标、材料用途、交付说明 | 运行上下文提供、身份绑定、报告入口 | 怎样完成工作，结果能否交接 |
| 下游找不到或误用产物 | 说明内容、用法、限制 | 产物引用、归属、访问与格式检查 | 内容是否正确、是否接受 |
| agent 之间反复询问状态 | 何时沟通、消息含义与回复方式 | 发现、寻址、投递、进度与未回复事实 | 是否需要沟通，问题是否解决 |
| 多处等待人类回答 | 清楚提出问题，解释选项和后果 | 请求与回复关联、统一待处理视图 | 人类选择、授权与确认 |
| 每次结束后手工复盘 | 解释成败、提出经验修订 | Run 引用、可用历史与证据定位 | 归因是否成立、是否采纳修改 |

### 产物不是完成状态的同义词

建议把用户发起时指定的产物位置与本次 Run 绑定，由 Map 描述约定格式；具体字段和校验强度仍需验证。至少区分：**已提交**、**通过约定检查**、**被接受用于交接**。引用登记不等于冻结文件字节；若需要快照或不可变性，应另行定义，不能暗中承诺。

### 消息不是换一个名字的报告

OMP IRC 值得借鉴的是整套能力：registry、发现与状态、直接消息与广播、progress、unanswered、生命周期配合、上下文注入，以及 observer 的显示路径；不能只截取一个 send 工具。观察者界面能看见旁观消息，不等于这些消息进入观察者自身的模型上下文；真正投递给 agent 的消息则按接收规则处理。OMP 的进程内机制也不能原样用于 Herdr 中彼此独立的 Chat，需要明确桥接身份、投递和生命周期边界。

“已发送、已投递、agent 回复、ack、问题 resolved、node completed”必须各有含义，不能混为一谈，也不能未经相应证据就推导后续状态。尤其 progress 不是最终答复，回复不是交接验收。

面向人类的请求与回复应沿用统一关联机制；“等待人类处理”是它的视图，而不是另建一套不相通的系统。对于 manual 报告策略，人类仍在**原节点 Chat** 确认发送报告；不要移到 manager 统一审批，也不要把发送确认当成节点完成。

## 六 让经验演进本身也可以被改进

每次 Map 运行后，人类已经可以手动回看历史并复盘。最小起点是把这个过程整理为可复用工作流：定位实际 Run 及可取得的 Chat 历史，列出关键事件与证据，区分提示词改进、局部工具改进和框架原语候选，交由人类审查。没有取得的历史要明确标注，不能以摘要补造事实。

复盘产出是候选修改，不是自动改写 Task、Bot、Map、记忆或 skill。问题重复出现只说明值得调查，不证明根因在框架；也可能是目标不清、上下文缺失、指引不合适或一次执行偏差。

人类主动带领的 grilling，用于对齐理解与抽象：先让模型展示它怎样理解，再通过反馈探查误解，逐步进入细节；不是固定问卷，也不是一次倾倒全部设计。实验用于获得尚未知晓的经验事实；计划、实验、评审这些方法本身仍可作为经验演进，不要求全部框架化。

## 七 从原则走向实现时的约束

先选一个真实重复问题，提出最小契约，明确成功、失败和仍需判断的部分，再用实际 Run 验证是否减少了重复劳动与错误。不要凭原则一次建设通用平台，也不要顺带引入启动时自动找目标、定时任务或自动恢复。

现行 `workflow-contract.md` 明确排除普通双向消息、原生 IRC、产物绑定与校验、通用人工审批，以及重启接管等能力。本文讨论的新方向**不自动撤销这些排除项**：若决定实施，应逐项、窄范围地修订契约，明确新的保证与仍保留的限制，再做实现和验证。现有三文件、会话恢复与部分生效语义，也不能被新抽象悄悄改变。

最终检验标准是：**提示词还能由人类持续改善，agent 仍保有必要判断，而重复的机械负担不再靠每次提醒来维持。**
