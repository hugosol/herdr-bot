以下建议按风险与影响排序。

## 1. 高：把原生 smoke 的隔离能力做成明确、可复用的执行入口

**事实**：执行者读取的 `herdr --skill` 要求 `HERDR_ENV=1`，环境检查却显示该变量及相关会话变量均不存在；之后仍自行创建了新的命名 session。实际命令显式绑定专用 session，没有观察到操作用户默认 session。原生 smoke 还依赖此前专用验收留下的临时目录、原生文件和 cwd，并手写启动配置；先后因缺少 `working_directory`、声明了 OMP 却缺少其固定扩展而启动失败。通用 JSON 命令包装器也曾错误解析 `agent read` 的文本输出。

**推断**：当前环境对“控制用户现有 Herdr”和“从外部创建专用验收 session”缺少清晰的能力分界。安全隔离和可重复性依赖执行者临场组织；本次成功不能证明临时 seed 被清理后仍能重复执行。

**建议**：提供一个本地原生验收入口，负责创建全新目录和命名 session、隔离配置与 HOME、固定每次控制命令的 session，并区分 JSON 控制结果与文本读取结果。启动配置复用现有配置装配模式，而不是让每轮代理重新拼装。seed 应由可重复的准备步骤生成，或由带身份与完整性信息的专用材料提供。将此入口与现有用户会话控制指引分支说明，避免让执行者自行裁定前置条件是否适用。

**完成标准**：从无历史临时目录的环境能够准备专用样例；缺少原生依赖时在创建目标前准确报出缺项；每条变更命令都绑定本轮 session；交接明确区分已停止的 HTTP 服务和为检查而保留的原生目标。

## 2. 高：让浏览器测试进入 TypeScript 检查，并接上仓库级自动护栏

**事实**：执行中曾写出 `duplicate.status()`，随后在运行前自行改为 Fetch `Response` 的 `status` 属性。现有 `frontend/package.json` 的 build 会运行 `tsc --noEmit`，但 `frontend/tsconfig.json` 的 include 不含 `browser-tests` 或 Playwright 配置。Playwright 执行本身不等于 TypeScript 类型检查。仓库中未找到版本化的 `.github/workflows`、`.husky`、Lefthook 或 pre-commit 配置；现有 npm hooks 则确实会检查测试网络策略。

**未验证**：未检查宿主是否另装了非版本化 Git hooks 或外部 CI，因此不能断言所有提交入口都完全没有检查。

**建议**：优先增加浏览器测试专用的类型检查范围，并接入现有检查命令；随后在仓库实际使用的 CI 或提交护栏中执行它及已有网络策略检查。复用已有检查，而不是另写一套网络规则。这类固定 API／类型错误交给编译器，不增加“注意 status 是属性”之类常驻代理指令。

**完成标准**：浏览器 spec 和 support 文件中的 `Response.status()` 误用会稳定导致检查失败；正常配置下浏览器测试也完整通过类型检查；版本化的自动入口实际调用这些检查。需要原生依赖或人工授权的验收继续独立运行，不混入默认网络边界。

## 3. 中：证据归档应保留完整性与退出状态，避免从阅读器预览重建检查结果

**事实**：执行者第一次读取 `artifact://216:raw` 时只取得 819 行中的前 300 行，并立即汇总、写下了“178 passed、0 failed”。随后发现末尾截断提示，完整读取后修正为“446 passed、1 failed、5 ignored”。最终交接如实记录失败，没有把最初的不完整统计提交为最终结论。

**风险推断**：本次靠事后检查修正了证据。若只从截断文本统计通过数，位于末尾的失败可能被排除；阅读用输出不适合作为归档或检查状态的权威来源。

**建议**：由命令执行或证据导出层直接保存完整输出、退出码及可用的结构化测试结果；阅读器只提供预览。导出接口应区分完整数据和截断显示，缺页时不生成完整汇总。能直接复制原始 artifact 时，不要求代理通过扩大行范围再拼回日志。

**完成标准**：一份末尾含失败的长输出经过导出后仍保留完整失败及非零退出码；不完整预览只能标记为 partial；汇总必须与完整记录一致。报告继续区分“本票验收通过”和“项目全量检查失败”，不以范围判断抹去失败状态。

## 4. 中：在 TDD 的测试设计参考中强调“契约观察范围”，减少无效 red

**事实**：第一组组合测试精确比较全部 CLI 调用序列，页面独立解析 Workspace 名称多产生一次只读 `workspace_list`，导致四个场景失败。后续四个交互场景又因同一 Workspace ID 同时出现在历史列和结果区，触发定位器歧义。修正分别是排除附带只读查询，以及把定位器限定到已有名称的“Resume 目标”区域；没有改变权威结果和启动次数要求。

**建议**：把这类经验放入现有 TDD 测试设计参考或 reviewer 的测试审阅项，而不是扩大根 `AGENTS.md`。设计时明确两点：

- 外部交互中，哪些次数或顺序是合同限制，哪些只是页面伴随读取；断言聚焦于受约束的启动、创建、输入与目标身份。
- 页面中，同一事实可能出现多处；使用已有语义区域限定观察对象，而不是依赖文本全局唯一。

同时保留失败分类：产品行为失败、fixture／定位器失败、已有行为直接通过。只有第一类才是产品修复的 red；已有行为不需要人为破坏实现来制造 red。

**完成标准**：合法增加一次只读名称查询或重复展示同一 Workspace ID，不影响这些行为测试；重复启动、遗漏降级和错误成功状态仍会使测试失败。具体业务契约属于审阅判断，不建议用机械规则一概禁止调用序列断言。

**推断**：借用相关分支的图有助导航，但不能证明当前 worktree 的符号位置和覆盖完整。当前会话没有证据证明它导致了错误修改；风险在于把相邻快照误当作当前索引，以及重复支付已知不可用搜索的失败成本。

**完成标准**：每次图查询能辨认其对应根目录；跨 worktree 结果不会被表述为当前覆盖；同一后端的确定性不可用不会反复触发整批判读。
