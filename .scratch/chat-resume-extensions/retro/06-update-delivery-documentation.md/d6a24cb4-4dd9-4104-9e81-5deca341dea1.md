## 1. 中优先级：统一“实现交接”与“票据关闭”的完成边界

**事实**：本轮注入指令同时要求“必须持续工作直到票据 closed”和“完成后交给独立集成代理，不自行合入”。实际读取的 `triage-labels.md` 又规定，`closed` 要求实现、验收且已经合入。agent 最终完成提交，保留 `in-progress`，并解释由合入方关闭（记录 21、160、165–166）。这是合理交接，但需要 agent 自行解释多个完成条件。

**风险推断**：同样的上下文可能使后续 agent 为追求 `closed` 而提前关闭票据、越权合入，或在可交接后继续无关工作。本轮未观察到这些后果。

**建议**：在派工宿主的单一完成契约中区分责任，而不是继续追加全局禁令：

> 实现代理完成条件：本票实现、指定验收及提交完成，交出提交与未验证项。集成代理负责合入，并在满足仓库状态规则后关闭票据。

仓库状态定义继续以 `triage-labels.md` 为准；替换派工模板中无条件的“直到 closed”，避免两处分别定义终点。

**建议验证方式**：观察后续独立 worktree 任务是否能在未合入状态下稳定完成交接，同时准确保留票据状态；该建议尚未试运行。

## 2. 中优先级：让语义搜索对确定性不可用错误快速降级

**事实**：首次 `find` 因服务返回地域限制 HTTP 451，25 次 judge 请求全部失败；工具报告扫描 243 个候选、读取 20 个文件，并明确说明这不是“没有匹配”的证据。agent 随后改用文件名与字面搜索，没有反复调用失效服务（记录 25、80、84）。

**建议**：改进 `find` 工具的服务可用性处理：对地域限制等确定性不可用响应，在当前批次快速停止同类请求，并将本次会话的搜索转交可用的本地查找路径。这里适合工具层的确定性分支，不需要让每个实现代理阅读一段故障处理说明。

保留现有“不可用不等于无结果”的错误语义；不要把所有临时网络错误都按永久故障处理。

**预期收益与限制**：可减少已知不可用服务上的重复请求。日志中的 20.9 秒是工具报告的 API 用时，不能直接当作节省的墙钟时间；本轮也不足以证明其他会话持续存在相同服务限制。
