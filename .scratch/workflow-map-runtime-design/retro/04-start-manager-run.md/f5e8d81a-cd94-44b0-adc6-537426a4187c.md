**建议**：由工作流的依赖记录统一维护外部交付项：责任仓库、所需入口、交付版本、修改权限和真实验收条件。恢复派发时直接提供这些字段的变化；前提未变时，只派发明确可完成的收尾任务，并保留整票阻塞状态。存在性检查可自动化，跨仓库授权仍应由人决定，不以文件存在替代真实宿主验收。

## 4. 中：给搜索工具加入环境故障降级，并缩小恢复任务的阅读面

**事实**：一次外部仓库 `find` 展开为 24 个 judge 请求，全部因同一个 HTTP 451 区域不可用错误失败；工具报告没有任何候选被判定。agent 随后改用字面搜索，正确地没有把失败当作“不存在”。另一次 MCP 项目列表返回了 20 个项目，但该轮后续没有使用这些项目标识。该轮还在没有新增测试或替身的情况下读取了完整测试设计、mocking 指引及较多通用词汇。

**建议**：

- 搜索服务对区域限制、鉴权等确定性环境错误实行短路，尽早返回不可用状态及可用的字面搜索路径；恢复后再启用语义判定。
- 已知配置位置和入口文件名时，优先走精确定位；只有符号关系仍不明确时才枚举索引项目。
- 为恢复任务设置“差量阅读”分支：先读拒收原因、继承报告和实际 diff；新增行为测试时再加载测试设计参考，引入替身时再加载 mocking 参考。把条件写在指向参考的现有 pointer 上，而非复制一份新的规则正文。

**完成标准**：确定性服务故障不会继续放大请求；纯交付收尾只加载能影响本次决策的材料，同时保留必要的仓库规则与安全约束。
