## 1. 高：让 P48 的验收能够拒绝所声称防范的“先删后换”实现

**事实**

- Windows 用例持有不共享 DELETE 的真实文件句柄，观察替换失败、正式路径与旧句柄字节保持，并在释放句柄后确认下一次替换成功。
- 并发用例通过真实 HTTP 读取详情，同时执行 40 次状态转换；文件访问仍经过服务的集合协调。
- 测试注释把“delete-first writer”列为可以发现的违规，但本轮日志没有针对先删后换实现的故障注入或变异失败证据。
- 原实现的 `FileStore::replace` 已使用临时文件加 `fs::rename`；本轮保留了这一实现，因此这些 Windows 检查初次通过本身符合 TDD 对已满足行为的处理规则，不需要制造 red。

**推断**

一个在同一集合锁内执行 `remove_file(正式路径)?` 再 rename 的错误实现，可能仍通过上述检查：不共享 DELETE 的句柄也会让删除直接失败；成功分支中的删除空窗又可能被 HTTP 读取所使用的同一把锁遮住。80 次读取与 40 次写入也没有单独证明读取确实进入了替换的关键时段。通过结果能支持实际成功/失败与协调行为，但不能单凭这些断言排除全部已命名违规。

**建议**

- 优先落实现有 TDD skill 的 **green 后敏感性检查**，而不是再增加一条同义要求：针对“正式文件先删后换”做一次隔离、可恢复的定向变异，记录哪条断言实际拒绝它；若变异仍通过，先修正证据或限定结论。
- 将“正式路径不先删除”视为适合机械约束的部分，在仓库检查入口增加范围明确的静态检查：替换路径中的删除只能用于临时文件清理。该检查与 Windows 行为测试互补，不发布私有 helper 为新契约 seam。
- 并发用例若承担“特定交错已发生”的证明责任，应通过测试已有的受控调度能力确认交错；否则将其明确称为并发回归样例，不把请求次数视为交错证明。

**完成判据**：命名的错误实现会被行为测试或机械检查实际拒绝；报告分别说明行为证据、源码约束和未覆盖范围。

**未验证**：本复盘没有运行该变异，不能断言当前测试一定放过它，也不据此判定当前替换实现错误。

## 4. 中低：在工具层处理搜索服务不可用，并随 worktree 提供图索引身份

**事实**

- 首次 `find` 的 26 个判断请求全部因区域限制返回 HTTP 451，没有获得搜索判断结果；代理随后使用 grep/glob 找到了文件，没有把失败当作代码不存在。
- 为取得本 worktree 的图能力，代理读取工具 schema、分页列举已有项目，再创建新索引；返回规模为 4,505 个节点、22,889 条边，之后读取两个文件的大纲。
- 本轮还出现一次越界 spec 读取：请求 400–470 行，而实际文件只有 307 行。

**建议**

- 为 find 的权限/区域不可用错误提供会话级熔断与明确降级路径。一个已确定无法工作的提供方不应继续扩散同类判断请求；由工具实现处理，比在代理指令里增加特殊禁令更可靠。
- worktree 创建或派发时提供与当前根路径对应的图项目句柄及就绪状态；已有索引可直接用，确需建立时按真实读取范围选择策略，避免每张票先列举无关项目。
- 需求定位用已知验收 ID、标题或返回的实际行范围；不猜上游文档行号。这里需要改善导航输出，而不是把整个 spec 常驻上下文。

**完成判据**：新 worktree 能直接确定可用的本地导航入口；提供方返回确定性不可用错误后不再重复消耗同类请求；上游引用可以落到实际章节。

**边界**：本轮没有索引耗时或费用的独立比较，不能把全量索引认定为主要耗时来源。能确认的是额外初始化步骤与一次无效搜索调用。

## 建议保留的执行方式

- **保持公共 seam**：通过真实 HTTP 和实际持久文件观察行为，外部 Herdr 副本只提供确定性的故障与时序条件。
- **保持纵向循环**：先看到损坏记录或错误反馈的实际失败，再修改实现；已经满足的 Windows/锁行为直接验证，没有为了凑 red 故意破坏正确实现。
- **保持证据边界**：最终交付明确区分目标 Windows 文件检查、受控宿主等待与未验证的原生 Herdr/omp、角色 Prompt 注入，没有把后端测试冒充模型或宿主能力验收。
- **保持一次完整交付检查与后台等待**：本轮使用现有 runner 完成全量后端检查，后台任务通过 wait 接收结果，没有轮询，也没有把构建完成误当成测试全部完成。
