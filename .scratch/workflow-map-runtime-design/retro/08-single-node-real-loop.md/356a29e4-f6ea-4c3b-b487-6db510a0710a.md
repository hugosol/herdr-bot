# Ticket 08 TDD 执行复盘建议

## 证据范围与结论

本复盘仅依据指定的 ticket 执行 JSONL、其中的工具结果与接收到的协调消息；未读取父 session 或其他 ticket 的执行历史。本轮另只读了 `frontend/package.json`，用于确认现有检查入口，没有重跑验收或修改文件。

实际交付是提交 `e1af254`：为 `docs/workflow-runtime.md` 增加 81 行单节点原生验收指南与部署检查证据。两个 metadata 指定的角色入口实际不存在，前置检查退出码为 2。没有启动真实 Run/Chat，也没有发生行为测试的 red → green。最终报告明确区分了“当前可达工作已提交”和“真实闭环验收仍阻塞”，没有认领 P62/P63；这是应保留的证据边界，不应将环境检查失败包装成 TDD 的行为 red。

## 1. 高：将原生验收的外部依赖前置为票据局部的部署检查

**事实**：票据标为 `ready-for-agent`，显式阻塞项为 07。本轮查阅配置和 metadata 后，确认 `manager-chat.ts`、`node-chat.ts` 均缺失。同一执行历史收到的 07 协调消息也指出原生角色入口缺失；该消息只能证明对方报告了阻塞，不能替代本轮实际检查。

**影响［推断］**：实现依赖完成与真实环境可验收是两个维度；若交接只携带前者，原生验收票会重复发现同一个外部部署缺口。

**建议**：为此类真实宿主验收票提供一个局部、只读的部署检查入口，从当前 metadata 解析角色路径，输出缺失项、版本与检查时间；交接时分别记录实现依赖和外部部署状态。该检查只帮助选择“继续原生验收”或“记录精确阻塞”分支，不成为全仓库门禁，也不以入口文件存在代表 Session、Prompt 或工具装配成功。

**完成判据**：角色缺失时，不创建 Run/Chat 即可得到稳定的缺失清单与非零退出码；角色存在时，结果仅说明可以继续真实验收，不生成通过结论。既有 npm 测试前置检查主要运行网络策略护栏，不能据此推断原生角色已部署。

## 2. 中：由宿主严格校验工作池提交参数

**事实**：实现轮最后一次 `yield` 调用只有 `data`，没有当时契约要求的数字 `key`；工具仍返回了 `Result submitted.`。这说明该次调用在缺少协议字段时仍被接受，不能据此推断其他运行也如此。

**建议**：在宿主工具边界执行必填字段和类型校验；协议拒绝应返回缺失字段与合法形状。此问题属于机械协议约束，适合确定性检查，不应再增加一条让代理自行记忆的长提示。

**完成判据**：缺少 `key`、字符串形式的 `key` 或未知工作项均明确拒绝；合法单项提交正常完成。兼容处理若确有需要，应由宿主显式定义，而不是默默接受不完整参数。

## 3. 中：将稳定操作说明与一次性验收记录分层

**事实**：本轮把预期文件内容、执行步骤、隔离要求、具体机器路径、版本、失败 JSON、一次 shell 引号修正经过一起追加到了运行说明。原说明会提供给真实角色 Chat；因此这些一次性记录也可能进入后续运行的读取路径。没有真实 Chat 读取轨迹，尚不能证明它已造成注意力下降。

**建议**：运行说明保留稳定职责、最小证据要求，以及“执行单节点真实验收时读取验收指南”的条件指针。单节点指南集中放预定义产物、逐字节 oracle、执行顺序和结束条件；具体日期、部署路径和检查输出放本次验收证据附件。共用的进程、网络与隔离规则继续引用现有测试指引，减少重复维护。

这不是单纯按行数拆文件：切分应对应“运行中角色职责”“准备单节点验收”“复查某次证据”三个不同分支。

**完成判据**：普通 manager/node 读取运行职责时无需穿过历史环境故障；验收者通过一个明确指针能找到完整步骤；证据复查仍能定位本轮真实输出。行为规则只有一个权威来源。

## 4. 中低：为跨 shell 的 PowerShell 探针提供可靠调用方式

**事实**：第一次通过 bash 执行 `powershell -Command` 时使用外层双引号，PowerShell 的 `$paths`、`$_` 被外层 shell 展开，结果出现空管道等语法错误。改用外层单引号后，才实际得到两个 `isFile=false`。

**建议**：在 Windows 工具环境提供可直接调用的 PowerShell 通道；若继续经 bash 调用，多语句探针优先采用可复用的 `.ps1` 文件并使用 `-File`，或提供一个已验证、只在跨 shell 分支加载的调用范例。把引号机制交给工具或调用模板，不转化为 reviewer 的判断型编码标准。

**完成判据**：包含 `$变量`、`$_`、空格路径的探针能够原样到达 PowerShell；语法/调用失败与业务前提缺失有不同诊断。修正探针的成功只证明检查可执行，不证明真实宿主闭环通过。

## 5. 低：让导航围绕当前问题收敛，减少无产出的发现调用

**事实**：本轮两次行为搜索各在 20 秒后超时；MCP 项目列表返回 50 个项目且仍有下一页，后续没有使用其中项目进行符号查询；另读取了文件大纲工具 schema，但没有调用该工具。最终关键证据来自 metadata 中的已知角色名、部署目录读取和绝对路径检查。

**建议**：保留未知行为先定位的流程；当运行说明已经给出角色名与 metadata 位置时，直接沿“角色声明 → 实际入口 → 文件/装配状态”走。图工具用于需要符号和调用关系的问题；多 worktree 场景宜由环境提供当前项目标识，减少全局项目枚举。一次行为搜索超时后，使用已有精确标识缩小问题，而不是再次发起近似宽泛搜索。

**完成判据**：同类部署缺失可以从权威配置直接追到实际路径；只有需要关系证据时才加载图工具文档和项目索引。根 `AGENTS.md` 本轮已提供简短导航，不需要为此增加常驻长规则。
