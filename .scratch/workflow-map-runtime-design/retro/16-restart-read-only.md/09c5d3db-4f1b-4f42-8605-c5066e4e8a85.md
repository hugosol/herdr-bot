# Ticket 16 TDD 执行复盘建议

## 结论与证据范围

本复盘仅依据指定 ticket 执行日志中实现轮的记录；未读取父 session 或其他票据执行历史，未重跑验收，也未修改任何文件。

本轮没有观察到尚未修复的产品故障。最终记录显示：`workflowStart.spec.ts` 的 5 项浏览器检查通过，浏览器分区检查通过，提交为 `e4b67d9`。这些结果不等于全仓回归通过，也不证明真实 omp / toolkit 注入已验收；执行代理明确保留了这些证据边界。

以下按影响排序，均为环境改进建议，而非本轮已实施变更。

## 1. 中：把“服务重启”和“页面刷新”的边界放到测试 helper 的使用点

**事实**：P54.02 首次执行在重启后仍看到了两处 `failed-manager-restart`，其中一处来自旧的启动错误区，导致 Playwright strict-mode 失败。代理随后将重启后的同地址 `page.goto(...)` 改为 `page.reload()`，检查通过。记录中的 helper 只负责停止、启动服务；它不刷新浏览器。该场景复用了原地址，同地址导航没有触发所需的重新加载。（15:54:28–15:54:48）

**影响**：这类失败容易被误判为“后端恢复了不该恢复的错误”，进而诱导修改正确的业务实现。本轮通过先比对 HTTP 结果、再纠正页面观察方式，避免了这种误修。

**建议**：在 `E2EServer.restart` 的接口说明处集中注明其生命周期契约：重启仅作用于后端；现有浏览器文档保留；观察重启后的页面事实时显式刷新或重新加载文档。把这个非显然的 gotcha 放到 helper 旁，而不是依赖某个测试体中的注释被下一位作者发现。保留后端重启与浏览器刷新两种动作的独立性。

**完成判据**：新增重启场景的作者从 helper 声明即可判断何时需要 `reload()`；测试能区分服务事实已更新与页面仍显示旧文档，而非靠延时消除失败。

## 2. 中：为导航工具增加不可用熔断与当前 worktree 的直接定位

**事实**：首次 `find` 的 29 次 judge 请求全部因区域限制返回 HTTP 451，没有产生有效判断。随后代理回退到搜索和文件枚举；一次搜索使用了 `class Workflow` 等不适合本仓库 Rust 实现的候选。为取得大纲，代理又分页枚举了 54 个索引项目，最后才为当前 worktree 建立独立索引。（15:49:53–15:50:40）

**推断**：主要导航成本来自工具能力状态与项目身份发现，而不是该票据的业务复杂度。一次执行不足以证明该问题在所有环境中都会发生。

**建议**：

- 在工具层识别明确的区域不可用响应，停止同类 judge 扩散，并直接返回可执行的本地检索回退信息。
- 由宿主提供当前 cwd 对应的索引项目标识及覆盖状态；未索引时明确返回，而非要求代理枚举全部项目再推断。
- 对已知文件的大纲需求保留直接路径入口，减少无关项目列表进入上下文。

这些属于导航设施改进，不宜追加成每轮必读的长篇 `AGENTS.md` 规则。

**完成判据**：相同 451 条件下一次失败即可进入有效回退；当前 worktree 的索引定位不再依赖全量项目枚举。

## 3. 中低：分区检查默认输出结论，完整 manifest 按需披露

**事实**：仓库已有 `test:browser:partition`，本轮正常执行且通过，计数为 `full=306`、`fast=277`、`time=29`。但成功输出包含完整 manifest，产生大量结果清单，工具显示发生截断。这里缺少的不是分区 guardrail，而是紧凑的成功输出。（15:55:50）

**建议**：为现有检查入口提供摘要模式：默认输出计数、交集/遗漏检查结论及退出状态；失败时输出违规项。完整 manifest 写入机器可读产物，或由显式详细选项输出。维护一个检查实现，而不是另造第二套分区规则。

**完成判据**：成功调用的终端输出足以确认分区正确性；需要排查时仍能取得完整 manifest；检查失败仍返回非零。

## 4. 中低：在 worktree 交付环节提供依赖就绪信号

**事实**：首次浏览器构建停在 `tsc` 不存在，尚未进入测试；执行 `npm --prefix frontend ci --ignore-scripts` 后构建得以继续。下一次失败是新测试将创建 Run 的返回码误写为 200，而实际接口为 201；代理读取对应实现后纠正了夹具预期。这两次都不是重启只读行为的 red。（15:51:58–15:53:11）

**建议**：

- 由 worktree 准备流程提供依赖安装是否完成的明确结果；缺失时依据 lockfile 准备一次，避免首次行为验收兼任环境探测。
- 为新浏览器场景提供便于发现的现有 Run 创建样例，包含成功返回码和响应形状；优先复用真实公共入口，不为绕过准备工作引入内部 mock。
- TDD 证据继续区分环境失败、夹具失败与行为性 red；本轮已正确做出这种区分，应保留。

**未验证项**：本轮没有检查宿主是否已有可复用的依赖缓存或统一准备机制，因此不建议无条件为每个任务重新安装依赖，也不据此认定 CI 或 pre-commit 缺失。

**完成判据**：代理开始行为验证前可确认依赖就绪；创建接口的设置错误不会被计入业务 red 证据。

## 5. 低：将角色运行说明中的复验细节下沉为按需参考

**事实**：本轮新增的“后端重启：历史现场只读”章节同时承载了用户/角色限制、HTTP 拒绝语义、诊断保留方法，以及两个测试的长名称、命令、产物与观察窗口说明。执行时读取的原运行说明已达 432 行，并会通过路径提供给 Chat。

**推断**：运行中的 manager/node 需要只读限制与下一步行动，但通常不需要完整测试叙事。两类内容同层排列，会增加角色读取运行规则时的注意力负担。

**建议**：在 `docs/workflow-runtime.md` 保留重启语义、拒绝处理及诊断去向；将详细复验与证据说明归入已有测试指引，并设置单一条件指针，例如“复验后端重启或归档验收证据时，读取测试指引的对应章节”。按分支披露，不增加新的常驻规则文件，也不在两处复制验收命令和测试清单。

**完成判据**：角色能在运行章节内直接判断“可读哪些事实、拒绝后如何处理”；验收代理通过明确指针取得唯一的复验说明。

## 本轮值得保留的执行方式

- 先声明获批 seam、独立预期及可能违例，再通过真实 HTTP、文件和进程测试，而非替换内部实现。
- 发现后端只读边界已经成立时，以新增覆盖验证既有行为，没有为制造 red 而破坏实现。
- 真正的新增页面指引先出现行为性失败，再实施最小改动并得到 green。
- 对文件保留使用重启前后逐字比较，并用已知状态字面值确认场景确实到达 running、failed 和已有报告条件。
- 无自主动作证据明确限定为 1000ms，并保留外部调用记录；没有把受控 Herdr 响应包装成真实原生宿主证明。

本轮没有足够证据支持新增全局编码禁令、修改 reviewer 标准或宣称仓库没有自动化 guardrail。优先修复上述具体设施与信息放置问题，比继续堆叠常驻指令更有收益。
