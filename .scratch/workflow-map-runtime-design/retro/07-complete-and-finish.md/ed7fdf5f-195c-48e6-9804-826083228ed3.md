# Ticket 07 TDD 执行复盘建议

## 范围与结论

仅依据本次 ticket 的指定执行日志，复盘范围截止实现轮提交及交付；未使用父 session 或其他票据执行结果。以下仅为建议，本轮未修改项目、检查配置或代理指令，也未重跑验收。

本轮完成了两个可观察的 TDD 循环：complete、finish 各自在入口缺失时返回 404，随后对应定向测试通过；新增的报告/会话事件隔离测试也通过。首次测试中的 Rust 日志格式编译错误被修正，未被当作行为 red。最终完整后端检查通过，提交为 `315938f`。

主要改善空间在**验收环境交付、导航工具的工作树身份、验证入口的前置检查**，而不是再增加泛化的“认真测试”指令。

## 1. 高：派单时明确真实角色工具的可用性与证据边界

**事实**

- 票据要求经实际 manager 工具完成 report → complete → 下游 dispatch → finish，并观察真实 Chat 仍在收尾。
- 执行中读取 metadata 后，搜索其指向的外部 manager-chat/node-chat 入口没有找到文件。代理向 Main 询问后，Main 明确确认没有新 toolkit worktree 或入口，要求按当前仓库可执行边界交付，并报告原生工具、Prompt、真实 Chat 未验项。
- 最终报告保留了这些限制，没有把 HTTP 身份、会话登记事件或受控 Herdr 副本冒充原生工具验收。

**推断**

确定性实现可以完成，但票据的完整宿主验收依赖未随任务提供的外部能力。若这个边界只在执行中确认，后续执行仍可能重复查找、询问，或误将后端通过理解成整个验收完成。

**建议**

在派单上下文中提供简短的**验收环境说明**：角色入口的实际位置/版本、是否可加载、隔离宿主是否可用，以及当前允许取得的证据层级。入口位置以现有 metadata 为来源，说明只补充其不能表达的交付状态和责任归属，不维护第二套路径配置。

外部能力缺失时，预先明确“继续交付本仓库实现，原生证据仍待取得”的处理方式。它是交付信息，不是新增 Run 业务门禁，也不应阻止可执行的确定性工作。

**完成判据**：下一次执行无需重新询问外部仓库位置和验收责任；交付仍分别列出实现完成、确定性验证、真实宿主未验项。

## 2. 中：将代码图查询绑定到当前 worktree，避免使用错位大纲

**事实**

- 代理两次分页枚举索引项目后，使用 `workflow-dispatch-05` 查询 `backend/src/runs.rs` 大纲，而本票工作树是 `hyper-ticket-XUPdgE`。
- 返回大纲中的 `NodeState` 仅列出 `status`，同轮读取的当前源文件则已有 `execution`、`failure`；返回的大纲也未呈现当前源文件中的完整 dispatch 实现。
- 后续代理实际读取了本地源码；日志没有证明错位大纲造成了最终实现错误。

**推断**

另一个工作树的索引不能可靠地充当当前源码的导航前置证据。相同相对路径容易掩盖版本差异，增加遗漏调用者或按旧结构设计的风险。

**建议**

由宿主向代理提供与当前绝对根目录绑定的索引项目句柄；工具查询时校验根目录，并对不匹配或不可确认的快照明确提示。没有匹配索引时，直接使用当前工作树的本地导航，或建立本票索引，而非以其他票据的索引替代。

这适合放在工具路由或 worktree 初始化中处理，比增加“多核对索引”的常驻文字更可靠。

**完成判据**：当前 worktree 的大纲可直接取得；查询另一工作树时有明确身份提示，不能无提示地成为当前源码依据。

## 3. 中：把完整后端检查的资产前提变成启动前检查

**事实**

- 代理已经读取 `docs/agents/testing.md`，其中说明进程级检查需要构建前端。
- 首次运行 `node scripts/test-backend.mjs` 仍在构建并执行部分测试后，因缺少 `backend/static/index.html` 失败；该轮耗时约 63 秒，39 个二进制未派发。
- 随后执行前端构建又因缺少 `tsc` 失败。安装锁定依赖并成功构建后，完整后端检查最终通过，用时约 147 秒。
- 现有 `frontend/package.json` 已有 `build`，浏览器构建验收入口也已经组合了构建步骤；问题不是缺少构建命令，而是完整后端入口没有在昂贵工作开始前有效暴露其前提。

**建议**

在现有后端 runner 开始 Cargo 构建和子进程测试之前，检查必需的前端入口资产；缺失时立即给出实际准备入口。新 worktree 的依赖安装与构建顺序可由宿主准备流程执行，或复用已有命令组合成统一交付入口。

保留测试内部的资产断言作为最终防线。无需再往 `AGENTS.md` 增加一条重复提醒，也不需要为本次已被编译器准确捕获的 `Display` 格式错误新增人工规范。

**完成判据**：缺少前端资产的新工作树在启动后端测试子进程前就得到明确错误；准备完成后仍执行原有完整检查，而不是跳过需要资产的测试。

## 4. 中：语义导航服务遇到确定性不可用时应快速降级

**事实**

首次 `find` 调用因服务返回 HTTP 451、区域不可用而失败。输出记录了 27 次失败 judge 请求、20 个已读文件、约 6.8 秒墙钟时间，最终没有任何候选得到判断。工具明确说明这不是“代码不存在”，代理随后改用本地搜索，没有据此推断缺少实现。

**建议**

在工具层对区域限制等确定性服务拒绝快速终止，并在本次会话缓存不可用状态；后续导航改用可用的本地搜索或已确认身份的代码图。降级输出继续明确区分“搜索未执行成功”和“执行成功但没有命中”。

这应修复工具的能力探测与失败路径，而不是要求每个实现代理重新学习服务不可用的事实。

**完成判据**：确定性拒绝不会继续扇出同类请求；代理能从一次明确返回进入可用导航路径。

## 5. 低：运行说明按角色操作与开发验收分层

**事实**

本票向 `docs/workflow-runtime.md` 增加了完整的 complete/finish 协议、状态准入、错误语义、验证命令、测试函数名、观察窗口和真实宿主复验要求。原文的派发、报告章节已经分别包含验证入口与外部工具证据限制。该文档同时作为运行中的 Chat 需要读取的说明。

**推断**

同一文档正在同时服务管理者、节点执行者、实现者和验收者。各角色并非每次都需要开发验证细节；外部入口未交付、HTTP 不等于原生工具证明等含义分散重复，会增加读取负担和后续维护成本。

**建议**

在运行说明中保留角色操作必需内容：动作准入、交接责任、首次事实与重复语义、部分生效错误、报告和完成的区别。将开发验证命令、测试名称和证据采集细节集中到既有测试指引的 workflow 验证分支，并用“开发验证/真实宿主验收时读取”的条件指针连接。

共同的证据边界保留一个权威说明，各章节只指出其特有差异。此项是信息层级和跨段一致性的判断，适合交给文档审阅者，不适合用机械行数规则代替。

**完成判据**：运行角色可以沿主文完成操作；验收者沿明确指针找到全部证据要求；修改共同限制只需更新一个权威位置。
