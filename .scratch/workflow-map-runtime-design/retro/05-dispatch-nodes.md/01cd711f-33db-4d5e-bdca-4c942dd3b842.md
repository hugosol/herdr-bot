# Ticket 05 的 TDD 执行复盘建议

## 范围与结论

本复盘只依据指定 ticket 执行 session 的 JSONL、其中的工具结果，以及为核对建议而只读查看的仓库测试入口、等待 helper 和检查配置；未读取父 session 或其他执行历史，未继续实现、重跑验收或修改文件。

**已观察事实：**实现提交为 `36607e3`；最终完整后端回归通过，`workflow_dispatch` 为 **7 passed、0 failed、0 ignored**。执行者明确报告真实角色工具与 omp 链路未验证，没有把受控 adapter 的结果声明为原生宿主验收通过。

主要改进机会不是再增加“务必认真测试”的指令，而是：提前暴露跨仓库前提、收紧 TDD 每轮的行为边界，以及让现有检查入口更早、更准确地失败。

## 1. 高优先级：把真实验收前提作为可定位的交付依赖

**事实。**13:31:57，执行者已向 Main 询问外部 toolkit 的交付范围；13:35 收到“只操作当前 worktree、如实报告真实验证缺口”的答复。13:37 实际读取 metadata 指定的 `manager-chat.ts`、`node-chat.ts`，两者均不存在。因此，本轮没有经实际管理者角色工具完成派发，也没有取得真实 omp 的输入、身份、目录与 Workspace 证据。

**推断。**票据的实现依赖与验收依赖没有同时落实到执行环境。将阻塞关系只表达为前置票完成，不能保证另一个仓库中的必需入口已经部署。该缺口不会由增加 HTTP 测试数量补齐。

**建议。**在派发前的环境准备信息中，为此类跨仓库依赖提供一个明确的“真实验收前提”分支，列出：配置引用的实际入口、对应交付归属、可修改仓库边界、隔离宿主的取得方式，以及需要保留的真实证据。路径从现有 metadata 解析，避免另建容易过期的路径清单。执行开始时做只读可用性检查；缺失时继续独立可执行的实现与受控检查，同时立即明确哪些 coverage 尚不能完成，**不新增阻止所有工作的总体验收门禁**。

**完成标准。**下一次同类任务开始时，能够直接判断真实工具入口是否可用、由谁补齐，以及受影响的验收项；不必在实现后半程重新确认权限与交付边界。

## 2. 高优先级：让“已满足”的例外以本轮改动前的基线为准

**事实。**首次测试在 13:33 因节点身份为 `null` 而红；随后一次实现已经加入 readiness、批量派发、状态拒绝、Workspace 不回退、身份检查及多种失败处理。第二个测试到 13:35 才加入，其红点是历史记录为 0 条而不是预期 2 条。身份/指示失败、归属拒绝等多项测试是在上述实现之后加入，并以“这些条件已经满足”为由直接验证通过。

**判断。**本轮确有真实的红→绿证据，但不能据此把后来覆盖的每项行为都归为测试先行。首轮绿的实现边界较宽，后续不少用例实际承担的是回归验证，而非各自的 tracer bullet。它们仍有价值，只是证据类别不同。

**建议。**精确修订现有 TDD skill 的“已满足”例外，而不是增加全局提醒：只有在引入本轮相关实现之前已经存在的行为，才使用“验证既有覆盖”的路径。对本轮刚新增的行为，按当前验收切片写测试并观察红，再补足实现。每轮直接在对话中保留简短的“行为／独立预期／具体违规／红点”说明，无需新建状态文档。

这属于需要语义判断的流程审查，宜由 review 阶段核对测试与实现的时间线；单靠静态 lint 无法判断一个断言是否真的约束了先前实现。

**完成标准。**每个新增行为都能对应先于其相关实现的测试证据；没有红证据的用例明确称为回归覆盖，不用最终全绿替代过程证明。

## 3. 中优先级：将同步屏障的超时变成直接、可诊断的失败

**事实。**`common::wait_until` 超时返回 `false`，本票新增用例多处直接调用 `.await;`，没有消费结果。首次红等待约 5 秒后继续读取记录，最终报的是 `sessionId == null`，而不是“预期节点 prompt 事件未到达”。之后的绿能够证明已运行场景通过，但不能证明屏障超时时诊断仍然准确。

**建议。**这是机械性遗漏，优先用代码级护栏处理，不写成 reviewer 的记忆规则：为必须到达的同步事件提供带事件名称的断言型等待 helper；保留布尔型 helper 给真正需要分支判断的调用。对布尔结果增加可强制执行的未使用结果检查，并由版本化检查入口运行。

同时，让异步场景在请求提前结束时直接呈现 HTTP 状态与响应正文，避免把入口缺失、业务拒绝和屏障未到达都折叠成后续字段断言失败。

**完成标准。**故意让事件不发生时，测试直接报告事件名称和超时；故意让请求提前返回错误时，能够看到真实响应。这里建议的是未来定向检查，本轮未执行该故障注入。

## 4. 中优先级：让完整后端入口在编译前检查静态页面前提

**事实。**第一次 `node scripts/test-backend.mjs` 在约 59.6 秒后因缺少 `backend/static/index.html` 失败，39 个测试二进制未派发；随后前端构建又因未安装 `tsc` 失败。执行 `npm ci`、构建前端后，第二次完整回归用时约 145.2 秒并通过。

已存在 `frontend` 的 build、测试脚本和 npm 网络护栏；后端 runner 则直接开始 Cargo 构建。测试指引列出了完整后端入口，但没有在该入口旁明确表达这次触发的前端产物前提。

**建议。**在现有后端 runner 加入轻量、确定性的前提检查，在 Cargo 编译和测试派发之前发现缺失的交付页面，并指向已有安装／构建说明。若希望提供一键准备入口，应组合既有脚本，而不是复制构建命令或绕开 npm 护栏。文档只补“完整后端含进程级页面检查时”的分支指针，不新增一份环境安装缓存。

**完成标准。**新 worktree 缺少静态产物时快速退出并给出准确修复入口；准备完毕后仍使用原有完整回归流程。

## 5. 中优先级：把已有检查接到可复现的提交／集成护栏

**只读观察。**仓库已有网络策略检查、前端类型检查与后端回归入口；所查的 `.github/workflows`、`.githooks`、`.husky` 中未发现版本化配置。**未验证**本机全局 hooks、外部 CI 或平台分支保护，不能据此断言所有环境都没有护栏。

**建议。**先确认外部集成是否已有等价检查；若没有，将现有检查接入版本化的 Windows CI 或仓库 hook。快速层消费现有网络策略与类型检查，集成层在准备页面产物后运行现有后端回归。等待结果等机械规则也应接入该检查层，而不是继续堆进 `AGENTS.md` 或另写一条“提交前记得运行”的要求。

**完成标准。**漏跑代理手工检查时，提交／集成仍有明确可观察的自动结果；失败能保留日志，安全测试边界与手工授权项保持不变。

## 6. 较低优先级：为导航工具设置能力降级与作用域默认值

**事实。**首次 `find` 的 25 个 judge 请求全部因区域限制返回 451；执行者随后成功切换到本地索引。之后一次宽泛的 graph 搜索返回大量无关 runtime 符号，另一次 `file_pattern: workflow` 返回 `.scratch` 中其他票据和设计材料的条目，收窄到 `backend/src/*run*` 后才得到目标声明。

**建议。**工具层在确认 judge 不可用时提供本 session 的明确降级状态，后续导航直接采用可用的本地索引／字面搜索。为单票据执行默认限制代码搜索目录，排除其他票据；先查目标文件或声明，再展开需要的调用关系。工作树索引名称与根路径宜由宿主随任务提供，减少列举所有项目和宽范围试探。

**完成标准。**相同环境下不再重复触发已知不可用能力；寻找运行实现时直接落到项目源码范围，而不是把其他票据内容带入上下文。

## 值得保留的做法与证据边界

- 通过真实 HTTP TestServer、生产 adapter、独占临时记录和外部受控进程观察行为；混合批次使用明确屏障，而不是任意 sleep 推定执行次序。
- 初始输入使用独立字面预期和互异标记；重复请求联合观察外部调用与持久事实，负向观察明确限定时间窗口。
- 最终报告区分了实现提交、受控检查通过和真实角色链路未验收。这一点应保留，不能因实现轮结束而自动转成全部验收通过。

本轮没有独立 reviewer 的执行历史，因此不评价 reviewer 是否漏检；也没有真实角色链路的失败现场，因此不把缺少验收证据推断为原生宿主行为存在缺陷。
