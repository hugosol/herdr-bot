## 1. 高优先级：把“证据已落盘”纳入浏览器验收的自动完成条件

### 观察事实

最初的页面测试使用 `info.attach` 传入截图及 JSON buffer。相关测试已经通过，但随后查找附件返回空结果；读取 `frontend/test-results` 时，本票对应目录没有证据文件。执行者之后改用 `page.screenshot({ path: info.outputPath(...) })` 和实际 JSON 文件写入，再次运行后才保留了可读取的截图和前后对照。

这是实际发生的 **测试通过但交付证据尚未留存**，不是对 Playwright 所有 reporter 行为的泛化结论。本仓库该轮配置使用 `list` reporter。

截图读取也发生得较晚：已通过测试的桌面页面仍过窄，表格文字被切成多行；看图后才复用宽面板和控件样式、调整链接颜色，并补充移动端检查。最终截图和回归已经更新。

### 建议

在现有浏览器测试设施内提供一个统一的**验收工件**机制：

- 将需要长期留存的截图及 JSON 写入测试输出目录，生成包含文件路径的 manifest。
- 对声明需要工件的用例，结束时确定性检查文件存在且非空；缺工件使验收失败，而不是仅在报告里附一个名称。
- 在 `docs/agents/testing.md` 的页面验收分支集中说明工件约定，并指向可复用的现有实现；不要把完整做法再复制进 AGENTS.md。
- 将可读性留给审查者：首个页面 tracer green 后就查看桌面截图；有窄屏要求时同时查看移动截图。自动文件检查只证明工件存在，不证明视觉质量。

**建议完成条件：**一次通过的页面验收能直接交出实际工件路径；一次故意缺失必需工件的试验会失败；审查记录明确区分“行为断言通过”和“页面可读性已检查”。

## 2. 中优先级：让 TDD 证据按当前 tracer 归属，而不是由一个宽用例的首个失败代表全部标准

### 观察事实

P51.01 与 P52.01 合在一个较宽的浏览器用例中。首次 red 停在“找不到当前 Map 来源说明”，随后一次实现加入了图状态、目录读取和多项节点详情，再得到 green。该 red 证明了来源说明缺失，但没有执行到后面的报告、失败原因、依赖方向或独立选中态断言。

后续确实加强了测试：从只看 SVG 标签和 marker，补到检查真实绘制端点；从仅登记 Chat，补到实际工作中状态及其无障碍在线标记。P57 的三种条件也获得了具体失败证据。**未见针对上述关键图/详情错误的临时 mutation 记录；这不等于断言无效，但不能声称它们逐项经历过 red。**

### 建议

复用 TDD skill 已有的“设计后 red、green 后回看违例”规则，不再追加同义禁令。改进宿主和审查的证据接口：

- 为当前 tracer 保留“验收分区 → 具名违例 → 实际失败位置 → green 结果”的简短映射。
- 区分 setup failure、接口缺失与已触达行为断言的失败。缺少 `tsc` 的第一次失败只能记为环境准备失败；本轮随后建立了真正的列表 red，这个区分值得保留。
- 由审查者核对：首个缺失界面的 red 能支持哪些结论，哪些结论还依赖后续断言和代码检查。对无法通过检查确定敏感性的关键违例，再做定向 mutation；不要求每个断言机械地单独变红。
- 后续 tracer 尽量围绕一个行为推进，保留必要的端到端联合检查，避免为追求“小测试”退回内部 seam。

**建议完成条件：**审查者能指出每个本票分区的独立预期和真正能区分违例的观察，而不是仅看到一个同时带多个 coverage ID 的绿色用例。此判断属于语义审查，不宜用语法 lint 冒充。

## 3. 中优先级：给已有检查入口补执行护栏，而不是再发明一套检查

### 已核实边界

`frontend/package.json` 已有构建、Vitest、浏览器构建验收和浏览器分区检查；npm 测试前也已接入网络护栏，本轮多次实际通过。`build` 包含 TypeScript 检查，但普通 `test` 不包含该检查。

本轮只读检索未找到仓库内的 `.github/workflows`、`.githooks`、`.husky` 或 ESLint 配置；包内也没有 lint 脚本。**这不能证明没有全局 Git hook、外部 CI 或其他平台的受保护检查，它们尚未核实。**因此发现是“仓库内可见的持续执行护栏存在缺口”，而不是“仓库完全没有检查”。

### 建议

先核实外部 CI 和全局 hook 的实际接线；若确实没有，就在仓库中接入已有命令：

- 轻量提交护栏承担已有网络政策检查及适当的类型检查。
- Windows CI 承担现有构建、前端测试、后端入口和浏览器分区检查。
- 涉及图、页面可访问名称或 workflow 导航的改动，在 CI/集成阶段选择相应浏览器回归；不要把需要 Chrome 和宿主夹具的整套测试塞入每次本地提交。

本轮两个后期失败——在线状态实际是带 aria 名称的图片而不是正文、“未接管”文字因列表新增而匹配两处——均由真实浏览器回归捕获。应保证这类现有测试稳定执行，而不是增加一条“注意选择器”的审查口号或指望通用 linter 判断页面语义。

**建议完成条件：**能展示一个提交在既有检查失败时被自动拒绝的记录；若外部 CI 已覆盖，则补清晰入口即可，不建立重复流水线。

## 4. 较低优先级：为 worktree 导航提供准确落点，减少失效检索

### 观察事实

本轮三个 scoped `find` 分别超时 20 秒，随后才通过文件名枚举与已知字面量搜索定位实现。MCP `list_projects` 返回了 50 个项目且仍有下一页，没有直接解决当前 worktree 的定位；之后又出现一次对猜测测试文件名的搜索，返回路径不存在。

**推断：**当前 worktree 到有效索引项目的映射不够直接，导致导航成本上升。不能据此断定当前 worktree 一定没有索引，也不能把所有超时归因于索引。

### 建议

- 由 worktree 初始化或工具层直接提供“当前根目录对应的索引项目及覆盖状态”，优先准确根目录匹配，不默认把全局项目目录倾倒进模型上下文。
- scoped 行为搜索超时后，利用已经获得的模块名称和目录结构转入文件名发现；降低继续执行同类超时查询的概率。
- 在现有测试指引的页面分支加紧凑导航指针：真实服务夹具看 `support.ts`，SVG 绘制检查看 `schedulerGraph.spec.ts`，Run 启动/重启场景看 `workflowStart.spec.ts`。这些是导航目标，不应把文件正文复制成第二套说明。

**建议完成条件：**新 worktree 能以一次准确定位找到项目索引或明确的文件导航后备路径；搜索命中范围不跨入其他票据。

## 5. 较低优先级：检查工具默认输出摘要，把完整清单留作工件

### 观察事实

浏览器分区检查正常通过，结果为 `311 = 278 fast + 33 time-contract`，但默认输出展开了完整 manifests，工具报告共 **7,624 行**，并将中间数千行折叠到 artifact。其运行仅约 5.4 秒，主要浪费在输出和上下文，而不是检查计算。

### 建议

调整现有分区工具的输出契约：默认只显示结果、三组计数、集合关系和详细工件路径；出现差集时展开差异，完整 manifest 通过显式详细模式或文件保留。保持原有集合检查和 npm 网络护栏不变。

**建议完成条件：**成功输出是短摘要，失败输出直接指出不一致项，完整清单仍可追溯。无需在 AGENTS.md 教代理用 shell 截断输出来弥补工具接口。
