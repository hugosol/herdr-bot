**事实**：票据要求实际 manager／当前／旧 Chat Resume 与真实宿主证据。执行中发现 metadata 指定的 `manager-chat.ts`、`node-chat.ts` 均不存在；Herdr 和 omp 可执行文件虽存在，真实角色链路仍未建立。代理向 Main 报告阻塞，继续完成确定性检查，并在交付中保留未验证项。

**推断**：当前派工环境没有在本次启动前确认这些外部交付物。单靠实现阶段阅读验收文字，无法把“可实现”与“可完成真实验收”可靠分开。这不意味着应停止所有可执行工作，而是应提前分开交付状态。

**建议**：由派工宿主提供只读的 **readiness** 检查，从 metadata 解析角色入口，确认路径可读，并列出独占命名 Herdr、配置隔离及资源清理所需前提。检查结果分别记录：

- 确定性实现／契约检查可执行；
- 真实宿主检查可执行或被何项前提阻塞。

路径存在只表示准备条件成立；实际扩展加载、原生身份和导航仍由 S3 验收证明。涉及凭据或隔离宿主配置的缺口交给环境所有者处理，不让实现代理猜测默认实例是否安全。

**落点与完成标准**：派工准备流程及现有测试指引中的真实宿主分支。下一次派工前即可得到带明确缺项的结果，且受控检查通过不会自动使真实宿主分区变绿。无需扩大根 `AGENTS.md`。

## 2. 中高：将现有检查接到仓库级自动触发入口

**事实**：`frontend/package.json` 已有 TypeScript／Vite 构建、Vitest、浏览器构建验收和分区检查；npm 的测试生命周期也已接入网络护栏。本次代理手动执行这些入口并通过。只读检查未找到 `.github/workflows/`、`.husky/`、`.githooks/` 或 `.pre-commit-config.yaml` 中的仓库配置。

**边界**：这只能说明所查仓库位置未发现相关接线；本次未核实机器级 Git hooks、外部 CI 或宿主的集成门禁，不能据此断言整个环境完全没有自动检查。

**建议**：先确认是否已有外部门禁；如无，将已有构建、单元测试和分区检查接到 CI 或提交门禁。浏览器验收安排在具备 Chrome 与 Windows 构建条件的 runner，继续通过 npm 入口保留网络护栏。复用现有脚本，不另写一份同义的检查体系。

**分类**：这是机械检查的接线问题，应由自动化承担，而不是新增“代理记得运行测试”的 reviewer 规则。

**完成标准**：类型错误、单元测试失败或分区不一致会使自动入口失败；检查日志能够追溯实际运行的命令。

## 3. 中：给浏览器夹具补充“重启后重新读取”的明确操作分支

**事实**：新增环境场景先在页面查看 Run，再重启后端并对相同 workflow URL 调用 `page.goto`。随后“未接管”断言失败，页面仍展示旧的“当前后端管理”。代理读取页面快照和 `restart()` helper 后改为 `page.reload()`，场景通过。

另一个准备阶段失败来自夹具 Workspace：zone 名称为 `process-cwd`，受控 Herdr 的默认 Workspace 不匹配，导致启动请求返回 500 而非预期 201。修正 Workspace 样例后才进入后续行为检查。

**推断**：现有测试设施能控制进程和页面，但“进程重启”“浏览器重新请求文档”“按 zone 名称配置 Workspace”之间的依赖没有被一个清晰操作入口承载，容易被误认成产品失败。

**建议**：

- 在现有 `docs/agents/testing.md` 的浏览器重启分支说明：需要观察新后端事实时，显式重新加载文档或执行应用读取动作；相同 hash URL 的导航不能充当重新读取证据。
- 若后续多个用例重复该操作，在现有 support 模块提供窄的重启并重载辅助操作，并以一次新的文档／数据请求作为完成条件。
- Workflow 夹具准备阶段显式建立与 zone 匹配的受控 Workspace；名称从夹具所拥有的路径取得，不从用户环境推测。

保留每个测试独立的预期值，不把生产状态计算搬进夹具，也不为单次失败搭建通用场景框架。

**完成标准**：用例能够区分“后端确实返回旧归属”与“浏览器仍持有旧内容”；Workspace 准备失败在启动行为断言前给出直接诊断。

## 4. 中：修复工具输出的两个具体浪费点

### 语义搜索的不可用降级

**事实**：首次 `find` 的 26 次 judge 请求全部返回区域不可用的 HTTP 451；没有任何候选完成判断。代理随后改用文件名／文字搜索，并为当前 worktree 建立索引。

**建议**：工具层对同一依赖的明确 451 做短路或本会话熔断，返回一次不可用原因与可用替代路径，避免继续发出同类请求。若宿主已知该依赖不可用，应在工具能力发现阶段暴露状态，而不是让实现代理每票重新付出一次失败成本。

### 分区检查的成功输出

**事实**：`check-browser-test-partition.mjs` 已执行完整身份与集合校验，但成功后把三份完整 manifest 都打印到 stdout。本轮组合验证输出达到约 7,800 行，测试汇总被淹没，代理随后额外搜索日志才取回通过数量。

**建议**：保留现有完整校验；默认 stdout 输出计数、结论和产物路径，完整 manifest 写入可保留的结果文件。需要排查时再显式展开 manifest。

**完成标准**：搜索依赖不可用只产生一次明确诊断；成功分区检查在短输出内给出结果，同时仍能定位完整审计数据。这是工具行为改进，不需要增加常驻代理指令。

## 5. 中低：让证据持久化在场景开始时就有固定出口

**事实**：初版场景使用 `info.attach({ body: ... })`。后续代理补上 `saveEvidence`，将 JSON 显式写入 `info.outputPath` 并附加文件；最终又把五个场景的 JSON 与截图从 `test-results` 复制到票据证据目录，一同提交。

**边界**：对话没有证明初版 body attachment 在所有 reporter 下都会丢失，因此不能把“初版一定无法保存”当成已发生缺陷。已发生的是：代理在执行后段额外设计持久化出口并手动整理证据。

**建议**：在现有浏览器支持设施中复用小型证据写入能力，由场景同时保存请求／结果、外部调用、观察窗口起止和截图；宿主按本次测试结果收集实际产物路径。长期文档指向该入口，记录事实的 JSON 留在运行产物中，避免手工复制多个 Playwright 派生目录名。

**完成标准**：默认 reporter 下，成功与失败场景的所需证据都有明确保留位置；无需执行代理在结束阶段重新搜索、拼接目录。证据中继续区分受控 adapter 与真实宿主，不以统一格式抹平证明范围。
