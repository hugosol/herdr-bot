本轮值得保留的做法：发现业务实现已经满足要求后，没有为制造代码变更而重写锁；两个新增测试分别经历了“现有实现通过 → 定向故障注入失败 → 恢复后通过”。其中，旧快照授权故障命中字面拒绝断言，逐目标持锁故障命中完整批次等待断言。最终 `workflow_dispatch` 为 **21/21 通过**；交付同时明确报告全后端存在一项范围外失败、doctest 未执行，以及受控 Herdr 不代表原生宿主能力。

以下建议按优先级排列。标为“推断”的风险不等于本轮已经发生错误验收。

## 1. 高优先级：把后端验收前置条件接到执行入口

**类别：自动化检查。**

**事实：**首次运行 `node scripts/test-backend.mjs --binary-jobs 2`，约 **104.6 秒**后才在 `herdr_config` 暴露缺少 `backend/static/index.html`，并留下 39 个未派发 binary。随后前端 build 又因缺少 `tsc` 失败；执行 `npm ci`、完成前端构建后，才启动第二轮完整后端检查。相关前置要求此前已经通过测试指引进入上下文，因此再增加一句提醒不是主要修复方向。

**建议：**在现有后端 runner 的 Cargo 构建与测试派发之前，增加明确的 **preflight**：检查完整后端验收所需静态产物是否存在，缺失时立即给出已有准备入口及非零结果。若希望自动准备前端，提供显式的准备模式，并把安装、构建、测试分别记录为 stage；避免让测试入口隐式安装依赖。

本轮只证明了“缺失产物”的问题；是否还需要检测产物陈旧，应依据实际构建约定另行决定。

**护栏接线：**仓库已有前端类型检查、网络护栏及后端测试入口。本次未发现 `.github/workflows` 或 `.husky` 的仓库内接线，建议先确认外部 CI／本机 hook，再选择一处持久接入现有检查，而不是新增同义规则。未查看机器级 hook，不能据此断言所有护栏都不存在。

**完成标准：**空白 worktree 缺少静态产物时，在启动 Cargo 和测试子进程前报告准备失败；准备完成后沿用原有测试调度、失败停止派发与进程清理语义。

## 2. 中优先级：区分“请求已发送”与“动作已进入业务排队点”

**类别：并发测试夹具与证据质量。**

**事实：**新增 `OpenJsonRequest.response()` 将请求发送和响应读取分开；测试在 A/B 外部门闩处，以 **200 ms 无响应**观察同 Run 动作等待，并以另一 Run 真正启动、同 Run 查询成功及 SSE 上报可见证明局部独立性。定向故障注入确实使两个测试失败。

**推断：**TCP 写入完成能够证明客户端已经发送请求，但不能单独证明后端已经完成身份解析并到达业务锁等待点。无响应也可能包含尚未调度请求的时间。本轮没有观察到因此造成的假通过，已有 mutation 结果也增强了测试可信度；不过，“不用任意等待推定排队次序”仍可有更直接的证据。

**建议：**为确实需要固定排队位置的竞争场景，提供私有、测试专用的调度事件或门闩，在动作到达业务排队点时确认到达。业务结果继续通过真实 HTTP、外部宿主调用和持久记录断言，不把内部锁状态变成产品接口或主要断言面。200 ms 窗口保留为有界负向观察，而不是到达确认的替代品。

**完成标准：**先观察到动作到达排队点，再释放前置宿主门闩；完整批次、逐目标持锁、旧快照授权三种情形仍能被独立区分。

## 3. 中优先级：给 workflow 验收提供窄而准确的导航指针

**类别：导航与工具经济性。**

**事实：**早期探索出现了 `src;tests` 路径不存在、使用其他语言常见锁符号无匹配，以及 `serial` 命中大量 `Serialize` 的噪声。一次 `find` 因区域 HTTP 451 导致全部 27 个 judge 请求失败。随后还枚举了 52 个索引项目，才为当前 worktree 建立索引。之后使用声明大纲、现有 `Scenario` 与宿主门闩例子，探索才明显收窄。

另一个可避免的入口误判是尝试 `GET /api/sessions` 得到 404；读取实际路由后改用已有 SSE helper，测试才到达目标行为。这次 404 是夹具／入口错误，不是业务红灯。

**建议：**在现有测试指引中增加一个按分支触发的导航指针，例如“验证 workflow 并发时，先定位 `workflow_dispatch` 场景、外部宿主门闩和 SSE 客户端”。正文只解释各入口证明什么，不缓存完整路由表或锁符号清单。为临时 worktree 提供按当前根路径解析索引项目的能力，避免每次先全量列出其他项目；语义 finder 不可用时，一次说明后进入可用的结构／字面搜索路径。

**完成标准：**新执行者能够从票据直接到达现有场景和公共观察 helper；无需先猜源码布局、接口路径或枚举无关索引项目。

## 4. 中低优先级：把验收结果做成按目标查询的稳定摘要

**类别：工具经济性与信息访问。**

**事实：**读取全量结果时，先猜测 `binary-053.stdout.log`，实际读到的是 `zone_commit`；随后按错误层级查询 `summary.json` 得到空字段，再读取整个约 50 KB 的摘要。最终通过 `.targets[]` 按 `workflow_dispatch` 名称筛选，才准确找到 `binary-050.stdout.log`，并统计出 60 个通过、1 个失败。

**建议：**保留现有 JSON 为唯一事实来源，在 runner 完成输出中直接列出失败目标及日志路径，并提供按目标名称查询摘要的轻量入口。摘要应区分 build、binary、未派发和 doctest，避免调用者把阶段缺失解释为通过。该能力属于现有 runner 的结果呈现，不需要新建一份人工维护的验证台账。

**完成标准：**一次目标名称查询即可得到 `workflow_dispatch` 的状态、日志位置及全局未完成阶段，无需猜 binary 序号或展开整个摘要。

## 5. 低优先级：将运行角色指引与开发验证参考分层

**类别：面向 agent 的文档层级。**

**事实：**本轮读取的 `docs/workflow-runtime.md` 原本约 33.6 KB，既承载传给角色 Chat 的运行说明，也包含多段开发测试命令、coverage ID 与证据边界。本票又增加了测试方法和复验说明；正文中的并发语义本身有价值，但运行角色与开发验证者需要的内容并不相同。

**建议：**保留角色每次决策都需要的业务语义：pause 等完整批次、旧 ready 不构成授权、查询可能看到已提交中间事实、既有 Chat 与业务写入排队的区别。把开发测试名称、coverage 映射、mutation 说明及完整复验配方放到按“验证并发／定位验收失败”触发的参考段或独立参考文档，并由运行说明使用一个精确指针到达。命令与规则各保留一个权威位置，减少多处同步。

**完成标准：**角色读取运行说明即可决定下一步动作；验证者沿一个指针取得测试配方；调整测试入口只需修改一处。拆分应按读者分支发生，而不是单纯按篇幅平均切文件。
