以下建议按严重度排序。

## 1. 高：把真实验收前置条件纳入执行环境的就绪检查

**事实**

- 任务开始即要求真实 retry、新旧原生 Chat、实际 trigger config 与角色工具证据。
- `15:35:57` 已从 metadata 找到 manager-chat/node-chat 的绝对入口，但直到 `15:40:24` 才实际检查存在性；两个路径均返回 `Path not found`。
- 到此时已完成多轮后端 red→green。最终真实 S3 证据仍未取得，agent 正确地向 Main 报告了阻塞，没有用受控身份冒充原生验收。

**建议**

在宿主派发需要真实角色工具的票据时，先运行一个**只读的验收前置检查**：从现有 metadata 解析所需入口，报告部署位置与可用性，并指出哪些验收项仍需要隔离宿主和真实调用。复用既有入口校验能力，不另建一份路径清单，也不把“文件存在”升级为“扩展可运行”。

就绪结果分别表示“后端实现可执行”和“真实宿主验收可执行”。缺少后者时仍允许完成确定性实现，但交付中持续保留对应未验证项及其接手条件；不新增替身入口来消除阻塞。

**完成标准**：执行首个测试前，运行记录已列出本票真实验收的缺失条件；补齐入口后，仍须以实际角色工具调用和原生身份/输入证据解除阻塞。

## 2. 中高：让权限负向测试只改变权限这一项条件

**事实**

`late_old_reports_remain_history_without_controlling_new_execution` 对旧身份调用 `fail`、`retry` 使用同一份 `retry_body()`，并接受 `400 || 403`。其中 `fail` 请求带有不属于该动作的 `confirmed` 字段，而现有接口采用 `deny_unknown_fields`。

**推断**：这个 `fail` 分支可以仅因请求格式非法而通过，未必执行到旧身份权限检查。它不能独立证明旧执行无权 fail 当前执行。其他测试对 retry、complete 的明确 403 断言仍有价值，不能据此认定权限实现存在缺陷。

**建议**

复用真实 HTTP seam，为每个动作构造格式合法的请求；权限用例只替换身份，并断言该权限分支的确定状态码或错误代码。把未知字段检查留在独立的参数校验用例中。

这是**测试语义判断**，不是可靠的通用语法规则。宜由 reviewer 的测试证据审阅承担：检查每个负向场景是否到达它声称约束的条件，而不是在全局指令增加“禁止所有 `400 || 403`”之类机械禁令。新增或修正的回归仍通过仓库已有 `workflow_dispatch` 测试目标及 `node scripts/test-backend.mjs` 执行，不需要另一套检查入口。

**完成标准**：若临时移除旧身份权限限制，格式合法的负向请求能使测试失败；仅保留未知字段校验不能让该权限测试通过。

## 3. 中：让异步测试门失败时报告真正的前置原因

**事实**

首个 tracer red 等待外部 `agent_prompt` 调用达到预期次数，随后读取保存的状态。实际 red 在约 5 秒后表现为 `retry-old != retry-new`。该时点路由尚未接线，但测试没有先报告 HTTP 请求结果或等待条件未满足，而是在后续状态断言才失败。

这可以作为接口尚不存在时的初始 red，却不是“新关联保存屏障已被测试击穿”的独立证据。

**建议**

在现有测试夹具中，让门等待具有可检查的完成结果：条件达成才继续；到期则返回明确失败，附已观察的宿主调用。对于并发 HTTP 请求，同时关注请求是否提前结束，以便区分接口拒绝、宿主门未到达与真正的落盘顺序错误。

优先补充这个测试基础设施的确定性回归，例如条件恒为 false 时必须报告超时，而不是给每个测试增加一段新的等待纪律。它属于测试工具改进，不是新增业务观察 seam。

**完成标准**：缺失路由时显示请求提前结束；门未到达时显示门等待失败；只有门确实到达后，状态断言才承担启动顺序的证明责任。交付中的 red 记录也相应区分“接口初始 red”和“目标行为 red”。

## 5. 中低：批量编辑只输出有界结果，保留完整详情供按需读取

**事实**

`15:37:58` 的 Eval 对每个 edit 返回值直接 `console.log`，输出包含多次完整 `oldText/newText`，记录长度约 49,571 字符，并触发 50KB 展示截断。末段同类编辑改为只打印 `r.text`，输出约 2,593 字符。

这是已观察到的上下文膨胀，不需要靠推测来论证。另一次临时 Eval 有语法错误，但随即修正；单次语法失误不值得新增永久规范。

**建议**

把工具调用的呈现层默认收敛到状态、文件位置与精简 diff；完整对象留在 artifact 或按需诊断中。Eval 编排成功时打印简要字段，失败时保留可操作的错误信息。若工具封装可以统一这一行为，优先在封装中解决，而不是给每个实现 agent 再加载一段说明。

**完成标准**：连续编辑不会重复输出整文件的前后内容，失败信息仍完整可取；小幅修改的可见输出规模随修改量而非文件总长增长。

## 6. 低：把运行指引与验收证据清单按分支披露

**事实**

**推断**：运行中的角色需要动作职责和错误处理，不一定需要测试函数清单；把两类内容放在同一路径，增加后续角色阅读时的注意力负担和重命名维护成本。本会话没有真实 Prompt/模型阅读证据，不能声称已发生指令遗漏。

**建议**

运行说明保留 retry 的职责、准入、结果解释、报告适用性及恢复路径；确定性验收清单归入已有测试指引中，并用“retry 验收”这一明确分支指针到达。测试命令与函数枚举尽量由现有脚本、测试源码承担，文档主要留下源码不能直接表达的证明边界和真实宿主取证要求。

让每项语义有一个权威位置：其他章节通过指针引用，而不是反复完整陈述。无需为这一个 ticket 再创建一份只有重复信息的新文档。

**完成标准**：角色完成 retry 处置所需材料在同一处可读；验证者沿一个明确指针获得取证要求；测试重命名不再要求同步维护多处运行期说明。
