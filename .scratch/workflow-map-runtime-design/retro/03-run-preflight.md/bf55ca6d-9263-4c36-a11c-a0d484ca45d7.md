## 1. 较高：为同一 worktree 的构建和运行检查建立资源租约与源码快照归属

**事实：**12:28:09 启动完整后端检查并转入后台；12:30:02 又修改了后端字段可见性；12:30:52 在后端检查尚未结束时启动浏览器构建。后者无法替换正在使用的 `backend/target/debug/herdr-bot.exe`，报 Windows `os error 5`。后端任务结束后，浏览器完整构建及检查成功。

**判断：**这次不是产品逻辑故障，而是验证入口之间缺少共同的生命周期协调。期间源码继续变化，也使较早启动的后端回归不能精确归属最终源码快照。该次后端编辑只是可见性调整，日志不足以证明由此产生了行为回归。

**建议：**在现有检查入口实现按 worktree／产物目录划分的资源租约：构建替换二进制与运行该二进制的检查互斥，租约持续到所属子进程退出。检查开始时记录源码内容指纹，结束时若输入发生变化，将结果标记为“源码已变化”，而不是直接作为最终快照的验收结果。独立 worktree 之间仍可并行，不需要全局串行化。

**完成标准：**同时启动这两个现有入口时，后启动者明确等待或给出可操作的资源占用信息；没有覆盖运行中 exe 的尝试，也不终止非所属进程。每份最终结果均能对应其实际检查的源码快照。

**放置位置：**优先改进 `scripts/test-backend.mjs` 与浏览器构建／进程入口的协调机制。现有测试指引只需指出租约规则，不向全局 `AGENTS.md` 再叠加一组“不要并行”的禁令。

## 2. 中等：把有效红灯的证据粒度缩到当前行为机制

**事实：**整图绑定检查采用一个包含多种场景的测试。红灯运行在第一个 `bot-missing` 场景收到 200 后即停止；随后一次加入了 Task 缺失、角色、agent、zone 等多类校验，再运行矩阵全部通过。相比之下，后补的“缺失 Task 返回原 Bot 绑定”经历了清晰的单行为红灯，再添加对应按钮并通过。

**判断：**最终矩阵确实执行并通过了各场景，但第一次红灯只直接证明了首个场景的失败，不能作为所有后续校验分支各自的敏感性证据。这是 TDD 步长偏大，不等于其他测试无效。注销／重登记用例则属于已经满足的行为；执行者没有为了制造红灯而破坏实现，这一点应保留。

**建议：**将矩阵组织成可按行为机制独立选择的参数化用例。开发时只运行当前机制的一个区分性场景，完成 red → 最小实现 → green 后再推进下一机制；完整矩阵作为回归集合。让 TDD 宿主将当前用例、预期违例、实际失败断言及后续 green 结果关联保存，避免仅凭“整项曾经失败”判断循环完成。

**完成标准：**新增角色、agent 或目录有效性检查时，记录可以指出哪个具体场景在实现前因该行为缺失而失败。依赖未安装、接口用错、locator 歧义等失败单独归类为准备／夹具问题，不计作业务红灯。

**放置位置：**测试组织方式和 TDD 宿主的证据关联能力。现有 TDD 指导已经明确要求单片循环，无需再写一份同义规则，也不应改成先批量写完全部红灯的水平切片。

## 3. 中等：补齐浏览器测试的静态检查范围，并把现有检查接入版本化护栏

**事实：**现有 `build` 运行 `tsc --noEmit && vite build`；`pretest*` 已接入网络策略检查，不能说仓库没有任何自动护栏。本轮只读查看发现，`frontend/tsconfig.json` 的 `include` 覆盖 `src`、`tests` 和相关配置文件，**没有覆盖 `browser-tests`**。标准位置中未发现版本化的 `.github/workflows` 或 `.husky` 文件。

**限制：**没有核实外部 CI、全局 hooks 或自定义 `core.hooksPath`，因此不能断言完全不存在提交护栏；也没有运行浏览器测试的类型检查，不能声称本票存在已经确认的 TypeScript 编译错误。

**建议：**复用现有 TypeScript 依赖，为 `browser-tests` 建立明确的类型检查入口，再接入仓库采用的 CI 或提交护栏。保留现有 npm 网络策略 hook，不直接绕过 npm 调用测试工具。若外部 CI 已存在，应先补接其漏掉的范围，而不是另建一套重复流水线。

**完成标准：**浏览器测试或公共 helper 中的类型错误能在启动真实服务之前被确定性拒绝；提交护栏使用可从仓库追溯的检查入口。完整运行检查应遵守上一项资源租约。

## 4. 较低：为缺失页面入口提供更短的动作失败预算

**事实：**第一次页面红灯直接点击不存在的“+ 发起 Run”，消耗了完整 **90 秒用例超时**。已有 `expect` 预算为 10 秒；后续缺失 Bot 修正按钮的检查先断言可见性，约 12 秒便返回了明确失败。另一次失败来自两个 node 引用同一 Task，修正按钮重复；执行者最终按 `node B` 的列表项限定目标，而不是用任意第一个匹配掩盖歧义。

**建议：**在现有 Playwright 配置中区分普通控件动作预算与长链路用例预算，普通动作使用较短、明确的等待时间；真正需要长等待的操作在局部显式说明。重复业务实体继续按所属 node／区域定位，不为消除 strict-mode 错误统一追加 `.first()`。

**完成标准：**缺失普通按钮无需耗尽整项 90 秒预算；等待真实长链路的既有场景仍保有其独立预算。该调整应由运行结果验证，不机械压缩所有超时。

**放置位置：**Playwright 配置及既有浏览器测试约定，不需要新增 reviewer 禁令或全局代理指令。

## 5. 较低：在语义搜索工具内部对不可用 provider 快速熔断

**事实：**首次 `find` 在一次调用内发出 26 个判断请求，全部因地区限制返回 HTTP 451，耗时约 5.1 秒，未产生可用判断。工具明确报告“不是不存在的证据”；执行者随后转用文件名／符号搜索和本 worktree 的图索引，没有反复重试该服务。

**建议：**在工具或 provider 适配层把明确的地区／能力不可用响应作为快速熔断条件，避免同一次搜索继续派发同类请求，并返回可用的结构化替代路径。保留执行者本次正确的降级行为。

**完成标准：**一次确定性的 provider 不可用响应即可结束该轮同源判断派发；输出仍清楚区分“搜索不可用”和“没有匹配”。不需要在每个项目的 `AGENTS.md` 缓存一次外部服务故障。
