# Ticket 23：TDD 执行复盘建议

## 复盘范围与结论

本次只复盘指定 ticket 执行记录 `23-durable-documentationmd-158e44df-dcd8-4ed3-83.jsonl`，截至实现轮提交与交接；未读取父 session 或其他票据执行历史。另只读查看了交付的文档检查脚本、现有 `frontend/package.json` 及仓库内可见的自动化入口，用于判断建议是否已有实现。本轮未修改文件、执行建议或重跑验收。

**已观察到的正向结果：**实现轮按批准的 P66 非运行 seam 进行文档审查，没有运行无关产品测试；最终文档检查返回 15 份 Markdown、154 个本地链接、零错误。隔离副本移除临时材料后检查成功，三个副本分别注入坏文件链接、缺失锚点、临时依赖后均明确失败，副本随后清理。提交 `60b1928` 的结果有工具输出支持。交接也明确区分了本票文档完成、上游真实 Agent 验证缺失及 H1/H2 未确认。

以下按影响程度列出环境改进候选。事实、推断和未验证项分别标注；不把改进建议倒推为本票验收失败。

## 1. 高：让依赖放行使用“证据完成”，而不是仅使用 integrated

**事实。**票据要求 21、22 完整完成后收口；执行者开场就向 Main 查询依赖完成证据。Main 后续明确说明：二者已工作流 integrated，但真实角色演练因外部 `manager-chat.ts`、`node-chat.ts` 未部署而未验证，并要求完成可达文档、如实保留缺口。最终交接仍需说明：若关闭票据以完整真实验收为前提，则不能据本次成功调用宣布全功能通过。

**推断。**工作流集成状态与契约证据完成状态没有在派发入口充分区分，迫使实施者重新解释依赖门槛。文档工作可以继续，与后续验收能否放行，是两项不同决定；仅显示 ready/integrated 容易把这两者合并。

**建议。**在派发环境中提供精简的、只读的依赖摘要，至少区分：

- 已交付或集成的产物；
- Agent 指定验证及其证据路径、缺失前提；
- 用户最终判断及其确认状态。

允许“可达工作继续”时，把授权边界写在当前 ticket 的派发信息中；依赖放行仍使用所需证据是否齐备的条件。这样无需实施者读取其他票据，也不会让每次执行都向 Main 重问。

**完成标准。**同样遇到“已集成、真实环境未验证”时，执行者能直接判断当前可做范围与关闭条件；后续人工验收不会把缺失的 Agent 验证理解成仅待用户确认。此建议改进调度信息，不增加产品功能或人工例外。

## 2. 中：把已交付的文档检查接入自动化，并保留负例回归

**事实。**`scripts/check-workflow-docs.mjs` 已能检查文件、锚点及临时导航依赖；本轮实际运行成功，三个故障注入也证明了对应检测能力。故障注入由临时 Python/Eval 程序执行，没有作为独立可重复测试文件提交。

只读查看现有入口发现：`frontend/package.json` 已通过 npm pretest 系列接入网络护栏，但没有文档检查入口；本轮查看的脚本入口中也未发现该检查的调用。仓库路径查询未发现 `.github`、`.husky` 或 `.pre-commit-config.yaml`。**这不证明机器级 Git hook 或外部 CI 不存在**，这些不在已核实范围内。

**建议。**复用现有 Node 工具体系，为文档检查保留小型 `node:test` 回归，覆盖本轮已经验证的成功副本、坏文件、坏锚点和临时依赖；再把检查接入现有交付检查，或增加仅在相关文档/脚本变更时执行的 CI 门。若项目确实没有仓库级 CI/hook，应先补上最小自动检查入口，而不是再写一条“提交前记得检查”的代理指令。

**完成标准。**后续修改无需重构临时 Eval 场景，就能重复这些负例；破坏检查器检测能力或引入失效链接时，标准交付入口返回非零。语义完整性仍由批准的文档审查负责，不扩张成关键词测试。

## 3. 中：为非运行 seam 提供明确的 TDD 分支，保留语义审查的可复核差异

**事实。**首次 red 是新脚本检查到尚不存在的 `docs/workflow-contract.md`，返回 `ENOENT`。补齐文档后 green；后续故障注入针对链接与依赖有效性，而非需求语义。长期契约中提供了逐项规则索引、内容复审步骤和缺口修复总结，并明确机械检查不能替代内容审查。

**判断。**这符合本票不运行无关产品测试的边界；缺文件的 red 只能证明交付物缺席，不能证明“恢复原执行与另起执行混淆”等语义缺口能被发现。历史中没有逐条展示所有规则审查前后的具体差异，因此不能仅凭链接 green 独立复核所有语义审查结论；也不能据此断言审查未执行。

**建议。**在 TDD 工作流中为已批准的非运行审查增加一个短分支：

1. **基准**：列当前规则的独立要求及一个具体违规。
2. **发现**：指向原文缺失或冲突的段落，说明读者会如何误解。
3. **修复**：指向长期文档的权威落点。
4. **结论**：记录已解决、原本满足或仍受外部前提限制。

将这些证据保存在交接/审查记录中，长期正文只保留产品规则与必要的复验说明。已有满足项直接核对，不为凑 red 先人为制造缺失；也不要求通过模型或关键词测试替代批准的 Agent 内容审查。

**完成标准。**独立审查者能从少量明确的“要求—原文—修复”证据判断本票修复了什么，并能区分机械 green、语义审查与未验证的外部行为。

## 4. 中低：按读者分支组织长期材料，避免完整性收口变成重复和沉积

**事实。**执行开始时 `docs/workflow-runtime.md` 已约 93.9 KB。此次新增约 27 KB 的长期契约，包含职责、关键取舍及 P1–P70 索引；又在运行说明“发起与观察”之前加入公开接口和持久字段参考。已有运行说明同时包含操作步骤、协议、测试入口、历史部署结果和证据限制。

**推断。**这些内容各自有用途，但面向用户、角色 Agent、接入维护者和验证者的分支混在同一阅读路径中。部分规则在职责表、关键取舍、承诺摘要及运行章节多次表达，后续变更容易产生多个事实副本；常用操作也可能被维护参考挤到后面。没有实际 Agent 使用对照，故这里是可维护性风险，不是已观察到的使用失败。

**建议。**由文档审查阶段确定权威分工：

- 长期契约保存需求、不变量、排除项和稳定承诺索引；索引主要负责定位。
- 运行指南优先呈现角色职责、操作顺序、错误分支和完成条件。
- 接入字段/HTTP 参考通过“接入或变更协议时读取”的指针披露。
- 历史执行结果保存在可追溯的证据材料，指南保留复验入口和解释结果的方法。

先消除重复语义、强化现有指针，再判断是否需要拆文件；无需立即增加一组新文档。对必须重复提示的安全边界，保留简短提醒并链接权威规则。

**完成标准。**维护一个行为时只有一个权威规则需要修改；角色 Agent 沿自身分支即可取得所需步骤和错误解释，接入维护者仍可直接找到完整字段契约。该类跨文档判断交给 reviewer，比增加实施者的常驻指令更合适。

## 5. 低：改进搜索失败回退和索引定位，减少无关结果进入上下文

**事实。**一次行为发现调用因全部候选判断返回 HTTP 451 而失败；执行者正确上报工具问题并改用其他搜索。随后读取了 MCP 搜索/片段接口说明与项目列表。项目列表实际返回前 30 项、总数 58、`has_more=true`；历史未见继续分页便转入本地 grep。一次在整个 `backend/src` 搜索通用序列化标记的调用返回了许多与 workflow 无关的模块。

**建议。**优先在工具层提供“按当前 worktree 根精确解析索引项目”的能力，并在依赖的判断服务不可用时明确返回可用的确定性回退。拿到 workflow 路由或源文件位置后，将后续字面搜索限定到已定位文件；通用序列化标记不作为全源码入口。若仍使用分页项目列表，应消费到找到精确根，或明确记录索引状态未确定，而不是把首屏缺席当作不存在。

**完成标准。**同类文档接口核对能直接定位当前源码与响应定义；服务不可用只触发一次清晰回退，不产生无关项目列表和多模块结果。未验证精确根解析工具是否已在其他环境存在，建议实施前先检查现有能力。

## 建议保留的执行习惯

- 保留文档审查、确定性 HTTP/文件证据、真实宿主证据和用户判断的明确分层。
- 保留隔离副本验证及有针对性的负例，避免删除真实临时材料来证明独立性。
- 保留针对共享文档的编辑范围协调，以及明确文件列表提交后交给独立集成者的方式。
- 不因本次顺利交付而删去“真实环境缺失仍未验证”的事实；也不把这些事实变成需要每轮完整重读的常驻指令。

**优先顺序：**先消除依赖完成状态的歧义，再把已经有效的文档检查变成自动回归；随后改善非运行 seam 的审查证据与文档分层，最后优化发现工具的定位与回退。
