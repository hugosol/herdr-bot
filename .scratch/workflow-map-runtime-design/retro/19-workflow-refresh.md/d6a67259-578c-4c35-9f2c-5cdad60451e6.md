## 1. 高优先级：为原生可见性验收建立明确导航，先验证夹具能力

**事实**

- 隐藏场景经历了五次 `Expected: "hidden" / Received: "visible"` 的失败，另有一次 `test.use({ headless })` 放在 `describe` 中导致收集失败。
- 期间依次尝试最小化、有头模式、切换页面、关闭焦点模拟及组合操作。直到检查已安装 Playwright 的实现与公开类型，才找到默认焦点覆盖及 `connectOverCDP(..., { noDefaults: true })` 的入口。
- 最终新增 `workflowVisibility.ts`，使用独占 Chrome profile、动态回环端口和原生窗口生命周期，检查通过；移除产品中的可见性判断后，该检查确实失败。
- 通用 `docs/agents/testing.md` 尚无原生可见性分支的导航；相关说明落在业务运行文档中。

证据：原会话 L337、L353、L375、L397、L419、L456 的失败结果，L426–L432 的驱动实现/API 查询，以及 L514 的故障注入结果。

**推断**

主要绕路来自测试环境覆盖了待观察的浏览器条件，而不是轮询实现本身。未来 agent 若只读通用测试入口，仍可能重复这条试错路径。

**建议**

在现有测试指引的浏览器部分增加一个仅在“文档可见性、后台节奏或原生窗口生命周期验收”时触发的短指针，直接指向已交付的原生浏览器 helper 和对应契约场景。将自动化覆盖的原因、隔离与清理要求放在该分支附近，不扩充全局 `AGENTS.md`。

该分支先以夹具门槛结束：**实际文档能够在 hidden 与 visible 之间切换，且没有冻结 JavaScript 定时器**；随后才进入轮询断言。保留本次故障注入的敏感性要求，避免“浏览器自己停表”造成假通过。

**完成标准**：后续同类验收能从通用测试指引直接找到已有入口，无需重新搜索 Playwright 内部；夹具不满足门槛时，报告环境失败，而不是产品行为红灯。

## 2. 中高优先级：让异步验证结果绑定其实际执行的源码版本

**事实**

- 原会话在启动可见性检查后，继续修改同一个 `workflowRefresh.spec.ts`：增加 Map 夹具、图断言等。
- 随后失败仍是 hidden/visible 断言，但输出代码框已将箭头指向 `const cover = await context.newPage()`；另一次甚至指向注释。执行时的位置与报告时读取的文件内容发生错位。
- 最终统一回归通过，未观察到因此造成错误交付。

证据：L404 启动检查，L407–L416 修改相同 spec，L419 返回错位代码框；L456 再次出现错位。

**推断**

这种错位会增加诊断成本，也会削弱 red、故障注入与源码之间的可追溯性。不能据此否定最终绿灯，但它使中间证据更难解释。

**建议**

优先在验证宿主或任务调度层记录执行输入：命令、相关源码/测试文件哈希、构建标识及结果目录。对在途验证涉及的文件建立写入冲突提示；agent 可以继续修改不相交文件，而相交修改应等待该轮结果，或明确将旧结果标为旧版本证据。

这是可机械检查的证据归属问题，适合宿主或验证包装器，不宜靠 reviewer 的风格规则维持。

**完成标准**：每次 red/green 能定位到执行版本；如果在途输入发生变化，结果明确标注版本差异，失败代码框仍能还原到执行时的源码。

## 3. 中优先级：把已有快速检查接入持续守卫，补齐浏览器测试的静态覆盖

**事实**

- 仓库已有 `build` 中的 TypeScript 检查、Playwright 收集/分区检查和 npm 生命周期网络护栏，不需要再发明同类检查。
- 本次错误的分组内 `test.use({ headless })` 已能由 Playwright 收集阶段发现，属于现有检查可捕获的机械错误。
- 当前 `tsconfig.json` 的 `include` 不包含 `browser-tests`，因此普通前端 build 的类型检查不覆盖本票新增的浏览器测试及 helper。
- 本轮只读查看未发现 `.github`、`.githooks` 或 `.husky` 目录，`package.json` 也没有 lint 脚本。已有自动网络护栏，但未见仓库内持续执行类型检查和测试收集的 CI/提交守卫。

**未验证项**

未检查仓库外部流水线或全局 Git hook，因此不能断言项目完全没有外部守卫；也未观察到本票最终留下浏览器测试类型错误。

**建议**

先确认外部守卫是否已覆盖这些入口；若没有，优先接入现有前端 build/typecheck 和浏览器收集/分区检查。为浏览器测试增加独立、适配其 Node/Playwright 环境的类型检查入口，避免业务前端 build 通过被误认为所有 TypeScript 均已检查。

此处属于确定性检查覆盖，采用检查配置和 CI/hook，而不是新增 `CODING_STANDARDS.md` 禁令。真实浏览器时序与原生窗口能力仍由已有交付页面检查负责，静态检查不替代它们。

**完成标准**：浏览器测试中的类型错误、收集错误能在启动 Chrome 和服务之前被自动阻断；已有网络护栏继续生效。

## 4. 中低优先级：将工具默认输出改为摘要，完整证据保留为按需读取的产物

**事实**

- `test:browser:partition` 成功时打印 full、fast、time 三套完整清单；本次输出达到 7,736 行，并产生约 188KB 的中段截断。实际即时判断所需的是检查通过、集合计数以及异常项。
- 读取脚本确认：它确实检查完整身份与集合关系，但将全部清单输出到 stdout，临时收集目录随后删除。
- 起始 `find` 调用还遇到地区限制：25 个判断请求全部失败，错误均为 HTTP 451。agent 正确改用其他搜索，没有将失败解释为代码不存在。

证据：原会话 L551 的分区结果及 `scripts/check-browser-test-partition.mjs` 的报告逻辑；L80 的检索失败结果。

**建议**

- 分区工具继续校验完整清单，默认 stdout 只报告通过状态、计数、异常摘要和产物路径；完整清单持久保存，提供显式详细输出选项。这样保留审计能力，而不是删减检查。
- 检索工具遇到相同凭据/模型组合的确定性地区拒绝时，应快速停止该轮扇出并返回可用回退入口；不必让全部候选请求重复得到同一拒绝。

这些是工具输出和能力探测的改进，不应转化为常驻上下文中的“少看输出”提醒。

**完成标准**：正常检查用短摘要即可判定结果，完整身份清单仍可读取；不可用的检索后端能明确、快速失败并保留原因。
