# Ticket 22 TDD 执行复盘建议

## 范围与结论

本复盘仅依据指定 ticket 的执行 JSONL、其中的工具返回及本轮可见的同票对话；未读取父 session 或其他票据的执行历史，也未重跑验收。

**事实**：本轮提交 `0415bcf`，交付故障指南、角色责任矩阵及证据文件。现有 `workflow_dispatch` 测试运行结果为 **53 passed、0 failed、0 ignored**。真实角色入口的前置检查返回两个 `isFile=false`，退出码 **2**；P64/P65 所需的真实界面处置和实际 Prompt 注入没有执行，最终交接明确保留了这些缺口。

本轮没有新增行为测试，也没有发生新的 red → green 循环。**不能据此认定 TDD 失败**：既有后端约束已有测试，真实 S1/S3 前提缺失时，制造关键词测试或受控模型演练反而会削弱验收标准。主要改进点在于环境就绪判定、交接协议和证据工具，而不是再要求实现 Agent“更努力测试”。

## 1. 高优先级：为真实验收票增加部署就绪门槛

**事实**：票据标为 `ready-for-agent`，但其验收明确要求真实 manager/node 角色工具与实际注入。执行时发现 metadata 指定的 `manager-chat.ts`、`node-chat.ts` 均未部署；目录中仅有 `codebase-tools.ts`、`connect-bot.ts`。Agent 完成仓库与文档探索后，才执行带退出码的部署前置检查。最终可交付指南改进，却无法完成票据核心实演。

**推断**：当前“可派发”信号未充分区分代码依赖满足与真实验收环境可用。即使依赖票已经交付本仓库部分，也不能据此推导外仓角色部署、独占 Herdr 或模型访问已经可用。

**建议**：在调度层为需要真实宿主的票增加可检查的 admission gate，并与实现状态分开保存：

- 先执行廉价前置检查，记录实际 metadata、入口存在性和检查时间。
- 真实实演另需角色加载、公共 Prompt、独占宿主和模型访问证据；入口文件存在只代表第一层通过。
- 缺少前提时允许继续独立可交付的文档工作，但将真实实演保留为环境阻塞；只有部署证据发生变化后才重试实演。

这是适合自动检查的机械条件，不应只在全局 `AGENTS.md` 增加一条“先检查环境”。本轮没有证据证明角色加载或 Herdr 隔离实际可用，建议也不应替它们补写通过结论。

## 2. 中优先级：让交接协议准确表达“已提交但验收受阻”

**事实**：实现轮最终 `yield` 的实际参数只有 `error`，没有执行指令要求的数字 `key`；工具仍接受调用并返回 `Task aborted`。与此同时，交接正文包含有效提交、通过的后端检查和未完成的真实验收。

**推断**：仅靠自然语言约束完成参数，以及将这类交接统一显示为 aborted，容易让下游混淆“没有交付”“有交付但环境阻塞”和“promise 已通过”。是否已经造成调度误判，本票历史不能证明。

**建议**：由宿主工具 schema 校验必需的 item key，并在调度结果中分开记录：

1. 交付物与提交引用；
2. 已执行检查及其结论范围；
3. 外部阻塞与重新执行条件；
4. promise 是否通过。

缺失必需字段应在工具边界明确报错，不依赖长篇代理指令补救。有效提交与未通过验收可以同时成立，二者不应互相覆盖。

## 3. 中优先级：让验证入口直接产出可保存的完整证据

**事实**：后端测试已经结束后，Agent 为保存约 **423KB** 的输出进行了五次 Eval 调用：无界 raw 读取被拒绝；一次有界读取又被 120KB 限制截断；分块循环在第 221 行附近再次触发截断；随后改为逐行读取，并补回分块边界的换行。最终证据也如实说明，该日志不是原生进程输出的逐字节副本。

**建议**：优先复用已有验证入口的日志能力，让测试进程在执行时同时持续输出并保存完整日志，结束后返回日志路径、退出码和摘要；目标是“进程结束即已有完整证据”，而不是由模型重组阅读器输出。

历史中读取过的 `docs/agents/testing.md` 已说明 `scripts/test-backend.mjs` 会生成目标日志及 `summary.json`。因此，应先评估复用其既有记录机制；若定向 Cargo 开发反馈仍需要单独入口，只补齐捕获与交接能力，不新建第二套业务测试系统。

**完成标准建议**：成功、失败和取消均有退出结果；完整日志的保存不受对话展示截断影响；调用者得到可供后续复查的文件引用。原始日志与便于阅读的摘要分别保存，避免再手工修补证据格式。

## 4. 中低优先级：按用户步骤和角色参考组织长期指南，减少语义副本

**事实**：原 `docs/workflow-runtime.md` 已有约 495 行内容，并分别解释 recover、retry、人工交接、report 和 collect。本轮新增集中速查，改善了用户入口，却又在速查矩阵和后续详细章节中重复了部分动作准入、禁止自动行为、collect 原因与预算说明。

**建议**：由文档审查阶段应用信息层级，而不是要求实现 Agent 继续堆叠说明：

- **步骤**：集中保留查看失败 → Resume → 核实/修复 → 表达意图 → 核对结果，每步给出明确的完成条件。
- **分支**：四种故障只保留选择条件、自然语言意图和应观察结果，随后链接至对应详细章节。
- **参考**：动作准入、参数面、错误语义各保留一个权威位置。若保留统一矩阵，详细章节以补充特殊条件为主。
- **实演证据**：将具体日期、部署缺失和本次验证结果留在证据包；长期指南保留前置检查方法与证据要求。

例如，“recover 完成”的观察条件应是原执行/Chat 身份不变且跟踪状态恢复，而不是原 Chat 已继续工作。这样的完成标准比重复多处禁止语句更能防止提前宣布成功。

是否需要进一步拆文件，应由实际阅读分支决定；本轮没有执行真实用户实演，不能声称现有篇幅已造成用户误操作。

## 5. 低优先级：工具在已知失败与精确文件查询上更早收敛

**事实**：首次 `find` 的 24 个 judge 请求全部因 HTTP 451 失败，返回明确表示没有文件被评判。Agent 随后正确改用其他搜索工具并报告问题。之后为查两个已知入口名，读取了两页共 58 个索引项目；`search_graph` 的 BM25 查询返回了 session-manager 等不相关符号，而精确目录枚举已经能确认部署文件情况。

**建议**：

- 对明确的服务级不可用错误设置本 session 的降级状态，后续直接使用可用的文件名或字面搜索；与“检索无命中”分开呈现。
- MCP 提供当前工作目录对应项目的直接解析，减少先列全部项目的导航成本。
- 已知入口文件名优先精确路径或文件名查询；文件是否部署以实际文件系统为准。精确查询没有匹配时明确返回无匹配，不用低相关 BM25 结果填充。

本票只观察到一次 `find` 失败，不能把它描述成反复重试故障；这里是减少无效探索的机会，不是主要阻塞原因。

历史中的 `frontend/package.json` 已显示网络护栏 hooks、类型检查构建和测试入口；不能据此提出“仓库没有检查命令”。本复盘未检查 CI 或提交 hook 的实际接线，亦不推断仓库缺少这些 guardrail。以上均为环境改进建议，本轮未执行建议、修改文件或重跑验收。
