**推断。**这是验收所需资产与派票交付边界没有预先对齐，不是本轮缺少更多 HTTP 测试。执行者本轮正确处理了边界，但下一位执行者仍可能重复探索，或误把后端完成等同于端到端完成。

**建议。**在派票生成或调度阶段，为涉及外部仓库的验收项附上最小的“前提归属”：所需外部资产、负责交付的任务或人员、本票可验证的分区，以及缺失时应保留的未验证结论。继续保留“工作流执行结束”与“契约全部验收”的区别，不为已授权的本地交付另设阻塞门禁。

**完成标准。**执行者读完票据即可判断 P59.02 所需入口在哪里、谁负责提供，以及本轮是否具备原生验收条件，无须再次询问交付权限。材料放在相关票据或调度信息中，不扩充全局 AGENTS.md。

## 2. 中：把 TDD 的 red 绑定到当前违例，缩小首个实现切片

**事实。**13:46:29 的首个 red 是 report 路由返回 404。随后一次写入约 6.7 KB 的报告模块，已经包含存储失败处理、通知失败处理、诊断容错及待办适用性等行为；这些行为中的若干项直到后续才加入专门测试。后续两个 red 分别是 manager 查询缺少 `pendingReports`、响应缺少 `diagnostic.status`。保存失败测试首次执行即通过，执行者没有为已有行为人为制造失败，这一点符合 TDD 指引。

**推断。**首轮存在“一条测试承载多个承诺、一次预实现后续分支”的倾向。404 可以证明入口缺失，却不能单独证明测试对错误归属、错误回滚或重复投递敏感。诊断测试最终确实覆盖了真实管道故障，但当时的 red 停在成功模式缺少新响应字段，并未到达管道故障条件。

**建议。**在现有 TDD skill 的 red 判据处补一个局部辨别标准：记录此次失败对应的具体违例；入口接通后，当前验收的关键条件与观察必须实际执行。首个 green 优先只交付当前切片；对于已满足的后续条件，直接记录既有行为验证。新增响应字段应有调用者或契约依据，而不是仅用来取得一个 red。若无法从测试与实现检查确认敏感性，再使用局部故障注入，不把 mutation 变成每个测试的固定负担。

**完成标准。**每个 owned criterion 都能说明“什么具体错误会让哪条观察失败”，而不仅是列出失败命令和通过命令。本项属于 TDD 执行判断，不适合用代码风格 lint 代替。

## 4. 中：搜索工具提供可用性降级和当前 worktree 绑定

**事实。**首次 `find` 的 25 个 judge 请求全部因区域限制返回 451，工具明确说明结果不能作为不存在的证据，随后执行者改用 grep。图工具发现项目需要两页枚举，列表中没有当前 worktree 的精确路径；后续读取的是另一个 worktree 的 `workflow-dispatch-05` 大纲。该大纲中的 `NodeState` 仅列出 `status`，而本轮读取的当前源码还包含 `execution`、`failure`。另一次宽泛图查询返回了 1,383 条以上候选中的前 15 条，多数是 HTTP 模块符号；改用精确名称后才定位到 `PromptDeclaration`。

**推断。**这里有两种独立成本：不可用的 judge 仍展开多次请求；未绑定当前副本的索引容易提供过时导航。没有证据表明本轮因此产生了错误实现，但工具确实增加了探索步骤。

**建议。**

- 工具层将区域不可用等确定性错误快速收敛，并在本会话后续请求中直接使用可工作的搜索路径。

- 已知符号优先使用名称过滤，行为未知时再使用语义查询。把这些策略放在工具默认行为或现有工具说明中，不新增一份长期必读文档。

**完成标准。**同类不可用错误不会在一次搜索内扩散成大量失败请求；其他 worktree 的大纲不会被默认为当前源码事实。

## 应保留的做法

- 通过真实 HTTP、独占文件与生产 Herdr adapter 观察行为；诊断故障使用独立子进程关闭 stderr 管道，没有替换内部 logger 来证明容错。
- 投递延迟使用外部屏障，并在等待期间读取已保存报告，确实区分了保存阶段和通知阶段。
- 无自主重投的结论限定为 300 ms 观察窗口，并输出外部调用证据，没有声称有限测试证明无限期性质。
- 完整后端检查只执行一轮，等待后台任务结束后再交接；最终明确区分本地验证、后续 collect 分区和外部原生验收。

本轮没有 reviewer 执行记录，因而不据此增设“reviewer 未发现错误”的编码标准。现有根 AGENTS.md 主要承担导航，也没有证据支持继续扩充它。
