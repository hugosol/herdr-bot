# 通用协作消息、交付与决策会话：Lighthouse

> Question and discussion: [通用协作消息、交付与决策会话](../decision/04-collaboration-protocol.md)

## Question

同一 Run 的管理者与节点执行者如何通过统一结构化消息通信，让 collect 不依赖自由文本即可推动正常交接，同时让各 Chat 自动接收业务信息？本票决定通信契约，不实现产品、不规定 extension 代码布局。2026-10-28 本票会话 Q3–Q37 逐项确认；用户在最终发布授权问题后答复“同意”。

## Discussion

### 参与者、寻址与角色

管理者 Chat 类比 omp 主会话，节点执行者 Chat 类比 subagent；实际 node 是静态工作定义，调用工具的是其关联 Chat 中的 Agent。同一 Run 内管理者与执行者双向通信，执行者之间可直接通信，不要求经管理者转发。普通消息支持一个明确接收者或当前 Run 内除发送者外的全部已关联参与者；未启动 node 不是可投递 Chat。不做跨 Run 寻址，不按管理者／执行者限制当前 Run 消息记录的读取。广播不要求全员回复。

交接报告固定发送给管理者，报告者的 node／Run 归属由可信运行上下文取得或校验，不能报告其他 node。通信自由不授予流程状态操作权限。管理者独占状态操作；合并完成与放行的修订只由[运行状态机权威](03-runtime-state-operations.md)持有。

确认来源：Q4、Q12、Q14、Q16 获同意；Q29 用户要求“不需要对消息访问设置任何权限，用最简单的方式实现即可”；身份与 Run 隔离不因此取消。

### 一套消息，两种消费方式

仅有普通协作消息、交接报告两种消息类型。普通消息承载指示、问题、回复、进度及异常说明；回复是独立消息，不增加 replyTo、线程或问答状态机。首版不增加结构化执行失败报告或其自动触发机制；不删除运行工具既有的记录失败能力。

普通消息输入为目标与正文；交接报告输入为正文，目标由系统固定为管理者。工具可以通过类型选择语义，最终参数名和包装由接入票决定。消息标识、时间、发送者及 Run／node 归属由系统产生或可信绑定取得，不由模型任意自报。消息类型是 collect 可识别的结构化信号，不从正文推断完成。

同一条消息保存后，一路由自动输入机制交给目标 Chat，另一路供 collect 读取结构化流程信号。collect 不重复返回正文、不从 Chat transcript 抽取报告。只有交接报告产生交接待办，普通消息不推导 node completed。正常交接的控制路径不依赖管理者理解 IRC 正文；这不保证不读正文就能解决任意业务问题或故障。

确认来源：用户提出“collect即使不阅读IRC的消息内容，也能顺利完成流程的流转”；Q10 确认“一套结构化消息协议，两个消费入口”；Q12/Q14 同意，Q13 要求暂不扩大失败报告需求，Q17 要求只实现独立消息收发，Q34 同意最小输入。

### 交付、交接时机与提示词

不建设 Delivery 对象、delivery_id、命名输出表、材料自动复制／绑定、路径校验或产物快照。交付内容和地址由 Agent 自行决定，在正文和 node.input 中表达，系统只从提示词引导，不验证可访问性或稳定性。blocked_by 仍只表示依赖，不自动传递材料。

配套工具规则引导执行者：当当前结果已经可以供下游使用时，主动向管理者发送交接报告，说明结果、地址和必要限制；后续可以继续不影响已交接结果的收尾。此为行为指引，不是自动完成检测保证。沿用用户说明的首版基线：必要时用户主动提醒调用工具；何时通过宿主事件自动触发报告不在本票范围。

工具使用规则随注册提供；运行接入在首次使用工具前提供当前 Run、角色、node 归属以及运行文件和消息记录位置。其他联系人和工作说明按需从已有运行信息／Run 文件取得，不重复注入完整名单，不新增专门联系人或历史查询工具。注入信息不取代可信身份校验。不改变 node.zone_id 或管理者所选 zone，不要求各 Chat 使用同一工作目录。消息在既有关联 Chat 中处理，不为每条消息创建独立决策会话。

确认来源：用户澄清“可以交接”不等于所有动作完成，工具提示词属于本票；Q18 要求“agent自行决定交接内容与地址，不作更多限制，只从提示词作引导”；Q32 选择直接读取记录文件；Q33 同意最小上下文注入并澄清目录用途。

### 发送、重发与生命周期

发送不等待接收者推理或回复。结果返回消息标识及保存、各目标投递情况：保存失败不能报告已接受；保存成功但实时投递失败要如实指出；交给输入队列不等于模型已阅读或处理。广播分别报告目标结果，不将部分成功当全体成功。具体投递确认协议由接入票落实。

允许重复发送交接报告，每次都是新消息并保存、投递，不覆盖旧报告。collect 按 node 汇总为一个交接待办，附最新报告标识；读取消息、自动输入或 collect 检查都不消除待办，管理者将 node 置为 completed 后才不再列入。只有当前状态允许完成操作的 node 才形成可操作待办；其他状态收到消息仍保留，不绕过状态规则。completed 后重发不回退节点、不重复产生完成效果。

node 或 Run 已 completed 不禁止普通消息和交接报告，暂停也不阻止已有参与者通信。通信不重新打开 Run，不授权终态状态变更，不要求关闭 Chat、进程或 Tab。重试后的执行身份与旧报告适用性由故障／身份票提供，不能按 node 聚合就默认为旧报告适用于新执行。

实时投递失败不自动补投、不后台重试、不恢复 Chat；发送者或用户可以重新发送。消息已保存时，交接报告仍可由 collect 识别，不依赖正文实时投递成功。

确认来源：Q15/Q21 同意按 node 保留与汇总待办；Q19/Q20 用户要求允许重发、不要增加限制；Q27/Q28 同意发送结果边界及不自动补投。

### 自动接收与 collect

管理者与执行者均采用 IRC 式自动输入。正在工作时在宿主安全边界注入，不强行终止有副作用的工具；等待输入时启动新一轮；正在 collect 时可结束等待，并在下一轮模型推理前提供相应消息。Chat 进程退出或接入不可用不自动恢复，保存并报告未能实时投递。消息保持 Agent 来源身份，不假冒人类用户输入；接入 API 尚待核实。

collect 仅管理者可用，用户在 Q26 明确“这个原则可以确认不会变更”。执行者发问后可以结束当前轮次，由后续消息唤醒，不要求执行者 collect。

collect 返回等待结束原因、最新运行快照、按 node 汇总的交接待办及报告标识，不返回消息正文。快照复用运行工具的状态语义：Run／node 状态、可派发 pending、阻塞原因、活动执行、已记录失败阶段和原因、成功结束条件；不另维护 ready 或独立放行状态。快照返回后可能变旧，状态操作仍须重新校验。具体 schema 由接入／持久化票细化。

沿用 hyper-auto-coding 的保留通知与合并检查原则：

- 已暂停或结束，直接返回当前现场。
- 有未检查通知，立即检查并返回快照／交接待办；无人等待时到达的通知也要保留。
- 没有新通知且没有 running 节点，不无限空等，明确返回原因，要求管理者派发或结束。
- 否则可以等待；不另加“只要有 ready 就必须立即返回”的 collect 规则，管理者仍应遵守已有的主动推进指引。
- 所有发给管理者的消息均可结束等待；仅交接报告产生流程待办。普通消息打断不触发状态修改、自动回复、派发或自动再次等待。
- 连续通知合并为一次检查；本次检查之后的新通知留给下一次。检查位置由系统维护，不要求模型传游标。消息正文仍逐条保存、投递。
- “新通知已检查”与“交接待办已落实”独立。已检查的报告不反复触发即时返回，但未完成 node 的待办仍保留。
- 等待超时可配置，初始值 1.5 小时（90 分钟）；到期只返回现场，不将节点置为 failed 或暂停 Run。接入须核查宿主长等待能力，不静默改短默认值。
- collect 不阻塞消息提交或状态操作；处理输入后由管理者决定推进或重新等待，不强制自动循环。

确认来源：Q7 同意统一自动输入；Q21 同意汇总；Q23 用户要求参考 hyper-auto-coding；Q24 同意 IRC 注入。曾临时选择“只有交接报告唤醒”，随后用户明确“允许打断更灵活……先按允许打断设计”，该限制已被替代。Q26/Q30 同意，Q31 指定可配置和 1.5 小时。

### 存储与跨进程接入的权威

消息记录与 Run JSON 同目录的部分决定由[运行事实与内存文件一致性](07-persistence-consistency.md)持有；通信模块消费其保存保证，不另建文件格式政策。消息记录通过已有文件读取能力查看，不设置独立历史查询接口。

跨进程方案由[omp extension 接入与可信执行身份](08-omp-tool-integration.md)持有：herdr-bot 统筹 HTTP 通信，具体推送／接收／回执机制以及 connect-bot 底层复用调查由接入票承接。SSE 只是参考候选，未锁定。manager／executor extension 的组织和共享模块布局未在本票决定；此前“只能一个统一 extension”的建议未获批准，已撤回。

### 证据与限制

静态核查 oh-my-pi：`packages/coding-agent/src/prompts/system/subagent-system-prompt.md:27–48`、`irc-incoming.md`、`prompts/tools/task-coordination-advisory.md` 包含联系人、主动协调与回复指引；subagent 最终结果自动送达 Main，因此其禁止重复完成报告的规则不能直接照搬。`src/irc/bus.ts:65–79`、`src/session/irc-bridge.ts:191–261` 区分投递、注入、唤醒；进程内 IrcBus 不是独立 Chat 已有跨进程通道的证明。

静态核查 oh-my-wayfinder `extensions/hyper-auto-coding/workflow.ts:489–520`：保留检查标记、合并通知、暂停直接返回、无活动拒绝空等；本函数没有 90 分钟超时实现。当前 herdr-bot `backend/src/lib.rs:275–278` 已有会话 POST 上报与 GET SSE 观察模式，只是复用模式的证据，不证明运行消息接口已实现。connect-bot 底层实现尚待接入票调查。

本轮未运行产品、测试或真实 Agent 验收；所有运行行为均为批准设计，不是已实现保证。

## Decision

采用同一 Run 内的一套结构化消息协议：自动输入承载业务交流，管理者专用 collect 消费流程信号与运行快照。执行者通过交接报告通知管理者，状态变更仍通过管理者运行工具；通信、等待和状态操作职责分开，不建设额外审批、交付或进程管理系统。

## User stories

1. As a 节点执行者, I want 向管理者报告结果可交接并与同伴直接通信, so that 下游可开始工作且业务协调不必经管理者转发。
2. As a 管理者, I want collect 提供结构化交接待办和当前运行快照, so that 不解析 IRC 正文也能推进正常交接与结束。
3. As a Run 参与者, I want 消息自动进入当前 Chat 并在等待输入时唤醒, so that 不必手工轮询才能回复协作消息。
4. As a 运行观察者, I want 直接查看同次运行的消息记录, so that 可以核对保存、投递与状态处理的不同事实。

## Preconditions

- 绑定／字段契约提供独立 Chat、Task、zone 与 node.input；Run 关联不等于共享工作目录。
- 状态机消费本轮已批准的 completed／放行合并修订，管理者仍独占状态操作。
- 接入提供可信身份、跨进程传输、注入及长等待能力；持久化提供单写入事实、检查边界与可靠保存。这些票据尚未完成。

## Postconditions

- 消息已保存、交给输入机制、被模型阅读、交接已落实是不同事实，不互相冒充。
- collect 与自动输入使用同一消息标识和来源，不要求执行者发送两份报告，不重复返回正文。
- 结构化报告不直接改变运行状态；普通消息不自动形成交接待办。
- 产品实现、文件 schema、重试代际与 extension 布局留在对应后续契约，不能将本票视为真实能力验收。

## Invariants

- Map／node 是定义；Chat 是实际对话，既有 Chat 内接收消息不等于新建执行或修改 Task。
- 参考 IRC 的身份明确、自动输入与安全边界，参考 hyper-auto-coding 的通知保留与合并检查；不搬入其自动集成、Git 或 worktree 业务。
- 普通通信在管理者和执行者两侧对称；collect 和流程状态操作只属于管理者。
- 文件记录不充当各 extension 直接写入的消息总线；读取历史不会消费运行待办。
