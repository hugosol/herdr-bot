# 通用协作消息、交付与决策会话：Lighthouse

> Question and discussion: [通用协作消息、交付与决策会话](../decision/04-collaboration-protocol.md)

## Question

首版如何通过节点交接报告、管理者 collect 与单向对话通知推进 Run？本权威保存通信业务语义；工具、宿主与 HTTP 接入消费[接入契约](08-omp-tool-integration.md)。

## Discussion

### 首版范围修订与确认来源

原通信会话 Q3–Q37 曾批准普通协作消息、交接报告、双向及同伴通信、广播和原生 IRC 式自动输入。2026-10-28 接入会话用户要求曳光弹、避免一次塞入过多需求；Q16“同意，非常准确”同意后置通用实时协作，Q19“是”保留 node 报告 → manager 自动输入。随后用户明确希望采用 Herdr 输入，不为准确性新增 harness/adapter 接收机制，并答复“接收”。最终授权“请发布”。这些明确选择替代旧范围，不是继续要求实现双向能力。

首版只保留节点提交结构化交接报告、后端保存并形成待办、管理者 collect 与 Herdr 单向正文通知。普通指示/问题/回复/进度消息、manager → node、同伴通信与广播后置；不新增联系人或运行归属查询接口/工具。不是丢弃已保存事实或允许伪造身份。

### 交接报告与参与者归属

report 只接受正文，固定通知同 Run 的 manager。extension 自动携带原生 session_id，后端从 Run 关联解析 node 与当前执行；消息标识、时间、来源、目标与执行归属由系统产生，不由模型自报。权限及同机信任限制由接入契约持有。

报告表示结果已可交接，不直接改变节点状态；manager 通过 run complete 显式记录 completed。正常流程不额外增加业务质量校验，不从正文、Chat 轮次结束或退出推断完成。新执行不得使用旧执行报告作为依据，当前执行关联及历史由持久化和接入契约提供。

允许重复报告，每次保存新消息，不覆盖旧记录；collect 按 node 汇总一个待办并附最新适用报告标识。读取、投递与 collect 检查都不消除待办，节点 completed 后才不再列入。只有当前状态允许完成的节点形成可操作待办；其他状态的报告不绕过状态机。completed 后重复报告不回退状态或重复完成；暂停不阻止已有关联执行者提交报告。Run completed 不因此重新打开。后端重启旧 Run 只读限制优先。

### 交付内容与信息阅读

不建设 Delivery 对象、delivery_id、命名输出表、材料复制/绑定、路径校验或产物快照。执行者通过报告正文说明结果、地址和限制；结果可以供下游使用时报告，可继续不影响交接结果的收尾。blocked_by 只表示依赖，不自动传递材料。

工具使用规则及初始化信息消费接入契约：Task 保存职能，extension 经 framework Prompt 注入工具指引，启动 input 提供本次信息与文件路径。manager 主动读取 Map、说明文档和记录，不重复注入完整定义或联系人。消息记录通过已有文件读取能力查看，不增设历史查询工具。

### 保存、Herdr 投递与流程通知

报告先保存；失败不投递、不形成待办。成功后更新内存索引与通知，collect 可以独立返回；同时尝试通过 Herdr 将报告正文提交给 manager。collect 不依赖投递成功，也不保证正文先于 collect 结果进入对话。接入会话 Q22 后用户逐步澄清并确认 collect 只依赖已保存事实、不依赖 IRC 请求，继而要求继续设计。

Herdr 输入是辅助通知，替代原先必须具备 Agent 来源标记、安全边界与空闲唤醒保证的原生 IRC 方案。正文标明来源与报告标识，但不冒充宿主级 Agent 认证；提交成功不是已阅读或处理，不保证打断 collect、工具安全边界或严格时序。manager 需要正文时可按标识读消息文件。

report 返回报告标识、保存与 Herdr 投递情况。保存成功而投递失败仍保留待办，不自动补投、重启 Chat、暂停 Run 或撤销报告；Q27 用户“是”确认不应仅因投递失败重复 report。投递诊断沿用持久化权威，不另存投递文件。

### collect

collect 仅 manager 可调用，返回结束原因、最新运行快照、按 node 汇总的待办与报告标识，不重复正文。状态语义消费运行工具，不另存 ready 或独立放行状态。返回后的现场可能变化，状态动作须重新校验。

- Run 暂停或结束时直接返回现场。
- 已有未检查通知时立即检查；无人等待时仍保留通知，连续通知合并为一次检查，检查后的新通知留到下次。
- 没有新通知且没有 running 节点时，不无限空等，返回原因，要求管理者派发或结束。
- 否则可等待；不新增只要有可派发 node 就必须立即返回的规则，管理者仍须主动推进。
- 首版报告/运行变化触发相应检查；普通消息唤醒随普通消息能力后置。检查通知与落实交接待办相互独立。
- 默认等待 90 分钟，可配置；到期返回现场，不置 failed、不自动暂停。
- 等待不持有文件锁或状态操作串行入口；中断、HTTP 预算与取消消费接入契约。
- 正常路径不要求 manager 先理解正文再推进；这不保证任意故障或业务问题都可忽略正文。
- manager 提前结束轮次由人工处理，不增加强制续轮或自动选路；Herdr 通知不是持续执行保证。

### 历史与证据限度

旧原生 IRC、两类消息及双向通信是被本轮范围修订替代的方案，不是并存承诺。旧 HTTP 方向与先调查 connect-bot 的确认仍有效，具体接入由接入权威持有。hyper-auto-coding 的保留通知/合并检查可参考，但其原等待未提供本设计的取消和 90 分钟期限；未运行真实 Agent。本次修订不新增实施或真实验收。

## Decision

首版采用结构化交接报告与管理者 collect 推进流程，Herdr 单向输入正文作为辅助通知；后置通用双向协作，不将投递成功作为交接依据。

## User stories

1. As a 节点执行者, I want 报告结果与地址已可交接, so that 管理者可以推进下游而无需等待 Chat 退出。
2. As a 管理者, I want collect 返回结构化待办与现场, so that 即使正文投递失败也可推进正常流程。
3. As a 管理者, I want Herdr 提交报告正文且可读取保存记录, so that 能了解结果细节而不依赖新增长连接或联系人查询。

## Preconditions

- 绑定提供独立 Chat，状态机提供管理者操作和 completed 语义。
- 接入提供实际身份关联、工具、可取消 HTTP 与 Herdr 路径；持久化提供报告保存、索引与通知提交规则。设计不等于实现。

## Postconditions

- 只注册首版报告能力，不建设普通收发/广播或 extension 接收连接。
- 报告保存、Herdr 输入、模型阅读、状态完成是不同事实；collect 依据前者及运行状态。
- 人工恢复的信息交接须消费本次收窄，不再假设有通用发送工具。

## Invariants

- 管理者独占状态操作；report 不改变 node 状态。
- 运行归属后端解析，消息正文不能成为身份或完成检测依据。
- 消息文件不是跨 extension 共享写入总线，所有业务记录由 herdr-bot 保存。
