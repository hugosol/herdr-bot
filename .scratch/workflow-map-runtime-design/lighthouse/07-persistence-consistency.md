# 运行事实与内存文件一致性：Lighthouse

> Question and discussion: [运行事实与内存文件一致性](../decision/07-persistence-consistency.md)

## Question

首版运行事实怎样通过业务无关的文件持久化层保存，并在内存、文件、外部 Chat 动作和错误响应之间保持明确的提交语义？本票决定文件职责、访问协调、提交顺序及故障保证边界，不实现产品、不改造静态 Map／Bot 存储。

## Discussion

### 范围与确认来源

2026-10-28 本票 grilling 会话：用户要求先列出文件，再将状态和增长型 log 分离，并提出业务无关的统一文件操作层。Q3 限定本次需求涉及的文件；Q4–Q5 确认当前状态无需重放、历史与消息分开；Q8–Q11 确认读取保证、按文件协调及业务分层；Q14–Q21 确认提交顺序、消息、文件布局和状态内容；Q25 确认重启只读；Q26 用户“同意”授权完整发布。本节各主题保留被修订方案的明确来源，不把讨论候选当作最终契约。

原部分发布的同目录决定继续有效：协作票据会话 Q35 指定本票文件名后用户“同意”，消息记录与 Run JSON 同目录；本轮进一步确定物理布局。

本次只约束运行系统的新持久化读写，不迁移全仓库文件操作。静态 Map／Bot、Task／zone 配置、Chat 原生会话与 transcript、Agent 业务产物均不接管。后端通用错误机制作为使用原则，不扩展为全后端改造。

### 文件布局与记录职责

Q19、Q20 用户均“同意”：每个 Run 使用独立目录，根目录沿用项目数据目录配置，不锁定绝对路径。

```text
<运行存储根目录>/<run-id>/
  run.json
  history.jsonl
  messages.jsonl
```

- `run.json`：完整当前状态，正常查询和操作不依赖历史重放。
- `history.jsonl`：执行与状态变更历史，包括旧执行关联、失败与恢复经过、成功状态变化。记录操作标识、时间、操作者、动作、目标、前后状态和说明，消费状态机既有要求。
- `messages.jsonl`：普通协作消息与交接报告，记录系统产生或可信绑定取得的消息标识、类型、时间、来源、目标、执行归属和正文；不从正文推断流程完成。
- 两类 log 采用每行一条完整 JSON 的 JSONL，只追加；恢复或更正通过后续记录表达，不抹掉旧记录。
- 安全替换的临时文件在同目录，由底层管理，不是业务记录。不引入事务日志、自动回滚备份、独立投递结果文件或 collect 游标文件。

新建 Run 时创建状态文件与两份空 log，全部初始化成功后才允许启动关联 Chat；初始化不获得跨文件原子保证。已有 Run 必要文件缺失、状态无法解析或 log 损坏，明确报错，不自动当作空记录重建。Q16 确认：准备向已有 JSONL 追加时检查尾部是否为完整记录；尾部残缺则停止向该文件追加，由人工处理，不自动截断修复。JSONL 格式检查属于记录处理逻辑，不塞入通用字节文件层。

### 当前状态内容与派生数据

Q21 内容范围获得用户“同意”，字段拼写不是本票固定的 API：

| 内容 | 保存职责 |
|---|---|
| Run 身份与来源 | Run 标识、所属 Map 引用、创建时间 |
| 本次启动配置 | 管理者 Task、zone、Herdr Workspace 引用 |
| 管理者关联 | 实际管理者 Chat 引用；尚未建立时明确为空 |
| Run 当前状态 | running／paused／completed，以及必要说明和时间 |
| node 当前状态 | pending／running／completed／failed |
| 当前执行关联 | node 当前执行与 Chat 引用；可信身份表示消费接入契约 |
| 当前状态必要依据 | 当前失败阶段和原因、完成说明等，无需查询历史即可返回当前现场 |

当前失败事实可以同时出现在当前状态与历史中；当前状态以 Run JSON 为准，历史不反向驱动它。旧执行与旧失败保留在历史，不因重试覆盖丢失；旧执行报告不得冒充新执行的依据。精确可信身份字段由[接入票据](../decision/08-omp-tool-integration.md)落实，不引入额外执行代际树。

可派发 pending、阻塞原因、成功结束条件由当前状态与静态 Map 计算，不保存另一套 ready／待办真相。不复制 Map／Bot／Task 完整配置，沿用运行期间配置不变的前提；不增加额外版本号或配置快照。状态操作返回快照的串行约束消费[状态机权威](03-runtime-state-operations.md)。

### 通用文件层与访问协调

Q9 修订后用户“是”：底层不认识 Run，按调用者声明的文件集合协调访问。在 herdr-bot 进程内按固定顺序取得排他锁，从读取前持有到本次提交或错误处理结束；普通读取遵守相同规则，不相交的文件集合可并行。不因为来自不同 Run 而允许冲突访问；业务层决定可访问哪些文件。首版不做复杂读写锁优化、不建设多进程写入协议。

Q10 用户“是，与业务层分离”：底层提供读取、创建、整体替换、追加的内容操作，隐藏临时文件、必要同步、替换和清理细节。JSON 解析、记录格式、状态合法性和通知规则在业务层，不预建查询语言、任意字节修改或数据库接口。

Q8 确认：经过统一存储层的读取遵守访问协调；Agent 直接读文件只用于查看，不承诺跨文件一致快照。流程判断与状态修改通过运行工具重新校验。即使经过存储层，异常后的部分提交也不享有跨文件原子保证。

业务操作串行与文件访问锁不同：状态机按 Run 串行，派发等待启动结果期间占用业务入口；文件锁只覆盖实际读改写，不跨 Chat 启动、HTTP 投递或 collect 等待，避免阻塞并行反馈。

### 单文件保证与撤回的强事务方案

首版采用单文件先写同目录临时文件、完成必要同步，再替换正式文件；不先删除旧文件制造缺失窗口。追加 log 不为每条新记录复制完整历史。具体 Windows 同步与替换保证须实施验证，不宣称已验证断电安全。

Q6、Q7 曾确认多文件事务及启动恢复；在 Q12 讨论暂存／回滚机制后，用户明确修订：“多文件提交出错导致数据不一致的问题是否可以先忽略……不要在第一版设计太复杂的机制去解决低概率边界情况……直接迁移到数据库即可”。后续 Q14 及 Q26 收口确认采用弱化方案：

- 不保证跨文件整体成功或回滚，不建设事务日志、备份回滚和启动事务恢复。
- 中途失败或进程中断可能留下部分已提交文件；log 尾部也可能残缺。
- 保留进程内访问协调，但不再把锁定一组文件的操作称为具有原子保证的事务。
- 不承诺突然断电或磁盘损坏后仍可恢复；更高一致性要求出现时评估数据库，不预建事务引擎。

Q12 的具体回滚机制未获采用，Q13 的强事务持久性前提不再成立。早期 Q1 的全成功候选、Q2 的文件候选均以本轮最终分层与部分提交规则为准。

### 状态与消息提交顺序

Q14 用户“是”：状态操作检查合法性并计算新状态，先保存 Run JSON；失败则不更新内存、不追加成功历史。保存成功后内存采用新状态，再追加运行历史。历史失败时明确返回“状态已提交，历史记录失败”，不撤销状态、不报告操作未生效。其他读取者不应看到尚未保存的新内存状态；成功路径返回结果与快照并发出相应通知。

Q15 用户“是”：消息先保存，成功后更新内存通知／报告索引并尝试实时投递；保存失败不投递、不形成交接待办。消息保存成功而投递失败，报告仍可被 collect 识别，不自动补投。消息不修改 node 状态，不为正常报告收取同时写 Run JSON。实际投递确认及广播逐目标结果消费[通信权威](04-collaboration-protocol.md)和接入契约。

Q17 最终选择：不将投递结果保存为业务记录；用户补充“我们可以添加日志追踪投递是否成功”。沿用后端诊断日志，记录 Run、消息、目标 Chat 标识、实际投递结果及原因，不重复消息正文。日志不参与业务提交，不因日志写入失败撤销消息或重投；成功只表示接入层实际确认的阶段，不冒充 Agent 已阅读。发送调用仍返回保存及各目标投递情况。消息文件只能证明保存，不证明投递或阅读。

### collect 内存信息

Q18 用户明确“通知已检查位置在内存中即可”。它只决定是否有新通知应使 collect 立即返回，不是消息已读或交接完成标记。等待者、截止时间等是当前调用的内存信息；报告索引可以在内存中维护，来源是已保存消息。当前快照和按 node 汇总的待办临时计算，不另存文件。

已检查通知不消除未完成的交接待办；当前执行关联与状态决定报告适用性。重启不保留已检查位置，也不意味着消息被删除。首版不重建并继续原 collect 等待。

### 通用错误传播与外部副作用

Q22 用户要求“前端明确报错，后端中止后续操作”；Q23–Q24 澄清不是持续封锁 Run。用户进一步要求作为后端通用机制：“只要有错误未被处理，都可以按照类似原则实施”，随后“同意”分层规则：

- 文件层返回错误并清理能够清理的临时文件，不吞错、伪造成功或空数据。
- 当前层没有恢复办法则传播错误，通常以 Result／`?` 中止本次调用后续步骤；业务层补充阶段及已发生效果。
- HTTP 入口统一转换明确错误响应并记录诊断信息；前端展示错误，不显示成功或自动重试。
- 部分已生效不等于未生效，不自动回滚。历史失败明确状态已提交；Chat 已启动而关联保存失败，明确外部 Chat 已启动并附已取得引用，不暗示 Chat 已停止。
- 默认只中止当前调用，不自动封锁 Run、停掉服务或重试。既有明确处理分支继续有效，例如批量派发某目标失败不阻止其余目标。

Q23 曾建议的持久封锁、拒绝该 Run 全部后续操作、collect 连带取消均已撤回。状态写入失败后未来请求仍可能进入；Chat 启动但关联未保存时，首版接受后续重复启动风险，不宣称崩溃／保存失败窗口的完整幂等保证。正常已记录派发的重复调用约束仍由状态机执行。文件层不能回滚 Chat 启动或消息投递。

### 后端重启后的历史现场

Q25 用户“同意”：重启前未结束的 Run 仅作为历史现场读取，不自动或手动重新接管，不开放原 Run 状态修改、消息发送或 collect。不新增重新接管入口，不重新派发。

保留三个文件，不将旧 running 推断成 failed／completed；展示明确说明“上次保存状态，本次后端未接管，关联 Chat 可能仍在执行”。允许查看记录和已有 Chat 关联。“未接管”是服务是否持有运行上下文的信息，不新增 Run 生命周期枚举、不要求写回文件。后端仍存活时的人工节点恢复消费故障权威，与后端重启后接管不同。

### 证据与实施限制

静态阅读 `backend/src/tasks.rs:380–440`、`history.rs:190–240`，并定位 `zones.rs`、`scheduler.rs` 的临时文件／sync_all／rename 使用：仓库存在可参考模式，不证明已有统一文件层、跨文件事务或目标运行能力。Rust 官方 [File](https://doc.rust-lang.org/std/fs/struct.File.html) 与 [rename](https://doc.rust-lang.org/std/fs/fn.rename.html) 提供文件同步、创建和替换原语，不提供本票业务提交语义。

未运行产品、测试或 Windows 故障场景；本次是设计发布。实际文件 API、路径协调、Windows 替换及错误响应复用须后续实施验证。没有选择具体第三方存储库，也不以流程图证明原子性或断电持久性。

## Decision

采用业务无关的文件层与每 Run 三文件布局：当前状态直接读取，历史和消息只追加；保留进程内按文件访问协调及单文件安全替换，接受跨文件部分提交，以统一错误传播如实暴露副作用。后端重启只读旧 Run，不建设事务恢复或运行重新接管。

## User stories

1. As a 运行观察者, I want 在同一 Run 目录查看当前状态、运行历史和消息, so that 我能区分当前现场与历史经过。
2. As a 后端维护者, I want 通过业务无关的文件层协调读取和写入, so that 运行逻辑无需重复实现锁、临时文件和错误传播。
3. As a 管理者, I want 操作失败明确说明已发生效果, so that 我不会把已启动 Chat 或已提交状态误认为未生效。
4. As a 运行参与者, I want 消息保存后才投递并供 collect 使用, so that 流程待办有持久记录作为依据。
5. As a 人类处理者, I want 重启后的旧 Run 明确显示为未接管的历史现场, so that 我不会把上次记录误认为当前仍受管理的执行。

## Preconditions

- 绑定与字段契约提供静态 Map、固定 Task／zone／Workspace 引用和运行期间配置不变的前提；不需要配置快照。
- 状态机提供操作准入与 Run 级业务串行；通信提供两类消息、投递结果及 collect 语义；故障原则提供新旧执行不得混用的要求。
- 接入票据仍须提供可信身份、实际 Chat 启动结果及投递确认；观察票据提供前端错误与历史现场呈现；开放提供者不是已实现能力。
- 所有本次运行写入由 herdr-bot 进程负责；直接文件读取不绕过业务工具取得状态修改权限。

## Postconditions

- 本票文件职责、访问协调、提交顺序、异常与重启范围已决定，精确字段命名由接入及跨模块交接收敛，不要求新增版本号或配置快照。
- 接入与观察继续落实本票消费契约；跨模块交接纳入三文件、部分提交错误、残缺记录、重启只读及人工指南的验收边界，不新增强事务保证。
- 不迁移静态存储、不执行产品实现或真实验收，不建设跨进程写入平台、自动修复或跨系统回滚。

## Invariants

- Run JSON 是当前状态的持久表示，内存采用已提交状态；历史与消息不是第二套可独立修改的流程状态。
- 复用 tasks／history 等现有临时文件替换模式的思路，但统一文件层不依赖 Run 业务，也不声称现有模式已验证本设计。
- 文件锁协调并发，不保证跨文件原子性；错误中止当前调用，不撤销外部副作用。
- 运行记录位置与 node.zone_id／Chat 工作目录不同；Chat、进程及 node 状态不互相冒充。
- 新旧执行与报告必须区分，重试不抹掉历史；重启只读不等于把活动 Chat 终止。
