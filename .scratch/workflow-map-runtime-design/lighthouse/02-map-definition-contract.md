# Map、Bot 与运行配置的契约边界：Lighthouse

> Question and discussion: [Map、Bot 与运行配置的契约边界](../decision/02-map-definition-contract.md)

## Question

确定 Map、Bot、Task 与本次 Run 的字段和职责，覆盖输入、交付、执行绑定、管理配置、重试策略、校验及旧格式处置。本票决定定义契约，不设计自动规划编排、通信协议或运行状态机。

## Discussion

### Bot 的三个阶段文档

Bot 保留结构化 id、name，使用三个独立字符串字段：

| 字段 | 提供阶段 | 职责 |
|---|---|---|
| when | 搜索、筛选 | 何时使用该能力 |
| plan_guide | 规划 | 能力、边界、预期产出等规划指导 |
| node_guide | 填写 node | 字段填写指导、所需背景和示例 |

这些文本给 Agent 阅读，属于 Bot 层级；所有引用该 Bot 的 node 共用指导，不复制到 node。各字段独立提供给对应阶段，允许重复信息，不以已读取其他字段为前提。隔离是内容提供边界，不要求独立 Agent、Chat 或清除已有上下文。Markdown 章节用于维护与理解，程序不解释章节语义，不将文本转换成校验规则。三个字段允许空字符串，保存不审查语义完整性，启动也不因说明为空而失败。

when 替代 use_when；description、inputs、outputs 的内容按职责并入两个 guide，不再保留旧字段。预期产出仍须由能力文档表达，但不是运行时验收规则。规划与填写过程怎样编排，不属于本票或本地图的自动规划交付。

旧部分结果保留了 inputs 作为候选载体，现由上述字段替代；单一 Markdown 正文、独立 node_instructions、execute_guide 等讨论方案均未采用。确认来源：本票 Q6/Q7 用户明确“bot配置只服务能力发现，字段填写，还有id映射，不直接影响运行时执行的提示词”；Q10/Q11 要求两份文档隔离；Q13 同意阶段化提供；Q14 指定 when、plan_guide、node_guide 并允许重复；Q18 最终同意沿用 node_guide；Q22 允许空文本。Q30 完整收口及“同意，请发布”授权本次发布。

### Task 绑定与执行提示词

Bot 顶层使用 task_id，移除占位 implementation 及其中的 type。首版仅接入 Chat，不为未支持执行类型保留判别字段。task_id 可暂缺，允许先保存 Bot 后配置执行绑定；不使用默认 Task，不增加 runnable 字段。node 继续引用 bot_id，不复制或覆盖 Task 绑定。

Task.prompt 保存可复用背景、工作方法与固定业务限制；本次具体输入来自 node.input。when、plan_guide、node_guide 都不自动注入执行 Chat。执行隔离、绑定不可临时替换等政策消费[绑定决策](01-execution-binding.md)，不在此另设权威。

确认来源：Q19/Q20 用户同意，按后提出的 Q20 顶层结构替代 Q19 嵌套候选；Q21 用户“允许，这样创建bot时的顺序可以更灵活”。

### Map 与 node

Map 保留 title、description、nodes；node 保留 title、bot_id、blocked_by，以单个字符串 input 替代 parameters，并增加必填 zone_id。input 沿用发起 Chat 的输入规则，允许 Markdown，不新增变量插值、槽位补全或结构化业务参数系统。zone_id 引用登记的 zone，使用规则沿用发起 Chat，不保存具体路径、不使用运行时默认位置，失效不自行更换。

input 表达本次背景、工作要求、交付内容和交接要求。Task 表达固定要求，两者不另复制为 node outputs 或独立交付方式字段。Bot 的预期产出是能力发现说明，不自动生成本次交付要求。blocked_by 只表达前置依赖，不承载材料传递或自动派发；实际交接由协作模块承接，寻址、材料引用和送达契约由[通用协作消息、交付与决策会话](../decision/04-collaboration-protocol.md)决定。允许在 input 引用尚待产生的材料，不要求定义时存在产物正文。

修订：旧部分结果中的必填 zone 泛称落实为 zone_id，标识而非路径已决定；独立命名交付声明的候选由 input 方案替代。确认来源：Q1 同意依赖边界；Q4 用户“node.input已经可以承载这个功能”；Q16 指定单个文本字符串；Q17 指定 zone_id；Q30 确认完整字段收口。

### 保存与启动的边界

保存检查当前格式与图结构：拒绝未知字段、字段类型错误、缺失必需字段、blocked_by 指向不存在的同图 node、依赖成环。node 仍须明确填写 bot_id、zone_id。Bot 的 task_id 可暂缺，三个说明字段可为空。

外部引用无效不阻止保存：Bot 尚不存在、绑定缺失或无效、Task 不支持 omp、zone_id 失效，都可以作为待完善定义保存。启动前统一检查整张 Map，存在这些已知执行配置错误时拒绝启动并指出原因，不静默选择替代配置。格式合法与可执行分开，不额外增加可能失真的可运行标志。

确认来源：Q21、Q22、Q23 均获同意。执行前检查的原始权威仍为[绑定决策](01-execution-binding.md)，这里确定其与保存校验的分工。

### 格式版本、示例与运行期间修改

Map、Bot 移除 schema_version，按当前唯一格式解析，继续严格拒绝未知字段。不每次保存递增版本，不设计多格式读取或运行时兼容。用户确认存量只有示例，无需历史数据迁移；后续实施按新契约重建示例，本次不执行。

平时可以编辑配置，后续启动使用修改后的配置；本版不要求当前 Run 动态加载变更。沿用运行期间配置不变的前提，不新增配置快照、版本锁定、变更检测或编辑锁；也不因此保证运行中修改的行为。

修订来源：Q24 曾提出版本升级，未获确认；Q25 用户“不需要考虑历史数据，只有示例，重新生成内容即可”；Q26 用户“是，不需要这个字段”；Q27 用户“是，不需要动态加载新的变更”。

### 管理配置、重试与循环边界

管理者的 Task、zone、Herdr Workspace 属本次运行的启动配置，不放入 Map 或 Bot，不增加默认管理者或覆盖层；直接启动管理者的职责消费[绑定决策](01-execution-binding.md)。具体启动接口由接入与观察票据决定。

Map、Bot 及运行配置首版不增加 max_retries、自动重试条件等声明式策略字段。管理者选择是否重试，流程代码检查合法性、落实动作并记录事实。工具的状态约束、新执行身份、Chat 复用及迟到反馈由状态机和故障票据决定，不保证任意状态均可重试。

地图原来笼统排除“循环”，现收窄为不专门建设循环能力，但不禁止合法既有动作组合出重复执行。不能把撤销放行、下游失效等额外机制称作自然涌现或当作已批准能力；也不将本次决定解释为只允许故障重试、禁止所有其他合法重复执行。

确认来源：用户澄清“不需要为了这个功能特地去开发，但如果本身流程自然涌现出这种能力，或者可以归类到某个已经实现的功能下，我必不排斥这种整合方式”；Q28/Q29 同意管理配置与策略归属；Q30 授权完整收口。

### 证据与限制

本轮静态读取 backend/src/scheduler.rs 的 WorkflowMap、MapNode、Bot、BotImplementation：当前实现含 schema_version、parameters、Bot inputs/outputs，implementation 仅含 type。它们是变更前事实，不是目标格式已实现证据。未运行产品或真实 Agent 验收；input 与 zone_id 沿用发起 Chat 规则是批准的设计要求，精确宿主接口仍由接入票据核查。

## Decision

采用阶段化 Bot 指导文档与直接 Task 绑定，node 使用具体 input 和 zone_id；静态定义、运行配置及通信执行各守职责。定义可保存与可启动分开，首版不保留格式版本、历史迁移或声明式重试策略。

## User stories

1. As a 规划 Agent, I want 按阶段读取 Bot 的适用说明与指导, so that 我能选择能力并填写具体 node，而不把能力说明注入执行提示词。
2. As a Bot 维护者, I want 分步完善指导与 Task 绑定, so that 我能灵活创建定义而无需伪造执行配置。
3. As a 流程作者, I want 用 input 和 zone_id 表达本次工作与位置, so that 节点能沿用 Task 发起 Chat 的输入和位置规则。
4. As a 运行启动者, I want 启动前拒绝已知无效的外部引用, so that 不因可提前发现的配置错误执行部分流程。
5. As a 管理者, I want 使用合法运行工具决定是否再次执行, so that 无需额外声明式策略也能处理重试，而不把未设计的返工能力当成保证。

## Preconditions

- 消费[绑定决策](01-execution-binding.md)的 Bot/Task/Chat 分层、独立 Chat、管理者启动、Workspace 与配置不变前提。
- Task 发起 Chat 的实际输入、zone 解析及 omp 能力必须由接入设计核实；本票不证明宿主已支持。
- 存量仅有示例；用户已免除历史迁移需求。

## Postconditions

- 定义字段与职责可供后续设计使用；本票不存在待决定的格式版本或迁移分支。
- 状态机、协作、故障、持久化、接入和观察票据消费本契约，继续决定各自的操作、身份、协议与接口，不重复建立字段政策。
- 自动规划编排、运行时通信协议与重试算法不作为本票交付；具体规划流程仍不在地图目的地内。
- 本次只发布设计，不代表代码、示例或真实运行能力完成迁移。

## Invariants

- Bot 是共享能力定义，node 是具体工作，Task 是发起预设，Chat 是实际对话；与 GLOSSARY 和 Task/Bot 命名 ADR 的概念分层一致。
- 对齐已有 Task 发起 Chat 的 input 与 zone 使用规则，不另建第二套输入解释或路径入口。
- Markdown 指导用于 Agent 理解，程序执行绑定依赖结构化 ID；静态 Map 不承载本次运行状态。
- 保留 scheduler 严格未知字段检查，但将定义内部合法性与外部执行引用检查分层；不把当前代码行为当成目标契约已实现证明。
