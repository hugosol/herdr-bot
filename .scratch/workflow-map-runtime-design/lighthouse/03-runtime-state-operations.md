# 运行状态机、管理者工具与决策 seam：Lighthouse

> Question and discussion: [运行状态机、管理者工具与决策 seam](../decision/03-runtime-state-operations.md)

## Question

管理者如何通过受约束工具推进 Run，并将策略判断与状态操作分开？2026-10-28 会话 Q70 确认单运行工具，Q71 正常流程收口后用户澄清 collect 仍须可调用，并明确“可以，请发布”。本票完成正常流转及已确认故障动作的职责契约；协议、身份、恢复和持久化细则交由对应已有票据。工具名与参数拼写是语义候选，不是最终 API。

## Discussion

### 管理者与运行边界

Q55–Q59：一个 Map 可以对应多个 Run／运行文件；每个 Run 与一个管理者 Chat 一对一绑定，节点执行者 Chat 不计入该一对一关系。不增加 Map 级单运行限制。管理者独占流程状态操作，执行者使用运行通信工具反馈，不调用完成等状态操作工具；不限制 Task 原有业务工具。身份不依赖模型自报 ID。

用户确认 LLM 判断 → LLM 调用 tool → 代码校验并执行。可替换的是决策与调用者，不是两套状态执行逻辑。首版不设后台自动派发、自动选路或固定工具调用链，不为每个内部步骤建立插件。Q30、Q36：有可执行工作应主动推进，尽量派发全部符合条件的 pending，不因已有执行而空等；不同业务阶段均用普通 node，不内置 TDD／集成／验收阶段。

### 完成、交接与依赖（经协作会话修订）

completed 表示流程层面的交接完成，同时满足全部下游对本 node 的前置依赖；删除独立放行标记和放行动作，不新增可交接生命周期。正常路径中管理者收到交接报告后显式调用完成操作；人工处理后的失败节点也可按下文动作契约手动完成，不强制交接报告凭证；消息本身、Chat 轮次结束或退出不直接改变 node 状态。执行者仍可继续不影响已交接结果的收尾。首版不跳过 pending 的执行，正常完成不撤回；blocked_by 保留静态依赖边，不自动传递材料或派发下游。新执行不得以旧执行报告作为完成依据；人工恢复与交接责任见[故障恢复原则](05-fault-pause-retry.md)，不能沿用独立放行位来假定行为。

修订来源：2026-10-28 [通用协作消息、交付与决策会话](../decision/04-collaboration-protocol.md)中用户明确“completed直接就代表‘已放行’就可以了”，Q3 再确认“状态管理依然集中在管理者chat中”；最终授权发布。原 Q1–Q5、Q7–Q16、Q37–Q40、Q48 的独立完成／放行方案被此选择替代，原因是简化流程状态与管理操作，不是把 Chat 退出当完成。

### 派发与正常节点状态

Q41 的内部派发列表候选被 Q42 取代：采用 pending、running、completed；派发报错／超时进入 failed，不增加 dispatching 状态或独立派发中列表。pending 表示未派发；running 表示已确认启动且尚未记录流程交接完成，不表示模型正在生成回复。正常完成将 running 置为 completed；重复完成返回原事实，不对 pending 变相跳过执行。

Q42、Q44–Q45、Q53–Q54、Q61–Q62：每个 Run 的状态操作串行；派发等待启动结果期间占用串行入口，批量派发整个批次处理完才落实后续暂停等操作。执行者工作仍并行。管理者明确给出目标列表，dispatch 内部就是 check + dispatch；逐项检查 Run 允许派发、目标 pending、全部前置已 completed。检查拒绝不改状态；启动失败记 failed。一个目标被拒绝或失败不阻止其余目标，不回滚已启动节点。已派发目标不重复创建 Chat。不同 Run 无需共用串行入口。

派发失败不自动暂停整个 Run，failed 不可直接普通派发。Q43 的专用恢复需求：人类确认已创建 Chat，则补齐实际关联并恢复 running，不重建；确认未创建则恢复 pending，不自动再派发；不确定保持 failed。本核实动作只解决派发失败；执行阶段失败使用下文恢复执行状态、重试或手动完成动作，不授权任意状态改写。具体身份与 API 由接入票据提供。用户要求先收集真实恢复场景，若过多再评估通用入口，目前未批准后门。该人工核实方案不是跨超时／崩溃创建 Chat 的已验证幂等保证。

### 操作结果与记录

Q11、Q40、Q49–Q50、Q56–Q57：保存成功状态变更列表，记录操作标识、时间、操作者、动作、目标、前后状态与说明。完成需简短说明，不强制引用消息或交付物，不审查业务质量；机械动作可由系统生成说明。重复完成、派发返回已有事实，不重复产生效果或成功变更记录，不覆盖首次说明。无效请求返回原因。

状态操作返回结果与最新运行快照；状态更新与快照生成处于同一串行边界。快照包含节点状态、可派发 pending、阻塞原因、活动执行与结束条件，不另维护 ready 生命周期。返回后快照可变旧，因此派发仍须重新校验。精确 schema、持久化原子性仍待后续票据。

### 暂停与正常结束

Q47、Q51–Q52、Q60、Q63：暂停立即禁止新的执行启动，不等已有节点收尾；仍允许完成及人工核实的事实修正。暂停后可恢复，不自动派发；暂停／恢复重复调用不重复生效。正常结束仅检查全部节点 completed，不要求 Chat 退出或收尾全部结束，paused 时也可成功结束。成功终态禁止状态变更，查询可用，重复成功结束返回已有结果。

独立 stop 生命周期的处置由[停止 Map 与 graceful shutdown 生命周期](06-stop-lifecycle.md)单独持有，不在此建立第二份权威。

### 单运行工具与动作契约

Q70 用户“同意”：状态操作注册为一个运行工具，通过 action 选择操作，不为每个动作注册独立工具；每个 action 只接受自身必要参数。首版所有流程状态操作仅限当前 Run 绑定的管理者。以下是语义名，最终名称由接入票据确定。

| 动作 | 前置条件 | 效果与拒绝边界 |
|---|---|---|
| 查看状态 | 可信管理者绑定 | 只读快照，终态仍可查询 |
| 派发节点列表 | Run running；逐项 pending 且全部前置已 completed | 检查并串行启动；拒绝不改状态，启动失败记 failed；返回逐项结果 |
| 记录完成 | Run 未结束；节点 running，或执行阶段 failed 且人工处理后结果已可交接 | 转 completed，同时解除下游依赖；需说明，不自动派发或补发交接，不要求消息凭证；保留失败事实，重复完成返回原事实 |
| 记录执行失败 | Run 未结束；节点 running | 转 failed，需说明，保留 Chat 关联；不自动重试、暂停或终止 Chat |
| 核实派发失败 | Run 未结束；节点因派发失败而 failed；人工已核实 | 已创建则关联实际 Chat 并恢复 running，未创建则恢复 pending；不启动新 Chat |
| 恢复执行状态 | Run 未结束；节点执行阶段 failed；人工已确认原 Chat 可以继续 | 转 running，保留原 Chat 与失败事实；需处理说明，不启动或修复 Chat |
| 重试 | Run running；节点 failed；派发结果不确定时须先核实 | 发起独立新 Chat，确认启动成功后转 running；启动失败仍为 failed；保留旧执行关联和失败事实，需处理说明 |
| 暂停 | Run running | 转 paused，禁止新执行启动，不等待已有节点收尾；重复暂停无新效果 |
| 恢复 | Run paused | 转 running，不自动派发；重复恢复无新效果 |
| 成功结束 | Run running 或 paused；全部节点 completed | 转 completed，不要求 Chat 退出或收尾全部结束；重复结束返回原结果 |

成功终态拒绝一切状态变更；正常失败不自动将 Run 终结。Run 正常状态为 running、paused、completed，独立停止范围见原处置权威。暂停允许完成、核实修正及不启动 Chat 的恢复执行状态；重试须先恢复 Run。故障记录作为事实更新不启动新执行。

Q67 用户“是”：记录执行失败与派发失败共用 failed 状态，但保存失败阶段，避免把派发核实工具用于执行失败；重复失败不覆盖首次记录。随后用户明确先设计 happy flow，不为 Q68／Q69 的完成后迟到失败、重试执行代际等边界设计复杂机制；这些候选未批准，不作为本票要求。基本动作前置条件仍有效。

本轮故障会话修订：原完成动作仅允许 running，现扩展至人工处理后结果可交接的执行阶段 failed；新增恢复执行状态与重试动作，区分原 Chat 继续和独立新 Chat 启动。原因是覆盖常见人工恢复，不建立通用 checkpoint 或任意状态后门。确认来源：2026-10-28 [节点故障、等待人工处理与重试](../decision/05-fault-pause-retry.md)会话中，用户提出两条 failed 恢复路径，对工具重试答复“可以，这样更简单，只要有工具就可以让管理者从工具入口执行”，并最终同意统一发布恢复机制与使用指引。精确 action 参数、可信身份和落盘机制仍由接入与持久化票据落实。

collect 与发送消息是管理者必需的可调用能力，不能因本表只列状态动作而删掉。是否将 collect／发送消息作为同一工具的 action 或独立通信工具，由协作和接入票据决定；本票不固定通信包装。

### 参考机制与后续分工

静态阅读 oh-my-wayfinder/extensions/hyper-auto-coding/agent-tools.ts 与 workflow.ts：状态快照包含 ready；collect 保留变化、合并检查、无活动时拒绝空等；session_stop 阻止未完成且未暂停工作流提前退出；实现结束自动集成属于其业务特例，不直接迁入本设计。未执行宿主或真实 Agent 场景。

Q64 确认参考防空等规则：无待消费反馈且无活动执行时，不无限等待，返回状态与原因；协议、唤醒与有界等待需由协作票据正式承接。管理者持续运行的宿主保障尚未验证。此处是本票的消费需求，不代替协作 Lighthouse。

后续分工：运行工具的单工具 action 包装已决定，精确命名和接入由接入票据落实；执行失败记录及最小恢复动作已确认，人工处置与使用指引由[故障恢复原则](05-fault-pause-retry.md)持有，不批准 Q68／Q69 的额外机制。空 Map 可启动及拒绝启动均为未确认候选，启动合法性由运行启动票据明确，不应落为现行政策。collect 协议已由[通信权威](04-collaboration-protocol.md)确定：仅管理者使用，读取结构化交接待办、自动消息可打断、通知合并检查、可配置 90 分钟默认等待。等待并不替代状态操作串行机制。

### 发布追踪

本次对照绑定、字段契约和停止处置：无新的上游政策冲突。状态快照／通信／无进展等待由协作票据提供；真实 Chat 启动、可信管理者与宿主持续推进由接入票据提供；失败阶段、人工核实与手动重试由故障票据提供；串行状态与外部启动／落盘窗口由持久化票据提供；多 Run、只读状态与启动校验由观察票据提供；跨模块动作完整性由交接票据复核。提供者未完成不代表能力已实现。空 Map 启动问题作为现有启动范围的未回答输入保留，不新增决策票据。没有需要新开票的确认缺口；不将罕见边界候选转为实施要求。

## Decision

采用状态驱动管理者与单运行工具的独立 action：LLM 显式选择动作，代码串行检查并执行；completed 合并流程交接与依赖解除，批量派发逐项处理，不引入后台自动调度。本票正常流转及本轮修订的最小故障恢复动作职责已收口；人工处置原则见故障恢复权威，通信、接入和持久化消费各自契约；不表示产品已实现。

## User stories

1. As a 管理者, I want 从一致快照识别可执行节点并显式派发, so that 并行工作能持续推进而不靠固定工具链。
2. As a 管理者, I want 在结果可以交接时记录 completed 并解除依赖, so that 下游可在前置 Chat 收尾期间开始工作。
3. As a 人类处理者, I want 核实派发失败后由管理者修正事实, so that 不因未知启动结果重复创建 Chat。
4. As a 管理者, I want 暂停新派发而继续接受已有执行反馈, so that 保留后续恢复自由度。

## Preconditions

- 消费绑定与字段契约：独立 Chat、固定 Task 绑定、静态 Map、运行期间配置不变。
- 协作提供反馈与等待；接入提供可信身份与实际启动结果；持久化提供一致提交。开放票据不是已实现能力证明。

## Postconditions

- 各调用入口共用串行操作约束；不直接改 JSON、任意 setStatus 或绕过依赖。
- 故障、协作、接入、持久化与观察继续落定各自契约；不将本票局部结果解释为全部前置已满足。

## Invariants

- Map、node 是定义，Run 与 Chat 是执行关联；管理者角色不要求 Bot 定义。
- 节点 completed 同时表示交接与依赖解除，但不等于 Chat 退出、Tab 关闭或不再产生任何动作。
- 外部动作与落盘的一致性不能由单纯串行假设证明。
