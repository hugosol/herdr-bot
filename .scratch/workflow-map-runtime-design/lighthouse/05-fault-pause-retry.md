# 节点故障、等待人工处理与重试：Lighthouse

> Question and discussion: [节点故障、等待人工处理与重试](../decision/05-fault-pause-retry.md)

## Question

常见节点故障后，人工如何处理实际问题，管理者如何通过工具恢复流程并补齐交接？本票确定最小恢复机制及使用指引要求，不穷举复杂故障路径，不实现产品。

## Discussion

### 人工处理现场，管理者落实状态

人工修复文件、环境或核实 Chat 的实际情况，再通过管理者 Chat 表达处理结果与意图。管理者选择工具动作；人类消息本身不修改状态。恢复流程状态不等于恢复执行现场，不建设 Chat 内部 checkpoint、通用数据回滚或任意 JSON patch／setStatus 入口。

用户将目标明确为 failed 后恢复状态机，并要求“只需要提供一个统一的原则，能满足最常见的故障就可以”。据此将原问题中的全面边界枚举收窄为常见恢复契约；不预先设计已完成节点返工、下游失效传播、复杂迟到反馈、容量策略或完整重试幂等协议。既有串行操作、重复完成／普通派发约束不因此取消；具体 API 与保存机制仍由接入和持久化票据提供。

### 恢复、重试与手动完成的分工

状态转换及动作准入的唯一权威为[运行状态机、管理者工具与决策 seam](03-runtime-state-operations.md#单运行工具与动作契约)，本轮在该权威修订完成动作，并补齐恢复执行状态与重试动作。

恢复原 Chat 的跟踪与发起独立新 Chat 是不同动作；不得仅把状态改为 running 就宣称执行已经重新启动。实际需要新执行时，由管理者调用重试工具动作，系统负责发起 Chat 并根据启动结果更新状态，不新增界面按钮。派发结果不确定时沿用原有人工核实路径，不直接重复启动。

保留原失败事实与执行关联；新执行不能以旧执行的报告作为完成依据。不要求旧 Chat 被终止，也不保证撤销其文件修改或其他副作用。身份表示和历史存储由接入、持久化契约落实，不预设复杂执行代际树。

### 状态与交接分别补齐

failed 后手动完成表示结果确实可交接，不是跳过工作。完成动作只处理流程状态与依赖解除，不自动构造、校验或补发交接消息，不要求消息凭证，也不伪造原执行者的交接报告。

人工或管理者仍负责补齐结果位置、使用方式和必要限制。2026-10-28 接入会话 Q16/Q19 将首版收窄为节点报告与 manager 单向通知，替代此处原先依赖通用发送工具向下游补发的方案。首版不提供 manager→node 或同伴消息工具；人工通过已有 Chat 介入补充信息，不能把手动完成当作信息已经交接。通信范围消费[通信契约](04-collaboration-protocol.md)，不另建恢复消息协议或材料绑定系统。

### 用户指南与管理者工具使用指引

后续实施须交付简短的故障处理指南，以及管理者工具使用指引；本地图确定其要求，不在工具和界面尚未落定时编造操作命令。

- 用户指南说明如何查看故障、核实或修复现场、通过管理者 Chat 表达恢复／重试／完成意图。用户无需理解内部状态机或手动填写工具参数。
- 管理者指引说明如何选择动作、信息不足时如何核实、状态恢复与实际执行的区别，以及人工完成后的交接责任。使用自然语言意图，不设置固定口令。
- 必须说明重试不撤销旧执行副作用、手动完成需要真实可交接结果、状态修正不等于实际修复。
- 按最终工具名称和实际操作路径编写，引用本设计权威，不维护第二套恢复政策；不新增恢复按钮，也不扩展为完整运维手册。
- 由跨模块设计收敛与实施交接契约纳入最终交付要求；接入提供真实工具规则，观察设计提供故障和关联 Chat 的可达路径。

### 确认来源与证据限制

2026-10-28 本票会话：用户要求统一原则而非逐个复杂故障讨论；明确提出 failed → running 与 failed → completed 两条恢复路径；要求人工构造交接信息并确认状态／交接分别补齐；对工具发起新 Chat 的重试方案确认“可以，这样更简单，只要有工具就可以让管理者从工具入口执行”；对故障处理指南和管理者工具指引答复“纳入”。最终在“将此前确认的恢复机制与这项使用指引要求统一发布，并完成本票”的授权问题后答复“同意”。

仅核对已发布绑定、字段、状态机、通信设计和领域文档；未核查或执行产品恢复路径，不声称现有代码已支持这些动作。最初将恢复 running 强制等同于新建 Chat 的建议已被用户纠正，不是现行政策。

## Decision

采用人工处理实际故障、管理者通过工具显式恢复／重试／完成的最小机制；状态恢复与信息交接分别补齐。交付要求包含用户故障处理指南与管理者工具指引，不建设通用 checkpoint 或穷举复杂恢复路径。

## User stories

1. As a 人类处理者, I want 用自然语言向管理者说明修复结果和意图, so that 无需理解内部状态机也能恢复常见故障。
2. As a 管理者, I want 区分原 Chat 继续、新 Chat 重试与人工完成, so that 不用任意修改运行文件也能落实恢复动作。
3. As a 下游执行者, I want 收到人工补齐的交接信息, so that 前置节点手动完成后仍知道结果位置和使用限制。
4. As a 实施者, I want 有明确的用户指南与工具使用指引交付要求, so that 恢复能力不仅存在于接口中，也能被用户和管理者正确使用。

## Preconditions

- 绑定与字段契约提供固定 Task、独立 Chat 及运行期间配置不变的前提。
- 状态机提供串行管理者操作、失败阶段、暂停与成功终态约束。
- 通信提供报告保存与 manager 单向通知；接入已决定实际启动关联与同机信任，持久化已决定失败和新旧执行事实保存。设计已发布，不是现有能力证明。

## Postconditions

- 原状态机权威持有恢复动作准入与效果，本票持有人工处理原则、交接责任和使用指引要求。
- 接入与持久化落实最小恢复需要的身份和数据契约；跨模块交接纳入指南交付，观察设计提供实际观察入口。
- 本票全部确认范围已收口；不将复杂恢复路径列为本票未完成前置，也不宣称产品或操作手册已交付。

## Invariants

- 管理者独占流程状态操作；执行者通信和人工消息不自动修改状态。
- 完成满足依赖但不自动传递材料，首版报告与人工 Chat 补充信息消费已收窄的协作/接入契约。
- Chat、进程、node 状态与外部文件现场不是同一件事；恢复状态不回滚副作用，历史事实不被重试抹除。
