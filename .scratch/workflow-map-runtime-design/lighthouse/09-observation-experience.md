# 运行启动、只读图与人工观察路径：Lighthouse

> Question and discussion: [运行启动、只读图与人工观察路径](../decision/09-observation-experience.md)

## Question

用户如何从 Map 发起 Run，在 workflow 中观察运行与节点现场，并通过关联 Chat 介入？本票决定界面路径与观察契约，不实现产品或重新设计运行内核。

## Discussion

### 确认来源与范围

2026-10-28 本票会话：用户提出 chat 右侧新增 workflow、Map 上的 + 发起页面、实例流程图及 manager/node Resume 入口。Q6–Q9 确认名称、空 Map、启动去向和列表；Q10–Q12 确认 user_input；Q13/Q15 确认布局和节点详情；Q14 要求不同状态样式，Q16 将轮询改为默认 5 秒且可配置；Q17–Q20 确认样式、服务配置、历史定义降级与旧 Chat Resume。用户对 Q21/Q22 明确“同意”，授权原权威修订及本票完整发布。

本轮只确定需求与设计。旧票中的定义快照、独立放行展示和消息投递业务详情已由此前权威取代，不作为未完成要求恢复。

### Task 类型配置入口

2026-10-28 Traverse 审计补齐此前接入票已交接但未显式列出的界面表面：复用现有 Task 管理入口创建、查看和编辑 Task 类型，展示随类型确定的固定角色扩展；不另建角色配置入口。类型默认值、agent 合法组合、角色扩展的可选性与迁移唯一消费[字段契约](02-map-definition-contract.md#task-类型与必需角色扩展)，界面不能只在 Run 发起页筛选而无法配置。用户在审计收口汇总后“同意”统一发布本项交接补充，具体控件文案在实施时落地。

### 入口、启动与本次要求

在 chat 右侧增加并列的顶层 workflow tab，展示所有 Run；workflow 是入口名，不新增同名业务对象。在 scheduler 的选中 Map 上增加 + 按钮，进入发起页面，不在 zone 另设运行启动入口。

发起页显示 Map 名称，选择管理者 Task 与 zone，只读显示从 zone 推导的 Herdr Workspace。管理者 Task 选项限定 manager 类型的 omp Task；节点绑定、zone 和 input 来自定义，不在发起页临时覆盖。无效配置明确指出对应对象，回原定义处修改。空 Map 可保存但拒绝启动，不创建 Run 或 Chat。整图启动检查消费字段与绑定契约，不审查业务质量。

增加可空、支持 Markdown 的多行 user_input，表达本次特定要求。管理者启动输入的追加规则唯一由[接入契约](08-omp-tool-integration.md#提示词文档与启动-input)持有；原文保存规则唯一由[持久化契约](07-persistence-consistency.md#当前状态内容与派生数据)持有。界面提供输入并在详情只读显示；不提供启动后编辑。用户 Q12 明确“只作为manager-bot的输入，不作任何后续逻辑”：不改写 node.input，不增加节点传参机制，也不把该机制列为后续必决缺口。

不新增运行名称输入，用 Map 标题与创建时间辨认实例，Run ID 是身份。取得已创建 Run 的标识后进入该 Run 详情，实例同时出现在 workflow 列表；详情只展示既定 Run 状态，不展示 manager-chat 启动进度；启动过程只写日志，启动失败仍展示简短错误及已发生的部分效果。尚未创建 Run 的校验失败留在发起页。记录已存在不等于 manager 已启动或指示已提交；已发生的 Chat 启动等部分效果必须如实显示，不自动重试。刷新或重新进入只查询已有 Run，不重新发起。

### manager-chat 启动错误的展示边界

2026-10-28 [跨模块设计收敛与实施交接契约](../decision/10-spec-acceptance.md)会话 Q4 用户明确“只需要有run状态，manager-chat的启动只有日志显示状态，没有进度显示页”；Q7 确认“需要错误信息展示”；Q8 明确“有错误日志即可，json不需要作为承载错误历史记录的载体”；Q9 同意当前后端内存保留错误、页面刷新可查询、重启后仅查日志。随后用户要求记录决策并完成 wayfinder 结束工作，暂不发布 spec.md。

这替代原“详情显示启动进度”要求。不新增启动生命周期、进度页或进度查询字段。manager-chat 后台启动失败的简短错误由当前后端内存保留，供 Run 详情查询和展示；错误需说明已发生的部分效果，不能把已创建 Chat 说成已回滚。刷新不丢失该内存错误；后端重启后不从日志重建页面错误，旧 Run 按历史现场／未接管展示，启动错误历史查诊断日志。不新增日志读取接口或日志浏览页，不将该错误写入 run.json 或新增业务历史记录，也不新增自动重试或管理者恢复入口。

此决定仅约束 manager-chat 启动错误的观察生命周期；不撤销[持久化契约](07-persistence-consistency.md)中 node 当前失败原因、失败阶段与执行历史的保存要求。正常启动过程只写日志，不用 Run 的 running 值宣称初始指示已成功提交。

### Run 列表与详情布局

列表混合展示所有 Map 的 Run，按创建时间倒序；首版不增加分组、搜索或状态筛选。每项显示 Map 标题、创建时间、Run 状态和 completed 节点数／总节点数，点击整项进入详情，不提供列表内流程操作。未接管的旧 Run 额外标注“历史现场／未接管”，保存的 running 不代表当前后端仍在管理。

详情采用运行概况、流程图、选中节点详情的单页布局：

- 顶部：Map 标题、Run ID、创建时间、Run 状态、完成节点数，图外的 manager Chat Resume 按钮。
- 可展开的“本次用户要求”，空输入显示“未提供”。
- 中间：复用已有 Map 图布局，叠加运行事实；不把管理者画成业务 node。
- 下方：选中 node 的详情；未选择时提示选择节点。

运行观察只读，不增加暂停、恢复、重试、完成等状态操作按钮；人工通过 manager Chat 表达意图，动作仍由管理者工具执行。

### 节点样式与详情

图保留静态依赖箭头，节点显示名称及 pending/running/completed/failed 文字，以边框、填充和标记辅助区分，不只依赖颜色：pending 弱化填充和虚线边框；running 强调色边框与浅填充；completed 成功色及完成标记；failed 错误色边框及警告标记。选中态用独立外圈，不覆盖状态，不加动画。Chat 在线、工作中或退出不映射为流程状态；不另建 ready 或放行状态。

节点下方详情包含：

| 区域 | 内容 |
| --- | --- |
| 工作定义 | node 名称、Bot/Task 引用、zone、node.input、前置依赖 |
| 当前现场 | 节点状态、阻塞原因或失败阶段与原因、完成说明、当前 Chat Resume |
| 交接报告 | 当前执行的已保存报告正文与时间；报告存在不等于 completed |
| 折叠执行历史 | 失败、恢复、重试和状态变化，旧 Chat 单独标注并提供 Resume，不冒充当前执行 |

无 Chat 关联时显示“尚无关联 Chat”，不提供隐式创建执行按钮。投递诊断仅在后端日志，不在消息记录中虚构已送达或已阅读。当前状态和历史依据消费持久化权威，不通过聊天正文猜进度。

### 轮询与查询错误

列表和详情共用服务级可配置轮询间隔，默认 5 秒；首版不增加界面设置，不写进 Map/Run。配置键名和读取方式由最终 spec 沿用项目惯例收敛。

仅当前可见的 workflow 页面轮询；离开页面或浏览器标签隐藏时暂停，返回立即查询；同一页面不重叠请求，保留手动刷新。查询失败保留上次成功内容，明确显示更新失败与最后成功查询时间，不清空成“没有运行”，不修改运行状态。不引入实时推送作为前置。

### 历史定义与 Chat Resume

不保存 Map 配置快照、不增加版本控制或复杂容错。能读取定义时展示图并说明结构来自当前 Map，不是历史快照。定义丢失、不可解析或节点无法可靠对应时说明具体问题，不补造历史图；保留能读取的运行状态、用户要求、报告、历史和 Chat 关联，缺失名称以已保存标识表示。并不保证仅凭现有引用还原历史定义。

复用现有 Resume 的定位/恢复及错误反馈，不另做假跳转。未接管的旧 Run 仍允许尽量尝试 Resume；醒目说明恢复 Chat 不会接管 Run，旧 Run 的运行工具不可继续操作。Resume 成功不改节点状态、不移除未接管标记，不自动重试；失败或未知结果如实反馈。该行为不扩展为恢复执行现场或后台自动接管。

### 证据与限制

静态阅读 frontend/src/SchedulerPanel.tsx 的 Map 选择及 MapGraph/MapNodeDetails 组合、ChatCreationDialog.tsx 的创建请求与观察逻辑、ChatPanel.tsx 的 ResumeChat：现有 Resume 请求 /api/chats/resume，区分 located/restored 并反馈失败或未知结果。阅读领域词汇及 zone 命名 ADR，核对绑定、字段、状态、通信、故障、持久化与接入 Lighthouse。

未运行页面、真实 Chat 或产品测试；静态代码只是复用线索，不能证明目标 workflow、Run 查询或本次设计已实现。具体查询 schema、配置键及跨模块验收由交接票收敛。

## Decision

采用 scheduler 发起、workflow 集中观察的运行界面：只读流程图与节点详情展示后端事实，关联 Chat 复用 Resume。user_input 仅交给管理者；不增设前端状态机、定义快照或节点传参机制。

## User stories

1. As a 运行启动者, I want 从 Map 填写管理者环境及本次要求, so that 同一 Map 可用不同意图发起独立 Run。
2. As a 运行观察者, I want 集中查看 Run 并在图中辨认节点状态, so that 能发现阻塞或故障并查看当前事实。
3. As a 人类处理者, I want 从运行和节点详情 Resume 关联 Chat, so that 能通过已有对话处理现场而不直接修改运行状态。
4. As a 历史查看者, I want 区分旧执行与当前执行以及未接管的记录, so that 不把旧报告或保存状态误认为当前活动事实。

## Preconditions

- 绑定/字段提供管理者 Task/zone、统一 Workspace、节点配置及整图检查；空 Map 拒绝由本票补齐。
- 状态/通信/故障提供节点状态、阻塞与恢复语义、交接报告及人工职责。
- 持久化/接入提供 Run 记录、历史、user_input、实际 Chat 关联及启动部分效果；设计已定不等于能力已实现。
- 既有图与 Chat Resume 提供复用基础；Run 查询和启动接口由最终交接契约收敛。

## Postconditions

- 启动、列表、详情、节点信息、刷新和 Chat 导航的首版范围已确定，可供最终 spec 使用。
- 交接票纳入 user_input 两处权威修订、空 Map 拒绝、只读观察、部分失败、5 秒可配置轮询及历史未接管呈现。
- 不新增节点输入传播、版本控制、自动重试、重新接管或独立投递记录要求。

## Invariants

- Map 是定义，Run 是实例，workflow 只是 UI 入口；node 状态不冒充 Chat 状态。
- 复用 SchedulerPanel 的 Map 图/节点选择模式及 ChatPanel 的 Resume 交互；不复制前端调度状态机。
- 后端事实为权威，查询/刷新不启动 Run，Resume 不等于接管 Run。
- 本票仅发布设计，不表示产品界面、接口或真实 Agent 验收完成。
