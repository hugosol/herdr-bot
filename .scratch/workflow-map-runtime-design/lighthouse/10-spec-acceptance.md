### 实施入口与长期文档

后续 spec 按启动、派发、报告、collect、complete、下游派发、finish 的主路径组织模块职责、接口和数据结构、失败结果、界面消费及验收。设计期间各 Lighthouse 是主题政策权威，spec 可以引用；HTTP 路由、字段拼写与配置键按现有仓库惯例整理，不逐项作为产品决策，但新行为或冲突必须交由用户裁决。

spec 与 Lighthouse 是开发后会删除的临时材料。实施交付时，长期文档必须完整承接最终需求、模块职责、接口与数据契约、状态规则、限制和重要取舍；用户指南、运行背景文档及 extension 工具指引必须提供各自读者需要的信息。可以引用其他长期文档，不得依赖临时 spec、Lighthouse 或票据才能理解行为。代码注释与其他长期记录遵守同一原则。

删除前排除临时材料检查：仍能理解系统、使用工具、处理常见故障和维护接口；长期文档、提示词与代码注释不存在对这些材料的必要依赖。不是永久维持两套权威，而是交付时由长期文档承接最终契约。Q6 明确替代 Q1/Q3 最初“最终指南引用原 Lighthouse、不复制政策”的安排。

### 使用指引

| 载体 | 必需内容与检查 |
| --- | --- |
| 用户故障指南 | 从 workflow 查看失败、Resume 关联 Chat、核实或修复现场、向 manager 表达恢复意图；说明重试副作用与手动完成的交接责任；按实际界面验证路径 |
| manager-chat 工具指引 | 全部 run action 的适用条件、何时 collect、原 Chat 继续与新 Chat 重试及人工完成的区别、信息不足先核实；通过已确定的 framework Prompt 机制注入，验证实际 Chat 取得指引 |
| node-chat 工具指引 | 何时 report、正文中的结果位置与限制、报告不等于完成、仅投递失败不要重复报告；随扩展注入并验证真实报告路径 |

本票确定内容结构和场景要求，最终产品文案在实施时按真实入口落地。不新增固定口令、恢复按钮或完整运维手册；指引随相应能力交付，不能全部推迟到最终阶段。

### 验收一：真实 Agent 主链路

固定 A、B → C Map，输入材料来自验收专用目录，不依赖不稳定外部服务。A、B 分别生成事先约定的不同文件，report 说明路径与限制；C 的 node.input 预先写明两个路径，实际读取并形成结论文件。检查 C 确实使用两份材料，不建设动态传参、材料绑定或 Delivery 对象，不操作用户现有工作文件。

| 验收项 | 通过标准 |
| --- | --- |
| 发起 Run | scheduler 选择 Map、管理者 Task、zone 与可空 user_input；创建独立 Run，进入 workflow 详情 |
| 管理者启动 | 真实 omp Chat 取得 session_id、保存关联后才提交初始指示；可调用 run、collect；启动过程与错误展示消费观察权威，不要求进度页 |
| 输入边界 | manager 获得运行文件路径及非空 user_input；node 获得自身 input 与必要路径，不注入 Bot 指导文档或自动传递 user_input |
| 并行派发 | manager 显式派发 A、B，独立 Chat 使用各自 zone、同一管理者 Workspace；node 可 report，不可修改流程状态 |
| 报告与收取 | 真实 report 保存交接报告，collect 返回待办和报告标识；报告不改变节点状态 |
| 完成与依赖 | manager 显式 complete；A、B 均 completed 后才可派发 C，不存在独立放行 |
| 下游材料 | C 实际使用 A、B 文件，不仅收到依赖 ID |
| 提前交接 | 至少一个前置报告后仍有收尾，manager 可 complete 并推进符合条件的下游，无需等 Chat 退出 |
| 结束 | 全部 node completed 后显式 finish；Run completed，文件与界面一致，不要求 Chat 全部退出 |
| 刷新与导航 | 刷新读取同一 Run，不重复启动；manager/node Resume 可定位或恢复关联 Chat |

保留真实工具结果、三文件记录、Chat 关联与页面观察；接口测试或人工修改 JSON 不能代替真实链路。manager 提前停轮可按既定范围人工处理，记录干预，不增加强制续轮保证。

### 验收二：定义、启动与操作约束

- Map/Bot 新格式严格检查未知字段、类型与依赖图；重建示例，不保留旧格式兼容。外部引用不完整可保存，启动整图检查 Bot、Task、zone、角色及 omp 类型；空 Map 拒绝启动，不创建 Run/Chat。
- Task 类型、保存合法性及角色固定扩展按[字段权威](02-map-definition-contract.md#task-类型与必需角色扩展)验收；覆盖默认类型、非法 agent/角色扩展组合的前后端拒绝及类型切换。已有 Task 按[迁移契约](02-map-definition-contract.md#格式版本示例与运行期间修改)一次性转换，核对 ID、完整配置和历史来源关联保留，不以 Map/Bot 示例重建豁免代替 Task 迁移。
- zone 路径按字段权威验证登记及有效性，取消登记后拒绝启动、同路径重新登记后重新执行整图检查，不要求新增稳定 ID 或目录搬迁跟随。
- 双角色自动装配须核对[接入权威](08-omp-tool-integration.md#孪生-extension-与-framework-分层)的 startup policy、配置文件路径及稳定基目录；在不同 node zone 下仍解析正确配置并实际取得角色工具指引。
- 首次启动和 retry 保留完整 Task trigger，包括初始 Skill；关联保存成功后才提交，Resume 不重放。
- 三文件初始化成功后才启动 Chat；关联保存失败不提交指示，已启动的外部 Chat 不伪称回滚。
- 前置未全部 completed 时派发被拒绝且不创建 Chat；已记录派发不重复创建；重复 complete/pause/resume/finish 不重复生效或覆盖首次事实。
- 批量派发逐项结果，一个目标拒绝或失败不阻止其余，不回滚已启动者。同 Run 状态操作串行，pause 等待正在处理的批次；节点 Chat 仍可并行。
- 后端按 session_id 校验归属、角色与当前执行；无关联、错误角色、不适用报告不能越权推进。
- Chat 创建、轮次结束、退出、report 保存均不自动 complete；全部 node completed 才能 finish；终态拒绝状态变更，查询及重复 finish 返回已有事实。
- 不承诺跨崩溃／关联保存失败窗口完整幂等，不把同机信任当强认证。

### 验收三：报告、collect 与通知

- 报告先保存；失败不投递、不形成待办。成功后 collect 不依赖 Herdr 投递。
- 每次重复报告保存新记录，待办按 node 汇总最新适用报告；读取、投递与 collect 检查不消除待办，completed 后不再列为可操作待办。旧执行报告不得作为新执行完成依据。
- 无等待者时保留通知，连续通知可合并检查；没有 running 节点且没有新通知时不无限空等。暂停/结束直接返回现场；到期返回原因，不自动 failed 或 pause；默认 90 分钟，可配置。
- 工具中断/Chat 结束取消 HTTP 并清理等待者；网络错误不伪造快照、自动重试或改变状态。等待不占文件锁或操作串行入口。
- 观察 manager 工作中、空闲、collect 等待时的 Herdr 实际投递表现，不承诺原生 IRC、严格时序或已阅读。保存成功但投递失败保留待办、返回分层结果并写诊断日志，不撤销、自动补投或仅为投递失败重复 report。

### 验收四：常见故障与人工恢复

- pause 禁止新执行，已有执行可报告/完成；resume 不自动派发，paused 拒绝 retry。
- 派发不确定保持 failed 和失败阶段；人工核实已创建则关联实际 Chat 恢复 running，未创建则恢复 pending；核实本身不启动 Chat。
- recover 保留原 Chat 和失败历史，不宣称重新启动；retry 创建独立 Chat，成功更新当前关联，失败仍 failed，保留旧关联和历史。
- 执行阶段 failed 在真实可交接后可人工 complete，但不伪造报告、不自动补齐材料。人工通过已有 Chat 补充结果地址和限制，不依赖 manager→node 新工具。
- 指引区分现场修复、状态恢复、新执行和手动完成，说明重试不撤销旧副作用。不扩展已完成节点返工、下游失效传播或自动恢复平台。

### 验收五：持久化与重启

- run.json 当前状态、history.jsonl 执行/状态历史、messages.jsonl 报告职责分离；当前状态查询不依赖历史重放。
- 状态保存失败不更新内存或成功历史；历史追加失败明确状态已提交，不回滚或说未生效。
- 文件访问协调，文件锁不跨外部启动/投递/collect；目标 Windows 验证安全替换及失败路径，不先删除正式文件，不承诺跨文件事务或断电安全。
- 文件缺失/损坏明确报错，不自动重建为空；JSONL 尾部残缺停止追加，不自动截断。
- 重启旧 Run 只读、不接管、不推断修改原状态，拒绝状态操作/report/collect；Resume 旧 Chat 不接管 Run，不改 node 状态，失败或未知如实反馈。
- manager-chat 启动错误只在当前后端内存与诊断日志，不扩充业务文件；页面刷新保留，重启不重建。此观察规则由原观察权威持有，不取消 node 失败事实持久化。

### 验收六：观察与文档

- 现有 Task 管理入口可创建、查看和编辑类型，固定角色扩展随类型呈现；消费[观察权威](09-observation-experience.md#task-类型配置入口)，不以 Run 发起页的类型筛选替代配置路径。
- workflow 列表/详情展示状态、完成数量、用户要求与 manager 入口；节点显示定义、阻塞/失败、当前报告与 Chat，旧执行单独标注；不新增流程操作按钮。
- node 状态不能只靠颜色或 Chat 在线状态表示。默认 5 秒可配置轮询，仅可见页面轮询、不重叠，恢复可见立即查，支持手动刷新；错误保留上次内容并显示失败和最后成功时间。
- 图明确来自当前 Map；无法可靠对应时不伪造历史图，保留可读取事实与 Chat。无启动进度页；当前启动错误按观察权威展示。
- Task 固定职能、extension 工具指引、本次 input 路径/信息分工不混用；真实界面和工具路径验证使用指南；长期文档通过临时材料依赖检查。

### 验收层次、前提与排除项

真实 Agent 主链路必须实际取证；状态边界和故障用确定性契约检查补齐，页面检查实际界面，不让每个边界都重复昂贵 Agent 全流程。运行前须具备真实 Herdr/omp、角色 Task/扩展、有效 zone、共同 Workspace 能力、可读取的文档/记录/产物路径及可用模型配置；沿用已确认 omp 未开启 autoResume、运行期间配置不变和同机信任前提。缺失真实环境不能以替身宣称主链路通过。具体可执行命令和目标版本由实施核对，本轮不声称运行过。

不再沿用旧验收中的双向问答/广播、独立放行、Delivery、定义或产物快照、独立 stop/graceful shutdown、等待所有 Chat 退出、重启接管/自动重试、human/code 策略实现、强制续轮、原生 IRC、跨文件事务和崩溃窗口完整幂等。pause/resume 承接停止新派发；通信与停止处置分别消费原权威。

### 实施顺序

| 阶段 | 交付与证明 |
| --- | --- |
| 单节点真实闭环 | 定义/Task 角色、必要存储、双扩展、启动关联和 dispatch/report/collect/complete/finish；真实 manager 推动一个 node 完成 |
| 并行与依赖汇合 | A、B → C、批量/依赖/重复约束及新旧报告归属；固定文件主链路与确定性拒绝场景 |
| 常见故障与恢复 | pause/resume/fail/核实/recover/retry/人工完成、部分提交、重启只读；故障注入与人工恢复 |
| 完整观察与交付收口 | scheduler 发起、workflow、Resume、轮询、长期文档；实际页面、完整主链路复验及临时材料依赖检查 |

四阶段不是可选范围，最终全部验收必须满足。必要错误反馈与工具指引随能力交付，不到最后才补。本次不创建实施票据。

### 静态证据与限制

本轮读取全部相关 Lighthouse、原计划、GLOSSARY、Task/Bot 命名 ADR 和测试指引。静态核对 backend/src/chats.rs:28–101 的创建阶段与错误模型、lib.rs:1130–1173 的后台创建回执/查询、lib.rs:967 附近请求 camelCase、现有 code/message 错误响应、config.rs 的服务配置惯例。现有 Chat 创建进度是参考，不意味着 Run 必须复制它；用户明确拒绝。未执行产品、测试、浏览器或真实 Agent；未确定并发布最终逐字段 schema、HTTP 路由或配置键，不将机械整理说成已交付。

## Decision

以六组现行验收和四阶段实施顺序交接既定运行设计，长期文档独立承接最终契约与使用指引。管理者启动观察修订归原观察权威；本次发布决定，按用户要求暂不生成 spec.md。

## User stories

1. As a 实施者, I want 一致的验收范围与阶段顺序, so that 不会重新实现已撤回的放行、双向消息或恢复平台。
2. As a 维护者, I want 长期文档独立完整, so that 删除临时设计材料后仍能理解接口、状态规则及重要取舍。
3. As a 用户或管理者, I want 与真实入口一致的故障和工具指引, so that 能区分现场修复、恢复、重试与交接责任。
4. As a 验收者, I want 真实 Chat 链路与分层边界证据, so that 不会把模拟接口或文件写入当作产品端到端成功。

## Preconditions

- 绑定、字段、状态机、通信、故障、持久化、接入和观察权威提供已确认政策；停止票提供范围处置，不提供停止实现。
- 真实环境与产品能力须后续实施准备和验证；现有静态源码只提供复用线索。

## Postconditions

- 后续 spec 整理按本契约组织，并将长期文档独立性纳入交付验收；本次无 spec 发布。
- 不恢复旧计划的被替代功能，不以阶段顺序削减总验收。
- 具体接口字段和配置整理若出现新行为选择须重新讨论，不把候选命名变成已批准行为。

## Invariants

- Bot/Task/Chat/node 按现行术语分层；管理者操作、报告与 Chat 状态互不冒充。
- 复用现有 Chat 创建、错误响应与配置惯例不等于照搬进度 UI；用户修订优先。
- 长期文档不能依赖临时 spec/Lighthouse；本轮发布仍各主题一个权威，不复制观察政策到消费票。
- 决策完成、spec 整理、产品实现、真实验收是不同完成事实。
