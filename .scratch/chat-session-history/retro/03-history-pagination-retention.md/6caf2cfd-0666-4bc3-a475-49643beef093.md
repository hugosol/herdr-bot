## 1. 高：把已有检查接入仓库级自动护栏

**事实**

- `frontend/package.json` 已有 `test`、包含 TypeScript 检查的 `build`、以及 `test:browser`。
- 本轮靠代理手动串联前端构建、Rust 构建及 Playwright，才完成交付产物验收。
- 本轮补充检索未发现 `.github/workflows/`、`.husky/`、常见 pre-commit／lefthook 配置或统一检查入口；`scripts/` 下发现的是已有 mDNS 专用脚本。

**推断与风险**

现有检查能力已经足够有用，缺口主要在自动执行，而非缺少更多检查规则。后续提交可能遗漏类型检查、受影响回归，或者对旧二进制与旧页面运行浏览器测试。此次代理正确完成了构建顺序，不能据此保证未来每轮都会重复做到。

**建议**

优先建立 Windows CI 护栏，复用现有命令；提供一个统一的浏览器验收入口，把前后端构建作为运行 Playwright 的前置条件。快速检查与较重的浏览器检查分层执行，避免把整套验收塞进每次本地提交。

这是可机械执行的约束，应落在脚本和 CI，而不是新增“提交前记得检查”的代理指令。具体命令继续以包配置和脚本为单一来源，不在多份文档中复制维护。

**完成标准**：干净检出可通过同一入口构建并运行验收；类型错误、Rust 编译失败或分页回归会使自动任务失败。

**未验证**：未检查机器级 Git hooks、外部 CI 平台或分支保护设置，因此结论限定为“当前检索未见仓库内护栏”，不是断言所有外部护栏均不存在。

## 2. 中：提前提供服务端时间夹具，降低公开接口测试对存储格式的耦合

**事实**

**推断与风险**

这不是已证实的验收失败：预写文件能提供明确的排序样例，且本轮还通过真实 register 验证了后续更新。但测试的准备阶段依赖内部存储布局，存储格式重构可能迫使公开行为测试一起修改；新记录取得首次时间的路径也没有由这些预写样例本身证明。

**建议**

后续涉及首次时间、排序或过期的票据，在分票前明确共享的时间控制能力及其依赖归属。通常优先通过受控服务端时间和公开 register 建立记录；预写磁盘夹具保留给必须构造既有文件、损坏文件等条件的分支。

将这一取舍集中放在现有测试参考中，并由 reviewer 判断夹具是否绕过了当前承诺所需的机制。不要把存储字段提升成新的公开 seam，也不要要求执行代理临时引入尚未合入的其他票依赖。

**完成标准**：排序断言保留独立字面预期；更换内部序列化格式不需要改写普通排序／分页行为测试的准备过程。

**未验证**：其他代理只通过协作消息报告了时间注入能力；本复盘没有读取或验证其实现，不将该消息视为已落地的共享接口。
