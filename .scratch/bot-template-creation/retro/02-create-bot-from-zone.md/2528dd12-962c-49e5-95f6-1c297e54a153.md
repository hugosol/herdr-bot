## Retrospective

# 复盘：02 从 zone 创建 Bot（TDD 执行轮）

## 结论摘要

本轮功能交付与针对性验收证据是完整的，但环境层面有三类明显摩擦：**仓库级格式化没有基线、缺少统一自动检查入口、长耗时测试的输出策略不适合代理上下文**。这些问题没有让最终实现失效，却显著增加了操作次数、上下文消耗和误判风险。

以下建议只针对环境与工作方式，不要求继续实现或重跑本票验收。

---

## 高严重度

### 1. `cargo fmt --all` 会污染大量无关文件：先建立格式化基线

**事实**：本轮执行 `cargo fmt --all` 后，`git diff --stat` 从 19 个文件膨胀到 56 个；其中约 37 个与票据无关的文件被重新格式化，随后用 `git checkout --` 手动还原。`backend/src/config.rs` 与 `backend/src/lib.rs` 仍保留了格式化产生的无关 hunk。每次 Git 操作还出现 LF/CRLF 警告。

**推断**：仓库当前不是 rustfmt 干净基线（或 rustfmt 版本/行尾与现有文件不一致），因此“顺手格式化”会制造合并冲突噪声；兄弟票据同时改 `lib.rs`/`config.rs` 时尤其明显。

**建议**：

- 在集成分支上做一次**独立**的“格式化基线”提交（不混入功能提交），并加入 `rustfmt.toml` 固化项目风格。
- 在基线干净后，才把 `cargo fmt --all -- --check` 接进 `scripts/check.ps1` 或 CI。
- 基线清理完成前，提供一个 `scripts/format-changed.ps1`：只对 `git diff --name-only` 中的 `.rs` 文件运行 `rustfmt`，并让 `AGENTS.md` 指向它，明确“不要运行仓库级格式化”。
- 添加 `.gitattributes` 固定行尾，例如 `*.rs text eol=lf`、`*.ts text eol=lf`，消除 CRLF 警告和整文件差异风险。

**预期效果**：格式化不再触碰无关代码；兄弟票据合并时不会因纯格式 hunk 冲突；`git status` 的审查噪声显著降低。

---

### 2. 长耗时测试的输出策略：不要 `--nocapture` + `tail` + 反复轮询 `proc://`

**事实**：

- 本轮运行 `cargo test -- --nocapture | tail -120`，管道在命令结束前不输出；代理因此误判任务挂起，终止了第一次完整测试（`bg_20`）。
- 随后重跑 `bg_21`，多次读取 `proc://bg_21`，每次都返回不断累积的完整测试日志；工具本身多次提示“identical output”，上下文被大量重复测试输出占据。
- 完整后端套件实际运行超过 4 分钟，其中 `no_auto_termination` 约 81 秒、`session_expiry` 约 40 秒、`session_window_config` 约 28 秒。

**建议**：

- 长命令统一重定向到文件，例如 `cargo test > backend/target/test-full.log 2>&1`，代理只读失败段或文件尾部；不要用 `tail` 包裹长进程。
- 默认不加 `--nocapture`；只在单独复现某个失败用例时使用。
- 在 `docs/agents/environment.md`（由 `AGENTS.md` 一行指向）写明：“长耗时测试写入日志文件；不要为长任务反复读取 `proc://` 的累积输出；优先读取失败摘要。”
- 如果测试入口支持，使用 `cargo nextest` 或 `--quiet` 降低成功用例的输出量。

**预期效果**：避免“以为挂起”的误杀，减少重复日志带来的上下文消耗，缩短定位失败的时间。

---

### 3. 缺少统一自动检查入口：错误只能靠实现代理自觉发现

**事实**：仓库根目录未看到 CI 工作流或 `.github` 目录；本轮没有预提交钩子运行 `cargo fmt --check`、`cargo test`、`npm test`、`tsc` 或 `cargo clippy`。格式污染、浏览器测试漏写 `page.goto`、成功文案多一个句号，都是靠代理过程中自行发现并修正的。现有 `cargo clippy` 还有大量既有 warning，因此直接加 `-D warnings` 会失败。

**建议**：

- 新增单一入口 `scripts/check.ps1`，按顺序执行：格式化检查、`cargo test`、`npm test`、`tsc --noEmit`，可选 `cargo clippy` 与 Playwright；把它接进 CI，或至少接进 pre-commit。
- 先处理既有 clippy warning（修复或显式 allowlist），再启用 `-D warnings`。
- 浏览器验收保持独立入口，但在文档中说明“完整检查必须先构建前端与后端”。

**预期效果**：机械性错误在交接前统一暴露；代理不需要凭记忆选择“该跑哪些检查”；review 代理也有稳定的复现命令。

---

### 4. 完整套件与其它验证并发会放大既有 flaky 测试

**事实**：完整 `cargo test` 在运行 `zone_commit::configured_timeout_stops_git_and_its_children_then_releases_the_repository` 时失败一次（期望 200，实得 409 `git-write-in-progress`）。当时 Playwright、clippy 和多个 cargo 验证并发运行；该用例单独重跑通过。该测试与本次票据代码无直接关系。

**推断**：失败与 CPU 负载下的终止确认/资格释放时序有关，属于测试等待条件不够稳健，或并发环境放大了竞态；未验证具体根因。

**建议**：

- 在 `scripts/check.ps1`/CI 中**串行**运行完整后端套件；文档明确“完整验收期间不要并发跑浏览器测试或其它 cargo 任务”。
- 将该用例的“确认终止后资格恢复”改为带截止时间的轮询等待，而不是立即断言；这是测试质量修复，不是重试掩盖。
- 如引入 `cargo nextest`，用其更清晰的失败输出，但不要用自动重试替代修复。

**预期效果**：完整套件的结果可直接作为交接证据，减少“假失败—单独重跑—再解释”的循环。

## 中严重度

### 5. 浏览器测试缺一个“打开页面”的共享前置

**事实**：新增的两个 Playwright 用例最初都忘了 `page.goto(server.baseURL)`，各自等待 90 秒后超时；修复只是补一行导航。错误本身是代理疏漏，但当前支撑文件没有提供可复用的“启动服务并打开应用”入口。

**建议**：

- 在 `frontend/browser-tests/support.ts` 提供 `openApp(page, server)`：导航到 `server.baseURL` 并断言四个顶层入口；所有浏览器用例以它开头。
- 更彻底的做法是提供 Playwright fixture：`appPage` 内部完成 `startServer` + `goto` + 初始断言，测试直接拿可用页面。
- 在 `frontend/browser-tests/README` 或 `CODING_STANDARDS.md` 写明“浏览器用例不得自行裸 `goto`”。

**预期效果**：整类“忘记导航导致 90 秒超时”的错误被结构性消除，并减少每个用例的样板代码。

---

### 6. 测试运行时应隔离所有可配置存储路径

**事实**：一次浏览器测试在 `frontend/zones.json` 留下了运行时登记文件，因为当时测试配置没有设置 `[zones] registry_file`；代理发现后删除，并在 `support.ts` 补上隔离路径。根 `.gitignore` 只覆盖根目录的 `zones.json`。

**建议**：

- `support.ts` 的临时配置一次性写全所有可落盘路径（zones、bot_templates 等），并在测试结束后断言仓库根/前端目录没有新增运行时文件。
- 在 `.gitignore` 增加广义运行时文件模式，如 `**/zones.json`、`**/zones.json.tmp`、`**/bot-templates.json`、`**/bot-templates.json.tmp`。
- 若可行，在 pre-commit 或 `scripts/check.ps1` 中增加“未跟踪的运行时文件”检查。

**预期效果**：测试之间、worktree 与集成分支之间不再留下未跟踪产物；`git status` 的交接检查更可信。

---

### 7. 进程级 TOML 测试配置重复，新增必填段会反复改多处

**事实**：`[herdr] workspace_name` 成为必填后，代理需要修改至少 8 处测试 TOML 写入点（`bot_templates.rs`、`manual_shutdown_process.rs`、`mdns_conflict.rs`、`mdns_failure.rs`、`session_window_config.rs` 两处、`zone_registry.rs`、`shutdown.rs` 旧配置），以及 3 处 `Config` 结构体字面量。多个测试文件各自维护 `write_process_config`。

**建议**：

- 在 `backend/tests/common/mod.rs` 提供统一的 `process_config(overrides)` 构建器，默认包含所有必需段与安全默认值；各用例只覆盖自己关心的字段。
- 为 `Config` 字面量提供测试构造器（如 `common::test_config()`），避免每个新增字段要求所有测试同步修改。
- 让 `[herdr]` 这类“无代码缺省”的必填项只在一个 helper 中出现。

**预期效果**：未来新增必填配置只需改一处；测试文件不再因无关字段变更而大面积编辑。

---

### 8. 缺少本仓库视角的 Herdr 控制面参考文档

**事实**：本轮实现 Herdr adapter 时，需要阅读外部 herdr 仓库的 agent automation 文档、运行 `herdr --help`、`herdr agent start --help`，并导出 `herdr api schema` 来确认 `workspace list` / `tab create` / `agent start` / `agent prompt` 的 JSON 形状与就绪语义。`docs/bot-template-agent-inputs.md` 覆盖了输入语义，但没有这些控制命令与响应指针。

**建议**：

- 新增 `docs/herdr-control-surface.md`，固定记录：本产品使用的 CLI 命令、成功响应的 JSON 指针（`/result/workspaces`、`/result/tab/tab_id`、`/result/root_pane/pane_id`、`/result/agent`）、`agent start` 的“成功即就绪”语义、`agent prompt` 不等待轮次、无 Shell 传参原则，以及受控 fixture 的行为约定。
- 从 `AGENTS.md` 或 Bot 创建相关文档加一行指针；外部 herdr 版本变化时只更新这一处。

**预期效果**：后续票据（03/04/05/06/07）不必重复探索外部仓库与 schema；adapter 行为有单一事实源。

---

### 9. 后端进程级测试隐含依赖前端构建产物

**事实**：`backend/tests/herdr_config.rs` 的“合法显式值启动成功”用例要求 `backend/static/index.html` 存在，因此在一份未构建前端的 worktree 中，纯后端配置测试也会失败或需要额外构建。测试中对此有显式断言与提示。

**建议**：

- 为测试提供静态目录覆盖（例如 `HERDR_BOT_STATIC_DIR` 或启动参数），让后端进程测试使用一个最小静态夹具，而不是依赖 `frontend` 的真实构建。
- 若不改产品入口，至少在 `docs/agents/environment.md` 和测试说明中把“后端进程测试需要先构建前端”写成前置条件，并让 `scripts/check.ps1` 自动完成构建。

**预期效果**：后端测试可独立运行；新代理不会被“配置测试为何需要 npm build”卡住。

---

### 10. 受控 Herdr 替身位于生产 `src/bin`，会被普通构建包含

**事实**：受控替身放在 `backend/src/bin/herdr-fixture.rs`，是普通 bin target；`cargo build` 会构建它。它只在自动验收中使用，但当前没有 feature gate 或独立测试包。

**推断**：release 构建产物会包含一个模拟 herdr 的可执行文件；未实际检查 release 包内容。

**建议**：

- 用 `required-features = ["test-fixture"]` 限定该 bin，并让测试以显式 feature 运行；或把它移到独立的测试支持 crate/目录。
- 在 `CODING_STANDARDS.md` 或 review 清单加入一条：测试替身不得进入生产 binary target。

**预期效果**：交付产物保持干净；测试支撑代码与生产入口的边界明确。

---

### 11. TDD 期望值曾镜像实现，而不是规格

**事实**：成功文案最初实现为“创建成功，初始指示已提交。”，浏览器测试也按这个带句号的字符串断言；后来重新对照 spec 才改为不带句号的版本。也就是说，该断言在某个阶段是**同义反复**的，无法发现实现与契约文案的偏差。

**推断**：从编辑顺序看，部分测试是在实现之后补写的（`bots.rs` 单元测试、`bot_creation.rs` 集成测试等），因此更容易把实现的当前值当成期望值，而不是先固定 ticket/spec 的字面值。

**建议**：

- 在 `CODING_STANDARDS.md` 增加一条 review 规则：**ticket/spec 引号内的 UI 文案必须在测试中以字面量出现，且该测试应先于组件实现存在**；不得从组件常量或当前实现复制。
- 在实现票据模板或最终报告模板中增加一个轻量字段：“本票新增测试的首次 red 输出/失败原因”，迫使每个验收标准至少有一次可观察的红。
- 对多验收标准的票据，按“一个标准 → 一个测试 → 一段实现”维护垂直切片清单，而不是最后集中补测试。

**预期效果**：减少“测试通过但契约文案/行为已偏离”的盲区；TDD 的红绿证据可审计。

## 低严重度

### 12. 测试辅助函数避免位置索引，API 客户端避免重复归一化

**事实**：Vitest 的 `openDialog` 默认 `rowIndex = 1`，在只有一个 zone 的用例中直接失败；浏览器测试则已改为按 zone 路径定位。`botCreationApi.ts` 与 `botTemplateApi.ts` 各自实现了几乎相同的 `ok / rejected / unreachable` 请求归一化。

**建议**：

- 测试中按 zone 路径或稳定 test id 定位行，而不是数组下标；若保留索引，默认值应为 0。
- 提取共享的 `jsonRequest<T>`（或 `requestJson`）工具，集中处理响应解析与错误类别；两个 API 模块只保留类型守卫与端点函数。

**预期效果**：测试不因列表顺序或多一个 zone 而脆弱；请求语义只有一个实现。

---

### 13. 启用 `-D warnings` 前先处理既有 clippy 基线

**事实**：`cargo clippy --all-targets` 在本轮新代码中（修复一个 collapsible-if 后）没有 warning，但仓库既有测试/模块存在大量 warning。

**建议**：在把 clippy 接入 `scripts/check.ps1` 或 CI 时，先修复或显式 allowlist 既有 warning，再启用 `-D warnings`；否则新 guardrail 会一上来就红。

**预期效果**：lint gate 可以真正阻止新问题，而不是被既有噪声淹没。

---

## 可保留的做法

- 用**独立进程的受控 Herdr 替身**记录调用与 Tab 标识，而不是让测试读取实现内部状态；外部记录与公开响应分开比对，证据链清晰。
- `P49` 名称测试直接验证“逐参数、无 Shell”的包装层，并用 Shell 标记文件作为反证；这是比断言私有函数更可靠的接缝测试。
- README 中补充了 H1 真实运行步骤（Workspace、目录、Tab/Pane 定位、cwd、阶段与提交确认），为后续人工验收保留了可执行证据清单。
- 对模板快照、独立创建生命周期、独立 agent 别名等基线约束，在实现中直接采用，没有先依赖显示名唯一或请求存活。
