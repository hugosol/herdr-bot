# Ticket 06 失败与超时语义 — TDD 执行复盘

## 摘要

本票已提交实现（ticket 分支 `b224c00`），自动验收实际运行结果：`cargo test --test bot_creation` 13 通过、全量后端 `cargo test` 完成且可见套件均通过（344.71 秒）、前端 `npm test` 178 通过、`npm run build` 通过、`npx playwright test` 6 通过。以下建议按严重度排列，并标注事实、推断与未验证项。

## 1. 高 — 提交超时切片的 red 未被独立观察，且测试硬编码了 31 秒

**事实**：`a_timed_out_submission_is_unconfirmed_and_keeps_the_site_without_retrying` 使用 `prompt_delay_ms: 31_000` 睡过生产 adapter 的 30 秒 `PROMPT_TIMEOUT`，单测耗时约 30.72 秒，整个 `bot_creation` 套件因此约 30.79 秒。该用例是在 `backend/src/bots.rs` 的 `stage_message` 已经改好之后才第一次运行并通过；真正观察到的 red 只有启动失败与提交被拒绝两条消息断言（`tests/bot_creation.rs` 约 576、461 行）。因此“超时测试能抓住旧的错误表述”来自对旧字符串的推断，而不是实际 red 运行。

**推断**：慢测试是这次把多个测试先批量写完、再统一改实现的直接诱因；TDD skill 明确要求每个切片先观察 red，慢反馈会让 agent 倾向跳过该步骤。

**建议**：
- 给 Herdr 控制 adapter 增加可注入的时限（例如 `HerdrClient::with_timeouts`，或 `HerdrConfig` 中可选、带生产默认值的 `timeouts` 字段），让测试把提交时限调到几百毫秒，同时保留生产默认值。这样超时测试可从 30 秒降到 1 秒内，red/green 循环才可持续。
- 用该接缝补上 `tab_create` 超时与 `agent_start` 超时用例；它们能同时验证“未取得标识不伪造”和 `FailureStage::Tab/Start` 的未知结果表述。
- 在修改实现前单独运行新超时用例并保留失败输出；如果测试仍很慢，至少先运行一次“旧实现 + 新测试”的对照，而不是仅靠阅读旧字符串推断。

## 2. 高 — 新增的 Tab/Start 超时分支没有被测试覆盖

**事实**：`backend/src/bots.rs` 新增了 `FailureStage::Tab if outcome_unknown` 与 `FailureStage::Start if outcome_unknown` 两条消息分支；本票测试中 Workspace 查询、Tab 创建、启动、提交都有“明确失败”覆盖，但只有提交阶段有超时覆盖。没有测试让 `tab_create_delay_ms` 或 `agent_start_delay_ms` 超过对应时限。

**推断**：这两条分支目前只靠代码审查保证正确；未来修改 `HerdrError` 分类或时限时，变化不会被测试发现。

**建议**：
- 在可注入时限的基础上补两条受控超时用例：Tab 超时断言无 `tabId`/`paneId`/`agentName` 且说明“无法确认 Tab 是否创建”；启动超时断言 Tab/Pane 已保留、`agentName` 已保留、没有提交初始指示。
- 在 CI 中加入后端覆盖率检查（如 `cargo llvm-cov` 或 `cargo tarpaulin`），至少对本功能的 `bots.rs` 分支做人工审阅；本票未运行覆盖率工具，这一点属于未验证项。

## 3. 中 — 仓库缺少可用的格式/静态检查护栏，`cargo fmt --check` 基线不干净

**事实**：`cargo fmt --check` 报告了多处与本票无关的差异，例如 `backend/examples/safe_shutdown_shell.rs`、`backend/src/browse.rs`、`backend/src/commit.rs`，以及 `backend/tests/bot_creation.rs` 约 1001 行的既有格式差异。为避免改动其他票据的工作，我只手工格式化了本票新增/修改的片段，没有运行全局 `cargo fmt`。

**推断**：在这种基线下，agent 无法把 `cargo fmt --check` 当作可信的完成门槛；格式漂移会继续累积，review agent 也难以区分本票引入的格式问题。

**建议**：
- 先做一次独立的“仅格式化”提交清理基线，然后在 CI 或 pre-commit hook 中启用 `cargo fmt --check`。如果没有现成 CI，至少提供 `scripts/check.ps1` 之类的仓库级检查入口。
- 同一次检查入口中加入 `cargo clippy --all-targets -- -D warnings`。本票没有运行 clippy，仓库当前是否存在 CI/pre-commit 配置也未检查，属于未验证项。
- 如果短期内不能清理全仓格式，至少在 PR/票据检查中对“变更文件”运行 rustfmt，避免新增格式债务。

## 4. 中 — Ticket 工作树缺少前端依赖与构建产物，没有预检

**事实**：首次运行 `npx vitest run tests/botCreation.test.tsx` 因缺少 `@vitejs/plugin-react` 与 `vitest/config` 失败（`ERR_MODULE_NOT_FOUND`），执行 `npm ci` 后才可运行。Playwright 还需要 `backend/target/debug/herdr-bot.exe`、`herdr-fixture.exe` 与 `backend/static/index.html`；`support.ts` 对缺失二进制/页面已有明确报错，但前端单测的模块缺失报错是较长的 Node 栈。

**推断**：每个新 ticket worktree 都要重新安装依赖与构建产物；没有预检时，agent 会先撞错误再排查，浪费时间并可能误判为代码问题。

**建议**：
- 在 README 的测试命令旁补一句首次运行 `npm ci`；更好的是提供 `scripts/bootstrap.ps1`（或类似入口）一次完成 `npm ci`、`cargo build`、`npm run build`。
- 在 `frontend/package.json` 增加一个 `pretest` 检查：若 `node_modules` 缺失，直接输出“请先运行 npm ci”，而不是让模块解析失败。不要让 `pretest` 自动联网安装。

## 5. 中 — codebase-memory 对临时工作树未建索引，回退到整文件读取

**事实**：本票开始时 `mcp__codebase_memory_mcp_search_graph` 返回 `project not found or not indexed`，可用项目列表中没有当前 worktree；我没有调用 `index_repository`，随后改用 grep 与 `read`。`read` 的裸代码读取只返回声明并省略实现，导致我再次用 `:1-N:raw` 重读 `bots.rs`、`herdr.rs`、`bot_creation.rs` 等文件。

**推断**：临时 ticket worktree 不会自动注册到 codebase-memory，用户“先查大纲/符号片段”的提示在未索引时无法执行；整文件重读增加了上下文与 token 成本，也让探索路径更依赖人工 grep。

**建议**：
- 在 ticket 执行预检中增加一步：MCP 报告项目未索引时，先对当前 worktree 调用 `index_repository`（或由宿主在派发前注册），再使用 `search_graph`/`get_file_outline`。

- 如果不想新增文档，至少在本票模板或派发提示中直接给出上述文件清单与 “README 的‘从 zone 创建 Bot’与测试章节”。这次我是在实现完成后才读 README 对应章节，顺序上本可以更早。

## 6. 低-中 — 页面用错误码字符串推断“明确拒绝/未知”

**事实**：`frontend/src/BotCreationDialog.tsx` 的 `failureOutcomeText` 用 `failure.code === 'herdr-command-failed'` 区分“明确拒绝”与“结果未确认”；后端 `stage_message` 同样按 `HerdrError` 变体分类。公开结果目前只有 `failure:{stage,code,message}` 与 `inputSubmitted` 布尔值。

**推断**：错误码字符串已经成为事实上的语义契约；新增错误码时，客户端默认落入“未确认”分支，虽然保守，但“明确拒绝/未知”的语义仍要靠客户端理解后端错误目录。

**建议**：
- 在公开创建结果中增加一个显式的结果分类，例如 `failure.kind: "rejected" | "unknown" | "not-attempted"`（或 `inputOutcome`），页面只读该字段，不再解析错误码。契约 P36 已经要求“明确区分已有现场与未确认投递”，这会让该承诺在 S2 上机器可读。
- 如果暂不扩展公开结果，至少在 README/契约中把 `herdr-command-failed` 与 `herdr-timeout` 的语义写成稳定契约，并在 review 标准中要求客户端不要用 prose 判断结果。

## 7. 低 — 实际使用了 shell `grep`/`cat`/`find`，绕过专用工具

**事实**：本会话多次通过 `bash` 执行 `grep -n ...`、`grep -rn ...`、`cat backend/Cargo.toml`、`find backend frontend -type f`，而工具策略要求使用专用 `grep`、`read`、`glob`。这些调用结果本身正确，但违反了声明的工具使用规则。

**推断**：这属于执行习惯而非仓库文档缺失；系统提示已经写明规则，再在 `AGENTS.md` 重复一遍会是 no-op。若宿主支持 pre-tool hook，拦截 shell 形式的文件检索/读取会更有效；否则只能在执行提示中保留简短检查项。

**建议**：
- 如果宿主支持工具前置拦截，对 `bash` 中的裸 `grep`/`rg`/`cat`/`find` 给出警告或拒绝，并提示对应专用工具。
- 如果不支持，考虑在 ticket 执行提示中加入一行“搜索用 grep/find，读文件用 read，列文件用 glob”的检查项；不要把它写进仓库 `AGENTS.md`，避免与全局策略重复。

## 8. 低 — `AGENTS.md` 本身已经精简，暂不需要新增规则

**事实**：仓库 `AGENTS.md` 只有 issue tracker、triage labels、domain docs 三个导航指针，没有大段行为规则；本票执行中没有发现需要新增的“全局行为”规则。
