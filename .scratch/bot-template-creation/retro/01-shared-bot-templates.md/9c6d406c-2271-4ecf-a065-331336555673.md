# 复盘：01-shared-bot-templates（TDD 实现轮）

## 高

### 1. 缺少统一检查入口，也缺少任何 CI / 预提交门禁

**事实**：仓库没有 `.github/`、没有 `justfile`/根 `package.json`/`.pre-commit-config.yaml`；`scripts/` 只有 `run-mdns-tests.ps1`。本票的检查分散在四条命令：`cargo test`、`npm test`、`npm run build`、`npx playwright test`，且真实浏览器用例不在 `npm test` 里。会话中全量 backend suite 跑了两次，每次约 270 秒。
**推断**：后续 agent 很容易只跑 `cargo test` 或只跑 `npm test`，漏掉真实浏览器验收；本票新增的 Playwright 用例没有默认入口，等于半自动检查。
**建议**：增加一个仓库级 `scripts/check.ps1`（或 `.cmd`），作为唯一入口，按依赖顺序执行：
1. `npm --prefix frontend ci`（可选，首次）
2. `npm --prefix frontend run build`（同时生成 backend 测试所需的 `backend/static`）
3. `cargo test --manifest-path backend/Cargo.toml`
4. `npm --prefix frontend test`
5. `npm --prefix frontend run test:browser`

把它接到 pre-commit hook；若未来引入 CI，同一脚本直接复用。**完成判据**：干净 checkout 上执行该脚本一条命令即可完成本票全部自动检查，且失败时能指出是哪一层。

### 2. `cargo test` 隐性依赖前端构建产物，干净工作区会失败

**事实**：本票开始时先跑 `cargo test --quiet`，`session_write_boundary::reads_are_open_to_lan_sources` 因 `GET /` 返回 404 失败；执行 `npm run build` 生成 `backend/static/index.html` 后同一套测试全绿（305 passed）。
**推断**：这不是本票代码缺陷，而是测试前置条件没有编码：该用例断言“局域网来源读得到打包页面”，因此必须有前端构建产物；README 的测试章节却直接从 `cargo test` 开始。
**建议**：两选一，优先第一个：
- 在 `docs/agents/testing.md`/README 明确“backend 测试前先 `npm run build`”，并由统一检查脚本保证顺序；
- 或让该用例在缺少打包页面时给出明确的跳过/前置错误，而不是 404 断言失败（不改变“页面读取不受来源限制”的断言本身）。

### 3. 能力事实仍散在外部仓库，文档没有给出本票所需的定表

**事实**：`docs/bot-template-agent-inputs.md` 说明了 OMP/Pi 的能力元数据位置，但没有直接列出本票两个模型（`gpt-6.1-sol`、`deepseek-flash`）在 OMP 与 Pi 下的确切 efforts/levels。实现时 agent 用 Python 读取 945KB 的 OMP `models.json`、筛选 25 条记录，又阅读 Pi `generate-models.ts` 与 `models.ts` 的 `getSupportedThinkingLevels`，最后把表硬编码进 `backend/src/templates.rs` 和测试。
**推断**：后续 03（provider/model 映射与启动参数）和 04（投递）会再次需要同一组事实；目前“源码 → 记忆 → 代码/测试”三处可能漂移，且每次都要重新访问外部仓库。
**建议**：在现有 `docs/bot-template-agent-inputs.md` 增加一张“本产品固定模型能力表”，至少包含：模板值、OMP provider/id、OMP `thinking.efforts`、Pi provider/id、Pi `getSupportedThinkingLevels` 结果、非推理模型处理、源码路径与核对日期/版本。测试仍用独立字面样例断言，但事实来源收敛到这张表；未来改动先改表再改代码。
**完成判据**：实现者不再需要打开外部 OMP/Pi 目录即可回答本票所有 thinking 选项问题。

## 中

### 4. Vitest 不做类型检查，缺失 import 直到执行对应路径才暴露

**事实**：`BotTemplatesPanel.tsx` 曾引用未导入的 `deleteBotTemplate`；Vitest 直到点击删除按钮时才以 unhandled rejection 暴露，而不是在测试文件导入时失败。`npm run build` 的 `tsc --noEmit` 才会静态发现。
**推断**：前端 TDD 的快速红绿循环容易漏掉“只在某些分支执行的未定义符号”；把类型检查放进每轮循环或至少统一检查入口，能更早拦截。
**建议**：在 `frontend/package.json` 增加独立 `"typecheck": "tsc --noEmit"`（`build` 已包含，但语义更清楚），并把它加入 `scripts/check.ps1` 与 pre-commit；前端测试文档明确“Vitest 只验证行为，类型检查由 typecheck 负责”。

### 5. README 同时承载当前文档与 20+ 条历史变更记录

**事实**：`README.md` 约 2066 行；当前配置/测试/功能文档集中在前半部，后半部有大量 `## 变更记录：…`、`## 交付验证记录…`、人工验收移交章节。本票为找配置与测试位置多次 `grep` 并读取多个区间。
**推断**：每次新功能都往同一个文件追加，导航成本随历史线性增长；agent 很容易把历史验收记录误当当前承诺。
**建议**：把历史 `## 变更记录：*`、`## 交付验证记录*`、`## 人工验收移交*` 迁到 `docs/releases/` 或 `docs/verification/`，README 保留当前行为、配置、测试和一条“历史记录见 …”指针。历史内容不改写，只做物理分层。

### 6. 没有测试导航文档，测试接缝靠逐个文件拼出来

**事实**：本票为写测试读取了 `backend/tests/common/mod.rs` 三个区间、`zone_registry.rs` 三个区间，以及 `FileListPanel.tsx`、`zoneApi.ts`、`fileList.test.tsx`、`tabs.test.tsx`、`setup.ts` 等；才拼出 `TestServer`、`get_over_tcp`/`post_json_over_tcp`、`TempDir`、真实进程 `Panel` 模式、前端 fetch stub 与 `data-testid` 约定。`AGENTS.md` 目前只有 issue tracker、triage、domain 三个指针，没有 testing。
**建议**：新增 `docs/agents/testing.md`，一句话概括各层接缝与最小例：
- backend HTTP 集成：`TestServer` + `get_over_tcp`/`post_json_over_tcp`/`request_json_over_tcp`；
- 文件/进程隔离：`TempDir`、`FixtureTree`，真实重启复用 `Panel` 模式；
- 前端组件：Vitest + 全局 `fetch` stub + `data-testid`，`within(dialog)` 缩小查询；
- 真实浏览器：`playwright.config.ts`、先 build frontend/backend；
- 配置构造：优先 `common::config`，直接 `Config { … }` 会在新增字段时编译失败（本票实际发生过 `fixed_operations.rs`、`start_operation.rs` 两处）。

在 `AGENTS.md` 增加一条带分支的指针，例如：“写测试前读 `docs/agents/testing.md`；backend 集成、frontend 组件、真实浏览器分别按其接缝选择。” 指针只写触发条件，不复制正文。

### 7. 票面粒度过宽，削弱了“一红一绿一实现”的切片纪律

**事实**：`backend/src/templates.rs` 在首个 list/create 测试变绿后，一次性写入了 update/delete、完整校验、options 能力表；对应测试是之后补的。TDD skill 要求“one seam, one test, one minimal implementation per cycle”。本票同时承载持久化、HTTP CRUD、字段/能力校验、前端 tab/表单联动、Playwright 基础设施。
**推断**：票面把多个垂直切片装进一张票，实现 agent 倾向先铺完模块再补测试；这不是单个测试写错，而是工单切片与 TDD 循环冲突。
**建议**：在 `/to-tickets` 的 implementation ticket 模板中增加“Vertical slices（建议顺序）”小节，例如本票可切为：① 持久化 + list/create 字面往返；② 校验与能力表；③ edit/delete；④ 前端读取/create；⑤ agent/model/thinking 联动；⑥ 保存失败 + 重启。每个切片要求“先红后绿”，并只改该切片需要的代码。票面可保留完整验收标准，但执行顺序显式。

### 8. `cargo fmt --check` 不可用作门禁

**事实**：`cargo fmt --check` 在 29 个既有文件上报告差异，本票无法把它作为提交前检查；新增 `templates.rs`/`bot_templates.rs` 只能单独 `rustfmt`。
**推断**：格式检查长期不可用，会让新代码依赖人工/模型自觉，也让 review 噪声增加。
**建议**：单独做一次“只跑 `cargo fmt`”的格式化提交，随后把 `cargo fmt --check` 加入统一检查脚本/pre-commit。不要在本票这类功能提交里顺手格式化全仓。

## 低

### 9. 真实浏览器策略与前置依赖未预先固定（本票已部分解决）

**事实**：`npx playwright --version` 为 1.64.1，但本机已有 Chromium 是 1243，测试要求 1248；先启动 197MB 下载，后改用 Playwright `channel: "chrome"` 使用系统 Chrome，测试通过。本票已在 `playwright.config.ts` 与 README 记录该选择和构建前置。
**推断**：如果下一位 agent 不知道这个选择，可能再次触发浏览器下载或版本漂移。
**建议**：把 `@playwright/test` 固定为精确版本（当前 `package.json` 是 `^1.64.1`，`package-lock` 已锁但重新安装可能升级），并在统一检查脚本里先做 preflight：检查 Chrome、`backend/static/index.html`、`backend/target/debug/herdr-bot.exe`，缺失时给出与 README 一致的修复命令。

### 10. 工具 schema 先猜后读，造成两次 MCP 参数失败

**事实**：`mcp__codebase_memory_mcp_index_status` 首次调用缺 `project`；`index_repository` 首次误用 `project` 而非 `repo_path`。系统本已要求首次使用前读 `xd://<tool>` 文档。
**推断**：MCP 工具的参数名与直觉不一致时，猜参数比读 schema 更贵。
**建议**：保持“首次使用前读 `xd://...`”的规则；若可改 MCP，考虑为 `index_status` 提供 cwd 默认 project、或在错误中直接给出最小合法调用示例，降低一次失败成本。

### 11. 小 `old_string` 的歧义失败，以及 python/cat 文本编辑

**事实**：本会话有 5 次 edit 失败，其中两次因 `old_string: "})"` 匹配 9/19 处而返回大段上下文；随后 agent 两次用 `python - <<'PY'`、一次用 `cat >>` 修改文件，违反“不要用 shell 做单点编辑”的明确规则。
**推断**：歧义错误返回过大 + 追加型修改的诱惑，使工具规则在上下文压力下被绕过。
**建议**：优先在工具层收紧：对 `python`/`sed -i`/`cat >` 形式的文件写入直接拒绝并提示用 `edit`/`write`；`edit` 的歧义错误只返回“匹配 N 处 + 前几个短位置”，不要整段 dump。仓库侧可约定：新增测试文件用 `write` 整文件落盘，追加测试时用唯一的 `describe`/函数名作锚点，而不是 `})`。
