## 候选改进（按严重度）

### 1. 高｜Rust 格式化没有稳定护栏，一次仓库级 `cargo fmt` 改动 48 个已提交文件；随后的宽泛回滚又丢失两个前端文件的编辑

**类别：** Automated checks / 工作流

**事实：** 本票开始时 worktree 干净。执行一次 `cargo fmt --manifest-path backend/Cargo.toml` 后，`git diff --stat` 显示 48 个文件、+1602/−588，其中绝大多数与本票无关。随后用 `git diff --name-only | grep -v <两个后端文件> | xargs git checkout --` 清理，结果把此前已完成的两个前端文件编辑（`frontend/tests/botCreation.test.tsx`、`frontend/browser-tests/botCreation.spec.ts`）也回滚了；重新跑 Vitest 时发现用例数从 4 变成 3 才察觉，随后重新应用。

**推断 / 未验证：** 从一次 `cargo fmt` 即可改动 48 个已提交文件推断，仓库当前没有以相同工具链强制 `cargo fmt --check`，或已提交格式与当前 rustfmt 版本不一致。未检查 CI 配置，也未确认这是否是预期状态。

**建议：**
- 先运行 `cargo fmt --check` 并做一个明确决定：要么一次性规范化格式并加入 CI 的 `cargo fmt --check`，要么用 `rust-toolchain.toml` 固定工具链版本，避免本地与 CI 漂移。
- 在护栏建立前，文档或脚本只格式化改动文件：`rustfmt --edition 2024 <touched files>`（本会话最后即用此方式验证 `FORMAT_OK`），不要运行仓库级 `cargo fmt`。
- 若仍需清理格式化噪声：先提交或暂存与本次任务相关的编辑，再只对**显式列出的纯噪声文件**执行回滚；回滚后检查 `git status` 并重跑受影响用例数。不要把 `git diff --name-only` 的输出整体交给 `git checkout --`。
- 可考虑加一个很小的 `scripts/fmt-touched.ps1`，但核心是 CI/工具链护栏，而不是再加一条“不要跑 cargo fmt”的文字。

**为什么严重度高：** 它直接造成已完成的实现被回滚和重复工作，且会让评审 diff 混入大量无关改动；这是可自动发现的环境问题，不是本票特有的失误。

### 2. 中高｜Playwright `afterEach` 的清理在 Windows 上偶发 `EPERM`，把通过的用例判为失败

**事实：** 第一次完整运行 `botCreation.spec.ts` 时，业务断言已通过（页面快照显示了正确的全空失败流程），但 `afterEach` 在 `frontend/browser-tests/botCreation.spec.ts:28` 删除临时 `zoneRoot` 时抛出 `EPERM`，导致该用例被报告为失败。单独重跑该用例、以及随后两次完整浏览器套件均通过。

**推断 / 未验证：** 可能是服务停止后仍有 watcher、文件句柄或系统扫描短暂持有目录；未确认具体持有者。

**建议：**
- 给 `fs.rmSync` 的清理加短重试/退避（例如 3–5 次、50–200ms），并在重试后仍失败时只报告清理问题，不把业务用例判为失败；或至少对 `EPERM`/`EBUSY` 做显式处理。
- 确认 `server.stop()` 已等待所有后台任务、watcher 与子进程退出后再删目录。
- 不建议用 Playwright 全局 `retries` 作为首选修复：它会掩盖真实的业务失败；先修 teardown。

**影响：** 一个通过的验收用例被报告为失败，会直接侵蚀测试信号，尤其在做人工 H1 前需要稳定证据时。

### 3. 中｜`zone_sync` 的超时用例对机器负载敏感，全量套件会出现与本次改动无关的失败

**事实：** 较早一次全量 `cargo test` 中，`configured_timeout_stops_the_running_command_and_keeps_effective_pull_state` 因 `git push` 超过配置的 1 秒上限而返回 504（期望 200）；它单独运行通过，最终全量也通过。该文件本票未修改。

**推断 / 未验证：** 该用例依赖真实 `git` 进程在 1 秒内完成/超时，在并发或负载较高时不稳定；未确认 CI 是否已有重试或隔离策略。

**建议：**
- 让慢操作可控：用受控的慢 git hook/包装脚本，而不是依赖机器速度；或提高该用例的超时并明确其只验证超时分类，不验证绝对耗时。
- 若无法避免环境敏感性，将该类用例标记为 `#[ignore]` 或单独慢速套件，并在 README 记录“需要空闲机器”；不要让已知 flake 混在每次全量回归里。
- CI 中不要用盲目重试掩盖；至少把失败分类为“超时类”并单独报告。

### 4. 中｜浏览器测试不在 `tsc` 的 include 内，仓库脚本只转译不类型检查

**事实：** `frontend/tsconfig.json` 的 `include` 是 `["src", "tests", "vite.config.ts", "vitest.config.ts"]`，不含 `browser-tests`；`npm run build` 是 `tsc --noEmit && vite build`；`package.json` 没有浏览器测试的类型检查脚本。Playwright 默认转译 TypeScript，但不做类型检查。

**推断 / 未验证：** `browser-tests` 中的类型错误目前只会在运行时暴露；本会话的 `npm run build` 通过并不能证明浏览器 spec 类型正确。未检查 CI 是否有额外类型检查。

**建议：**
- 增加 `tsconfig.browser.json`（包含 `browser-tests`，设置 `types: ["@playwright/test"]` 及必要的 node 类型），并加 `typecheck:browser` 脚本，接入 `npm run build` 或 CI。
- 或者把 `browser-tests` 纳入主 `tsconfig`，前提是 Playwright 类型与现有 Vitest 类型不冲突。
