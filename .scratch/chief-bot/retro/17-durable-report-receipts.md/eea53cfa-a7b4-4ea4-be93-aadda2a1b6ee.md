# Ticket 17 TDD 执行复盘

## 1. 高：隔离依赖安装，避免并行 worktree 共用可变依赖链接

**事实**：首次 `bun install --frozen-lockfile` 和页面构建成功；随后完整浏览器构建因共享 Bun cache 中缺少 `picocolors` 失败。项目 `frontend/bunfig.toml` 配置了 `globalStore = true`。代理使用临时 `globalStore=false` 配置及本 worktree cache 重装后，完整浏览器入口通过。

**推断**：共享可变链接是安装成功后依赖不可用的风险来源，但现有记录不足以证明是哪一次并发安装破坏了它，不能归责于其他代理。

**建议**：在创建验收 worktree 的宿主初始化环节，统一使用 worktree 独占的依赖链接与 cache；保留 frozen lock。将隔离策略落实在安装入口，而不是让每票遇到模块缺失后临时修补。安装与构建失败的原始日志应同时保留，避免后续成功覆盖首次故障。

**完成标准**：两个并行 worktree 安装、重新安装和构建互不改变对方依赖解析；缺失依赖仍以原始非零状态报告。

## 2. 中：让“丢失回执”夹具显式区分请求取消与已提交响应丢失

**事实**：首次 TCP 场景写完请求立即关闭连接，5 秒内未观察到持久接收，测试失败。代理随后保留连接，先通过公开 receipt 接口确认提交，再丢弃从未读取的响应；该场景通过。记录明确保留了初始失败及修正原因，没有把失败解释为产品已满足要求。

**建议**：在现有 HTTP 故障夹具中提供可复用的“已提交、响应未消费”操作：提交请求 → 通过独立公开观察确认提交 → 丢弃响应。把“请求尚未接受即取消”保留为另一种故障。该区别应放在故障夹具旁，测试编写者使用对应场景时才加载，不增加全局 AGENTS.md 负担。

**完成标准**：回执丢失测试必须证明提交已发生；请求取消测试不冒充回执丢失。两者均保留有界等待、原始错误和所属资源清理结果。

## 3. 中：缩短图查询与日志读取的输出，保留必要证据而不是完整封装

**事实**：代理通过 eval 连续输出多个 MCP declaration outline 的完整工具返回，包含重复的 `text`、元数据和结构化结果，输出达到截断上限；读取完整后端 summary 后，也因目标数组被折叠，再次使用查询选择器提取所需 target。工具说明还被重复读取。

**建议**：MCP 批量调用默认只呈现声明名、路径、行号和分页状态；工具封装及原始响应留作按需证据。日志消费默认使用精确选择器，例如 summary 的总体状态、目标名称、退出状态及日志路径。已加载的工具 schema 在同一执行中复用。

**完成标准**：一次调用即可取得本次决策所需的完整声明或测试结论，不因重复封装造成截断后再读；原始证据仍可追溯。

## 4. 中：为长测试提供终态等待，消除无信息轮询

**事实**：后端完整检查转入后台后，代理连续调用 wait，经历多个“仍在运行”的返回及无进展提示，最终才收到完整结果。它没有另开测试或用 sleep 轮询，避免了额外 CPU 竞争。

**建议**：宿主提供等待指定任务终态的单次挂起操作，或在自动完成通知机制下允许代理直接挂起本轮。等待超时只作为可控取消预算，不要求代理反复发起短 wait。

**完成标准**：没有其他可做工作时，一次等待即可交付终态结果；期间不产生重复状态读取，也不引导代理启动无关工作来“保持进展”。

## 应保留的 TDD 做法

- 首次缺失接口产生可解释的 red，随后按接收、重发、明确查看逐片实现，而不是一次堆齐所有实现。
- 对关键去重断言做了临时变异：重复认领改为 `process=true` 后，测试实际观察到两个处理胜者并失败；恢复正确实现后完整回归通过。这比仅凭测试命名或接口缺失 red 更能证明测试敏感性。
- 已由当前实现满足的存储失败、竞态和恢复场景没有制造虚假 red；新增公开行为回归后直接验证现有路径。
- 接收、通知提交、模型呈现、用户已读及业务验收在实现、断言和报告中保持分离；受控响应没有被外推为真实模型职责证据。
