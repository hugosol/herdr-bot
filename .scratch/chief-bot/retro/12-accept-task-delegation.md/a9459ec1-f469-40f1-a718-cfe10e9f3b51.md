# Ticket 12：TDD 执行复盘

> 范围：本票实现代理的执行对话及其中实际工具结果，不采用父会话或其他票据的验收结论。下述“事实”来自本轮已呈现的记录；未独立查阅额外会话文件或当前检查配置，因此不判断现有 CI／提交钩子的覆盖情况。

## 1. 高：先让验收驱动成为可靠的测量仪器

**事实**：真实模型专项连续暴露了驱动假设，而非对应业务违约：

- 第一轮将 `AMBIGUOUS-731` 的逐字复述作为完成边界。OMP 已正确提出澄清问题，但返回的标记包含额外字符，驱动仍等待至超时。
- 默认终端高度不足以显示完整确认内容和 Yes／No，Pi 未获得驱动的确认操作，最终自然超时。
- 下一轮发送 Down 后立即截图，OMP 仍显示上一帧，驱动误判未选中 No。
- Pi 明确表示“不表示……业务已完成”，却被包含“业务已完成”的关键词断言判为违约。
- 最新一轮 OMP 使用原生 `ask` 表单澄清；驱动只等待最终 assistant 消息，没有回答表单，最终仍超时。Pi 在同一轮完成全部专项。

**推断**：驱动把“某一种回答和交互形态”当成了用户承诺，导致测试对实现细节敏感，而对合法的原生交互覆盖不足。

**建议**：在既有原生验收设施中增加一个独立的、受控响应的**测量自检**入口，先覆盖文本终轮、`ask` 表单、完整确认框、按键写入后延迟重绘，以及否定式完成说明。自检只证明驱动能正确观察和交互，不认领真实模型职责。真实 GPT-6-luna 专项仍负责独立业务案例，并保持当前 fail-closed 结果。

**完成标准**：合法交互不会被误判为超时或业务完成；明确的未批准派发、错误载荷和无条件完成声明仍使测试失败。

## 2. 高：原生输入需要“接纳”证据，而不只是写入回执

**事实**：一轮 OMP 的 Herdr `agent prompt` 返回退出码 0、`interactive_ready=true`，但修正输入没有出现在原生历史中。驱动随后等待一个实际上没有开始的确认阶段。后续实现才增加 ready 观察、一次提交及本次 working／blocked 活动证明，并在失败前保存屏幕。

**建议**：将这套**单次提交**过程收敛到现有共享原生验收设施；文档只保留触发指针和证据含义。固定记录提交前状态、本次活动、原生用户消息和失败屏幕。未证明接纳时返回“输入接纳未验证”，不继续当作业务决策失败，也不自动补发或补 Enter。

**完成标准**：写入成功但没有新活动或原生用户消息的受控案例能够被准确分类；确已接纳的输入不会重复发送。

## 3. 高：独立业务夹具也需要校验实际执行目标

**事实**：初始 Bot.when 声明审计摘要能力，但所关联 Task 的固定指示只描述等待 RELEASE，没有描述摘要职责。OMP 读取定义后指出实际目标不匹配，拒绝委派。后续才补充读取 brief、逐项核对、交付 summary.md 和禁止发布等职责。

**建议**：真实模型调用前，对本次**独立案例**做一次夹具审阅：用户目标、Bot.when、实际 Task 职责、材料和工作位置必须共同构成有效匹配；RELEASE 门闩只控制完成时机，不替代业务职责。这是跨定义语义判断，宜作为验收方案／独立审阅的要求，而不是另加名称或关键词匹配器。

**完成标准**：已知匹配案例的实际目标确实承担该业务；无匹配案例则保持真实缺口，不靠无效目标制造缺口。

## 4. 中：把驱动的红—绿循环与真实模型验收分开

**事实**：CLI 安全用例有清楚的红—绿证据：缺少入口、包装器拒绝新场景，以及临时删除 P13 后矩阵断言失败，恢复后通过。相较之下，终轮判断、确认框观察和输入接纳主要在耗时的真实模型全链路中逐步纠正。

**建议**：执行入口明确区分两类循环：

1. **驱动红—绿**：用受控原生交互证明测量机制能区分已命名的违反行为。
2. **真实模型验收**：使用固定独立需求、真实工具和批准交互，判断模型职责。

修复驱动或夹具后，保留原始失败，并用源码和环境指纹解释新结果归属；不要通过修改角色提示词来禁止合法的 `ask` 形态，换取驱动通过。

**完成标准**：每次真实模型重跑都能说明是何种已诊断的驱动／夹具变化；真实业务判断失败不会被普通重试掩盖。

## 5. 中：用有针对性的检查捕获兼容性问题，避免增加文字禁令

**事实**：实现为保留主失败和清理失败引入 `AggregateError`，现有 `bun run typecheck` 因 ES2020 类型目标而拒绝该名称。随后采用仓库已有的组合错误表达方式，类型检查通过。依赖安装也曾因链接布局中的缺失模块失败，改用本票拥有的 hoisted／copyfile 布局后通过。

**建议**：继续让现有类型检查承担语言／库兼容性约束，不新增“不要使用 AggregateError”之类代理规则。对隔离 worktree 的依赖准备，在现有测试指引中集中记录已验证的安装布局和最小可用性检查，供相关分支按需读取。

**未验证**：本轮没有核实这些检查是否接入 CI 或提交钩子，不能据此断言仓库缺少自动护栏。

## 6. 中：资源队列需要明确所有权和事件式交接

**事实**：实现代理曾长时间等待原生窗口；其间对后端全量、浏览器和原生／完整 dock 是否共用队列存在不确定性。Main 后来明确了不同资源的顺序。原生窗口交接后，新的集成代理又请求确认所有权，最终交接对象也发生了变化。

**建议**：由宿主维护一个简短的**资源租约**：资源类别、当前所有者、下一所有者和释放条件。交接通知应包含命令结束及所属进程退出确认；实现代理订阅释放事件，而不是反复探询。轻量构建和静态检查不继承原生窗口门禁。

**完成标准**：任一代理无需向多人重复询问，就能判断哪些检查可执行、窗口应交给谁。

## 7. 低：提供紧凑的证据读取方式，减少日志读取成本

**事实**：有一次 JSON 查询输出包含完整终端记录，结果显著膨胀；另一次在 eval 中把格式化后的读取文本当作原始 JSON 解析而失败。改用原始文件读取后，成功得到源码和环境差异：仅观察器／夹具及说明变化，后端二进制、前端产物、宿主身份和 paths 指纹保持一致。

**建议**：为已有验收证据提供紧凑摘要和明确的原始数据读取方式。默认只返回失败阶段、覆盖状态、退出状态、清理错误和原始记录位置；大段终端及历史按明确指针展开。机器消费使用完整结构化数据，不解析面向聊天展示、可能截断的文本。

**完成标准**：一次摘要读取即可定位原始失败；源码归属比较不会依赖展示层输出是否完整。
