## 高：把“最终验证”约束为稳定源码上的单一阶段

**事实**：第一次完整后端检查 `bg_13` 启动后，代理继续修改 `backend/tests/suites.rs`、catalog 及前端消费者，并运行定向 Cargo 测试。随后又启动最终完整后端检查 `bg_20`；定向 Cargo 输出出现 `Blocking waiting for file lock on build directory`。最终后端、完整浏览器、完整前端检查也存在重叠。

**影响**：第一次全量结果不能完整覆盖最终改动，产生重复构建与重复证据；同一 target 的并发编译已有可观察的锁等待。并发是否造成浏览器的 `document.visibilityState` 失败，未验证，不能归因。

**建议**：在已有 TDD 执行流程中集中定义一个“稳定快照”完成条件：所有实现与消费者迁移完成后，才启动最终检查；检查期间需要修改源码时，先让当前检查正常收尾，将其标为开发反馈，再对最终快照验收。共享同一 Cargo target 的检查串行执行。长任务输出自动送达时，代理只处理尚未完成的独立工作，不再补跑竞争同一构建目录的命令。

该约束应放在执行流程，而不是另添一份重复的项目说明。

## 高：先分类全仓失败，再决定是否允许验收完成

**事实**：最终完整后端检查因两个 `workflow_dispatch` 用例的 `input_files.description` 预期差异失败，11 个目标未派发，doctest 未执行；完整前端检查有 30 个失败；完整浏览器检查为 326 通过、26 失败、1 跳过。本票定向用例及相关浏览器文件通过，代理保留了全仓失败，并未修改其他业务。

**事实**：后端与前端完整入口各执行了两次；第二次仍出现上述失败类别。第一次之后的再执行也承担了覆盖后续改动的用途，不能简单称为无意义重试。

**推断**：不少失败像是接口或界面变化后未同步维护的旧断言，但对话没有基线对照，无法确认它们全部早于本票。

**建议**：由集成流程提供独立的失败归属判定：保留原始失败、明确本票覆盖结果、区分未派发项目，并由集成方决定阻塞或接收。只有归属不明且影响交付判断时，才安排隔离基线对照；不要把“看起来无关”当作既有失败证明，也不要要求每张票重复修复或重复运行同一批未归属失败。

项目已有 `node scripts/test-backend.mjs`、前端网络护栏和浏览器构建入口；建议修复和接入既有入口，不另建同义检查。是否已有 CI 或 pre-commit 持续执行这些入口，本次历史未核实，不能据此认定仓库缺少 guardrail。

## 中：分开 TDD 证据与变更后维护性验证

**事实**：以下行为取得了可辨认的红→绿证据：

- chief HTTP 保存：先因 `invalid-task-type` 失败，再通过。
- 默认预设：先因缺少 chief 预设失败，再通过。
- 真实编辑器：先因没有 chief 选项失败，再通过。
- 固定扩展目录：先因缺少 chief 角色失败，再通过。

已有执行目标限制则新增公开入口用例后直接通过，代理没有人为制造失败，符合“既有行为成立时验证覆盖”的规则。

**事实**：catalog 的后端红灯已建立后，前端 Suite parser、展示及其测试夹具在同一次修改中同步更新；最后的报告对这些路径总体给出了通过结论。

**建议**：最终报告将证据标为三类即可：新增行为的红→绿、已成立行为的回归验证、消费者迁移的通过验证。不要用统一的“TDD 通过”暗示每个消费者都独立经历了可观察红灯。对于新增协议值，至少保留一个真实消费者场景，使“后端已支持、客户端仍拒绝”的错误能被捕获；本次 Suite 真实浏览器用例已经提供了这种有价值的覆盖，应继续复用。

- 默认预设缺失与客户端缺少选项都取得真实红灯，而非仅靠编译失败宣布 red。
- 全量失败、未派发目标及未执行 doctest 均被明确报告；未用定向通过替代全仓通过。
- 未调用真实模型，且未把定义保存、受控宿主装配或浏览器通过外推为 GPT-6-luna 角色行为或 OMP/Pi 原生加载证据。

本轮没有足够证据支持新增全局 AGENTS.md 禁令、认定缺少 CI，或指责 reviewer 漏检；更优先的改进是稳定最终验证阶段、明确失败归属，并复用现有公开契约覆盖。
