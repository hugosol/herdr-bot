# 06: 保持脚本报告保存与通知失败隔离

**What to build:** 脚本报告一旦保存，即使向 manager 通知失败，原报告和已登记输出仍可读取，不撤销、不丢失，也不重新执行业务。

**Delivers:** P11

**Blocked by:** 02 — 通过真实 Map 异步创建空白 Bot 并交接报告。

**Repositories:** herdr-bot

**Status:** ready-for-agent

## Acceptance criteria

- [ ] 在真实脚本业务保存报告后，通过测试拥有的外部宿主边界制造明确通知拒绝和可控制的通知等待/失败，不模拟业务保存成功。
- [ ] 通知结束前后分别独立读回同一报告身份、body、canComplete 及全部已登记 outputs，并读取真实输出文件；已保存事实不因通知失败回撤或更换身份。
- [ ] 核对真实配置效果、执行数量及外部调用记录，在明确有界窗口观察没有自动业务重投或报告/通知重试；不以瞬间数量或源代码不存在循环作为证据。
- [ ] 结果如实区分保存与通知状态，保留可得错误，不把通知已提交解释成可靠接收或用户已阅读。继续复用既有保存后通知编排和唯一持久权威。
- [ ] 更新既有运行说明，说明通知失败后读取原事实而非重派、重做或回滚；不增设新接收工具、消息队列或自动恢复策略。

## Verification and ownership

本票唯一拥有 P11 的自动化。02 拥有正常保存/通知/collect 和输出校验；04 拥有业务在途时的管理并发/断连；11 拥有真实 manager 会话接收，不能以本票受控宿主代替。

使用公开 S1 HTTP、真实临时配置/输出及记录型外部宿主，复用现有报告故障设施，先检查已有报告测试覆盖并扩展适用场景，避免另建测试 seam。本 worktree 独立绝对 CARGO_TARGET_DIR，先构建静态页，再运行 `node scripts/test-backend.mjs`。证据包含保存先于通知的因果顺序、实际观察预算、调用记录及进程退出确认，遵守全部网络/隔离规则。
