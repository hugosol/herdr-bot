## Retrospective

## 高：把工作树内的锁定依赖安装与共享缓存隔离

**事实**：本票最初用 `bun install --frozen-lockfile --offline` 安装依赖，随后 `typecheck` 仍找不到锁定的 `@typescript/typescript-win32-x64`。按项目文档执行 `bun install --frozen-lockfile --force` 后，又在共享 Bun 缓存的发布步骤遇到多个 `EPERM`。改用 `bun install --frozen-lockfile --force --linker=hoisted --backend=copyfile --offline` 后，安装和现有 `bun run typecheck` 均退出 `0`。

**建议**：在 toolkit 现有 `docs/agents/testing.md` 的「隔离 worktree 依赖」段补一条 Windows 分支：**原生编译器可解析**才算准备完毕；遇到全局缓存发布 `EPERM` 时，使用上面已证实的 worktree 本地安装方式，保留原始失败，再运行原 `typecheck`。无需新增检查命令或常驻指令。**未验证**：`EPERM` 的具体占用者，以及冷缓存时离线安装是否可用。

## 中：让本地覆盖触及实际交付的可选 PR 分类

**事实**：审计适配修改了 `origin`／`gh` 的结果解析和 open／draft 分类，但通过的 Windows 审计用例全部带 `--no-pr`。该机未找到 `jq`；最终报告也明确未验证在线 PR 查询。Git 与文件系统路径已经由真实资源验过，不需要替换。

**建议**：扩展已有 `logs-audit` 分区：用本地受控 forge 命令提供独立的 open、draft、closed 和失败样例，保留交付脚本及真实 `jq`，以输出的 PR 列、`hold-open-pr` 分类和不可用警告为通过标准。真实 `jq` 不可用时如实记录该分支未验证，不把 `--no-pr` 的通过算作覆盖，也不接触生产 forge。**推断**：这能捕获查询字段或解析漂移；本轮没有证据证明该分支已经出错。

## 中：Windows 验收保留一个稳定筛选词和每次独立的证据目录

**事实**：`bun run test:pstack --test-name-pattern='P37|P41'` 被 Bun 的 Windows 批处理参数保护拦截，测试没有执行；换成 `--test-name-pattern=logs-audit` 后通过。早期证据命令中的 `pwd -W` 在实际调用 shell 中不受支持，红灯产物落到工作树外的意外位置，随后才移回。后续两次运行又复用了同一个 `final` 证据目录。

**建议**：沿用现有 `test:pstack` 入口，为每个票据分区使用只含字母、数字和连字符的稳定筛选词。证据目录由现有 runner 以文件系统 API 解析并新建，每次调用独占一个目录；同处保留命令、数字退出状态、原始输出和产物，重跑不覆盖前次证据。这样无需给每个票据重复编写依赖 shell 方言的记录逻辑。
