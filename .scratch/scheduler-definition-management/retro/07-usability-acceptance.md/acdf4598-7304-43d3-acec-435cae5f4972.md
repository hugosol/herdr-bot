## 1. 高优先级：为验收补测明确 red 的归因与切片边界

**事实**

- 首次写入 `schedulerUsability.spec.ts` 时，已包含一个跨模板修改、node 修改／新增、校验错误、冲突、放弃确认、恢复保存及模板新增的长流程，并同时参数化桌面和窄屏。
- 首次构建因缺少 `tsc` 退出，未进入行为检查。
- 随后几轮失败分别来自：严格要求控件底边完全位于 viewport 内（如 `900.171875 > 900`）、textarea 获焦后未整体滚入视口，以及重新打开已保存 JSON 时字段顺序与 `JSON.stringify(newNode)` 不同。
- 最终改为可见区域命中检查与持久 JSON 语义比较；失败草稿仍逐字核对。没有对应的生产修复。

**推断**

这些失败说明测试假设需要修正，不构成发现产品违约的 red。当前 TDD 指引已允许“行为已满足时验证既有行为”，但本轮没有在长流程落笔前，清晰形成逐项的“既有能力补证／真实缺陷修复”分流。前段几何断言失败也推迟了后段错误恢复行为的首次观察。

**建议**

在 TDD 的验收补测分支中，将每个切片的完成条件收紧为：

> 固定承诺与独立预期，先跑通最小用户路径；将失败归为环境、测试假设或产品行为，再决定修正测试还是实现。

按“模板往返 → 编辑保存 → 错误与草稿恢复”逐段扩展已批准的 S1 流程，而不是一次写完全部路径。行为本已成立时接受直接 green，不制造生产 red。

这是**测试设计判断**，应放在测试设计参考及 reviewer 的审查关注点，而非新增一条机械 lint。审查时确认：修改断言的理由来自 contract 或浏览器行为，而不是为了消掉失败。

**改进验收**：后续同类票据的每次失败都能对应明确归因；测试修正与产品修复分别报告，首个切片可独立到达其业务观察点。

## 2. 中优先级：沉淀浏览器观察语义，减少重复发明测试前提

**事实**

本轮在通用 `tabTo` helper 内先要求所有目标完整位于 viewport，之后加整数取整，再根据 textarea 的原生焦点行为改为可见部分与 `elementFromPoint` 命中检查。持久 JSON 也经历了从字符串相等到语义相等的修正。

已有 `docs/agents/testing.md` 实际提供了相关提醒：`toBeVisible` 不保证元素处于视口内，真实命中检查前需处理滚动。但该提醒以 SVG 连线为例，没有覆盖本轮遇到的 textarea 及草稿／持久内容差异。

**建议**

在现有测试指引的浏览器观察部分，集中放置两类可复用判断，不增加新的常驻 AGENTS 内容：

- **可操作性**：以实际键盘到达、输入、提交和可见命中面证明；完整控件同时在屏内仅在产品明确要求时断言。
- **内容保真**：保存失败的原始草稿逐字比较；保存后重读的 JSON 按语义比较，除非格式本身属于承诺。

将例外与规则放在同一处，由浏览器测试设计分支指向它。保留业务结果断言，避免把“部分可见”自身当作整个编辑流程可用的证明。

**改进验收**：后续测试使用上述区分时不再需要两轮 viewport 假设修正；格式重排不导致无关失败，真实丢失草稿仍会失败。

## 3. 中优先级：为语义搜索提供宿主级可用性降级，控制探索输出

**事实**

两次 `find` 分别发出 24 与 22 个 judge 请求，均因区域限制返回 HTTP 451，未产生有效判断。随后对整个 `frontend` 搜索 `scheduler|test:browser:build`，输出约 50KB 并被截断，包含依赖锁文件及大量已有测试。

**推断**

这里首先是工具依赖不可用，而不是仓库缺少相关代码。强制先用语义定位、但没有可用性状态，会使代理先付出一批必然失败的请求，再用过宽搜索补救。

**建议**

由宿主或 `find` 工具对确定性的区域／鉴权不可用提供快速失败及本轮可用性状态；不可用时明确进入结构检索降级，而不是继续批量调用同一不可用依赖。降级路径先返回匹配文件名，再按 browser-tests、src、docs 分区读取小范围命中。

若要补导航，优先在现有测试指引里说明 scheduler 浏览器测试与 `support.ts` 的关联，不将所有测试文件清单复制进常驻上下文。

**改进验收**：相同 451 场景最多触发一次可用性判断；降级搜索能定位入口，且结果不依靠截断输出传递关键信息。

**推断**

本轮门槛守住了，但依靠协作消息、票据备注与最终文本交接。若后续集成改变页面或数据行为，截图是否需要更新仍需下一位代理重新综合这些记录。

**建议**

在宿主的现有票据交接结果中区分并消费：

1. 本票自动交付完成；
2. 最终集成构建的全部自动工作完成；
3. 用户主观确认完成。

复用本轮已经报告的 `automatic_complete_human_pending` 含义，避免再建立一份手工状态账本。人工验收请求由最终集成者在第二个门槛满足后发出，并绑定对应构建及证据；“持续执行直到 closed”的通用要求应在这一分支以明确交接条件结束，不能诱导代理把等待用户确认写成完成。

**改进验收**：仅有分支测试通过或截图链接时，宿主不会关闭 P36；最终构建变化后能明确列出需更新的证据。

**未验证**：本会话没有最终合入、06 后续完成或用户反馈的记录，不能评价这些后续步骤是否实际漏做。

## 5. 低优先级：复用已有检查入口，补齐 worktree 启动与 Windows 进程调用路径

**事实**

- 历史中读取的 `frontend/package.json` 已定义 `build`、`test:browser:build`，以及运行网络护栏的 `pretest:browser`；完整执行日志证明这些入口实际运行成功。
- 初次构建缺少 `tsc`，执行 `npm --prefix frontend ci` 后恢复。
- 独立安全壳先用 `C:/...exe`，再用 `/c/...exe` 启动，均返回 `/bin/bash: ... No such file or directory`；改用 `powershell.exe -NoProfile -Command "& 'C:\...exe' ..."` 后服务就绪。

**建议**

把“新 worktree 依赖准备”放进宿主 provisioning 或现有构建说明的首次运行分支。依赖已就绪时直接使用现有 npm 检查入口，不在每轮测试前无条件重复安装。

Windows 原生服务启动优先复用文档已有 PowerShell 方式；若宿主长期同时暴露 Windows 路径与 Bash 风格调用界面，应由工具层明确可执行文件启动约定，减少代理尝试两种路径方言。该知识属于 Windows 分支参考，不适合扩成长驻全局指令。

**改进验收**：新 worktree 首次到达行为测试前，不因本地工具缺失失败；原生安全壳按已知调用方式一次启动。

**未验证**：本轮未读取 CI 或 pre-commit 配置，因此不能声称仓库没有自动检查护栏，也不建议据此另建一套 lint／CI。已知可复用的检查入口应保留。

## 6. 低优先级：让证据导出自动化，收敛文档中的运行记录与重复说明

**事实**

完整浏览器检查结束后，代理手工定位两个 Playwright 输出目录，再用 Eval 复制八张图片到 `docs/example/screenshots`。文档新增了截图表、完整操作步骤、检查命令、能力与限制；根 README 及票据备注也记录了部分相同说明。旧 P33 截图保留并被明确标为历史材料，未冒充 P36 最终证据。

**推断**

当前没有发现复制错图，但“运行 → 选目录 → 复制 → 更新链接”仍是容易在下一轮遗漏的人工链条；说明文字也存在继续沉积的风险。

**建议**

让现有浏览器交付入口导出受控证据清单，记录场景、viewport、来源运行及构建标识，并检查所需截图完整。文件存在、清单完整、链接有效可做确定性检查；是否足以证明可读和顺手仍保留人工判断。

文档保持三层：根 README 只提供能力摘要与入口；体验指引承载稳定的隔离复现步骤和评价标准；单次命令结果、临时 URL、目录与未验收状态留在交接结果或票据。操作步骤中的风险提示保留在相应动作旁，完整规则只保留一个权威位置。

**改进验收**：最终运行后不再需要猜测输出目录并手工挑图；构建证据可追溯，重新验收也无需在多个说明文件同步相同状态。

## 建议保留的做法

- 坚持批准的 S1 真页面与真实后端，不用模拟响应替代持久化和冲突行为。
- 每个场景独占目录、cwd、服务和回环端口，执行适配器只用来观察未执行。
- 定向迭代之后执行项目完整浏览器构建入口，并如实报告早期环境失败及测试假设修正。
- 清楚区分自动观察、最终集成门槛与用户主观确认；不把截图或等待反馈当作人工通过。
