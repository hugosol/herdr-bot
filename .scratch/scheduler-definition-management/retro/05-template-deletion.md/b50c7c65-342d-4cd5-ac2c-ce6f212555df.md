## 1. 高优先级：让 TDD 交接区分“接口 red”与“行为 red”

**事实**：首个 P21 tracer 在等待“删除模板”按钮时耗尽 90 秒测试超时，尚未到达跨 Map 引用拒绝断言。随后一次实现加入了引用扫描、预检查、实际删除、目标版本重查、确认交互和列表更新。P23/P29、P24 的测试是在这些实现之后补入，并直接通过。

**判断**：首轮确实提供了接口缺失的 red，也最终提供了行为覆盖；但不能把它等同于已经观察到“引用检查错误会被断言击穿”。此外，首轮实现提前覆盖了后续数个验收切片，削弱了逐项 red → green 的反馈价值。这不是在断言最终测试无效，也不是要求对已有正确行为制造失败。

**建议**：在既有 TDD 交接与审查入口增加一个简短的证据区分，而非在全局 `AGENTS.md` 重复整套 TDD 规则：

- **接口 red**：入口或类型尚不存在，行为断言未到达。
- **行为 red**：已到达约定条件，观察到具体违规结果。
- **既有行为覆盖**：实现已经满足该条件，新增或复用测试验证它，不追认此前发生过 red。

实现阶段按当前切片控制改动；对于删除这类破坏性操作，可优先选择能贯穿检查、确认、持久化及重读的最小切片，再逐项加入引用与过期检查。审查代理负责核对后补测试的敏感性；能通过检查确定的，不强制增加 mutation，无法确定时再做定向故障注入。

**完成标准**：交接证据能指出 red 停在哪个断言、实际暴露了什么违规；后补测试明确标为覆盖，而不是统一归入“先红后绿”。这是跨测试与实现的判断工作，不适合用语法 lint 代替。

## 2. 中优先级：把测试额外施加的要求与票据要求分开

**事实**：P22 要求指出无法检查的文件或目录及原因。首次测试收到 `.data/workflow-maps` 和明确的访问拒绝原因，却因期望完整绝对路径而失败。随后生产实现改为绝对路径；下一轮又因 Rust 保留 `/`、Node 使用 `\` 而失败，最终在测试中归一化分隔符。

**推断**：绝对路径可能改善诊断，但它比本票明示的要求更具体。会话未显示在修改生产实现前，明确区分了“真实行为缺陷”与“测试新增的展示要求”。

**建议**：在既有 TDD 的“保持验收条件”段落中，用这一类案例澄清预期来源：先确定独立业务要求，再确定表示形式。诊断测试通常应验证目标身份及原因；若要固定绝对路径、排序或精确文案，应说明其额外来源。平台等价的路径表示可以归一化，但保留对完整目标及错误原因的核对。

**完成标准**：遇到此类 red 时，记录一句“这是验收缺陷、夹具错误，还是新增约束”，再决定修改生产代码还是测试。不要把绝对路径规则另写入全局指令或编码标准。

## 3. 中优先级：沉淀真实 Windows 删除失败夹具，并保留原始失败

**事实**：本轮最初使用 `chmod(0o444)` 构造删除失败，但目标实际被删除；工具最终显示的是 `finally` 中恢复权限时的 `ENOENT`。随后改用文件 `Delete` 与父目录 `DeleteChild` 的真实 ACL 拒绝，测试通过。相比之下，P22 的读取失败夹具先验证了文件不可读、目录仍可列出等前置条件，证据更完整。

**判断**：这里暴露了两个独立环境问题：只读属性不能作为本环境中生产删除必失败的可靠前提；清理异常会覆盖更早的测试失败。现有 `docs/agents/testing.md` 已要求同时保留原始错误与清理错误，缺口主要是可复用设施，而非再加一条相同禁令。

**建议**：以本轮已通过的 ACL 场景为依据，在浏览器测试支撑层提供小型、可恢复的 Windows 权限夹具；测试指引只补充“只读属性与删除权限不同”这一平台陷阱，并指向实现，避免复制命令清单。夹具应保留读取能力、明确限制删除、恢复自己施加的权限，并同时呈现测试错误与恢复错误。

**完成标准**：夹具自身的自动回归能证明预期权限成立且最终恢复；测试主体与清理同时失败时，两条原因都可见。不要仅靠给审查代理新增“注意清理”的文字规则。

## 5. 中优先级：将全量时间断言失败交给所属测试维护者调查

**事实**：完整浏览器运行唯一失败为 `sessionHistory.spec.ts:83`：返回的 `firstRecordedAt` 比测试端 `savedBy` 大 **5ms**。该用例使用测试进程的 `Date.now()` 包围真实服务请求，并据此对服务生成的时间戳作精确上下界断言。本轮没有重跑或修改该无关测试，处理范围是克制的。

**推断**：跨进程墙钟取样、时钟粒度或调整可能使这个精确边界不稳定；目前证据不足以确定根因，也不足以排除真实时间戳缺陷。

**建议**：由所属测试维护者先明确此处真正承诺的是“持久化时间身份稳定”还是“精确落在客户端请求时间区间”。若是前者，围绕首次值在重读、浏览器关闭和服务重启后的稳定性构造预期；若是后者，应调查时钟来源与误差模型，建立有依据的时间检查。不要把任意加宽容差或自动重试作为默认修复。

**完成标准**：保留原有持久化保证，并用可解释的时钟关系验证必要时间承诺。本项是后续维护建议，不是本轮已完成的诊断。

## 6. 低优先级：把搜索服务可用性和依赖准备放在环境入口

**事实**：首次 `find` 的 23 个判断请求全部因区域限制返回 451；代理报告工具问题后改用 grep/glob，成功定位实现。首次浏览器构建则因找不到 `tsc` 停止，执行 `npm ci` 后才进入真实 red。首个缺失按钮的 red 还消耗了完整 90 秒测试超时。

**建议**：

- 工具宿主在供应商不可用时提供会话级 circuit breaker 或一次性降级提示，避免其他调用者继续依赖已知不可用的判断服务；不为这一服务故障新增仓库导航文档。
- worktree 准备入口根据现有锁文件确认依赖可用，把环境失败与行为 red 分开呈现；保留既有构建入口与网络护栏。
- 开发期对预期缺失的页面入口使用现有 Playwright 的短显式断言预算，再执行操作；不要全局缩短真实业务等待时间。

**完成标准**：新 worktree 首次验收不再因缺少已声明工具而中断；依赖与搜索故障被报告为环境状态；接口缺失能快速给出明确 red，而非耗尽整个用例预算。
