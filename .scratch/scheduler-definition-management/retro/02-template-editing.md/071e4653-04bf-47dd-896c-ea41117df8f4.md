# TDD 执行复盘建议

## 范围与结论

本复盘仅依据指定 ticket 执行会话的 JSONL 历史及其中记录的工具结果，截止首次实现交付；未读取父会话或其他执行记录，也未修改文件或重跑验收。

本轮有真实的测试驱动修复：严格校验用例先暴露字段路径诊断缺失，随后暴露 `implementation: ['chat']` 被接受；修复后转绿。页面、生产 HTTP、真实隔离文件及 Windows ACL 写入失败均实际参与了验收，而非由内部 mock 代替。最终本票 8 项浏览器测试通过，前端 205 项测试通过。以下建议重点改善**切片纪律、证据强度与反馈可靠性**，不以这些通过结果倒推整个过程都符合 TDD。

## 1. 高：把“当前 red 的边界”变成实现切片的完成条件

**事实**：首个测试覆盖新增草稿、取消、创建保存与预览。其 red 是缺少“新增模板”按钮。随后第一次实现同时加入了已有模板读取／修改、旧版本冲突、草稿退出确认、tab／server 导航保护及来源 Map／node 失效处理。对应的已有模板、冲突、退出确认和来源往返测试是在这些实现之后才加入，多数首次运行即通过。

**判断**：这不是“所有测试先写、再写全部实现”的水平切片，但仍存在反向的大批实现：一个 red 驱动了多个尚未建立测试的行为。“准则已经满足时验证现有行为”的例外，不应把本次运行刚刚提前实现的行为也当成既有基线。上述测试后来通过，证明最终行为，却不能补出这些行为的 test-first 过程。

**建议落点**：收紧现有 TDD skill 的“当前切片”和“既有行为”定义，不另建流程文档：

- 每轮选定一个可观察结果及反例；生产修改以使该结果转绿所需的路径为边界。
- 为首条端到端路径必须共同交付的跨层改动保留空间；独立的冲突、退出确认等行为进入各自下一轮。
- 使用“已满足”例外时，说明它来自执行前基线、此前哪个切片，还是本轮提前实现。后者如实记为补充覆盖，不计作新的 red → green。

宿主可从已有测试调用和编辑事件生成轻量时间线，供 reviewer 核对，不要求实现代理再维护一份手工状态表。切片是否独立属于判断题，应由 reviewer 审查，而非用“编辑行数上限”一类机械规则代替。

**完成条件**：每个新增行为能关联其实现之前的相关失败，或明确标注为既有覆盖／补充覆盖；不再以最终全绿替代过程证据。

## 2. 高：验收映射必须区分“场景已发生”与“实现方式支持该结论”

### P8：无开发仓库文档的部署环境

**事实**：实现使用 `include_str!` 编译打包天气示例；测试在独立 cwd 中打开、修改并保存草稿。记录中的浏览器 helper 仍从仓库路径启动二进制并使用仓库构建产物。未见使开发仓库文档不可访问的部署场景。最终报告却将本票所属自动验收全部记为完成。

**判断**：编译期打包是很强的实现依据，独立 cwd 也排除了相对工作目录依赖，但二者不是“文档不可访问环境已实际执行”的同一种证据。这是验收证据缺口，不是已经观察到的部署功能故障。

**建议**：为部署条件增加测试夹具分支：从测试拥有的部署目录启动所需应用产物，部署树中没有开发文档，再通过真实页面打开、删改和保存草稿。若当前打包方式不能支持该夹具，应将这一项列为尚未完成的部署验证，保留编译期打包作为静态依据。

### P13：并发创建

**事实**：同 ID 创建用例以 `Promise.all` 发出两个真实 HTTP 请求，断言一胜一败；未见对服务端竞争区间的同步控制或定向故障注入。

**判断**：这证明该次请求序列的结果正确，但没有确定证明两个请求同时到达身份检查与提交的竞争窗口。一个未正确协调、但恰好串行处理的实现仍可能通过。尚不能据此断言锁实现有错。

**建议**：沿用已批准的生产 HTTP seam，在本地可替代边界控制竞争窗口；或通过临时移除协调机制的定向 mutation，检查用例是否稳定捕获违约。若做不到控制或敏感性验证，报告应将其称为真实并发请求观察，而非确定性的竞争保护证明。

**共同落点**：强化现有 TDD skill 的“check the evidence after green”，要求部署、竞争等环境条件分别给出“如何进入条件、哪里观察结果、什么错误仍可能通过”。reviewer 按这一标准审查证据，不按 P 编号或测试名称判定覆盖完成。

## 3. 中：在既有浏览器测试支撑层沉淀快速、可取消的交互模式

**事实**：本轮出现三次消耗整个 90 秒测试期限的反馈：

1. red 阶段点击不存在的“新增模板”；
2. 读取无法由精确 label locator 命中的 JSON 编辑框；改成显式 `htmlFor`／`id` 后通过；
3. 取消原生刷新后，测试仍等待 `page.reload()` 的 load 完成，并假设会收到 `ERR_ABORTED`。改用浏览器重载命令、独立观察 `beforeunload` 后通过。

**建议落点**：复用现有浏览器 support 和 `docs/agents/testing.md`，只沉淀这类有实际踩坑证据的分支：

- 缺失界面是预期 red 时，先以短时可见性断言确认入口，再进行点击或取值；保留真实时间承诺用例的专用预算。
- 将取消／确认原生刷新封装为共享测试动作：取消分支观察草稿保留；确认分支再等待新页面就绪。取消本身没有 load 完成条件。
- JSON 编辑器示例采用稳定的显式 label 关联，继续由实际页面测试验证可访问名称，不引入“一律禁止嵌套 label”的过宽编码规则。

**完成条件**：缺少入口或标签关联错误在局部断言预算内失败；取消刷新不等待被取消的导航，仍通过真实浏览器验证原生提示行为。

## 4. 中：提高回归失败的可归因性，保留不绿的事实

**已知检查入口**：原会话读取过 `frontend/package.json` 和项目测试指引。已有 `build` 类型检查、npm 网络护栏、浏览器构建入口及后端并行入口；本轮均有实际使用。因此建议是完善现有支撑层，而非另建一套检查命令。未检查到 CI／pre-commit 是否接入，不能据此声称仓库没有自动护栏。

**事实**：

- 全量浏览器验收为 253 通过、1 失败，失败点是服务绑定 `127.0.0.1:53877` 时收到 Windows 10048。
- 全量后端回归在 `zone_sync::configured_timeout_stops_the_running_command_and_keeps_effective_pull_state` 中预期 200、实际收到 `git-write-in-progress` 409；doctest 因入口失败策略未执行。
- 交付报告保留了这些失败，没有把全量回归写成通过。

**未验证**：端口由哪个进程占用，以及 409 是时序问题、资源竞争还是产品缺陷，均未在本会话中确诊。失败位于未修改的测试领域，并不等于已经证明它们与本次变更无因果关系。

**建议**：

- 在现有进程 fixture 中记录监听地址选择、子进程身份、就绪与退出阶段。优先让服务实际持有端口后公布地址；若需规避浏览器禁用端口，限定在“尚未就绪的 fixture 启动”阶段处理绑定失败，并保留原始诊断，不重试业务断言来掩盖失败。
- 在 Git 写资格相关诊断中关联超时、终止确认、资格释放及后续请求事件，帮助区分业务故障与测试观察时序。
- 宿主交付摘要继续分开记录：本票验收结果、全量回归失败、未执行检查。对未确诊失败使用中性描述，留给独立调查，而不是直接归类为已有 flaky。

**完成条件**：下一次同类失败能从一次运行的日志定位到生命周期阶段；报告保持通过、失败和未运行三种结果。

## 5. 低：由宿主处理工具与依赖就绪，减少无效上下文和伪 red

**事实**：首次浏览器构建因找不到 `tsc` 失败，执行 `npm --prefix frontend ci` 后才得到功能 red。首次 `find` 的 24 个评判请求全部因区域限制 451 失败，随后使用 `grep` 找到目标。上下文还要求优先考虑 codebase-memory-mcp，但本轮可调用工具中未提供该工具。TDD 全文已经自动加载，代理又依据“匹配技能先 read”的通用要求读取了一遍。

**建议落点**：调整宿主装配，而不是向项目 `AGENTS.md` 继续追加规则：

- 新 worktree 就绪检查区分依赖／构建失败与行为 red；依赖准备结果由环境提供，测试命令仍从项目脚本读取，避免文档复制配置。
- 工具 capability 检查发现不可用或永久性 451 后，本轮直接选择已有本地检索路径；仅向代理暴露可用工具的导航要求。
- 已自动加载的技能正文满足“先读取”要求；其按分支引用的 `tests.md`、`mocking.md` 等仍按需读取。

**完成条件**：代理开始行为 red 前已经知道依赖与工具能力状态，同一技能正文只加载一次。保留本轮有效的本地搜索退路，不为没有出现的导航困难新增目录索引。
