## 1. 高：收紧首个 tracer 的实现授权范围，明确“已经满足”的时间边界

**事实**

- 首个测试同时覆盖示例预填、打开／放弃无持久化、实际保存、开放参数、当前选择、详情、依赖图和非目标文件保护。
- 实际 red 停在不存在“新增 node”按钮，尚未到达保存或图更新断言。缺失接口可以作为初始 red，这一点本身符合技能允许的起点。
- 这次 red 之后、第一次 green 之前，代理同时实现了 `new_node`、`edit_node`、`save_node`、新增／修改分支、完整 Map 校验、冲突检查及共享编辑器。真实 node 修改、无效输入、并发创建、外部冲突和写入失败等专项测试，均在这一批生产改动之后加入，随后直接通过。

**推断**

首个 tracer 承载了过多完成条件，形成了“一个缺失入口的 red → 大部分功能实现 → 后补专项验收”的路径。后续测试确实提供了交付证据，但不能据此追溯证明那些新增实现分别经过了 test-first。“行为已满足”的例外在本轮容易覆盖刚刚提前实现的行为，而不只是原有代码。

**建议**

优先修改现有 TDD 技能中这条例外及切片完成条件，而不是在全局指令中再加入一段“严格遵守 TDD”：

- 当前 red 授权当前行为所必需的生产改动；首个 tracer 先收敛到可独立观察的最小业务结果。
- 区分“进入切片前已存在的行为”与“本轮共享实现连带带通的行为”。后者补充验收和敏感性证据，并如实标记，不宣称经历过独立 red。
- 验收复核读取现有执行时间线，抽查生产改动与专项测试的先后关系；不另造一份重复维护的 TDD 状态台账。

**完成标准**：下一次可从已有日志直接找到当前切片的预期、具体违例、实际 red 和对应生产改动；连带满足项与独立红绿项能明确区分。

## 2. 高：为并发承诺补充可检出锁缺失的证据

**事实**

P13 测试用同一个 Map 版本，通过 `Promise.all` 发起两个同 ID 的生产 HTTP 保存请求，断言一个成功、一个冲突，并核对获胜内容及非目标文件。它使用真实服务与真实文件，是有价值的并发提交验收。

该测试没有控制服务端竞争阶段，也没有记录两个请求在冲突检查与提交区间实际重叠的证据。会话中未观察到针对提交锁的故障注入或临时变异。P18 的第二页面修改 B 后再提交 A，证明的是旧版本冲突，并不补足这一证据。

**推断，尚未验证**

如果移除协调锁，两个请求仍可能因调度顺序或提交前复查而得到“一成一败”；因此该测试可能无法稳定检出协调边界被破坏。此次没有运行此变异，不能断言它一定存活，也不能断言现有锁实现有缺陷。

**建议**

落实现有 TDD 技能的“green 后检查具体违例”要求，将并发性质作为需要重点检查的分支：

1. 用局部、可恢复的故障注入验证当前竞争用例能否检出缺失协调边界；无需引入全项目 mutation 平台。
2. 若检不出，由并发验收所有者在既有隔离 HTTP／文件系统测试支撑中设计可控竞争条件，继续通过批准的 S2 观察结果。需要新测试控制能力时先确认 seam，不改用私有函数测试。
3. 在证据补齐前，把结论准确限定为“并发请求得到正确持久化结果”，与“测试能检出协调锁缺失”分开陈述。P13 的本票责任与 06 的跨操作竞争责任也分别保留。

**完成标准**：明确命名的协调边界违例能被相关用例稳定检出；仅增加重复次数或任意等待不作为替代证据。
