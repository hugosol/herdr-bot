# TDD 执行复盘建议

## 范围与结论

本复盘仅依据本票执行会话的原始 JSONL、工具参数及返回结果，不采用父 session 或其他票据执行的结果作为本票证据。下文行号均指本票会话文件。

本轮值得保留的做法：

- 使用已批准的 S1／S2、真实隔离文件与服务进程，没有用模拟页面或内存文件系统替代验收。
- 对既有实现首次即通过的用例，没有人为制造生产缺陷来充当 red。这是验证型票据，符合 TDD 技能中“行为已满足时验证现有行为与覆盖”的分支。
- P25 不只断言请求成功，还检查胜者、文件内容和提交顺序；临时移除删除协调锁后，竞争测试出现 **5 failed／1 passed**，恢复后重新构建并通过验收。这是有效的敏感性证据，不是发现了需要保留修复的生产缺陷。
- 最终实际执行了完整后端、前端和浏览器入口：后端通过，前端 **205 tests passed**，浏览器 **293 passed／1 skipped**。文件 symlink 的 EPERM 限制在交接中明确保留。

优先改进的是**验收结论与观察能力的匹配**，其次是平台能力和实验产物管理；没有证据支持继续向全局代理指令堆叠一般性要求。

## 1. 高优先级：补齐“没有读取文件”的观察能力

**事实**：P34 的 `inert()` 检查页面／响应不包含秘密内容、哨兵文件字节不变、没有浏览器脚本效果，以及 Herdr、固定操作、扩展、关机等执行记录为空。这里没有文件读取事件记录器。最终交接却将此归纳为路径参数不会导致对应文件被读取。见会话 L212 的测试新增参数及 L339 的交接。

**推断**：一个“读取参数指定文件，但丢弃内容，不修改文件，也不启动其他动作”的错误实现，仍可能通过这些断言。现有证据能够支持“不泄漏内容、不改写文件、不执行记录中的动作”，单独不足以支持“没有发生读取”。这不是已经观察到生产代码越界读取，而是测试与结论之间的证据缺口。

**建议**：

- 在验收环境提供针对测试拥有哨兵、可归因到服务进程的文件读取审计能力；入口仍保持真实页面／HTTP，不为测试暴露生产内部 seam。
- 将“读取后丢弃内容”作为该能力的正向控制：控制程序实际读取时必须产生记录，正常管理操作则不应产生记录。具体采用何种 Windows 文件访问跟踪工具及其权限要求，需另行验证，不能把工具可用性视为既成事实。
- 若环境暂不能提供该观察能力，报告中分别列出“未泄漏／未改写：已验证”和“完全未读取：未直接验证”，由验收所有者决定是否还需要其他证据。

**落点**：现有测试夹具／宿主能力，以及 TDD 参考材料中的一个具体反例。原技能已有“观察被约束的实际交互”的规则，不需要在 `AGENTS.md` 再复制一条泛化禁令。

**完成标准**：带有上述“读取后丢弃”错误的受控版本会被测试或审计明确检出；最终结论与实际观察范围逐项一致。

## 2. 中优先级：将平台限制变成可交接的能力矩阵

**事实**：本轮实际尝试创建 Windows 文件符号链接，收到 EPERM，独立用例明确 skip；目录 junction、根路径和祖先路径的读写删除场景则实际通过。最终报告没有把这个 skip 隐瞒成全通过。与此同时，票据验收框被一次性全部勾选。见 L290–301、L318 的平台证据读取，以及 L328–339。

**推断**：完整叙述是诚实的，但只读取勾选状态或命令退出码的下游代理，仍可能丢失“文件 symlink 未验证”的细分状态。单次普通 Windows 运行也不能自动代表其他权限、文件系统或平台；P25 文件通知顺序的实际证据同样来自本次 Windows 环境。

**建议**：

- 由宿主输出简短的能力矩阵：场景、平台／权限、已验证或未验证、证据位置。将文件 symlink 与目录 junction 分开，不用单个 P33 勾选状态替代两者。
- 若交付门槛要求文件 symlink 场景通过，安排具备相应能力的验收环境；普通开发环境仍可显式 skip，但必需能力验收应在能力缺失时返回“未完成”，而非仅凭进程退出码通过。
- 保留当前对 EPERM 的透明报告，不为了消除 skip 自动提升权限或放宽安全边界。

**已有护栏与未知项**：会话已读取 npm 脚本，确认存在网络策略 pretest hook、构建时的 `tsc --noEmit` 和完整浏览器入口。本复盘没有检查 CI／提交钩子的接线情况，因此不宣称仓库没有 CI，也不建议重造现有测试入口。

**完成标准**：集成代理无需重读长篇对话，就能准确区分“Windows junction 已通过”和“文件 symlink 仍需特定环境验证”。

## 3. 中优先级：隔离实验产物，并让 mutation 恢复具有异常保障

**事实**：本轮先使用内存形式的附件，之后发现默认结果目录没有所需 JSON 文件，才改成显式写入 `info.outputPath()`。后续在 mutation 运行期间读取上一轮结果文件，又得到路径不存在。生产锁通过两次独立编辑完成移除与恢复，恢复后确实重新构建并通过完整验收。见 L183–186、L235–265、L274–301。

**推断**：当前手工流程最终正确，但依赖代理不中断地完成恢复；复用结果目录也容易使前一轮证据在下一轮开始后不可用。本次没有观察到最终源码遗留 mutation，不能把这种风险写成已发生的交付事故。

**建议**：

- 给定向验证、mutation 和最终回归分配独立结果目录，保存候选版本／恢复版本标识、命令、退出码及必要附件；交接引用稳定的本次运行证据，而非会被后续运行覆盖的默认目录。
- 若同类 mutation 经常使用，由宿主提供小型实验执行器：保留原始内容，确保异常退出也进入恢复路径，恢复失败时阻止发布，并要求恢复版本重新构建和验证。
- 复用现有 npm／后端入口，避免为一次实验引入项目级 mutation 平台。

**完成标准**：下一轮测试不会清除前一轮所引用证据；模拟实验中断后，宿主能明确给出恢复成功或恢复失败，而不是依靠对话叙述推断。

## 4. 低优先级：把可机械判断的工具问题交给工具回归

**事实**：

- `find` 的全部 25 个判定请求因地区限制返回 451，随后代理转用 `glob`／`grep`，并上报工具问题（L28–95）。
- 一次 `edit` 提交了空替换，暂时删掉 `if` 分支开头而保留 `else`；代理读取后修复。该请求的旧文本还比实际文件多一个分号，工具仍接受匹配，代理另外报告了超出“仅空白模糊匹配”说明的行为（L250–259）。空替换导致语法破坏与工具接受标点差异是两个独立问题，不能全部归咎于工具。
- Windows 宿主下向实际 shell 发送 `Get-ChildItem` 得到 command not found（L142–144）。

**建议**：

- 为编辑工具增加确定性匹配回归：允许的空白差异、分号等标点差异和零修改请求分别有明确结果；失败匹配保持文件不变。此类固定规则属于工具测试，不属于 reviewer 的主观编码标准。
- 对明确的地区／授权不可用错误尽早终止同一批语义判定，并在本次运行展示已降级的搜索能力；保留当前明确区分“搜索失败”和“没有结果”的做法。
- 在工具运行信息中明确暴露实际 shell，与宿主 OS 分开，减少命令解释器猜测。

**完成标准**：上述工具错误能由固定输入复现并被工具自身检测，不需要再向每个项目的全局指令添加提醒。

## 5. 低优先级：给错误恢复测试提供“业务语义与依赖文案”的示例

**事实**：P34 首次失败是测试寻找中文 `JSON 无效`，页面实际展示浏览器 JSON 解析器的英文消息。代理读取真实页面快照后改为匹配 JSON 错误，同时保留草稿原文与文件不变的断言，随后通过（L215–225）。这不是生产行为修复，也不能当作业务违规的 red。

**建议**：在现有 TDD 测试参考材料加入一个短例：没有契约承诺的浏览器／运行时诊断文案，测试以错误状态、草稿保留、未提交和可恢复为观察；只有产品契约规定的文案才作精确字面量断言。将其作为评审时的判断示例，不新增机械禁令，也不改写已经有明确文案约束的测试。

**完成标准**：替换运行时诊断措辞不会使业务正确的恢复测试失败，而“错误被吞掉、草稿丢失、错误提交到文件”的实现仍会失败。
