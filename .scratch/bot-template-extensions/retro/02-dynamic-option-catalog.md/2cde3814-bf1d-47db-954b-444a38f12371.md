## 1. 高：将新增启动映射行为单独经过 red，而不是由前段断言代替整个场景的 red

**事实**

- 原始日志第 196 行已写入包含 `Catalog::resolve` 的实现；随后接入创建快照及原生启动参数。
- 含动态 provider/model 与 Skill 映射断言的浏览器测试到第 363 行才写入。
- 该测试首次执行在“重新打开编辑器后出现 lab-model”的前段断言失败；修复编辑器后整个测试通过。后段启动映射断言没有在实现该新增行为之前形成独立 red。
- 首个 HTTP 测试也同时包含选项、保存、持久字段和热更新合法性；观察到的行为 red 是最先执行的 models 断言。

**判断**

这是 TDD 执行顺序的缺口，不是已证明的功能错误。最终独立预期与真实外部记录仍提供有效的行为证据，但一个长场景最前面的失败，不能证明后续每项新增机制都按 test-first 开发。

**建议**

在现有 TDD 执行器中使用“当前违约情景”作为局部检查点：当前新增的是展示、保存校验还是启动解释，就先让该边界的测试达到对应断言并产生行为 red，再修改负责该行为的生产代码。首次贯通后再保留综合场景验证整条路径。

对于已经实现、无法追溯补做 test-first 的行为，应明确记录为后补覆盖；需要加强敏感性证据时，可临时注入旧映射或旧缓存行为，观察对应断言失败，再恢复。不要为了补齐形式而制造无关失败，也无需新增一份验收台账。现有 TDD 技能已经包含这些要求，应改进执行检查点，而非重复写一条规则。

## 3. 中：将真实进程测试的超时、清理与元数据布局收拢到同一测试夹具

**事实**

- 新增启动拒绝测试对前四类故障设置了期限，并在超时后终止子进程。
- 同一测试的 Windows 不可读文件分支却直接使用 `Command::output()`，没有同样的退出期限。
- 元数据成为启动必需项后，多个既有进程测试通过切换 cwd 到仓库根目录来找到交付文件；公共配置夹具则显式指向仓库中的元数据。
- 本 session 的协调消息明确指出：其他隔离 cwd 的启动用例也必须提供元数据。这证明新增启动前提会跨测试文件传播，但不证明其他票据实际失败。

**推断**

若将来仅“读取拒绝”这一分支错误地继续提供服务，直接 `output()` 可能一直等待，而不是在期限内给出可定位的测试失败。依赖仓库 cwd 的启动方式也扩大了夹具对默认文件布局的隐含依赖；本次没有观察到用户文件被改写。

**建议**

复用或收拢现有真实进程夹具，使其统一提供：

- 隔离运行目录与按交付布局放置的元数据；测试需要变化时，在该目录修改副本。
- 有界的启动、退出等待，以及失败时的子进程清理。
- 失败诊断中附带 stdout/stderr 和实际配置位置。

这属于测试基础设施，不需要新增产品存储 port、配置回退或后台服务。尤其应让故障验收本身在目标行为退化时仍能可靠结束。
