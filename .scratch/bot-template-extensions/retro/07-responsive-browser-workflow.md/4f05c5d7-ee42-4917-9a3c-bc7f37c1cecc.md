## 1. 中：由宿主机械校验完成协议，避免指令与工具实际接收格式分离

**事实：** 实现轮要求逐项提交 `{ key: 1, data: ... }`，但最后实际调用只有 `data`，工具仍返回 `Result submitted.`。该次交付内容和提交均存在；历史没有显示因此丢失结果。

**推断：** 工具接收层没有强制体现该轮要求的 `key` 约束，或展示的 schema 与实际执行校验不一致。仅靠常驻指令提醒不能可靠约束机械格式。

**建议：** 在宿主的工作池提交入口校验当前轮协议：必填项、键类型、允许的成功/失败分支，以及待完成项身份。缺少 `key` 时直接返回可修正的结构错误，成功响应明确回显已完成项。

**完成判据：** 用缺少 `key`、字符串 `key`、合法单项提交三个输入验证：前两者被拒绝，最后一个明确完成对应项。此类约束放在工具校验层，不增加 `AGENTS.md` 或 reviewer 的格式检查负担。

## 2. 中：把“依赖错误可修正”拆成明确的验收终点

**事实：** 两档都触发了真实缺失入口文件错误；恢复元数据后，实际操作是重新打开创建弹窗、观察名称预览可用，再关闭。报告明确写出：**没有再次证明依赖检查成功，也没有成功启动真实 agent**。票据同时将对应验收项标为完成。

**判断：** 这不是隐瞒未验证项。风险在于“能继续修正”的完成边界不够精确：名称预览可用和依赖预检通过是两个不同观察，集成人可能对全勾选清单产生更强理解。仅依据本会话，不能断言本票必须成功启动 agent 才合格。

**建议：** 后续同类票据在执行前明确选择所需终点：

- **反馈与操作恢复**：原因可辨认、输入保留、能修改或退出；允许不再提交创建。
- **依赖修复确认**：修复后再次经过依赖检查，并取得约定的公开观察。
- **真实创建成功**：另需真实 Herdr/agent 证据及相应运行授权。

将该决定放在票据的验收条件中，报告直接引用，不让执行者用预览状态推断更深层成功。

**完成判据：** 每个终点都能指向一项具体操作和观察；未执行的更深层终点保持明确未验证。本票若由集成人接受第一档，应记录这一解释，而不是追加无关的真实启动要求。

## 3. 低：在工具入口暴露实际 shell，并减少嵌套 PowerShell 字符串

**事实：** 保存截图时，一条 `powershell -Command "...$destination...$_.FullName..."` 命令出现括号缺失等解析错误，错误文本还混入此前命令片段。改为外层单引号及直接通配符复制后成功。

**推断：** 嵌套命令中的变量被外层 shell 提前解释；本会话没有进一步验证具体展开机制。

**建议：** shell 工具在会话初始化时明确返回实际解释器及版本。对于含变量的复杂脚本，优先提供参数数组或脚本执行入口，让调用者不必手工跨两层 shell 转义。相关说明放在工具文档，平台条件下按需读取。

**完成判据：** 含空格路径、`$variable` 和 `$_` 的复制场景能按字面传递并成功执行；无需依赖调用者猜测名为 `bash` 的工具实际使用哪种 shell。

## 4. 低：对不可用搜索后端快速失败，并收窄检索输出

**事实：** 首次 `find` 的 25 个判断请求全部因地区限制返回 HTTP 451，最终没有有效检索结果。执行者正确报告了工具问题并使用其他方式继续，没有把失败当作“代码不存在”。之后一次 README 宽泛关键词搜索返回约 **49.6KB**，还触及大量与本票无关的旧记录。

**建议：**

- 搜索服务对同一后端明确的地区/权限拒绝进行快速熔断，直接返回“不可用及替代路径”，避免继续发出同类请求。
- 找到服务启动和浏览器测试入口后，后续导航限定到 `frontend/browser-tests/`、运行脚本及相关文档章节；将原始命中量、返回量和截断状态作为工具可见信息。

**完成判据：** 后端被明确拒绝时只发生必要的能力探测；定位运行方式时返回相关章节，而不是输出整份历史记录。这是工具及检索范围改进，不需要在常驻指令里再堆叠搜索禁令。
