- `test:browser`：Playwright。

本轮由代理手动组合后端构建、前端构建与浏览器测试，最终结果均有日志。只读查看常规位置时，未发现 `.github/workflows/*`、`.githooks/*`、`.husky/*` 或 `.pre-commit-config.yaml`。

此外，`frontend/tsconfig.json` 包含 `src`、`tests` 和 Vite/Vitest 配置，**没有包含 `browser-tests` 或 Playwright 配置**。因此，现有 `npm run build` 的类型检查范围不覆盖本轮新增和修改的浏览器测试代码。

### 推断与风险

- 在仓库可见范围内，检查通过主要依赖代理记住正确命令和构建顺序，而不是合入机制保证。
- 浏览器测试本轮实际运行通过，但其类型约束仍可能在其他改动中失去约束力；运行通过不等于整个测试目录已接受 TypeScript 静态检查。
- 尚未检查仓库外的 CI、全局 Git hooks 或分支保护，不能据此断言整个交付环境绝对没有 guardrail；本轮也没有观察到因此逃逸到交付物的具体缺陷。

### 建议

优先复用已有命令建立确定性检查，而不是新增“提交前记得检查”的代理指令：

1. 在仓库内可见的 CI／合入门禁中执行现有 Rust 检查、前端构建及单元测试。
2. 给 Playwright 测试补充独立类型检查入口，明确覆盖 `browser-tests`、Playwright 配置和所需 Node 类型。
3. 在适合该项目的 Windows 浏览器环境中，按真实依赖顺序构建后端二进制与前端静态资源，再运行浏览器验收。先接入现有检查，不另造一套重复测试框架。

## 2. 高优先级：给故障注入增加“前置条件已成立”的可观察断言

### 事实

“扩展元数据在同一进程重新编辑和保存时生效”测试最初使用相邻两行文本替换，把扩展的 Agent 适用关系改成非法组合。测试随后等待页面错误提示，但提示未出现，最终超时（L287）。代理将注入方式改为把可选项变为固定项后，同一验收预期通过（L288–L293）。

对话中代理将最初替换失效归因为 Windows CRLF 与替换文本中的 LF 不一致。日志没有单独展示字节级核对或“替换命中次数”断言，因此，**换行差异是有依据的解释，但其确切成因并未在该轮独立证实**。

### 风险

夹具没有真正改变目标条件时，测试仍会走到产品断言并呈现红色。这样的失败容易被误判为“保存未重新校验”，而实际可能只是“非法元数据没有被写进去”。本次代理最终修正了夹具，未见其为迁就测试而修改产品语义；但第一次失败没有清楚区分这两类原因。

### 建议

把故障注入做成一个有明确完成标准的测试准备步骤：

- 使用能确认目标唯一性的修改方式；涉及文本替换时，断言目标存在且修改后确实不同。
- 修改落盘后，通过公开选项接口核对独立预写的适用关系或固定／可选分类，再触发旧页面保存。
- 准备条件不成立时立即报“夹具准备失败”，而不是继续等待业务错误提示。
- 仍以公开保存拒绝、旧值独立读回和真实磁盘结果作为产品断言；夹具自检不替代这些行为证据。

该机制适合放在测试支撑代码中，不需要把 Windows 换行细节扩写成全局代理规则。

**完成标准：**替换未命中时，测试在准备阶段直接失败；合法元数据下保存可成功；已确认非法的当前元数据下，旧页面保存被拒绝且旧模板不变。三种结果可明确区分。

### 建议

优先修正索引工具的项目选择与输出，而不是再要求代理多读一份导航文档：

若需要调整现有工具指引，宜将“当前 worktree 的覆盖与新鲜度”合并进现有图导航入口，而不是额外增加一组重复规则。

**完成标准：**两个 worktree 的同名文件声明不同时，导航结果能够明确区分；当前索引缺失时，不会默认把另一 worktree 的行号和声明当成当前事实。

## 4. 中低优先级：对确定性不可用的语义搜索实行快速降级

### 事实

首次 `find` 调用中，28 个判断请求全部因地区限制返回 HTTP 451，工具明确说明“没有候选得到判断，不能据此认定不存在”（L86）。代理随后报告了工具问题，并改用文件列表、字面搜索和源码读取；没有把空结果当作代码不存在。

该次结果显示约 3.5 秒墙钟时间、28 次请求。不能据此把本轮大量时间归咎于搜索，但这是明确可避免的无效扇出。

### 建议

在搜索工具或宿主层处理稳定的能力失败：

- 鉴权、地区限制等同类确定性错误出现后，终止该次剩余扇出，并在会话内暂停相同不可用后端。
- 返回简短、可执行的降级提示：没有语义判断结果；继续使用当前文件系统定位或可用的当前项目索引。
- 保留“未判断不等于不存在”的语义，避免降级路径制造假阴性。

本轮代理已经完成报告和降级，不需要再给实现代理增加“遇到失败要换工具”的泛化提醒。

**完成标准：**稳定的 451 只触发有限的失败请求；后续定位不再重复调用同一不可用判断服务，仍能读取真实仓库完成工作。

## 应保留的执行方式

以下做法本轮已有证据支持，建议保留，不必再增写成新的常驻指令：

- **沿批准 seam 验收。**生产页面、公开 HTTP、真实磁盘和真实进程重启共同构成证据，未用纯内存原型替代持久性验证。
- **把外部加载与页面展示分开报告。**摘要中的固定扩展说明没有被当作真实 Agent 已加载的证据。
- **让编译器承担机械一致性。**新增错误枚举遗漏调用方时，穷尽性检查已经有效拦截；无需给 reviewer 再加一条手工穷举同类调用方的固定语法规则。
- **允许已满足行为直接验绿。**Agent 切换、磁盘失败等后续用例首次运行通过，不应为了凑 red 人为破坏实现。真正需要补强的是夹具条件可辨认和行为断言的区分力。

优先落实前两项自动化防线，再处理索引绑定与搜索降级。当前证据不足以提出新的 `CODING_STANDARDS.md` 判断性规则，也不足以断言某条常驻指令是 no-op。本轮未显示 reviewer 的独立审查过程，因此不把实现中的编译失败或夹具修正归因于 reviewer 漏检。
