# Bot 模板扩展选择、选项元数据与运行数据目录

Status: ready-for-agent

日期：2026-10-22

批准契约：[contract.md](contract.md)。承诺、seams、验收责任及后续批准的 B1/B2 配置与迁移澄清以契约为准；本规格保留需求叙述与范围。

## Problem Statement

用户希望通过 Bot 模板明确决定新 Bot 加载哪些 agent 扩展，而不是依赖电脑上用户目录、项目目录或 agent 配置的自动发现。目前模板没有扩展选择，原生启动参数也没有表达所需扩展集合；用户无法从模板判断实际会得到哪些扩展。

模型、thinking、Skill 等模板选项目前主要由代码维护。用户希望把这些选项与扩展入口、适用关系和启动映射集中到可直接编辑的元数据中；修改后，下次创建 Bot 即使用新映射，不需要重新保存每个模板或重启服务。

现有模板、zone 登记和 agent 会话文件分散在项目根目录。用户希望以一个被 Git 忽略的数据目录作为简易文件数据库，配置元数据则独立管理。旧模板和旧会话均不需要保留，只有 zone 登记需要迁移。

界面已有原型裁决：采用 C 的分步配置组织，但不能为了复用原型而削弱正式界面的命名编辑器、模型能力联动或其他已有字段功能。

## Solution

在 bot 入口中，将模板新增、编辑组织为“模板预设 → 扩展配置 → 确认保存”三个步骤。第一步完整保留现有字段和编辑能力；第二步显示不可取消的 Bot 固定扩展，以及按 Agent 提供的 Bot 可选扩展复选框；第三步展示配置摘要并由用户提交保存。

扩展选择只存于模板。新模板默认不勾选任何可选扩展，允许多选或全不选。OMP 提供 codebase-tools 和 connect-bot 两项，Pi 提供 codebase-tools 一项。两种 Agent 始终加载各自的 model-cost。创建 Bot 弹窗不增加扩展选择或临时覆盖。

选项元数据集中管理 Agent、模型、thinking、Skill、固定扩展和可选扩展的清单、显示信息、适用关系及实际启动映射。服务启动时校验；运行中打开模板编辑、保存模板和接受 Bot 创建请求时重新读取，使用当前有效元数据，不回退旧缓存。模板保存稳定选择标识，而非入口路径或模型映射的副本。

每次创建 Bot 自动先检查元数据、模板选择和本次所需扩展入口。失败发生在创建 Herdr Tab、启动 agent 和提交输入之前，界面明确告知失败原因及尚未产生的外部对象。检查通过后，固定本次模板与映射，关闭 agent 扩展自动发现，仅显式加载固定扩展与模板所选扩展，随后沿用既有创建流程。

运行持久数据集中进入 .data，手工维护的选项元数据放在 meta-data。切换时只迁移 zone 登记，清除旧模板和旧会话文件，后续所有模板和会话重新产生；不新增数据库服务或运行状态恢复功能。

## User Stories

1. 作为管理 Bot 模板的用户，我希望在 bot 入口新增、查看、编辑和删除模板，以便沿用现有管理入口而不寻找新的扩展管理页面。
2. 作为新增模板的用户，我希望按“模板预设、扩展配置、确认保存”三个步骤完成配置，以便逐步理解并确认完整预设。
3. 作为编辑模板的用户，我希望在步骤之间返回修改时保留尚未保存的草稿，以便不因查看下一步而丢失输入。
4. 作为用户，我希望进入确认步骤不等于自动保存，以便只有明确保存才改变服务端模板。
5. 作为用户，我希望第一步仍能编辑模板名称、Bot 命名规则、Agent、model、thinking、Skill 和 prompt，以便新增流程不削减原有功能。
6. 作为配置 Bot 名称的用户，我希望保留现有命名规则编辑、字段插入按钮和示例预览，以便继续组合固定文字与已有占位符，而不是只能查看只读规则。
7. 作为配置模型的用户，我希望仍可选择沿用 Agent 默认值、gpt-6.1-sol 或 deepseek-flash，以便不因界面重组改变现有模型范围。
8. 作为配置 thinking 的用户，我希望选项仍受当前 Agent 和具体模型能力约束，以便不会保存该组合不支持的级别。
9. 作为使用默认模型的用户，我希望 thinking 也沿用默认值，以便不为未知默认模型强加推理级别。
10. 作为切换模型的用户，我希望仍受支持的 thinking 被保留、不再支持的值被重置并提示，以便保持既有联动行为。
11. 作为用户，我希望保留 Skill 可不选、从现有预设中单选以及 prompt 可多行、可为空的行为，以便扩展配置不改变初始化输入的含义。
12. 作为配置 OMP 模板的用户，我希望能分别勾选 codebase-tools 和 connect-bot，以便独立决定两项能力是否加载。
13. 作为配置 Pi 模板的用户，我希望只看到 Pi 对应的 codebase-tools 可选项，以便不会选择 OMP 专用入口。
14. 作为新增模板的用户，我希望可选扩展初始全部不勾选，以便不会在未明确选择时启用额外能力。
15. 作为用户，我希望可选扩展支持多选和全部不选，以便 OMP 能表达零项、单项或两项组合，Pi 能表达零项或单项。
16. 作为用户，我希望 model-cost 独立显示为固定加载且无法取消，以便不会将其误认为默认勾选、仍可关闭的可选项。
17. 作为用户，我希望固定扩展随 Agent 使用对应入口，以便 Pi 不会误加载 OMP 的 model-cost，反之亦然。
18. 作为切换 Agent 的用户，我希望 model、thinking 和可选扩展选择按既有重置方向回到默认状态，以便同名扩展不会被静默替换为另一个 Agent 的入口。
19. 作为切回先前 Agent 的用户，我希望不恢复之前隐藏的扩展勾选，以便草稿中实际显示的选择就是将保存的选择。
20. 作为确认模板的用户，我希望保存前摘要展示已有字段、固定扩展、所选扩展以及自动发现关闭的信息，以便看懂模板决定的启动配置。
21. 作为保存模板的用户，我希望新增的扩展选择由服务端持久保存，以便刷新或换设备后仍能读取同一预设。
22. 作为用户，我希望保存失败时明确保留失败反馈且不宣称已保存，以便不会把本地草稿当作服务端结果。
23. 作为电脑或局域网设备上的用户，我希望共享同一份模板和选项目录，以便不同设备不会各自维护不同配置。
24. 作为创建 Bot 的用户，我希望只按既有流程选择模板和填写本次 input，不再临时选择扩展，以便模板成为扩展选择的唯一来源。
25. 作为用户，我希望新 Bot 的扩展自动发现被关闭，以便用户级、项目级或 agent 配置中的其他扩展不会绕过模板额外加载。
26. 作为用户，我希望实际显式加载集合恰好为对应 Agent 的固定扩展加模板勾选项，以便取消勾选具有确定的启动含义。
27. 作为未勾选 connect-bot 的用户，我希望仍可正常创建 Bot，但界面不承诺该 Bot 会自动登记到 chat，以便区分 Bot 与 connect-bot 接入。
28. 作为维护选项的用户，我希望直接编辑一个集中元数据文件来维护模型、thinking、Skill 和扩展选项及映射，以便不必分别修改前端清单、后端校验和启动映射代码。
29. 作为维护元数据的用户，我希望模板仅记录稳定选择标识，以便修改入口或 provider/model 映射后不用重新保存已有模板。
30. 作为维护元数据的用户，我希望修改后无需重启 herdr-bot，新打开的模板编辑界面、后续保存和后续 Bot 创建使用当前文件，以便下次操作及时反映更新。
31. 作为用户，我希望保存模板时重新检查当前元数据，而不是信任旧页面中的选项，以便页面打开后被移除的选项不能绕过校验。
32. 作为用户，我希望已被移除或不再适用的已保存选择仍可在模板中辨认，并明确提示不可用，以便不会丢失原始选择意图或无声改用默认值。
33. 作为修正模板的用户，我希望能移除失效扩展选择并重新保存，以便通过模板编辑解决元数据变更后的问题。
34. 作为用户，我希望存在失效选择的模板在修正前不能保存为有效模板或用于创建，以便不会启动一个与预设不一致的 Bot。
35. 作为用户，我希望单个模板的失效选择不会使其他有效模板无法使用，以便局部配置问题不扩大为全局停用。
36. 作为服务维护者，我希望启动时元数据缺失、不可读或非法就明确阻止服务启动，以便不会依靠隐藏备用清单运行。
37. 作为用户，我希望运行中元数据损坏时相关模板操作明确显示配置位置和原因、不能保存或创建，且不沿用旧缓存，以便不会误以为新配置已生效。
38. 作为维护元数据的用户，我希望修复文件后后续读取操作能恢复使用，以便动态读取不会变成必须重启才能解除的错误状态。
39. 作为创建 Bot 的用户，我希望创建动作自动执行启动前依赖检查，而不是要求另按一个检查按钮，以便不能漏掉检查步骤。
40. 作为用户，我希望检查覆盖本次模板选择及所有实际所需的固定扩展和可选扩展入口，以便在产生外部对象前发现确定的配置问题。
41. 作为用户，我希望所需入口缺失、不是文件或不可读取时阻止创建，并指出具体扩展与入口，以便能直接修复问题。
42. 作为用户，我希望未勾选扩展的入口缺失不阻止其他有效组合创建，以便只检查本次实际依赖。
43. 作为用户，我希望依赖检查未通过时明确得知未创建 Herdr Tab、未启动 agent、未提交输入，以便不必寻找或清理并不存在的外部现场。
44. 作为用户，我希望一次通过检查并被接受的创建固定使用当时的模板和映射，以便后续文件或模板编辑不会改变正在创建的 Bot。
45. 作为用户，我希望修改模板或元数据仅影响后续创建，不改配或关闭已有 Bot，以便已开始的对话保持稳定。
46. 作为用户，我希望通过依赖检查后仍按既有 Herdr 启动、就绪确认、初始输入提交及部分失败语义推进，以便新增前置步骤不改变创建成功的定义。
47. 作为用户，我希望界面不把入口文件检查通过说成扩展初始化成功、账号可用或 Skill 执行成功，以便检查结果不夸大实际保证。
48. 作为服务维护者，我希望运行持久数据集中在 .data 并被 Git 忽略，以便把它作为本机简易文件数据库而不提交个人模板和会话内容。
49. 作为服务维护者，我希望选项元数据放在独立的 meta-data 目录并可纳入 Git，以便把手工维护的配置与运行产生的数据区分开。
50. 作为已有 zone 的用户，我希望现有登记迁移到新数据位置且保持原有登记信息，以便升级后无需重新登记目录。
51. 作为 zone 用户，我希望迁移登记文件不会搬动、删除或改写 zone 指向的实际目录，以便文件浏览和 zone 创建边界保持不变。
52. 作为用户，我希望旧 Bot 模板直接清除、新模板从空列表开始，以便无需为不再需要的数据引入兼容机制。
53. 作为用户，我希望旧会话文件不保留、不迁移，后续 Bot 使用新数据目录下独立的新会话位置，以便所有新 Bot 都重新创建对话。
54. 作为用户，我希望缺少运行数据目录时服务能够创建它，以便新环境无需手工预建空目录和空数据文件。
55. 作为维护者，我希望切换完成后不再读取根目录旧模板、旧登记或旧会话位置，以便不存在两套互相漂移的数据源。
56. 作为用户，我希望已有临时登记、关机意图和创建进度不因数据目录整理而新增持久化或恢复，以便这次变更不改变其生命周期。
57. 作为手机或桌面浏览器用户，我希望分步编辑、摘要、失效提示和检查失败反馈在现有支持的界面尺寸下都可操作，以便新流程不损害已有跨设备使用方式。

## Implementation Decisions

### 产品与界面

- 采用原型已确认的 C 分步组织，顺序为模板预设、扩展配置、确认保存。A 的表单内分组加右侧摘要和 B 的三栏工作台均不是最终方案。
- 分步仅重组已有模板编辑流程，不简化已有字段。尤其保留正式 Bot 命名规则编辑器的编辑、四类字段插入和示例预览；不使用原型中的只读替代控件。
- 步骤间移动不隐式持久化，明确提交保存才更新模板。确认步骤展示完整配置摘要，固定加载、可选选择及关闭自动发现必须可区分。
- 可选扩展只在模板编辑中多选，创建界面没有扩展复选框、临时覆盖或第二份选择来源。新模板默认零项；model-cost 为固定扩展，不是默认勾选项。
- 切换 Agent 清空可选扩展，同时沿用现有 model、thinking 重置规则；切回不恢复隐藏的旧扩展选择。
- 模板失效选项保持可识别，不自动丢弃、替换或回退默认；通过模板编辑修正，提供移除失效扩展选择的操作。失效模板不能保存为有效配置或用于创建，其他有效模板不受其局部失效影响。
- 不新增扩展安装、注册、启停或元数据编辑界面；用户直接编辑服务端元数据。

### 选项目录与动态映射

- 一个手工维护的 TOML 元数据文档集中描述 Agent、模型及完整 provider/model 映射、按 Agent 和模型区分的 thinking、Skill、固定扩展、可选扩展、显示信息和适用关系。前端选项展示、服务端保存校验及原生启动配置读取同一来源，不再维护互相独立的选项清单。
- 初始 Agent 范围仍为 OMP、Pi；模型仍为沿用默认值、gpt-6.1-sol、deepseek-flash。两个显式模型分别映射为 openai-codex/gpt-6.1-sol 和 deepseek/deepseek-flash，不做裸模型名模糊匹配或 provider 回退。
- 保留当前已核对能力：OMP 的 GPT 级别为 low、medium、high、xhigh、max，DeepSeek 为 low、high、max；Pi 的 GPT 为 minimal、low、medium、high、xhigh、max，DeepSeek 为 off、low、high、max。显式 thinking 之外仍允许沿用默认值；模型默认时 thinking 必须默认。更换模型仍保留适用级别，不适用则重置并提示。
- Skill 保留无、teach、code-review 选项及现有原生 Skill 初始化输入语义；扩展自动发现开关不被扩展成关闭 Skill 或其他能力的产品要求。
- 模板增加可选扩展选择，保存稳定标识而非完整入口、provider/model 或能力表副本。固定扩展从当前 Agent 元数据解析，不作为可取消的模板选择。
- 服务启动先读取并校验元数据。缺失、不可读、语法非法、标识重复或关系矛盾时启动明确失败，不自动生成替代配置、不回退代码清单。
- 运行中打开模板编辑、保存模板和接受创建请求时读取当前元数据；有效修改无需重启。这是已取代“启动时加载、修改后重启”的最终决定，不要求文件监听或后台推送。
- 运行中元数据失效时相关操作失败并展示配置位置与原因，界面不能表示已保存或可创建；不使用旧缓存继续执行。后续操作可重新读取修复后的文件。
- 一次创建接受时固定模板内容与本次解析出的映射，整个创建保持一致；下一次创建重新读取，不因编辑而改配已运行 Bot。

### 原生加载与依赖检查

- OMP 初始可选扩展为 codebase-tools、connect-bot，Pi 为 codebase-tools；它们是三个具体入口，不代表 Pi 可选 OMP 入口。两种 Agent 分别固定加载对应的 model-cost。
- 通过 Agent 原生启动参数关闭扩展自动发现，并显式列出固定扩展与模板勾选扩展；不修改用户级或项目级 agent 配置，不增加全局安装或自动发现的旁路。
- 在创建 Herdr Tab、启动 agent、提交输入之前，自动读取并校验元数据、核对模板选择适用性、解析本次依赖集合、检查每个所需入口存在且为可读取文件。固定入口同样受检查；未勾选扩展的入口不作为本次启动依赖。
- 任一上述检查失败均拒绝本次创建，并指出配置或扩展入口原因；反馈明确外部 Tab、agent 和初始输入尚未创建、启动或提交。正式流程必须实际检查服务端文件，不能复用原型模拟结果。
- 前置检查不执行扩展 factory，不发模型请求，不检查账号余额，不承诺导入、初始化或 Skill 执行成功。文件检查与实际加载之间仍可能发生外部文件变化，不把检查包装成无竞态执行保证。
- 检查通过后沿用现有 Herdr Workspace 选择、新 Tab 和 Pane、新会话、就绪确认、输入提交、创建结果与部分失败保留现场语义，不新增自动重试、回滚删除或自动跳转 chat。
- Bot 不以接入 connect-bot 为成立条件，创建成功不等待扩展接入。零可选扩展仍须加载固定扩展，且不以“仅创建、不发输入”替代现有成功条件。

### 数据位置与切换

- 将运行持久数据集中于 .data，将手工维护的选项元数据归入 meta-data；运行数据整体忽略 Git，元数据纳入版本管理。实际配置位置见 Further Notes，不在此阶段设计代码模块或测试 seams。
- 新运行数据目录不存在时创建；数据写入失败延续明确报错、不能宣称保存成功的原则。
- 只迁移现有 zone 登记，保留登记内容和实际目标路径，不移动或删除 zone 目录。保留 zone 的显式创建父目录、浏览根边界和失败保留现场规则。
- 用户明确授权清除旧模板和旧 agent 会话文件；不保留兼容读取、模板格式迁移、会话恢复或双位置回退。新模板从空列表开始，后续每个 Bot 使用新数据位置下独立的新会话目录。
- 清理旧会话文件不等于向已运行 agent 发送关闭指令；本次不增加停止、重新接管或恢复已有 Bot 的能力。
- 不将创建生命周期表、connect-bot 会话登记、关机监听或倒计时改成持久化；遵守已有后端权威和生命周期边界。
- 具体内部模块划分、元数据序列化细节、错误表示及测试 seam 选择留给后续契约和实现设计；本 spec 不新增未经讨论的架构分层。

## Testing Decisions

- 现有项目已有模板公开接口与持久化、Bot 创建和原生启动参数、断线后创建推进的后端测试，以及模板与创建的前端测试、真实浏览器用例，可作为既有行为和测试习惯的先例；不在此指定新增测试的 seam 或数量。
- 既有受控 Herdr 夹具能记录创建、启动、提交顺序与参数，可作为不启动真实付费模型的已有先例；它不能被宣称为真实 Herdr、OMP、Pi 的端到端执行结果。
- UI 依据原型裁决验证 C 的步骤组织，并保留正式旧字段交互，尤其是命名规则的编辑、字段插入和示例预览。应实际观察桌面和移动尺寸界面；桌面浏览器移动视口不冒充真实手机验证。
- 元数据、文件检查、模板保存及创建在原型中均为内存模拟。生产验收不能把原型演示、原型类型检查或无网络请求记录当作本功能真实读文件、持久化、依赖检查或扩展加载的证据。
- 扩展入口存在性与可读性检查通过，不等于 factory 成功执行。验证报告需区分生产代码通过受控环境证明的行为、真实 agent 实际加载结果及尚未执行的场景，不以账号、权限或付费请求验证作为本次前置检查内容。
- 本轮仅生成 spec，不运行或宣称通过任何生产功能测试；具体测试承诺、seams、覆盖对应关系在 /to-contract 阶段确定。

## Out of Scope

- 创建 Bot 时临时选择扩展、覆盖模板选择，或对运行中 Bot 热插拔扩展。
- 扩展管理页面、在线安装、包市场、上传任意代码、通过浏览器编辑元数据或执行任意扩展路径。
- 自动发现新模型或扩展、自动更新模型能力、增加第三种 Agent 或额外初始模型。
- 改变已有 Skill 协议、初始正文合成、模型推理能力规则、Bot 命名规则或创建成功定义。
- 提前执行扩展以验证 factory、检查模型服务权限或余额、通过模型请求验证依赖。
- 让 Bot 创建等待 connect-bot 接入、自动插入 chat 登记，或新增 Bot 列表、聊天、关闭和历史恢复能力。
- 旧模板兼容和迁移、旧会话文件保留和恢复、根目录与新目录双读或回退。
- 将 zone 实际目录搬进数据目录，改变 zone 创建父目录、文件浏览安全边界或既有 Git 操作范围。
- 数据库服务、数据库引擎、通用数据访问框架、备份系统、文件监听服务、全局配置推送，以及临时状态持久化。
- 将原型完整代码、A/B 方案、演示情景切换器或演示用只读旧控件直接作为生产要求。
- 本 spec 阶段决定模块 seams、测试 seams、逐项测试承诺或实现票拆分。

## Further Notes

### 目标布局与清理范围

目标文件位置是本次需求的一部分，集中在此记录：

| 类别 | 目标位置 | 处理 |
| --- | --- | --- |
| 服务配置 | `herdr-bot.toml` | 保持服务配置职责；相关路径说明和实际配置需同步更新 |
| 选项元数据 | `meta-data/bot-options.toml` | 手工维护，纳入 Git；动态读取 |
| zone 登记 | `.data/zones.json` | 从根目录现有 `zones.json` 迁移，保持登记内容 |
| Bot 模板 | `.data/bot-templates.json` | 清除根目录旧模板，从空列表开始 |
| agent 会话 | `.data/bot-sessions/` | 不迁移根目录旧 `bot-sessions/`；旧文件清除，新 Bot 重新创建 |

现有根目录运行数据及其临时文件目前被忽略且不在 Git 当前跟踪列表中，服务配置由 Git 跟踪；这是已检查的当前状态，不是全部 Git 历史审计。切换时应同步运行说明和忽略规则，不在根目录留下仍会被程序使用的旧数据源。

### 初始扩展入口

扩展路径由选项元数据维护，初始值基于用户指定的本机 toolkit：

| Agent | 类型 | 显示标识 | 初始入口 |
| --- | --- | --- | --- |
| OMP | 固定 | model-cost | `E:\Developer\myhub\my-agent-toolkit\entrypoints\omp\model-cost.ts` |
| OMP | 可选 | codebase-tools | `E:\Developer\myhub\my-agent-toolkit\entrypoints\omp-auto\codebase-tools.ts` |
| OMP | 可选 | connect-bot | `E:\Developer\myhub\my-agent-toolkit\entrypoints\omp-auto\connect-bot.ts` |
| Pi | 固定 | model-cost | `E:\Developer\myhub\my-agent-toolkit\entrypoints\pi\model-cost.ts` |
| Pi | 可选 | codebase-tools | `E:\Developer\myhub\my-agent-toolkit\entrypoints\pi-auto\codebase-tools.ts` |

两个 Agent 下的同名 codebase-tools 是不同适用入口；切换 Agent 清空选择，不做跨 Agent 隐式继承。
