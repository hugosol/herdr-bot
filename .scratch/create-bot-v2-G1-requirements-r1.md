# G1：Bot 需求对齐能力——详细建设需求

## 1. 身份、用途与确认状态

- 方案：create-bot-v2；工作：W1；缺口：G1；本文：r1。
- 目的：新增一个 normal Task 及绑定它的 Bot，供未来「创建bot-V2」的第一个节点使用。本文不是让建设者立即为某个业务目标创建 Bot，也不授权生成 Map。
- 已确认业务：用户在概要规划 Chat 的 Q1–Q14 中确认两节点、三类既有目标、第一节点仅对齐意图、第二节点整体分层设计及创建；Skill／共享文档默认只读；原创建bot及当前 plan_workflow 不变。
- 本文细化 G1 的实施与交接要求，保留上述确认。新 Task 完整 prompt、执行配置及实际创建仍应由用户在建设 Chat 确认。两份能力完成之前，整体方案不可交给 Map 转换者。
- G2 的职责和接口在本文中完整说明到足够实现 G1 的程度，不要求读取另一 Chat 历史。

## 2. 整体业务与本能力边界

未来 Map「创建bot-V2」只有两个串行普通工作节点：

1. W1/G1 使用 grill-with-docs，读取目标和用户需求，与用户对齐意图，交付未按字段拆分的「Bot 需求」。
2. W2/G2 使用 writing-for-agents，依据该需求与真实目标，参考现有「prompt优化者——Bot维度」的分层原则，决定 Skill、Task.prompt、三指南与文档各自承载什么，再形成候选、确认并保存。

目标已存在，且唯一属于：normal Task、Map、TypeScript Script。Task 型绑定 normal Task ID；Map 型绑定服务目录内确切 Map 文件名；Script 型绑定实际 scripts 目录中的合法相对 .ts 路径。Script 不是 Task 类型。

G1 只读业务定义，不创建空白 Bot、不写三指南定稿、不优化 Task.prompt、不修改目标或已有 Bot、不试运行能力。允许安全写入本次授权的需求材料。后续全文批准与保存授权不能提前成为 G1 完成门槛。

## 3. 输入与目标核实

### 3.1 对外输入职责

V2 保留原创建bot的命名文件接口：必需 request、可选 materials。request 为自包含 UTF-8 JSON，保留以下业务信息：

- 唯一目标 type 及定位：Task ID、Map 文件名或脚本相对路径。
- requirements：本次需求；constraints、non_goals、resource_limits：相应约束数组。
- 可选 bot 命名信息：id、name、group。
- 本次已有授权、确认依据及适用范围；未知批准不能伪造为已确认。

V2 删除原版空白创建步骤，因而不沿用 create_blank 和 scope=create_blank 的强制要求。不得要求用户为不存在的步骤批准。最终候选、Bot 保存及 Task.prompt 修改批准可在 G2 取得。V2 的准确字段、版本和严格校验约定须在建设交付中明确；保留原版其他要求，但不声称旧创建 v1 Schema 兼容，不改旧协议或消费者。

materials 仅作为参考，注明用途及读取权限，不作为隐藏 request 参数或授权来源。可选缺席合法；已提供但不可读须明确阻塞。用户文字与参考材料冲突时澄清，不自行选一个版本。

根 Run 管理者可在启动后准备并确认必需输入，再派发 G1；G1 不承担 prepare_inputs、调度或其他管理动作。独立 Chat 必须直接提供同等委托与材料，不依赖别的 Chat。

### 3.2 真实事实核实

产品仓库：E:/Developer/myhub/herdr-bot；服务：http://127.0.0.1:18787。不得从当前 zone 推断服务配置位置。

先读 docs/scheduler.md 的定义、目标、HTTP 和路径契约，docs/usage.md 的 Task 类型及配置规则。通过公开目录和完整目标查询核实：

- Task：真实存在且为 normal；完整 prompt、执行配置、Skill／Suite 依赖及可核实能力边界。
- Map：完整定义、输入要求、命名输入、节点绑定、依赖、工作位置、所需资源与交付；必要时继续读取关联 Bot／Task，不以标题或指南证明可执行。
- Script：核实服务实际 scripts 根、合法相对 .ts 路径、真实文件、完整脚本及必要依赖／输入输出约定。只读，不 import、执行或探测副作用；内容缺失或无法解释的依赖如实记录。

读取完整 Bot 目录，核实已有目标绑定和命名冲突。只考虑新建，不修订：已有绑定由用户明确是否仍新建，服务不允许时报告限制；同 ID 冲突不得覆盖、随机改名或自动复用。

配置字段若包含提示词占位符，按当前初始化给出的词典路径及单次替换规则解释，保留原始字段用于基线比较。已合成正文不重复替换，用户输入和交付文件不插值。缺键时报告字段与键，不猜值。

## 4. 意图对齐流程

使用 grill-with-docs 的讨论方法：事实自行调查，业务取舍交用户；沿用有效确认，按已解锁的问题成轮澄清，不把可调查事实推给用户。

至少落实：

- 能力解决什么需求、何时应选用、何时不应选用。
- 真实职责与非目标、结果与验收；不得把尚不存在的能力写成事实。
- 输入、必要材料及其用途、输出、资源与权限、用户参与方式。
- 已有 Skill、文档、目标定义所承载的业务要求，哪些必须保持；此时不决定应写入哪个三指南字段。
- 命名及身份决定、已有绑定的处理决定、允许创建和未来修改的范围。
- 已确认内容、来源、尚未取得的批准、未验证条件和阻塞。

目标与需求不符时说明真实差异，不创建目标、扩充脚本或改 Map 来迎合需求。确需新能力由用户另行安排。只核实配置及材料不等于验证工具加载、模型遵循或业务效果。

## 5. 中间交付接口

为避免两个独立建设 Chat 各自猜接口，本文提出如下共同接口供两方落实；如发现必须变更，交回概要规划者确认，不能单方切换：

- W1 输出 bot_requirements：一份自包含 UTF-8 Markdown「Bot 需求」。
- W2 输入 bot_requirements：直接消费同一份文件。
- 该文件承载本次需求、核实基线和确认依据，不额外拆分未声明文件。参考材料中影响实施的必要事实须完整纳入；仅供追踪的地址不能成为隐式必需输入。若确有独立材料必须直接传递，先明确额外输入／输出及映射，再交回确认。

「Bot 需求」至少包含：

1. 文档身份、修订、目标类型和唯一定位、来源服务、拟建 Bot 的已确认命名。
2. 原需求及本 Chat 澄清后的统一意图，职责、非目标、输入输出、验收、权限和资源限制；不按三指南字段拆分。
3. 已核实完整目标基线：Task／Map 的完整原始配置；Script 的准确相对定位、已核实真实来源、完整原文及相关依赖事实。保留用于比较的原文，不用摘要代替基线；注明读取时点，不声称其为锁定快照。
4. 已有绑定、共享用途、冲突调查及实际决定；事实、推断、未验证项分开。
5. 确认来源和范围、实际授权、未来尚需取得的全文／保存批准。确认依据不得只写「用户已确认」而省略确认对象。
6. G2 的委托：整体分层设计后新建 Bot；Task 型可获准保义优化 prompt；Map／Script 不修改目标；Skill／文档默认只读；不得扩大原需求或能力边界。
7. 未决项、阻塞、资源缺口及处理去向。影响分层设计的意图冲突未解决时只能交草案，不宣称完成。

本接口是两节点内部约定，不套用旧 baseline 要求的已创建空白 Bot 或真实 Bot revision。尚未创建的 Bot 没有 revision，不得伪造。

## 6. 安全、完成与未来节点策略

要求文件时先按 docs/workflow-runtime.md「统一文件交接约定」及 docs/business-materials.md「文件与独立 Chat」核实授权、真实路径、父路径和链接安全，避免覆盖其他产物，UTF-8 保存后完整读回逐字比较。失败先核实现场，不盲重试、自动删除或回滚。

G1 完成须同时满足：目标与意图可核实、必要业务取舍已确认、需求材料完整自包含、文件保存读回一致、没有影响 G2 的未解决冲突。不能因没有三指南最终全文而拒绝完成，也不能把未知保存授权伪造为已授权。

未来节点固定 zone=hugosol/herdr-bot（服务已登记为 E:/Developer/myhub/herdr-bot），report_policy=manual、auto_close=true、end_node=false。策略由 Map 定义，Task 不重复实现报告协议或自行关闭 Tab。manual 原生发送确认与业务确认独立；管理者负责 complete 和下游派发。

## 7. 复用调查与缺口判断

- create-bot 的现有 Task task-18e31d347ccbeb4c-4 只支持 normal Task，且编写三指南并创建 Bot，与 G1 只对齐意图不符。
- prepare-bot-revision 的 task-revise-bot-baseline-v1 针对已存在的 Task／Map 型 Bot 修订，不适用于尚未创建 Bot 的三类型需求。
- create-bot-wrapper.json 是旧「创建bot」，8 节点，Task／Map 范围，不能作为 G1 隐藏子流程。
- 三个单字段编写者要求按字段编写，不满足 G1 边界。

G1 初步属于配置缺口：需要新的稳定 Task 职责和 Bot 绑定，不需新调度器或业务执行器。所需宿主／模型／Suite 由建设者核实合法选项并取得用户确认；初始 Skill 必须 grill-with-docs。已存在相同 Skill 的配置不证明新 Task 的原生加载已验证。

## 8. 建设操作边界与返回契约

用户可手动从 zone 发起「能力创建者 · Bot＋Task」：Bot create-bot-task，绑定 normal Task task-18e315be1cf0ef10-0；入口已从服务核实。建设 Chat 根据本文新增 G1 normal Task 与对应 Bot，先确认完整候选及执行配置，再按合法接口保存和读回。

不修改旧 Task／Bot／Map、当前执行配置、运行记录、Suite 或公共 Schema；不创建 V2 Map、不自动建设 G2、不运行生成能力、不安装工具、写凭据、扩权、调度、停服或删除资源。必要契约可直接作为本次新能力的自包含职责／交付说明，不以修改旧契约替代建设。

返回概要规划者：

- G1 真实 Bot 名称／ID、normal Task ID、完整最终配置和三指南。
- 实际 agent、model、thinking、skill、suite 以及完整读回证据。
- 精确 request 协议、bot_requirements 文档协议和输出 ID；任何与本文建议接口的差异及原因。
- 真实资源与条件、已验证／未验证项、阻塞与部分失败，明确配置读回不等于业务验证。
- G1 状态为已补齐、待验证或阻塞，并附依据。

结果带回后由概要规划者重新核实真实绑定及 G1→G2 材料一致性，再确认最终概要方案。本文件本身不代表 G1 已实现或 Map 可启动。
