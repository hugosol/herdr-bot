# Map 型 Bot、嵌套 Run 与命名文件输入

Status: ready-for-agent
Label: ready-for-agent
Created: 2026-11-06
Contract: [已批准契约 — Full automation](contract.md)

## Problem Statement

用户目前只能通过 Bot 引用普通 Task，在 Map 的 node 中调用单个执行者。已经编排好的 Map 无法作为业务能力被规划者通过 when、plan_guide、node_guide 发现，也无法作为另一流程的一个节点执行。复用已有流程必须重新安排其内部工作，不能保留独立运行边界。

现有命名文件交接只覆盖同一 Run 内的节点。Map 没有描述本次运行所需文件的输入接口，独立启动时也不能单独绑定输入文件。因此，即使允许节点启动 Map，父节点材料仍缺少明确进入子 Run 及其内部节点的途径。

两个现有业务案例还将目标限定为 normal Task，并在多份交接材料中重复完整配置基线和字段正文。用户希望以最小改造验证新框架：为已存在的普通 Task 或 Map 包装 Bot，以及独立修订既有 Bot 的三份指南；文件流转由系统承担，确定性规则由代码执行，框架指引负责通用执行协议，用户只提供本次业务知识、目标、选择与授权。

## Solution

Bot 允许以普通 Task 或 Map 作为互斥的执行目标。Map 型 Bot 与 Task 型 Bot 使用相同的三份能力指南参与规划发现和选择，但 node 执行 Map 型 Bot 时，使用该 node 指定的 manager Task、zone、业务要求和文件输入发起独立子 Run。子 Map 不展开或复制进父 Map。

Map 声明局部命名文件输入；根 Run 启动时由调用方提供对应文件，子 Run 则接收父节点本次执行解析出的同名输入绑定。内部节点可引用本次 Run 的输入，再沿已有 node 输出引用规则传递。支持无输入和可选输入，不建立全局文件管理系统。输出继续由父节点声明并由子 manager 通过 report 交付，不增加 Map 级输出声明。

子 manager 同时具有管理子 Run 和向父节点交付的身份，加载 manager-chat 与 node-chat。子 Run 结束与对外报告分开，父 manager 仍负责验收并完成父节点。暂停、失败和执行策略保持局部作用，多层嵌套允许，但直接和间接循环调用均拒绝。

在 workflow 中，各 Run 继续并列展示；嵌套节点提供跳转到本次执行所关联子 Run 的入口。以两个真实业务案例验证端到端能力，并只清理这些案例及受影响共享能力所需的提示词和定义，不全面重构现有 Map。

## User Stories

1. As a 能力维护者, I want a Bot 可选择普通 Task 或 Map 作为执行目标, so that 单人执行和完整流程都能作为业务能力复用。
2. As a 能力维护者, I want a Bot 的两个执行目标互斥, so that 系统不会通过隐含优先级决定执行方式。
3. As a 能力维护者, I want a 尚未绑定目标的 Bot 仍可保存, so that 我能保留现有分步编辑习惯。
4. As a 流程发起者, I want a 未绑定或绑定无效目标的 Bot 在运行前被拒绝, so that 草稿不会被误当成可执行能力。
5. As a 规划者, I want a Map 型 Bot 同样具有 when、plan_guide 和 node_guide, so that 我能按业务能力检索和选择它。
6. As a 用户, I want a Task 型与 Map 型能力保持为可分别选择的 Bot, so that 我能决定本次工作采用哪种执行方式。
7. As a 规划者, I want a Map 型节点明确指定 manager Task, so that 同一 Map 可由不同管理者预设执行而无需修改 Bot。
8. As a 规划者, I want a Map 型节点复用已有 input 和 zone, so that 不必维护两套重复启动信息。
9. As a 子流程执行者, I want a 子 Map 内部节点保留各自的 zone, so that 父节点不会覆盖内部工作位置。
10. As a 用户, I want a 每次 Map 型节点执行创建独立子 Run, so that 多次复用的状态、Chat 和交付互不混淆。
11. As a 规划者, I want a 子 Map 可以继续调用其他 Map 型 Bot, so that 多层业务流程能够组合。
12. As a 流程发起者, I want a 预检拒绝直接和间接循环调用并指出循环关系, so that 不会无限展开流程。
13. As a 规划者, I want a 多个不同节点合法复用同一 Map, so that 循环检查不会误拒绝正常重复使用。
14. As a Map 维护者, I want a 为 Map 声明命名文件输入, so that 流程定义不依赖每次运行的实际文件路径。
15. As a Map 维护者, I want a 输入 ID 仅在本 Map 输入接口内唯一, so that 不需要维护跨 Map 全局命名。
16. As a 流程发起者, I want a 启动表单将用户输入与输入文件分开, so that 业务要求与材料绑定清晰可辨。
17. As a 流程发起者, I want a 根据 Map 声明选择或填写已有输入文件, so that 不必手工编辑 Map 来更换材料。
18. As a 流程发起者, I want a 无文件输入时也能正常启动, so that 仅依靠文字要求的场景不被迫制造文件。
19. As a Map 维护者, I want a 声明必需和可选输入, so that 可缺省材料与必需材料有明确区别。
20. As a 执行者, I want a 可选输入未提供时被明确表示为缺席, so that 我不会猜路径或读取假占位文件。
21. As a 流程发起者, I want a 必需输入缺失和已提供文件不可读被明确拒绝, so that 错误不会被吞成可选缺席。
22. As a 规划者, I want a 内部节点可通过输入规则引用本次 Run 的命名输入, so that 文件可以从运行入口流入实际工作。
23. As a 规划者, I want a 沿用节点本地输入 ID 对上游输出重命名, so that 子 Map 无需了解父 Map 的内部节点名称。
24. As a 子流程调用者, I want a 父节点已解析输入按相同 ID 绑定到子 Run, so that 不需要再维护额外的跨层映射表。
25. As a 执行者, I want a 本次输入路径绑定在执行后保持不变, so that 上游后续报告新路径不会悄悄改变我的输入地址。
26. As a 用户, I want a 明确知道路径绑定不冻结文件内容, so that 不会把系统误认为文件快照或版本服务。
27. As a 文件生产者, I want a 不因本次改造被施加交付后禁止改写的新增规则, so that 系统保持简单且不作无法兑现的外部文件保证。
28. As a 文件消费者, I want a 消费前检查文件存在且可读, so that 缺失材料尽量在启动或派发时被发现。
29. As a 用户, I want a 了解消费前检查只证明检查当时的状态, so that 检查后改写或删除不会被误称为系统保证失效。
30. As a 子 manager, I want a 读取父节点的输出要求并 report 实际文件, so that 子流程结果能够进入父流程现有交接机制。
31. As a 规划者, I want a 下游能够引用 Map 型节点的输出 ID, so that 子流程输出可交给普通节点或另一个子流程。
32. As a 规划者, I want a 系统验证输出引用与输入声明是否有效, so that LLM 负责业务映射但不替代确定性校验。
33. As a 子 manager, I want a manager-chat 与 node-chat 同时可用且明确各自作用层级, so that 我能管理内部工作并向父流程报告。
34. As a 用户, I want a 双角色身份只能来自已保存的父子执行关联, so that 普通 manager 不会获得任意跨 Run 权限。
35. As a 子 manager, I want a run 和 collect 操作我的子 Run、report 指向父节点对应执行, so that 不必手工填写运行身份或接收者。
36. As a 父 manager, I want a 子 Run 全部节点完成且显式 finish 后才接受其可完成报告, so that 启动成功或内部局部完成不会提前放行。
37. As a 父 manager, I want a 子 Run finish 后仍由我验收并 complete 父节点, so that 内部完成不替代调用方交接验收。
38. As a 子 manager, I want a finish 与 report 是分开的动作且 finish 不关闭我的 Chat, so that 我可以在内部结束后提交外部交付。
39. As a 用户, I want a 报告保存和通知失败按原有阶段解释, so that 不会因投递失败撤销已完成的子 Run 或盲目重做。
40. As a 用户, I want a 暂停父 Run 不自动暂停已经启动的子 Run, so that 暂停仍只控制本层新执行。
41. As a 用户, I want a 子层失败保持在子层处理, so that 不会自动暂停或失败整棵流程。
42. As a 用户, I want a Map 型节点 retry 创建新的子 Run并保留旧现场, so that 重试与继续原执行的含义明确。
43. As a 父 manager, I want a 旧子 Run 的迟到报告不能完成新执行或提供其当前输出, so that 多次尝试不会串结果。
44. As a 用户, I want a 部分启动失败如实保留 child Run、Chat 和已发生效果, so that 核实时不会误以为整个调用从未发生。
45. As a 用户, I want a 恢复原 Chat 沿用合法双角色而不新建 Run或重放初始输入, so that 恢复行为保持原意。
46. As a 用户, I want a 服务重启后仍遵守原有历史只读和不自动接管限制, so that 嵌套不引入隐藏例外。
47. As a 用户, I want a 外层 report_policy 只控制子 manager 对外报告, so that 不改变内部节点各自的确认规则。
48. As a 用户, I want a 外层 auto_close 仅在父节点完成后关闭对应子 manager Tab, so that 不级联关闭子流程内部 Chat。
49. As a 用户, I want a 根 Run和子 Run在 workflow 中并列展示, so that 保持现有浏览方式。
50. As a 用户, I want a 从嵌套节点执行详情跳转到其子 Run, so that 能直接查看实际执行现场。
51. As a 用户, I want a retry 后仍能查看旧执行关联的子 Run, so that 历史不会被新关联覆盖。
52. As a 能力维护者, I want a 被 Bot 引用的 Map不能直接删除, so that 不会留下失效能力目标。
53. As a 用户, I want a 历史删除不级联删除子 Run且不破坏父子关联, so that 不会因清理一层记录丢失另一层现场。
54. As a 用户, I want a 为已有普通 Task或Map直接创建并绑定 Bot, so that 能把已有执行目标包装成可发现能力。
55. As a 用户, I want a 仅提供目标定位、业务要求与可选材料，由流程核实并形成基线, so that 不必手工抄写完整配置交接文件。
56. As a 用户, I want a 新建 Bot 的三份指南独立编写、确认和优化后一次保存, so that 分支不会互相覆盖配置。
57. As a 用户, I want a 新建 Bot 流程不创建或修改被包装的执行目标, so that 包装能力不扩大授权。
58. As a 用户, I want a 独立修订 Task型或Map型Bot的三份指南, so that 不必先修改 Task.prompt 或虚构对应 Task。
59. As a 用户, I want a 修订流程保留三路确认但不增加独立表达优化阶段, so that 沿用现有修订业务逻辑。
60. As a 分支执行者, I want a 显式接收共同基线、唯一正文及必要确认说明, so that 不靠 handoff 层层复制配置和全文。
61. As a 保存执行者, I want a 保留授权、基线冲突、revision、非目标字段保持与完整读回检查, so that 去重不会削弱安全保存职责。
62. As a 独立 Chat 用户, I want a 共享 Task 在没有 node 角色注入时仍能完成业务交付, so that 提示词清理不破坏独立使用。

## Implementation Decisions

### 能力与运行模型

- Bot 的直接执行目标为普通 Task 或 Map，二者互斥；可保留未绑定定义，但运行前拒绝。manager Task 不作为普通 Task 型 Bot 的执行目标。
- 保留 normal/manager Task 职责区分，不新增嵌套 Task 类型。嵌套是运行上下文中的双角色，而不是 Task 分类。
- Map 型 node 明确指定 manager Task；复用已有 input、zone、input_rule、output_rule、report_policy 和 auto_close 的职责，不增加重复的子流程业务输入或 zone 配置。
- Bot 只绑定目标 Map，不绑定其 manager Task。同一 Map 可以通过不同 Bot 描述不同业务能力，也可被不同 node 以不同启动配置使用。
- 每次执行创建独立子 Run，父子关系归属于具体 execution。当前与旧执行均保留其对应关联，不能仅给 node 保存可被覆盖的 child ID。
- 允许多层嵌套；在现有预检入口检查可达调用链，拒绝直接或间接循环，允许非循环重复引用。运行期间定义保持不变的现有前提不扩展为新快照系统。

### 文件声明、绑定与消费

- 保留现有局部输入/输出 ID，不增加跨 Map 全局 ID、文件注册表或独立文件实体管理。
- Map 增加命名文件输入声明，支持必需和可选；不增加默认路径、表达式或自动寻找文件。
- 根 Run 启动配置增加与用户输入分开的文件绑定。用户选择或填写已有文件，不要求制作完整配置基线。无声明、无规则及可选输入未提供均有合法空输入语义。
- 新增“本次 Run 输入”这一节点文件来源。只能引用所属 Run 的命名输入，不允许模型以任意 Run ID读取其他运行。
- 父节点输入规则完成上游输出到本地输入的命名转换；创建子 Run 时按同名绑定传入其输入接口，不再增加独立跨层映射配置。
- 业务文字、文件绑定与运行身份分开处理；用户输入不承担路径发现、报告协议或运行记录定位。
- Map 不新增输出声明。父节点 output_rule 声明所需对外交付，子 manager 通过 report 登记对应实际文件；后续普通或Map型节点通过父 Run 的节点输出规则消费。
- 规划者/LLM 选择业务上正确的输出到输入映射；代码校验引用存在、声明匹配、当前适用执行和必要绑定，不负责判断材料业务内容是否合格。
- 消费前新增文件存在且可读检查：根输入在启动时检查，节点解析输入在派发时检查，包括上游报告地址及 Run 输入。已提供但错误的路径不能按可选缺席处理；失败时不启动相应工作。
- 直接文件沿用已有 zone 路径安全原则；不为所有报告产物新增统一同-zone限制。不同来源的解析和验证必须明确，不把现有报告地址格式校验误称为文件可用检查。
- 检查只证明当时可读，不承诺检查后持续存在。派发后实际读取失败沿用错误和报告逻辑，不自动重试或修复。
- 固定的是本次地址绑定，不是内容。后续 report 更新地址不热更新已派发消费者；同一路径内容可被修改，不保证不同消费者读到同一版本。
- 不增加交付后禁止原地改写的规则，不新增快照、复制、版本库、哈希完整性或文件锁。共同基线表示共同材料来源，不是系统不可变快照。

### 双角色与生命周期

- 子 manager 同时加载对应宿主的 manager-chat 和 node-chat。内部 run/collect 定位到子 Run，外部 report 定位到父节点具体 execution；公共指引与初始化明确层级。
- 允许的双角色必须由真实持久父子关联证明；保留同 Run 内 manager 与节点身份独立、不同节点/attempt身份唯一的边界，不整体放宽授权。
- 工具不增加模型自报 session、Run、接收者或 execution 的选择通道；后端由真实会话关联确定操作对象。
- 子 Run 全部 node completed 后仍需显式 finish；子 finish 后才允许向父执行声明可完成，且服务端必须执行该门禁。进展报告不替代完成资格。
- 子 finish 与外报分开。finish 不关闭原生会话，也不自动完成父节点。父 manager 仍按当前执行最新有效报告验收并显式 complete；报告投递失败不撤销已完成事实。
- pause/failure 保持局部，不自动传播、接管或终止。外层 manual 报告确认只约束子 manager 外报，内部节点保留各自策略。
- 外层 auto_close 在父节点合法完成后只关闭该执行关联的子 manager Tab，不级联关闭内部会话。
- retry 是独立新执行、新子 Run，保留旧事实与副作用；旧子 manager 报告属于旧 execution，可留历史但不能控制新执行。恢复原执行不等于 retry。
- 部分启动失败需区分子 Run 登记、记录初始化、Chat 启动、身份关联、输入提交等真实效果；核实不能只凭 Chat 缺席就把已有子 Run视为从未创建。不承诺完整跨文件事务或自动回滚。
- 原 Chat 恢复沿用合法角色及来源环境，不重放触发动作；服务重启后旧 Run只读与不自动/手动接管的现有边界不变。
- 父子操作不能通过相互持锁等待产生互等；具体协调结构由后续工程设计确定，不在本 spec 选择 seam。

### 界面、规划与删除

- Bot 编辑/预览支持目标类型；Map 定义和启动支持输入声明与绑定；node 配置支持 manager Task及Run输入引用；服务端与前端严格校验同步更新。
- 三份 Bot 指南的原职责保持不变，不自动注入执行 Chat。规划者能发现Map型Bot、读取输入接口、填写本次配置和规则，不展开子Map。
- workflow 保持所有 Run 并列展示，仅为嵌套节点执行增加跳转到对应子 Run Map视图的入口；旧执行保留历史跳转，不要求树形或双向导航。
- 被 Bot 引用的 Map删除前拒绝并列出引用，不自动解绑、覆盖或级联删除。引用扫描损坏或不可读时不得当作无引用。
- 父 Run删除不自动删除子 Run；历史删除若破坏持久父子关联则拒绝并说明原因，保留现有无关联场景习惯。

### 两个实际案例与最小切换范围

- 案例一提供“为已有执行目标创建 Bot”的 Map型能力：目标定位/业务要求/可选材料 → 核实目标并创建空白Bot → 单份共同基线 → 三路指南编写与确认 → 各自表达优化 → 一次保存三字段 → 最终交付。支持既有normal Task或Map，不修改被包装目标，不自动覆盖既有Bot。
- 原创建Task＋Bot流程在创建并优化Task后调用案例一，不将创建/修改Task固化进可复用包装流程。
- 案例二提供既有Bot指南修订能力：核实Bot与Task/Map目标并形成共同基线 → 三路修订确认 → 一次保存 → 最终交付。不增加独立表达优化节点；Task.prompt优化保留为适用外层前置，而不是所有修订的强制步骤。
- 共同基线独立传给必要消费者；text为唯一完整字段正文；handoff只保留确认依据、来源、必须保留的业务语义、限制和未验证项，不为文件传输复制完整配置或全文。
- 不能仅删除副本：生产者、优化者和保存者的输入契约与核对方式必须一起调整。保留当前目标与基线核对、真实revision、权限、运行中配置禁写、非目标字段保持、完整读回及部分生效说明。
- 业务Task与node.input不再重复实现通用寻址、运行身份、报告和流转协议。确定性规则由代码执行；公共角色/交接指引承接通用行为；Task保留业务职责；用户输入只承载本次业务知识与决定。
- 文件安全写入和完整读回目前未被公共node指引完整承接。清理前必须确认职责可达，不能以去重为由删除保护，也不能使独立Chat必须依赖node角色才能交付。
- 仅迁移两案例及实际受影响的共享能力和规划契约；修正这条链路中的旧Task API字段/旧契约指示。保留旧create-bot-task与create-bot独立能力的原职责，不把它们一并泛化、替换或自动改成新Map型能力。
- 本节记录已确定的行为与影响面，不选择模块seam、测试seam或分票方式；具体持久化字段拼写、API形状和模块划分留给后续契约工作，在不改变上述语义前提下沿用仓库惯例。

## Testing Decisions

- 当前研究只是源码与定义核对，不能记为嵌套运行通过。实际执行过的只读JSON检查发现四张Map的29条文件引用可解析，未发现现有绑定和依赖环错误；这不证明真实模型执行质量。
- 复用已有单Run文件输入、report增量、当前/旧execution隔离、completion门禁、部分启动失败、恢复和重启检查的先例，但单Run通过不得外推为跨Run通过。
- 后续须实际验证OMP与Pi双扩展原生加载、工具与指引不冲突、真实session归属、finish后外报；仅配置入口存在或工具名称不同不是运行证据。
- 必须实际覆盖空输入、可选缺席、必需缺失、提供但不可读、同名局部ID、多层传递、输出进入普通及Map型下游，以及派发时检查与文件内容不冻结的区别。
- 必须验证子finish前不能让父节点获得完成资格、子finish后父仍须验收、retry创建新child且旧报告隔离、部分启动效果可核实，以及并发无父子锁互等。
- 两个案例需要使用隔离Task/Bot/Map目标验证真实交付、三分支共同材料、唯一正文来源、一次合法保存与读回；不能拿用户正在使用的配置试跑，也不能以静态连线或模拟报告声称业务成功。
- 保留共享Task独立Chat和其他受影响调用方的验证，不以删掉旧行为约束或收窄断言获得通过。
- 按仓库既有验证入口和网络护栏执行：独占临时目录、动态数值回环端口、隔离运行存储与Herdr、持续消费日志并清理所属进程。不操作用户daemon、Chat、真实关机、凭据或业务配置。
- 受控Herdr/provider只证明对应机制，不证明真实模型遵循。真实模型/原生宿主验证需已授权的服务和隔离依赖；缺少条件必须标为未验证，不使用用户认证或现有会话替代。
- 不在此决定seam、各promise的测试归属或覆盖矩阵；由 /to-contract 选择并审批。

## Out of Scope

- 全面梳理、合并或重写所有现有Map和独立能力入口；除选定案例与受影响共享调用链外不扩张范围。
- 把普通Task与manager Task合并、引入新的嵌套Task类型，或允许模型任意选择运行身份。
- Map级输出声明、自动汇总所有内部输出、父流程直接引用子Map内部节点、额外跨层参数映射语言。
- 全局文件ID、文件实体管理、上传/在线创建输入文件、默认路径、表达式、目录自动发现、文件自动复制或搬运。
- 文件内容快照、版本管理、完整性锁定、交付后禁止改写、保证外部文件持续可读或自动修复材料。
- 直接或间接递归调用、自动生成递归停止条件、定时调度、自动重试、级联暂停/失败/停止/关闭。
- 子Run结束自动完成父节点，报告取代验收，或只靠提示词执行完成门禁。
- 服务重启后的新接管机制、自动恢复管理权、完整崩溃幂等、跨文件事务或自动回滚。
- 嵌套树控制面板、额外双向导航、批量级联删除、自动清除引用。
- 自动运行新创建Bot的业务能力，或把配置保存成功宣称为业务能力已验证。
- 借本次改造自动为plan_workflow补建缺失能力、自动发起其生成的业务Map。

## Further Notes
