# 04 · 冻结 Run 历史：TDD 复盘建议

## 高：发票前核对「保留既有能力」是否有公开入口

**事实：**P30 要求保留独立 Run 删除能力，但本次执行查到 Run 路由只有列表、详情、重命名和定位，workflow 页面也没有删除操作。Rust LSP 和代码图都显示，`delete_map_history` 唯一调用方是 Map 删除分支。此矛盾在实现轮才上报；交付移除了连带删除，没有新增破坏性入口，也没有把争议项记为通过。

**建议：**在票据发布检查加入 **既有入口核对**。凡写「保留」「沿用」的可观察能力，票据须给出一个现有公开路由、页面动作或可运行的公开用例；找不到就先交给契约所有者确认。完成标准是每项都有可定位入口或明确的待决记录。脱钩后仍可做的工作照常推进；缺失的入口既不自动变成新功能，也不算验收通过。

## 中：用现有浏览器构建入口验证依赖安装约定

**事实：**`bun install --frozen-lockfile` 成功，但 `frontend/package.json` 的现有 `test:browser:build` 在 Vite/PostCSS 阶段找不到 `picocolors`，第一次未进入浏览器用例。该 worktree 改用 `--linker hoisted --backend copyfile` 重新安装后，构建成功，浏览器红灯才确实落在「副本缺失仍显示原图」的断言上。对话没有核实 CI 的安装方式，也不能仅凭这次对照归因于某一个安装选项。

**建议：**先读现有 CI 的前端安装配置，再在干净 Windows worktree 用现有 `npm --prefix frontend run build` 核对当前安装方式。若能复现，就在既有安装入口固定经验证的锁文件安装方式，并让现有 CI 构建使用同一入口。把这个实际前提写进 `docs/agents/testing.md` 的浏览器分支；不另造依赖扫描器，也不把构建故障记作行为红灯。

## 中：为共享状态的切换增加短路径导航

**事实：**本轮为找到 Map 的运行时读方，从 Run 启动、管理者操作、scheduler、chief 和 workflow 页面多次查图、查引用和定向搜索。图索引没有覆盖部分浏览器测试。切除连带删除时还遗漏了 `runs/scripts.rs` 的脚本输出登记读取 `runs.deleted`，直到浏览器命令中的 Rust 编译才报错；编译守卫有效，没必要为这个漏点另写 lint。

**建议：**在现有 workflow 开发资料放一个 **运行定义切换** 小节，由测试指引按「改 Run 定义来源或持久状态」触发。只索引三条边：启动如何把校验结果带入 Run；派发、retry、prepare、finish、collect 和页面从哪里读；报告与后台脚本还消费哪些共享状态。改字段时先查声明的全部引用，再跑受影响 target 的定向检查。导航只记录跨模块关系及其测试入口，不复制实现或运行协议；索引缺覆盖时直接切到限定目录搜索，不反复扩大图查询。

## 低：将已知的浏览器导航语义放在共用夹具旁

**事实：**Map 删除浏览器用例已走过删除请求和保留字节断言，却在 `page.goto(.../#workflow)` 后等不到列表链接，耗尽 90 秒用例时限。改为点击可见 workflow tab，并先显式断言保留的列表项出现后，定向检查通过。该对话证明了这条交互路径有效，并未证明所有 hash 导航都有问题。

**建议：**在浏览器共用 UI 指引区分「进入列表」和「打开指定 Run」：列表场景走可见 tab 并等待列表，详情深链场景才直接使用 Run hash。引用现有通过的用例即可，不新增导航包装层；若列表没打开，应在第一个对应页面断言失败，而不是耗尽整个用例时限。
