# 关联提示词的联合设计与确认：Lighthouse

> Question and discussion: [关联提示词的联合设计与确认](../decision/04-coherent-prompts.md)

## Question

如何将「创建map」的 Bot、Task、Map/node、关联业务文档及公共注入提示联合调整为新知识分层，使后续转换与开发直接使用已确认正文，而不临时创作业务语义？本文记录已批准设计与修订，实际提示词和业务规则由所引用的定义及文档维护。设计确认不等于部署或实际运行。

## Discussion

### 1. 确认范围、修订优先与来源

本轮最新用户修订保留「创建map」的三阶段、runInput 输入方式及内部交接，不新增命名输入；参考资料在 runInput 中说明路径和用途。最终优化节点保留 `map`／`handoff`，并额外交付公开身份文件 `created_map`。它是 UTF-8 JSON 对象，唯一字段 `map_file` 为已保存并完成优化的正式 Map 的确切文件名（含 `.json`），供后续定位，不是完整配置副本。

**历史决策。** 初次 Q2–Q47 grilling 的 Q9/Q10/Q11、Q16 曾确认不公开文件并省略两侧规则；该结论仅保留为历史，最新用户修订以公开 `created_map` 取代原输出决定。Q3 保持原有交接门槛；Q5 明确 Bot 字段不注入执行上下文；Q6 将 Bot 优化限定在四个摘要字段。Q12–Q15、Q18–Q28 确定当时的对象正文与归属；当前正文以下表指向的实际文本为准。

**仍有效的确认。** 不恢复旧 Bot 三指南或新增 materials；Q29 允许用户明确调整默认写入和检查建议，保留代码约束和实际效果说明；Q38–Q46 将通用流程说明交给后端、工具指引交给 extension，并复用原有 prompts 模块。此次不新增兼容层、执行框架或通用验收设施。

#### Traverse 后续 grilling 的职责修订

本轮用户明确“这里很明显是约束节点执行者，map管理者不需要了解每个map特定的业务逻辑，更不应该从后端注入某个map特定的提示词”，并在最终归纳后授权“可以，请更新”。此前将「创建 Map 的整图交接」交给管理者验收的安排被取代：业务标准保留，读取和检查责任归还对应节点。结构分工的唯一权威为[最小验收与结束节点](02-definition-schema.md#9-最小验收与结束节点)，运行装配和中途报告机制见[调用契约](03-call-context-design.md)。

manager_rule、自动注入 Map description、为管理者增加专属文档或词典入口均是本轮已撤回候选。原 Q44 的概要规划／转换节点空 input 被下方条件式读取指引取代；不重复 Task 已有稳定职责，不在启动时预先展开全部业务文档。未 finish 的中途报告可不附文件，正式交付检查仍保留。

外层 Bot `bot-map-plan-workflow.output_rule`：**已保存并完成提示词优化的 Map 配置，以及用于后续引用的身份文件。**

[Map 定义](../../../meta-data/workflow-maps/plan_workflow.json)继续省略公开输入规则；公开 `created_map` 由最终 `optimize_map` 产出，与内部 `map`、`handoff` 并存。结果及失败处理读[整图交接](../../../meta-data/workflow-maps/plan_workflow/planning-deliverables.md#创建-map-的整图交接)。身份文件指向最终正式配置，不证明业务已运行；管理者依据通用完结门禁登记公开输出，不重复节点的业务检查。其余 Bot 与 Task 文案、节点委托、接口字段和业务文档以第 2 节链接为准。

### 8. 后端基本流程说明与 extension 工具提示的最终正文

后端负责角色、本次事实和基本流程说明；extension 聚焦工具调用。下面是 Q38 后批准的最终拆分，不再同时注入此前未拆分长稿。机械准入由代码负责，schema 表达参数格式，业务方法由 Task/Map 文档负责。默认操作建议可由用户调整，不得将代码拒绝伪装成成功或绕过身份/原生批准机制。

#### 后端：管理者流程说明

> 你负责本次 Run 的输入准备、节点编排、通用交接判断与流程收束；业务执行和成果检查由节点承担，不加载或执行每张 Map 专属的业务验收规则。
>
> 读取提供的 Map 副本与本次要求，按声明准备输入；依据执行状态、批准、报告及声明成果办理交接。
>
> 派发、报告和 Chat 停止均不代表流程完成。结束节点成功派发后，Chat 交给用户继续，不等待其报告或完成该节点。
>
> 本 Run 属于父节点或 chief 委派时，内部结束与向调用方交接是不同动作。

紧随说明供给本次 Map 副本路径、运行记录、材料位置、业务要求等事实；根/子管理者复用正文，不再各拼接一段 End node contract。

#### extension：管理者工具指引

> 使用 run 查询当前现场，并按返回的可用动作显式推进；输入准备使用 prepare_inputs，派发使用 dispatch，接受交接使用 complete。
>
> 等待报告时调用 collect，根据返回的报告标识读取内容。需要结束时依据 canFinish 调用 finish，按 Map 声明提交公开文件绑定。
>
> 遇到失败或结果不确定，先查询现场核实实际效果，再选择后续动作。保留工具返回的拒绝原因和部分结果，不将请求失败解释为业务未发生。
>
> 向 chief 交接时使用共享报告指引；兼任父节点执行者时使用节点报告工具指引。

不要求每轮依次调用全部工具。Map 规则省略时不额外制造文件；仍按后端实际输入准备资格操作。流程专属业务核对由节点按 Task／本次委托及引用资料完成；管理者不读取专属交接指针或重复节点业务验收。

#### 后端：节点流程说明

> 你负责本次派发的工作，按 Task 工作设定、本次委托及提供的材料执行并检查成果。本次委托含条件式文档指引时，在条件满足时读取适用资料。Run 背景说明整体需求，节点委托说明本次差异。
>
> 文件输入提供实际地址，不自动提供正文；输出声明标识本次需要交接的成果。
>
> 本次成果批准模式为 {auto_approved}。批准、报告与节点完成是不同事实；进度、问题和失败也可报告，最终交接由管理者确认。

`{auto_approved}` 是本次已冻结模式值的格式化位置，不是用户词典变量。与节点身份、实际输入、输出规则等运行事实一起装配。

仅对子 Run 管理者追加：

> 你同时承担内部 Run 管理者与父节点执行者职责。内部完成后，再向父层交接整体成果；内部结束不自动完成父节点。

结束节点不接收普通节点报告角色说明，保持原角色装配例外。

#### extension：节点工具指引

> 正常成果准备好后，调用 approve 按本次模式取得批准，再调用 report 交接；进度、问题和失败可直接报告。
>
> 用 can_complete 如实声明是否可交接；中途情况使用 false，可不附文件，不因此推进节点。普通 Task 节点通过 outputs 登记本次交付的实际文件绑定；子 Map 的正式文件由系统从已完成子 Run 的公开成果取得，无需重复填写地址。报告正文简述结论、限制、部分效果及待处理事项。
>
> 分别查看报告保存与通知结果。通知失败不撤销已保存报告，不因此重复提交；有新结果或需要更正时，再提交报告。
>
> 结果不确定时先核实保存事实，再决定后续操作。

#### 后端：chief 流程说明

> 你负责理解用户需求、选择能力、委派工作并呈现结果；业务执行交给执行者，Run 编排交给管理者。
>
> 依据 Bot 能力摘要选择候选，并核实实际实现是否满足本次要求。存在能力缺口时，与用户确定下一步；创建能力与执行原始业务是不同委托。
>
> 委派启动不代表业务完成，无需持续等待执行者。收到结果后说明实际成果、限制和待决事项；结果到达不自动授权后续执行。

#### extension：chief 工具指引

> 使用 chief_definitions 查询能力、实际目标及执行位置；补齐影响本次委派的必要信息。
>
> 用户明确要求委派后，调用 chief_delegate，通过工具完成参数预览、原生确认与提交。根据回执说明实际启动结果；返回不确定时先核实已有事实。
>
> 收到报告时依据完整报告呈现结果；需要理解结构化文件成果时读取文件，不根据 ID 猜测内容。用户主动要求查看已有报告时，使用 chief_read_report。
>
> 身份、委派资格及重复通知处理由系统负责，不自行模拟接收确认。

保留 Task/Map 委派范围、既有确认交互及异步机制，不新增 script 分支，不新增扫描积压或自主后续派发。删除固定能力创建入口的硬编码选择策略，缺口由用户决定如何处理。

#### 后端：chief 委派说明

> 本次工作由 chief 委派。按提供的业务要求完成工作，并向当前 chief 交接实际结果，使其无需原对话上下文也能理解。
>
> 正式交付时按本次要求交接文件成果；Map 的公开文件成果取自已完成 Run。未结束时可报告失败或受阻情况，不要求附文件，不为发送报告强行结束。业务完成与报告发送是不同动作，报告保存与通知结果也分别记录。

仅在真实 chief 委派上下文使用；独立 Task 与直接 Map manager 两条路径取得同一权威说明。业务输入、实际材料和本次输出要求单独作为事实供给，普通 manager 不因工具可见被当作 chief 委派者。

#### extension：共享 chief 报告工具指引

> 需要交接结果或报告失败、受阻情况时，调用 chief_report，说明需求背景、实际执行对象、结果、限制及待用户决定事项。中途情况不要求附文件；正式交付按本次要求提供成果信息。Map 文件地址由系统从已完成 Run 的公开成果取得，无需重复填写。
>
> 通过工具完成原生预览与确认；用户拒绝或取消后，等待新的明确指示。
>
> 查看报告保存与通知回执。通知失败不意味着需要重做业务或重复提交。
>
> 用户要求重发已有报告时使用 chief_resend_report；内容变化时提交新报告。结果不确定时先核实实际效果。

manager-chat 与独立 chief-report 共享同一正文来源。需要通用条件入口时使用已确认的一句：

> 当本次工作由 chief 实际委派时，使用 chief 报告工具交接结果；具体资格由后端确认。该职责不改变你的业务工作或内部 Run 管理职责。

共享工具已经存在，共享工具不等于共享提示词；实施时必须落实两条加载路径。不能让节点 report 与 chief_report 混成一个角色。

### 9. 工具描述、参数说明与回执正文

| 位置 | 完整描述/提示 |
| --- | --- |
| run | 查询或显式推进当前管理的 Run；实际动作资格以返回结果为准。 |
| collect | 等待或取得运行现场与待处理报告标识；不返回报告正文。直接调用，不经 codemode/eval 包装。 |
| approve | 按本次成果批准模式取得批准；不发送报告或推进流程。 |
| report | 提交本次节点的进展、问题或成果，声明是否可交接，并登记文件输出。 |
| chief_definitions | 只读查询 Bot 能力目录、Task/Map 定义及已登记 zone。 |
| chief_delegate | 按 Bot 委派 Task 或 Map，经原生预览与确认后启动；返回启动结果，不等待业务完成。 |
| chief_read_report | 按报告 ID 读取完整已保存结果；读取不代表用户验收。 |
| chief_report | 向当前 chief 提交本次委派结果，经原生确认后发送。 |
| chief_resend_report | 用户明确要求重发时，重新确认并发送指定的已保存报告；不修改原内容。 |
| 报告已保存 guidance | 报告已保存；通知结果见 notification。 |
| 报告结果不确定 guidance | 无法确认报告是否已保存；请先核实实际结果。 |

参数说明仅保留使用语义，类型/必填/枚举由 schema 表达，不重复教学。以下为已确认的说明内容；保持实际字段所属动作及原大小写约定，不擅自重命名 API：

| 参数/语义 | 说明 |
| --- | --- |
| prepare_inputs.confirmed | 管理者确认输入已满足本次要求；false 仅保存待补齐绑定。 |
| fileInputs | 整批替换 Run 文件绑定，不是追加；遗漏旧 ID 会删除其绑定，空数组清空。 |
| can_complete | 如实声明本次执行是否可交接，不直接完成节点。 |
| outputs | 本次要求的实际文件 ID 与路径绑定，不是文件名或文件正文。 |
| 输出 id | 本次声明的输出 ID。 |
| 输出 path | 实际成果文件的绝对地址。 |
| map_output | 结束 Run 时提交的公开文件成果。 |
| botId | 实际 Bot ID，不是 Task ID 或 Map 文件名。 |
| zoneId | Task 或 Map 管理者的执行位置，不覆盖子图内部节点。 |
| materials | 本次材料；无材料时传空数组。Map 输入 ID 对应 map_input_rule.files；路径相对于显式材料 zone。 |
| managerTaskId | Map 型调用的管理者 Task；Task 型调用不使用。 |
| chief 委派 output_rule | 本次委派要求的文件 ID，不是 Bot 的文字输出摘要。 |
| chief_definitions.id | Task ID 或包含 .json 的完整 Map 文件名；省略时列目录。 |
| 报告 id | 已保存报告的身份。 |

其余仍适用的参数业务含义与 schema 保持，不增写与已确认角色正文重复的禁令。错误反馈说明实际问题及效果，不附加另一套流程政策。动态 guidance、工具 description、参数 description、初始化片段均纳入同一核对范围，不只改 init.md。

| 代码模块 | 读取已批准正文并装配事实；不动态生成未确认业务提示词 |

已发现需删除/替换的旧消费者文字：input_requirements/input_files、旧 Bot 三指南、只支持 file/node 的来源清单、finish 只收 action、缺少声明输出不影响完成、chief 禁止读取成果文件、仅文字 deliverables、各处重复的结束节点和批准教程。其新机械接口由调用设计权威提供；精简不取消声明输出、批准或身份的实际代码约束。

### 11. 证据、限制与后续使用

初轮设计静态读取实际磁盘配置、四个 Bot、三个业务 Task、manager/chief Task、Suite 与角色配置、选定 Map、规划/运行/定义文档、技能正文、后端初始化及工具包实际提示词/工具/回执来源。已确认当前 Map 目录读取只取顶层普通 .json，子目录业务文档不会成为 Map 条目。

初轮静态证据不证明新修订已部署、角色在真实宿主实际注入、模型消费材料或业务运行成功。当前源码中的公开声明和指针只说明约定；需另取真实运行、实际文件与公开状态证据，不能把旧样例、业务验收或历史观察算作新身份文件的证据。

[可复用迁移方法与转换规则](../decision/05-reusable-migration.md)、[单条流程初步转换试验](../decision/06-conversion-trial.md)和[系统切换与开发交接门槛](../decision/07-cutover-handoff.md)保留原设计演进；与本轮修订不一致的试验材料按历史读取，不覆盖实际 Map、Task 与业务文档。

## Decision

以「创建map」为首条样例，确认能力摘要、完整 Task、节点条件式业务指引及随 Map 维护的业务文档；专属业务检查归节点，管理者只承担通用编排交接。公共上下文拆分为后端通用流程说明与 extension 工具指引，中途报告可不附文件，默认操作建议允许用户明确调整。最新修订新增公开 `created_map`；业务定义以实际对象文本为准，代码组织改造由调用设计权威统一承接。

## User stories

1. 作为流程作者，我希望 Task 独立完整、节点只写本次差异，以便减少重复且不丢失执行必需信息。
2. 作为规划者，我希望 Bot 摘要表达输入输出的内容、成熟度与载体，以便判断能力组合而不依赖旧指南。
3. 作为用户，我希望通过 runInput 提供需求、在界面查看最终配置，并得到可供后续引用的正式 Map 身份文件。
4. 作为用户，我希望写入与检查建议允许明确调整，以便不被累积的提示词门禁阻塞，同时仍得到真实结果说明。
5. 作为维护者，我希望流程文档与 Map 靠近、后端提示词集中、工具提示精简，以便找到实际上下文来源并避免多处规则漂移。
6. 作为后续开发者，我希望得到确认正文及完整接入范围，以便按已定稿语义实现而非自行生成提示词。
7. 作为节点执行者，我希望在本次委托中取得条件式业务文档入口，以便在交付前按需检查本阶段成果，而不让管理者重复理解专属业务逻辑。

## Preconditions

- 静态结构、输入输出及独立实现原则以[Bot 与 Map node 的完整数据结构和知识归属](02-definition-schema.md)为准。
- 真实角色、冻结 Map、公开成果与 chief 机制以[调用上下文与系统代码改造契约](03-call-context-design.md)为准；已确认不等于已实施。
- 共享原件、用户选择和迁移完成/运行验证的区别以[流程迁移清单与共享影响范围](01-flow-inventory.md)为准。
- 本文不替代当前迁移清单、实际部署／切换或真实运行验收。

## Postconditions

- 后续转换读取本文链接的实际定义与共享权威，不恢复被明确替代的中间候选，也不补造业务语义。
- 文档迁移需同步所有实际引用；三个节点的条件式读取指引、完整 Task、业务标准与运行材料供给一起交付，不将节点业务检查转交管理者。
- 后端、extension 正文、工具 schema 描述及动态 guidance 同步对齐；不只修订可见业务文档。
