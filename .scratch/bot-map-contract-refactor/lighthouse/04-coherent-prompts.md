# 关联提示词的联合设计与确认：Lighthouse

> Question and discussion: [关联提示词的联合设计与确认](../decision/04-coherent-prompts.md)

## Question

如何将「创建map」的 Bot、Task、Map/node、关联业务文档及公共注入提示联合调整为新知识分层，使后续转换与开发直接使用已确认正文，而不临时创作业务语义？本文发布设计及正文，不修改生产定义、不搬移生产文档、不实施代码重构、不执行流程。

## Discussion

### 1. 确认范围、修订优先与来源

本轮用户选择「创建map」作为首条转换对象，确认保留三阶段及内部交接；输入只用 runInput，参考材料可以在其中说明路径及用途，无专门 materials 字段。用户明确最终配置通过界面查看，不需额外公开文件，因此省略整个 map_input_rule、map_output_rule。内部 outline、map、handoff 不因取消公开文件而删除。

确认来源为本票本轮连续 grilling 对话 Q2–Q47。关键确认：Q3 用户明确“交接门槛应该没有任何差异”“之前有的信息按照DRY原则重新分配”；Q5 明确 Bot 字段不会包含在实际执行上下文，必须检查信息缺失；Q6 将优化范围限定为四个描述字段；Q9/Q10/Q11 确认无公开成果文件、runInput 输入及内部交接不变；Q12 修订至 Q15 确认四个 Bot 正文；Q16 修订确认省略 Map 公开规则；Q18–Q21 确认三个精简 Task；Q22–Q28 确认业务文档、目录及系统原则；Q29 及随后“同意”统一将写入检查改为可由用户调整的建议；Q30–Q46 确认角色、工具提示及其最终后端/extension 拆分。Q42 用户明确“可以，扩展原有prompts模块”；Q44 最终确认空节点委托及共同写入规则读取入口。Q47 后用户明确“可以，请发布”。

本文合并已批准修订，不保留多个当前版本：

- 撤回降低概要方案交接门槛的建议；知识重新归位不减少必要信息。
- 不保留旧 Bot 三指南，不整段改名搬家；能力摘要不是执行补漏入口。
- 不增加 materials 输入或公开 map/handoff 文件接口；这些曾是候选，不是当前决定。
- Q29 取代早期正文中的固定写入、覆盖、检查、重试和回滚禁令：默认建议可由用户明确调整；代码约束与如实报告不变。全文下方已据此合并，不以旧“所有预设检查通过”作额外门槛。
- Q38–Q43 的最终分工取代早期“后端只提供事实、所有角色说明迁入 extension”以及未拆分的角色长正文：后端负责基本流程说明，extension 负责工具调用。
- 不新增专门的备份、兼容层、执行框架或通用自动流程验收设施。

#### Traverse 后续 grilling 的职责修订

本轮用户明确“这里很明显是约束节点执行者，map管理者不需要了解每个map特定的业务逻辑，更不应该从后端注入某个map特定的提示词”，并在最终归纳后授权“可以，请更新”。此前将「创建 Map 的整图交接」交给管理者验收的安排被取代：业务标准保留，读取和检查责任归还对应节点。结构分工的唯一权威为[最小验收与结束节点](02-definition-schema.md#9-最小验收与结束节点)，运行装配和中途报告机制见[调用契约](03-call-context-design.md)。

manager_rule、自动注入 Map description、为管理者增加专属文档或词典入口均是本轮已撤回候选。原 Q44 的概要规划／转换节点空 input 被下方条件式读取指引取代；不重复 Task 已有稳定职责，不在启动时预先展开全部业务文档。未 finish 的中途报告可不附文件，正式交付检查仍保留。

### 3. 知识归属与系统原则正文

判断 node.input 的标准是“Task 已完整，本次调用还增加什么差异”，不是把节点需要的一切写在 input。独立使用也需要的知识归 Task/实现资料；所有节点共用的流转知识归后端角色说明或 extension 工具指引；来源、依赖与策略归结构化配置。仅本次目标、材料用途、额外范围及本流程特有的条件式读取指引留在 node.input。Map 管理者不承担专属业务验收；description 不作为指令或业务文档读取入口。

以下正文在实施时放入 docs/scheduler.md「定义职责与唯一格式」的 Bot 说明处。静态结构原则的设计权威仍为[Bot 与 Map node 的完整数据结构和知识归属](02-definition-schema.md)，这里提供已确认的产品说明措辞：

> Bot 的 when、description、input_rule、output_rule 供规划者和调用者发现、选择与组合能力，不作为执行指令注入目标 Chat，也不要求执行者通过读取 Bot 补全工作规则。执行所需的稳定知识由 Task、script 或 Map 实现及其引用资料完整承接；本次差异由调用输入提供。Bot 的目标引用仍用于解析实际实现。

“不注入”不是禁止规划者或转换者按职责读取 Bot。Bot 输入输出摘要描述业务内容、成熟度与载体，帮助规划者判断衔接，不承担调用教程、运行校验或文件绑定。

### 4. 四个 Bot 的完整描述性正文

#### 创建map

**when**

> 需要将业务需求转化为可复用的业务 Map 时使用。

**description**

```markdown
## 能力职责
规划业务流程，生成 Map，并按知识分层规则优化关联提示词。

## 能力边界
交付止于配置创建与优化，不启动生成的业务流程。能力缺口由用户另行衔接补齐。

## 用户参与
业务方案及共享对象的修改范围需要用户确认。

## 操作效果
新增 Map，并在获准范围内修改相关定义和共同文档。
```

**input_rule**

> 待规划的业务需求，包括目标及已知约束；可以是初步需求，也可以是已有方案，可附相关参考资料。

**output_rule**

> 系统中已保存、完成关联提示词优化的业务 Map 配置，可通过界面或配置接口查看；不交付公开成果文件，尚未经过实际业务运行验证。

#### 概要规划

**when**

> 需要澄清业务需求、选择和组合既有能力，形成业务流程方案时使用。

**description**

```markdown
## 能力职责
与用户明确业务目标和边界，调查可复用能力，形成经用户确认、供 Map 转换者使用的概要方案。

## 能力边界
交付止于业务规划，不生成 Map 配置或执行业务。能力缺口由用户另行衔接补齐。

## 用户参与
业务取舍及方案需要用户确认。
```

**input_rule**

> 待规划的业务需求，包括目标及已知约束；可附参考资料、已有方案及其确认范围。

**output_rule**

> 经用户确认、满足转换条件的概要方案，包含工作划分、能力选用、依赖、材料交接和操作边界。独立使用可交付完整正文，流程内交付 Markdown 文件；尚有能力缺口或未决业务选择的方案仅作为中间材料。

#### 概要方案转 Map

**when**

> 已有经用户确认的概要方案，需要将其转换为业务 Map 配置时使用。

**description**

```markdown
## 能力职责
核实方案与真实实现，将业务安排转换为完整 Map，保存配置并按本次约定完成检查。

## 能力边界
忠实落实已确认方案，不重新决定业务目标、不补建能力、不启动生成的业务。影响方案的缺口交回规划者或用户确认。

## 操作效果
新增 Map 配置；覆盖既有 Map 需要明确授权。
```

**input_rule**

> 经用户确认、满足转换条件的完整概要方案，包含工作划分、能力选用、依赖、材料交接、操作边界及确认范围；可提供完整正文或可读文件。

**output_rule**

> 已保存的完整 Map 配置及实际核验说明；流程内交付完整 Map JSON 文件。说明保留待配置项和未验证事项，配置交付不代表业务已经运行或通过实际业务验证。

#### prompt优化者——Map维度

**when**

> 需要从整张 Map 的协作关系出发，优化关联提示词的分层、重复、冲突或遗漏时使用。

**description**

```markdown
## 能力职责
统筹 Map、关联 Task、Bot 及共同文档中的提示词，按知识归属重新组织内容，确保各执行节点能够取得所需信息。

## 能力边界
保持已确认的业务语义、拓扑、绑定和执行配置；不补建能力或运行目标业务。

## 用户参与
业务语义变化及超出既有授权的修改需要用户确认。

## 操作效果
在获准范围内保存提示词修改；共享对象的变化会影响其他调用方。
```

**input_rule**

> 待优化的 Map、优化目标及允许修改范围；可附已确认方案、必须保留的要求和参考资料。目标可由系统中的明确配置身份或完整 Map 文件提供。

**output_rule**

> 已保存并完成分层优化的配置，以及修改范围、共享影响、保存核对结果和未验证事项说明；流程内交付最终 Map JSON 与优化交接说明文件。文本与定义优化不代表实际业务行为已经验证。

### 6. 三个 Task 的完整 prompt

#### 概要规划

```markdown
与用户澄清业务需求，组合可复用能力，交付经确认、满足转换条件的概要方案。使用初始 skill 组织讨论。

产品仓库 ${herdr-bot-path}；服务 ${herdr-bot-api-url}。下文系统文档路径相对产品仓库，规划交付契约为 ${herdr-bot-path}/meta-data/workflow-maps/plan_workflow/planning-deliverables.md。

**需求与材料**

独立使用时读取用户提供的需求；流程内结合 Run 背景、节点委托和实际命名输入。完整读取所提供的参考资料，明确其用途及已有确认范围；必要信息缺失或冲突时与用户澄清。

**能力调查**

查询前读取 docs/scheduler.md「HTTP interface 与路径边界」；选择和组合能力前读取规划交付契约「能力选用与调用」。

根据 Bot 能力摘要形成方案，按规划契约核实必要事实。存在能力缺口时，按该契约「能力建设需求」交付需求，由用户另行衔接；取得补齐结果后重新核实。

**方案交付**

编写或修订前读取规划交付契约「共同身份」「概要方案」，据此组织方案并取得用户确认。只有满足其转换条件的方案才可正式交接，其他版本保留为中间材料。

独立使用且未要求文件时交付完整 Markdown 正文；要求文件时，按该契约「规划文档保存与交接」保存。流程内按声明交付方案文件。

保存交付材料或配置前，读取规划交付契约「共同写入规则」；具体配置接口按目标平台文档操作。

**操作边界**

默认只读调查并交付规划材料。额外写入、试运行或外部业务调用须另获授权；本 Task 不修改能力定义、生成 Map 配置或启动业务。
```

#### 概要方案转 Map

```markdown
将经用户确认、满足转换条件的概要方案转化为完整业务 Map，保存配置并核实结果。

产品仓库 ${herdr-bot-path}；服务 ${herdr-bot-api-url}。下文系统文档路径相对产品仓库，规划交付契约为 ${herdr-bot-path}/meta-data/workflow-maps/plan_workflow/planning-deliverables.md。

**核实方案**

独立使用时读取用户提供的完整方案；流程内读取命名输入 outline，结合 Run 背景及节点委托。

核实前读取规划交付契约「共同身份」「概要方案」「能力选用与调用」，确认当前版本、有效确认范围和转换条件。读取所选 Bot 的目标引用及真实实现，不以 Bot 能力摘要代替实现规则。

**转换定义**

转换前读取 docs/scheduler.md「定义职责与唯一格式」「node.input 的业务职责」「文件输入与输出规则」。

忠实落实方案中的工作、依赖、材料关系和操作边界。稳定职责由实现承担，接线与执行策略使用结构化字段，仅将本次业务差异写入 node.input；没有差异时允许为空。Map 型调用使用公开接口，不展开内部节点。

格式决定自行完成；业务选择缺失或实现不能承接时，列明问题交回用户或规划者，不通过节点提示词补建稳定能力。
```

> 使用 chief_definitions 查询能力、实际目标及执行位置；补齐影响本次委派的必要信息。
>
> 用户明确要求委派后，调用 chief_delegate，通过工具完成参数预览、原生确认与提交。根据回执说明实际启动结果；返回不确定时先核实已有事实。
>
> 收到报告时依据完整报告呈现结果；需要理解结构化文件成果时读取文件，不根据 ID 猜测内容。用户主动要求查看已有报告时，使用 chief_read_report。
>
> 身份、委派资格及重复通知处理由系统负责，不自行模拟接收确认。

保留 Task/Map 委派范围、既有确认交互及异步机制，不新增 script 分支，不新增扫描积压或自主后续派发。删除固定能力创建入口的硬编码选择策略，缺口由用户决定如何处理。

#### 后端：chief 委派说明

> 本次工作由 chief 委派。按提供的业务要求完成工作，并向当前 chief 交接实际结果，使其无需原对话上下文也能理解。
>
> 正式交付时按本次要求交接文件成果；Map 的公开文件成果取自已完成 Run。未结束时可报告失败或受阻情况，不要求附文件，不为发送报告强行结束。业务完成与报告发送是不同动作，报告保存与通知结果也分别记录。

仅在真实 chief 委派上下文使用；独立 Task 与直接 Map manager 两条路径取得同一权威说明。业务输入、实际材料和本次输出要求单独作为事实供给，普通 manager 不因工具可见被当作 chief 委派者。

#### extension：共享 chief 报告工具指引

> 需要交接结果或报告失败、受阻情况时，调用 chief_report，说明需求背景、实际执行对象、结果、限制及待用户决定事项。中途情况不要求附文件；正式交付按本次要求提供成果信息。Map 文件地址由系统从已完成 Run 的公开成果取得，无需重复填写。
>
> 通过工具完成原生预览与确认；用户拒绝或取消后，等待新的明确指示。
>
> 查看报告保存与通知回执。通知失败不意味着需要重做业务或重复提交。
>
> 用户要求重发已有报告时使用 chief_resend_report；内容变化时提交新报告。结果不确定时先核实实际效果。

manager-chat 与独立 chief-report 共享同一正文来源。需要通用条件入口时使用已确认的一句：

> 当本次工作由 chief 实际委派时，使用 chief 报告工具交接结果；具体资格由后端确认。该职责不改变你的业务工作或内部 Run 管理职责。

共享工具已经存在，共享工具不等于共享提示词；实施时必须落实两条加载路径。不能让节点 report 与 chief_report 混成一个角色。

### 9. 工具描述、参数说明与回执正文

| 位置 | 完整描述/提示 |
| --- | --- |
| run | 查询或显式推进当前管理的 Run；实际动作资格以返回结果为准。 |
| collect | 等待或取得运行现场与待处理报告标识；不返回报告正文。直接调用，不经 codemode/eval 包装。 |
| approve | 按本次成果批准模式取得批准；不发送报告或推进流程。 |
| report | 提交本次节点的进展、问题或成果，声明是否可交接，并登记文件输出。 |
| chief_definitions | 只读查询 Bot 能力目录、Task/Map 定义及已登记 zone。 |
| chief_delegate | 按 Bot 委派 Task 或 Map，经原生预览与确认后启动；返回启动结果，不等待业务完成。 |
| chief_read_report | 按报告 ID 读取完整已保存结果；读取不代表用户验收。 |
| chief_report | 向当前 chief 提交本次委派结果，经原生确认后发送。 |
| chief_resend_report | 用户明确要求重发时，重新确认并发送指定的已保存报告；不修改原内容。 |
| 报告已保存 guidance | 报告已保存；通知结果见 notification。 |
| 报告结果不确定 guidance | 无法确认报告是否已保存；请先核实实际结果。 |

参数说明仅保留使用语义，类型/必填/枚举由 schema 表达，不重复教学。以下为已确认的说明内容；保持实际字段所属动作及原大小写约定，不擅自重命名 API：

| 参数/语义 | 说明 |
| --- | --- |
| prepare_inputs.confirmed | 管理者确认输入已满足本次要求；false 仅保存待补齐绑定。 |
| fileInputs | 整批替换 Run 文件绑定，不是追加；遗漏旧 ID 会删除其绑定，空数组清空。 |
| can_complete | 如实声明本次执行是否可交接，不直接完成节点。 |
| outputs | 本次要求的实际文件 ID 与路径绑定，不是文件名或文件正文。 |
| 输出 id | 本次声明的输出 ID。 |
| 输出 path | 实际成果文件的绝对地址。 |
| map_output | 结束 Run 时提交的公开文件成果。 |
| botId | 实际 Bot ID，不是 Task ID 或 Map 文件名。 |
| zoneId | Task 或 Map 管理者的执行位置，不覆盖子图内部节点。 |

其余仍适用的参数业务含义与 schema 保持，不增写与已确认角色正文重复的禁令。错误反馈说明实际问题及效果，不附加另一套流程政策。动态 guidance、工具 description、参数 description、初始化片段均纳入同一核对范围，不只改 init.md。

### 11. 证据、限制与后续使用

本轮静态读取实际磁盘配置、四个 Bot、三个业务 Task、manager/chief Task、Suite 与角色配置、选定 Map、规划/运行/定义文档、技能正文、后端初始化及工具包实际提示词/工具/回执来源。已确认当前 Map 目录读取只取顶层普通 .json，子目录业务文档不会成为 Map 条目。

这些证据不证明运行中服务使用该配置、不证明角色在真实宿主实际注入、不证明模型行为或新格式可运行。当前产品文档与代码仍有旧格式；本文是已批准的新设计，不能伪装为生产已更新。只做本次规划文档发布和一致性检查，不执行系统检查、模型流程或业务验收。

后续[可复用迁移方法与转换规则](../decision/05-reusable-migration.md)消费本权威，不重复创作正文；[单条流程全要素初步转换试验](../decision/06-conversion-trial.md)将真实对象、上述正文、引用及差异组成完整资产，按当前源码核对消费者而不临时自决新语义；[选择性迁移的系统切换与开发交接门槛](../decision/07-cutover-handoff.md)决定部署/历史/活动执行及开发入口。生产开发与真实流程运行仍在本票之外。

## Decision

以「创建map」为首条样例，确认能力摘要、完整 Task、节点条件式业务指引及随 Map 维护的业务文档；专属业务检查归节点，管理者只承担通用编排交接。公共上下文拆分为后端通用流程说明与 extension 工具指引，中途报告可不附文件，默认操作建议允许用户明确调整。本文保存可直接消费的确认正文，代码组织改造由调用设计权威统一承接。

## User stories

1. 作为流程作者，我希望 Task 独立完整、节点只写本次差异，以便减少重复且不丢失执行必需信息。
2. 作为规划者，我希望 Bot 摘要表达输入输出的内容、成熟度与载体，以便判断能力组合而不依赖旧指南。
3. 作为用户，我希望通过 runInput 提供需求并在界面查看最终配置，以便使用创建map而不用维护额外公开文件接口。
4. 作为用户，我希望写入与检查建议允许明确调整，以便不被累积的提示词门禁阻塞，同时仍得到真实结果说明。
5. 作为维护者，我希望流程文档与 Map 靠近、后端提示词集中、工具提示精简，以便找到实际上下文来源并避免多处规则漂移。
6. 作为后续开发者，我希望得到确认正文及完整接入范围，以便按已定稿语义实现而非自行生成提示词。
7. 作为节点执行者，我希望在本次委托中取得条件式业务文档入口，以便在交付前按需检查本阶段成果，而不让管理者重复理解专属业务逻辑。

## Preconditions

- 静态结构、输入输出及独立实现原则以[Bot 与 Map node 的完整数据结构和知识归属](02-definition-schema.md)为准。
- 真实角色、冻结 Map、公开成果与 chief 机制以[调用上下文与系统代码改造契约](03-call-context-design.md)为准；已确认不等于已实施。
- 共享原件、用户选择和迁移完成/运行验证的区别以[流程迁移清单与共享影响范围](01-flow-inventory.md)为准。
- 本票不替代可复用迁移方法、完整样例或切换决策；这些提供方仍未完成。

## Postconditions

- 后续转换使用本文最终正文及唯一权威，不恢复被明确替代的中间候选，不让开发 Agent补定业务语义。
- 文档迁移需同步所有实际引用；三个节点的条件式读取指引、完整 Task、业务标准与运行材料供给一起交付，不将节点业务检查转交管理者。
- 后端、extension 正文、工具 schema 描述及动态 guidance 同步对齐；不只修订可见业务文档。
- 工程接入保留身份、状态、原生批准、通知和输出校验，不把默认建议可调整解释为绕过代码约束。

## Invariants

- ADR 0015 的普通 Task 独立使用、节点身份来自真实执行、结束节点例外保持；主/子 Run、chief 与独立 Task 均有上下文供给，不以同名推断身份。
- ADR 0019 的脚本宿主保持，Bot 三类实现不重建；chief 仍只直接委派 Task/Map。
- 沿用现有 prompts 词典与消息组合语义，模块化要求只有一个[调用设计权威](03-call-context-design.md#9-后端-prompts-模块的集中维护)。
- 公共角色的 OMP/Pi 入口、根/子 manager 以及直接 chief 委派路径复用各自权威，不复制维护规则。
