# 流程迁移清单与共享影响范围：Lighthouse

> Question and discussion: [流程迁移清单与共享影响范围](../decision/01-flow-inventory.md)

## Question

如何以现有 Map 为入口组织迁移清单，记录用户选择、必要依赖及完成情况，而不扩大迁移工作或维护多套共享定义？本文件发布清单与维护规则，不代表已生成完整依赖清单或执行转换。

## Discussion

### 清单入口与记录内容

采用新增 Markdown 文档，以配置指向的 Map 清单为入口，不新增产品界面或持久化格式。记录 Map 的稳定身份、来源、用途及关联 Bot、Task、子 Map、脚本、skill、引用文档；共享对象的其他消费者仅供用户参考，不成为当前流程的额外迁移或验收门槛。记录转换产物、待补内容及用户实际运行验证结果，不建立额外变更流水。

不把未关联 Task 列为独立迁移项。用户在 Q1 提出 Task 可能只需调整提示词，但明确指出结构是否需要调整应由“Bot 与 Map node 的完整数据结构和知识归属”决定；本票不批准“Task 结构不变”或“Task 不受影响”。关联 Task 按后续结构与调用契约决定必要修改范围，保留独立使用的完整性。

### 共享定义原地修改

格式未变的 Task、Suite、脚本、Skill 和引用文档保留原位；包括提示词在内的必要修改直接应用到共享原文件，不维护多套定义。旧 Map／Bot 的一次性离线暂存按下段新版切换修订处理，不是在线隔离副本。每条流程迁移只处理自身完成所需变化，其他流程如需调整，也修改同一共享原件；由用户把关这些修改是否影响已迁移 Map。列出其他消费者不等于要求同时迁移它们。

最初拒绝隔离复制、额外备份和复验状态。原 Q4“直接修改共享原件即可，我不想变成维护多套共享原件”和 Q7“每次迁移结束后默认就是对所有已有流程都有效的状态”继续适用；这是维护约定，不是全流程已测试的事实。原 Q5“已经有git修改记录，不需要再另外做备份”在切换交接会话中明确修订如下，Git 仍承担修改历史，不新增复验状态。

#### 新版切换修订：离线 backup，逐项迁入

旧 Map／Bot 一次性移至在线定义读取范围之外的 backup，不展示在系统列表，不自动回退读取；转换后写入正式目录，Bot 保留原 ID，Map 保留原文件名及图内引用身份。关联引用重新对应不等于业务已经验证。未迁移 Map 在 backup 内保留相同引用 ID；正式共享 Bot 自身迁移完成后，其旧副本即可移除，无需等待所有消费者一起迁移。

用户确认迁移完成后，可直接删除 backup 内该 Map／Bot 的旧副本，不能删除正式目录的新定义。处理完全部迁移选择后，定义 backup 只剩明确废弃部分；未处理项不得自动算作废弃。此删除授权仅针对已迁移对象的旧副本，不授权删除废弃项、共享依赖或实际业务文件。格式未变资源保持原位，必要提示词直接改原文件。

修订来源：[选择性迁移的系统切换与开发交接门槛](07-cutover-handoff.md)本轮 Q4、Q6、Q9。Q4 明确显示归属文件 01-flow-inventory.md 后，用户回答“是，迁移成功的map和bot可以直接删除，这样最后backup留下的只有废弃的部分”；Q6 再确认，Q9 明确“没有变更格式的资源保留在原位……提示词变更，这部分直接应用到文件上即可”。这是一次切换的离线暂存，不是长期维护第二套共享原件。旧 Run 归档和 chief 清理由切换交接权威负责。

### 三种状态与完成条件

用户 Q8 指定仅使用“未开始／迁移完成／废弃”。初始为“未开始”；转换未完成、有待补内容或尚未经用户确认时仍为“未开始”，详情记备注，不增加迁移中、暂缓或待复验状态。

“迁移完成”指当前 Map 及必要关联定义已完成转换、待补项已解决，并经用户确认；不要求已经实际运行。用户 Q9 确认：“实际流程运行验证由用户进行，自动化测试不需要覆盖这部分”。这不取消系统代码适用的既有自动化检查，也不把初步转换记为业务运行验收通过。

“废弃”仅表示不再迁移、不要求新版支持；用户 Q6 明确同意它不授权删除 Map 或共享依赖。未迁移定义不保证在新版运行。

### 证据与限制

本次静态读取 herdr-bot.toml、其引用的 paths.local.toml，以及配置指向的 meta-data/workflow-maps、meta-data/bots：目录中有 9 张 Map、32 个 Bot。Map 存在共享 Bot 引用，Bot 可通过 task_id、map_file 或 script 指向实现。数量是会话观察，不是固定契约；未核实运行中服务加载的配置，未完成全部 skill／文档的传递依赖调查，未执行任何流程。

确认来源为 2026-11-26 本票 grilling 对话 Q1–Q9；以上保留关键原话，便于恢复用户选择与拒绝理由。

## Decision

以 Map 为入口建立三状态迁移清单；旧 Map／Bot 离线暂存并逐项转换，确认迁移完成后移除旧副本，未变格式的共享资源原位维护。用户把关影响与实际流程验证，不维护长期并行副本或复验状态。

## User stories

1. 作为用户，我希望从 Map 清单逐项决定迁移或废弃，以便控制迁移范围，而不把独立 Task 自动列为迁移任务。
2. 作为维护者，我希望共享定义只有一个维护入口，以便后续流程直接复用和修订同一原件，而非维护多套副本。
3. 作为用户，我希望将转换确认与实际运行验证分开，以便在开发前确认转换资产，并在开发后自行验证真实流程。

## Preconditions

- 清单来源沿实际服务配置及路径根解析，不能把发布样例当作用户全部数据；本次已确认磁盘配置链，运行服务的配置尚未核实。
- 最终字段、Task 必要变化与运行时装配由“Bot 与 Map node 的完整数据结构和知识归属”和“调用上下文与系统代码改造契约”提供，本票不替代它们。
- 转换方法、完整样例和交接条件分别由“可复用迁移方法与转换规则”“单条流程全要素初步转换试验”“选择性迁移的系统切换与开发交接门槛”继续决定；未解决的票据不视为前提已满足。

## Postconditions

- 后续清单与转换使用本票的范围、共享维护及状态约定；具体资产尚待后续工作形成。
- 用户确认转换完成即可记录“迁移完成”，不得因此伪造运行验证结果。
- Git 保留修改历史；切换时 Map／Bot 使用上述离线 backup，迁移完成后可删除相应旧副本，不维护第二套在线定义。

## Invariants

- 遵循根 GLOSSARY.md：Map 是静态工作定义，Bot 是共享能力定义，Task 是可独立发起 Chat 的预设；迁移清单不是 Run 运行事实。
- 不默认全量迁移、不默认删除、不保证未迁移数据在新版运行。
- 保留适用的系统代码自动化检查；真实业务流程验证由用户进行，不为本次新增覆盖这部分的自动化测试要求。
- 本票只决定规则，不执行生产代码改造、数据转换或 /to-tickets。
