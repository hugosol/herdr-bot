# 选择性迁移的系统切换与开发交接门槛：Lighthouse

> Question and discussion: [选择性迁移的系统切换与开发交接门槛](../decision/07-cutover-handoff.md)

## Question

如何一次性切换到新 Bot／Map 与运行协议，保留用户需要的历史和选择性迁移能力，并明确开发交接边界？本文发布决策，不执行停机、移动、删除、迁移、开发或生成 spec。

## Discussion

### 1. 一次停机切换，不接续旧 Run

采用一次停机切换，不做新旧格式混跑、热切换或跨版本接管旧 Run。切换前停止相关执行并核实在途工作及外部效果，再停服务、处理数据、更新后端／前端／工具包与所需定义。pause 不取消在途脚本，后端退出不证明外部效果已结束；不能把停止服务当成业务回滚。

现有 managed=false 只是当前后端未接管该 Run，不表示成功、失败或 Chat／脚本已停止。新版从新的在线 Run 集合开始，旧流程若需继续，核实已有结果后按新定义重新发起，不通过恢复旧 Chat 接续旧 Run。

### 2. 定义逐项迁入，共享资源原位修改

Map／Bot 的 backup、稳定身份、迁移完成后删除旧副本和共享资源原位修改规则，统一由[流程迁移清单与共享影响范围](01-flow-inventory.md)维护。本票不建立第二套迁移政策。

backup 必须在服务实际配置的定义读取范围之外，归档中的 Map／Bot 不出现在在线列表，也不被作为运行回退来源。新版不需兼容移出在线目录的旧定义格式；正式目录只接收转换后的定义，不根据 Markdown 迁移清单建立运行门禁。保留 ID／Map 文件名使引用重新对应，不等于提示词、接口或业务已验证。

无需等待全部流程迁移完成。第一条流程迁移完成后即可测试，再继续逐项迁移；不要求全量完成才启用，也不将独立转换试验重新设为门槛。

### 3. 旧 Run 归档，chief 运行记录删除，Chat 保留

旧 Run 完整目录移到在线 run_directory 之外，保留 run.json、history.jsonl、messages.jsonl 等原始记录供离线查看，不迁回新版列表，不用当前 Map 补造历史副本或公开成果。不要求新版在线读取、展示或继续这些旧 Run；“归档可查看”指保留文件，不承诺新增归档浏览器。旧 Run 不直接删除。

chief 的身份账本、委派记录、报告及接收确认直接清理，不要求归档。它们不等于 Chat 历史。全部 Chat 历史目录和原生对话保留，包括 chief 会话与其他 Chat；实际产出文件、zone 及其他无关数据不随之清理。不可整目录删除 .data。

保留 chief 原生对话，不要求新建会话；其旧委派与报告职责不延续，之后使用现有恢复／登记机制建立当前 chief 身份。历史 Chat 留存不承诺恢复旧 Run 角色、管理资格或交接能力。

按本轮读取的 herdr-bot.toml → paths.local.toml，以下为本机配置的目标；实际切换必须按所用服务配置定位，不能将此表硬编码为所有部署的地址：

| 处理 | 配置解析后的项目相对路径 |
| --- | --- |
| 归档旧 Run | .data/workflow-runs/ |
| 删除 chief 身份账本 | .data/session-history.chief.json |
| 删除 chief 委派 | .data/session-history.delegations.json |
| 删除 chief 报告 | .data/session-history.chief-reports.jsonl |
| 删除 chief 接收确认 | .data/session-history.chief-reports.receipts.jsonl |
| 保留 Chat 历史目录 | .data/session-history.json |

原生对话在 agent 自身会话目录，不属于上述清理范围。仅重启不会清空持久委派、报告和接收记录：chief.rs 只在初始化时清除已 registered 的当前登记，保留来源、撤销及未确认效果等账本内容。

### 4. 交接复用原权威，后续由用户手动启动

交接输入沿用已确认的[结构](02-definition-schema.md)、[调用与代码契约](03-call-context-design.md)、[联合提示词](04-coherent-prompts.md)、[迁移方法](05-reusable-migration.md)及本文。消费者范围、现有分层自动化检查、开发 Agent 不自行补写未确认业务语义、用户执行实际业务验收，均沿用原票约束，不重新要求用户批准。

[独立转换试验处置](06-conversion-trial.md)已经取消完整样例／独立转换验收门槛；设计和正文已确认不等于生产资产迁移完成。实际迁移清单及每条流程转换随后续操作形成，不将本票完成写成这些交付物已经存在。

本票结束只发布决策并更新地图。即使所有票已完成，也不自动生成 spec.md，不执行 /to-tickets 或生产实现；等待用户手动启动后续流程。

### 5. 确认来源与证据边界

确认来源为本票本轮连续对话：Q1 用户选择“一次停机切换”；Q4/Q6 确认将定义移入 backup、迁移成功后删除旧 Map／Bot 副本，并以 01-flow-inventory.md 确认政策归属；Q7 经区分 chief 持久数据与 Chat 历史后明确“chief相关的历史数据可以直接清理”；Q8 明确“旧run我想还是归档处理，不要直接删除”；Q9 确认未变格式资源原位保留、提示词直接修改文件；Q10 明确“第一条流程迁移完成后就可以进行测试”；Q11 明确“本票完成后不要直接生成spec，等用户手动执行”。重复询问交接要求的 Q12 已撤回，用户最终“可以，请发布”。

未采纳：旧 Run 在线兼容展示、所有历史直接删除、chief 运行记录也必须归档、整批移走 Task 等资源、等待全部流程迁完、自动生成 spec。backup 不是长期并行维护的第二套共享原件。

静态证据：backend/src/runs.rs 的持久记录读取与 Chat 关联扫描；chats/resume.rs 的来源 Task 最新环境恢复；scheduler/maps/mod.rs 的目录与定义读取；chief.rs、chief_delegation.rs、chief_reports.rs 与 lib.rs 的独立持久存储；docs/workflow-runtime.md 的重启未接管与在途效果边界。只读取磁盘配置和代码，未核实正在运行服务的配置、未停止进程、未移动或删除数据、未运行业务验收。

## Decision

一次停机切换；旧定义按迁移清单权威逐项迁入，旧 Run 离线归档，chief 运行记录清理但所有 Chat 历史保留。首条流程迁移后即可测试；本票完成不自动生成 spec 或开始实施。

## User stories

1. 作为用户，我希望旧定义移出在线目录并逐条迁回，以便不维护新旧格式兼容或等待所有流程迁移。
2. 作为用户，我希望旧 Run 归档、chief 运行记录清理而 Chat 保留，以便新版从干净运行状态开始但不丢失需要的历史。
3. 作为用户，我希望未变格式的共享资源原位调整提示词，以便保留既有身份引用与独立用途。
4. 作为用户，我希望手动启动 spec 与后续交接，以便决策发布不擅自开始下一阶段。

## Preconditions

- 结构、调用、联合提示词、清单与迁移方法的原权威已确认；生产实现尚待开发。
- 实际切换前定位服务使用的配置、在线目录和相关活动执行；停止与核实在途效果后才处理数据。
- backup／Run 归档位置不在相应在线读取范围；迁入的定义满足新结构及关联实现要求。

## Postconditions

- 设计要求新版在线列表不读取归档 Map／Bot／Run，不新增归档 UI 或旧格式回退。
- 清理范围不包含 Chat 历史、原生对话、zone 或业务产物；旧 Run 归档与 chief 清理分别处理。
- 第一条流程迁移后可测试，不以全量迁移或独立转换试验作为门槛。
- 发布后本票可完成；spec、/to-tickets、开发及真实切换均等待后续用户操作。

## Invariants

- 清单三状态、用户逐项决定及业务验收沿用清单权威；未处理不等于废弃。
- runs.rs 的执行身份与 chats/resume.rs 的原生对话恢复是不同机制，Chat 恢复不赋予旧 Run 管理资格。
- chief_reports.rs 的报告与接收事实不同于 Chat 正文；仅清理明确指定的运行记录。
- ADR 0016 的 files 持久化边界不改变；本次人工停机切换不是新增自动启动迁移或回滚机制。
- 不从当前定义或 Chat 文字补造历史执行事实，不以决策发布声称迁移或验收已经完成。
