# Bot 与 Map 全面重构及选择性流程迁移

Status: ready-for-agent

Contract: [已批准契约：promises、四个 seam 与验收分工](contract.md)（含已确认的 tester 专项延期安排；后续切票以契约 Coverage 为准）

## Problem Statement

用户需要将现有 Bot、Map/node、运行交接和关联提示词调整为一致的知识分层，使同一能力既能独立使用，也能在流程和 chief 委派中复用。当前 Bot 的旧指南混合能力选用、规划方法和执行知识，必要信息可能散落在 Bot、Task、node.input 与公共提示词中；仅删除或改名会使执行者失去信息，简单复制又会继续造成重复维护。

当前 Map 的整体输入声明与节点接线不同层，缺少整图公开成果接口；调用方容易依赖内部节点或重复维护文件地址。现有 Run 记录使用 userInput/fileInputs，未保存本次完整 Map，finish 尚不登记整图公开文件。定义修改和删除、嵌套交接、chief 异步报告因此需要明确的新契约，而不是把文件存在、报告成功或 Chat 停止当作业务完成。

用户还需要逐条选择存量流程迁移或废弃，而非被迫全量转换、长期维护新旧格式，或丢失 Chat 历史。设计确认、生产定义转换、系统机制检查与实际业务运行验证必须分开陈述。

## Solution

将 Bot 收敛为供规划者与 chief 使用的能力索引；实际 Task、script、Map 及其引用资料独立承接完整执行知识。Map 声明整图输入输出规则，node 保留现有结构并只表达本次业务差异、适用业务文档的条件式读取指引和结构化接线。节点负责业务执行与成果检查，管理者只负责通用输入准备、编排和交接。

每个新 Run 冻结自己的完整 Map，归整本次实际输入，并在显式 finish 时登记公开文件成果。父节点和 chief 按本次要求取得公开成果，保持批准、报告、完成、通知和用户验收相互独立；中途报告不要求伪造文件或强行结束。

同步改造后端、现有界面、OMP/Pi 工具包、定义读写消费者和系统文档，直接使用已确认的提示词。首条选定流程为「创建map」，落地其已确认的 Bot、Task、Map/node 与业务文档，不重新决定业务语义。

以一次停机切换进入新版：旧 Map/Bot 离线暂存后按用户选择逐项迁入，旧 Run 离线归档，chief 运行记录清理，Chat 历史与业务文件保留。第一条流程迁移完成后即可测试，不等待全量迁移。后续流程按已有单流程调查与 grilling 方法处理。

## User Stories

1. 作为用户，我希望 Task 不经过 Bot 也能独立使用，以便不依赖能力索引补全执行规则。
2. 作为用户，我希望 Map 可以直接发起 Run，以便不必为每张 Map 配置默认 Bot。
3. 作为概要规划者，我希望通过 Bot 的适用说明、能力描述和输入输出摘要选择能力，以便不提前展开所有实现细节。
4. 作为概要规划者，我希望摘要保留影响组合的边界、用户参与和外部效果，以便不对能力作出错误承诺。
5. 作为 Map 转换者，我希望读取真实 Task、script 或 Map 接口，以便不把 Bot 摘要当作实际执行契约。
6. 作为 Map 转换者，我希望实现缺口和缺失业务决定返回确认，以便不在 node.input 中偷偷补建能力或授权。
7. 作为维护者，我希望旧指南中的有效知识有明确承接位置，以便删除旧字段时不丢失必要信息。
8. 作为定义作者，我希望 Bot 保留草稿保存能力，以便分步编辑而不把保存成功当作可运行证明。
9. 作为定义作者，我希望规则声明与实际值采用不同名称，以便区分静态约束和本次文件绑定。
10. 作为 Map 作者，我希望集中声明整图业务输入要求和命名文件，以便调用方不依赖内部节点布局。
11. 作为用户，我希望先启动管理者再准备必需材料，以便通过对话补齐输入，而不是在启动前被强制备齐。
12. 作为管理者，我希望明确确认输入就绪后才能派发业务节点，以便材料准备状态不被启动成功替代。
13. 作为节点执行者，我希望分别取得完整 Run 背景、本次 node.input 和实际材料地址，以便理解工作而不重复维护背景。
14. 作为节点执行者，我希望在适用条件满足时读取业务标准，以便交付前检查成果，而不在启动时展开全部文档。
15. 作为管理者，我希望只承担通用编排交接，以便无需了解每张 Map 的专属业务逻辑。
16. 作为 Map 作者，我希望可以不声明公开文件输出，以便操作型流程或交给用户继续的 Chat 不必制造文件。
17. 作为 Map 调用者，我希望按公开输出 ID 获取文件，以便不依赖内部 node 或固定路径。
18. 作为管理者，我希望通过现有 finish 一次提交完整公开文件，以便不维护额外登记工具。
19. 作为用户，我希望缺失、重复、未声明或不可读的公开文件阻止成功结束，以便不能用不完整成果冒充完成。
20. 作为用户，我希望已完成 Run 的公开成果不被再次 finish 改写，以便保留首次完成事实。
21. 作为父 Map 作者，我希望只要求子 Map 公开成果的必要子集，以便不被强制消费全部输出。
22. 作为子 Run 管理者，我希望系统从已完成子 Run 取得父层文件地址，以便不重复填写或覆盖公开成果。
23. 作为父节点调用者，我希望子 Run 结束、父成果批准和父节点完成仍分别发生，以便文件登记不自动推进流程。
24. 作为执行者，我希望中途进展、失败或受阻可以不附文件报告，以便如实反馈而不强行完成。
25. 作为用户，我希望结束节点仅表示 Chat 已交给我继续，以便不把未来对话成果当作本次已交付文件。
26. 作为 chief，我希望沿用已有预览、原生确认和异步委派，以便新输出要求不重建授权流程。
27. 作为 chief，我希望为 Task 或 Map 委派声明本次所需文件 ID，以便报告可以结构化交付成果。
28. 作为独立受委派的 Task 执行者，我希望取得本次输出要求并登记真实文件，以便不需要新增 Task 统一静态接口。
29. 作为接替后的当前 chief，我希望从持久报告读取陌生文件并呈现真实内容，以便不依赖原会话记忆。
30. 作为用户，我希望报告保存与通知分别反馈，以便通知失败不会触发重复业务或丢失结果。
31. 作为流程使用者，我希望 Run 使用启动时的 Map 副本，以便原定义变化不改变本次图和规则。
32. 作为流程使用者，我希望 retry 沿用本 Run 副本，而新 Run 使用最新定义，以便两种行为清晰可预测。
33. 作为流程使用者，我希望副本缺失或损坏明确报错，以便不以当前定义冒充历史。
34. 作为用户，我希望删除原 Map 不连带删除 Run 历史，以便定义维护不会隐式丢失运行记录。
35. 作为用户，我希望在现有 scheduler 编辑新规则、在 workflow 查看冻结图和实际成果，以便不用学习另一套结果管理页面。
36. 作为维护者，我希望通用角色说明与消息装配集中维护，以便根/子管理者和 chief 路径不各自维护冲突正文。
37. 作为维护者，我希望 OMP/Pi 共享业务权威而保留既有宿主机制，以便不用维护两套流程政策。
38. 作为用户，我希望「创建map」仍保留概要规划、转换、整图优化三个阶段，以便知识重分配不降低交接门槛。
39. 作为用户，我希望通过本次 Run 说明提供创建需求并在界面查看最终配置，以便不新增 materials 字段或公开文件接口。
40. 作为概要规划者，我希望能力缺口以明确需求交回用户另行衔接，以便不自动执行能力建设或原始业务。
41. 作为转换者，我希望只有经确认且满足转换条件的方案才能正式交接，以便不把中间草案当成可执行方案。
42. 作为整图优化者，我希望先列出共享对象的其他消费者并确认修改范围，以便不静默影响独立 Task 或其他流程。
43. 作为用户，我希望能明确调整默认保存与检查建议，以便不被额外提示词门槛阻塞，同时仍遵守代码约束并获知未检查项。
44. 作为维护者，我希望业务文档与 Map 靠近且只有一个正文来源，以便独立 Task 与节点读取相同标准。
45. 作为用户，我希望从 Markdown 迁移清单逐项选择迁移或废弃，以便不默认全量迁移或删除。
46. 作为用户，我希望清单区分未开始、迁移完成和废弃，以便转换未完或未经确认时不被标作完成。
47. 作为维护者，我希望共享 Task、Suite、脚本和资料原位维护，以便不形成多套长期副本。
48. 作为用户，我希望旧 Map/Bot 离开在线读取范围并保留稳定身份后逐项迁回，以便无需新旧格式兼容。
49. 作为用户，我希望仅在确认迁移完成后删除对应旧副本，以便未处理和废弃数据不会被顺带删除。
50. 作为用户，我希望切换前核实在途执行与实际效果，以便不把暂停或服务退出误作脚本停止和业务回滚。
51. 作为用户，我希望旧 Run 完整离线归档，以便保留原始记录而不要求新版接续旧流程。
52. 作为用户，我希望清理 chief 运行记录时保留所有 Chat 历史、原生对话、zone 和业务产物，以便不误删需要的数据。
53. 作为用户，我希望第一条流程迁移完成即可测试，以便不等待全部存量流程转换。
54. 作为后续 Agent，我希望直接消费已确认正文和迁移方法，以便不在开发中临时决定业务语义。
55. 作为用户，我希望系统机制检查与实际业务运行验收分开，以便不把静态检查或受控测试当作模型业务质量证明。
56. 作为用户，我希望本次只发布 spec，并由后续步骤选择 seams 和批准 promises，以便不擅自开始实施或数据切换。

## Implementation Decisions

### 1. 范围、知识归属与既有架构

- 本规格汇总已确认的结构、调用、提示词、迁移与切换决策，不创建新的业务政策。后端 scheduler、Run/workflow、chief 委派与报告、Chat 消息装配、现有前端、my-agent-toolkit 的 workflow-chat 扩展、相关定义读写脚本及文档均在接入范围内；不能只修改顶层 schema。
- Bot 是能力索引；Task、script、Map 是真实实现。索引文案不注入执行 Chat，也不成为执行者必须读取的补漏资料；实际目标引用仍用于运行解析。实现独立完整，不新增 Task 输入 guide 或 Task/script 统一静态输入输出声明。
- 能力摘要与实现接口是不同维度，允许必要概述；详细标准只维护一个权威。旧 plan_guide/node_guide 的有效信息分别归入能力摘要、实现资料、本次委托或公共规则，不能整段改名或直接丢弃。
- node.input 表达本次业务目标、范围、材料用途、特殊限制和本流程适用的条件式业务指引；Task 独立使用也必需的稳定知识归 Task/实现资料。材料来源、依赖、位置和成果策略归结构化字段。
- 节点执行者负责业务执行及成果检查。管理者只根据运行状态、批准、报告和声明成果办理通用交接，不加载每张 Map 专属验收规则。Map.description 仅描述用途，不自动注入执行上下文；不新增 manager_rule。
- 保留现有执行引擎、真实身份关联、成果批准、通知、恢复和文件协调机制。普通 Task 的节点角色来自实际 execution，结束节点保持例外；可信 TypeScript/Bun 脚本不伪造 Chat，也不改成另一类宿主。
- 本节记载既定模块与公开接口决定，不据此选择新增测试 seam、promise 编号或覆盖矩阵；这些留给 /to-contract。

### 2. Bot 静态定义

| 字段 | 已确认规则 |
| --- | --- |
| id、name | 必需字符串；保留稳定身份和显示名称 |
| group | 可选字符串或 null；省略/null 为未分组；沿用分组校验 |
| when | 必需字符串，可为空；发现与适用性 |
| description | 必需字符串，可为空；能力职责、边界及影响规划的特征 |
| input_rule | 必需字符串，可为空；规划用输入摘要，不是文件绑定或机器校验 |
| output_rule | 必需字符串，可为空；规划用输出摘要，不是完成事实 |
| task_id、script、map_file | 各自可省略/null；非 null 目标互斥，也可全部缺省以保存不可运行草稿 |

Task 目标仍为 normal Task；script 仍是脚本根下安全的相对 TypeScript 路径；Map 仍以确切文件名引用。保留未知字段拒绝、路径安全及现有目标检查；不新增 type、版本字段、嵌套实现对象或旧字段别名。删除 plan_guide/node_guide，不能同时维护新旧格式。

完整 Bot 的 description 按固定顺序编写：能力职责必写；能力边界、用户参与、操作效果、特殊前提按影响选用的需要出现。不保留空标题或用“无”填充，不重复 when 或输入输出，不讲内部步骤。该格式属于编写指引，后端不解析 Markdown 标题，不阻止空字符串草稿。

### 3. Map 与 node 静态定义

- Map 保留 title、description、group、nodes；仍以文件名引用，不增加 Map ID、schema_version 或默认 Bot 绑定。
- 移除顶层 input_requirements/input_files，分别归入 map_input_rule.description/files；新增 map_output_rule。两个规则对象均可整体省略。
- 每个规则对象内 description 省略视为空字符串，files 省略视为空数组。文件项 id 必填、非空、在所属接口内唯一，逐项 description 可省略为空。输入文件必须显式给出布尔 required；输出文件不设 required，声明即必交。输入和输出的 ID 命名空间独立。
- 不以 null 代替规则对象、字符串或数组；拒绝未知字段。总体说明只承接跨文件或非文件要求，逐文件要求不重复。说明供人/Agent 阅读，不自动转换为业务校验程序。
- 公开结构化成果首版仍仅为文件。允许仅有输出说明而没有文件，也允许完全省略输出规则；操作结果或交给用户继续的 Chat 不强制包装为文件。
- node 保留 title、bot_id、input、zone、blocked_by，以及既有 manager_task_id、input_rule、output_rule、auto_approved、auto_close、end_node。input 可为空；input_rule/output_rule 默认空数组；auto_approved 默认 true，auto_close/end_node 默认 false；manager_task_id 可省略/null，适用要求不变。
- zone 保留固定 zone ID 或严格的动态 zone 对象。input_rule 保留 file/node/run 三类来源及现有字段；output_rule 保留仅声明 id 的数组。沿用路径、ID、引用、图、执行目标与策略校验，不因材料引用自动补 blocked_by。
- 父 node 输入与子 Map 输入按同名 ID 对接；父输出要求只能是子 Map 公开输出的同名子集，要求未声明 ID 时拒绝。下游仍可用现有 input_rule 绑定本地 ID，不新增跨层别名或内部 node 导出映射。
- Map 静态规则使用 *_rule；map_input/map_output 留给运行实际值。保留 when、description、node.input 等已确认名称，不做无关改名。

### 4. 本次输入与消息供给

- Run 的 userInput/fileInputs 归整为 mapInput.runInput 与 mapInput.files；实际文件为 id/path 绑定。inputsReady 独立保留，不新增原始业务要求编辑功能。
- HTTP 与运行持久 JSON 继续 camelCase；静态定义及工具相应参数沿用既有 snake_case 约定。不机械改名所有操作参数：prepare_inputs 的文件绑定整批替换语义和现有适用参数名保留，只适配新存储位置。
- 必需材料齐备是确认输入就绪、派发业务节点的条件，不是启动管理者 Chat 的条件。直接启动、嵌套和 chief Map 委派对齐此规则；已提供的非法或不可读材料仍拒绝。
- prepare_inputs 可保存未就绪绑定；文件列表是整批替换，不是追加，遗漏移除原绑定，空列表清空。已派发 execution 的实际输入继续冻结，不随后续 Run 文件绑定变化。
- 普通 Chat 节点分段取得完整 Run 背景与自身 node.input，不把背景写回定义；独立 Task 保持自己的固定设定、初始 Skill、环境与自由用户输入，不强加流程协议。结束节点保持精简上下文和无普通节点报告角色。
- 不新增语义冲突检测、提示词优先级、强制澄清或授权推断；指令一致性由用户保证，既有机械身份、路径、状态与授权校验不取消。
- 脚本沿用原业务参数与命名材料，不增加 Run 背景，不要求理解自然语言，不扩大模板替换范围。

### 5. Run 副本、公开成果与显式结束

- 新 Run 启动时，在管理者开始执行前保存本次校验通过的完整 Map 为 Run 目录内不可变的 map.json。原文件名只保留为来源身份，不再作为本次执行定义入口。
- 管理者取得副本绝对路径；派发、retry、依赖判断、输入准备、finish 校验以及 workflow 图/定义展示统一消费同一副本。副本缺失或损坏明确报错，不静默回退。
- retry 使用原副本；新 Run 才读取最新原定义。子 Run 启动时冻结自己的 Map，不在父 Run 启动时递归冻结子图。
- 只冻结 Map，不冻结 Bot、Task、script、Skill、引用资料、实际文件内容或 Task 会话环境。引用仍可能改变或失效，不承诺完整环境可复现。
- 在既有 run 工具 finish 动作增加 map_output.files；HTTP 和 Run 持久结果使用 mapOutput.files。身份由真实 Session/Run 关联确定，不接受模型自行指定其他 Run。
- finish 一次提交完整公开文件列表，检查重复 ID、未声明 ID、所有必交项及文件路径合法可读。无公开文件声明时可省略列表，不制造空业务文件。
- 原有节点完成条件和结束节点例外继续适用。校验通过后保存公开成果并结束；校验失败不返回成功，不结束。保留既有持久化失败和部分效果表达，不宣称新增跨文件事务。
- 再次 finish 不改写已经结束 Run 的首次成果。没有分批登记、提前登记、自动报告、自动重试、回滚或新验收状态机。
- 结束节点成功发起 Chat 后交给用户继续，Map 仍由管理者显式 finish。所有公开必交文件须在 finish 前齐备；不能依赖结束节点未来的用户对话补交。

### 6. 父子 Run 交接与中途报告

- 子 Run 保存全部已声明公开成果；父 execution 只取得自身冻结 outputRule 要求的同名子集，不扩大父层输出。
- 正式父节点报告的文件地址由后端从已完成子 Run 的 mapOutput 取得。子管理者不重复填写地址，也不能通过报告覆盖公开成果；内部输出名与公开输出名不必相同，公开路径由本次 finish 登记。
- 子 Run finish、父 execution 成果批准、报告保存/通知、父管理者 complete 是不同动作。自动取得绑定不自动批准、报告、完成父节点或派发下游。
- 子 Run 未 finish 时可发 can_complete=false 的中途报告，不要求附文件，不新增临时 Map 文件登记接口。普通 Task 节点仍以 outputs 登记文件；正常成果批准后再报告，进度、问题、失败可直接报告。
- 文件存在和机械门禁通过不证明业务质量；业务检查由执行者承担，管理者办理通用交接，不引入独立的整图业务验收职责。

### 7. chief 委派与结构化报告

- chief 继续只直接委派 Task/Map，不增加 script 分支，不统一成父节点生命周期。保留能力发现、按需读取实现、原生预览/确认、变化核对及异步返回机制。
- 委派增加可选 output_rule，形状与 node 输出声明相同，省略为空；HTTP/持久记录使用 outputRule。要求随原委派保存，不依赖 chief 记忆，也不是 Bot 的文字 output_rule。
- Task 执行 Chat 接收本次要求，在报告中提交 id/path 结构化 outputs。成功交付须齐全且合法可读；失败/受阻可保留实际部分成果，中途情况不强制附文件。
- Map 委派要求只能取公开输出的同名子集；正式文件交付取自已完成 Run，不重复输入地址。Map 自身声明的全部成果仍须交齐，不能因 chief 只取子集而省略。
- 未结束 Map 可以无结构化文件报告失败/受阻，不等待 mapOutput，不为报告强行 finish。不对所有 chief success 报告新增通用 finish 门禁；需要交付 Map 公开文件时，才以已完成 Run 的成果为文件交付前提。chief_report 保留原结果分类，不新增 can_complete 或进度枚举。
- 保留报告原有 background、execution、result、summary、deliverables、pendingDecisions 等说明，新增结构化 outputs；不解析文字 deliverables 作为文件校验来源。
- 报告先持久保存，再向当前合法 chief 尝试通知，保留既有接收确认和权限。通知失败不撤销结果，不自动重投或重做业务；显式重发沿用既有确认机制。
- 新 chief 可读取陌生报告中的真实路径，按内容呈现，不按 ID 猜含义，不要求记得原委派或预先声明同名 ID。持久路径不等于文件副本或永久可读保证。
- 删除提示词中硬编码的能力创建入口选择策略；存在缺口由用户决定下一步，不自动建设能力或继续原业务。

### 8. 后端提示词与工具包接入

- 已明确的组织决定是扩展现有 prompts 模块，集中词典、消息组合、运行事实格式化和角色静态说明。将 Run 启动、chief 委派和 Chat 发起中的对应拼接迁入，不能只加转发入口而继续散放正文。
- 调用方提供已核实角色和事实；模块负责通用流程说明、格式及组合顺序。身份判定、状态准入、文件绑定解析、Chat 启动不迁入提示词模块。
- 后端提供基本流程说明与本次运行事实，extension 提供工具调用提示；根/子管理者复用正文，manager 与独立 chief-report 两条路径共享 chief 报告指引，OMP/Pi 使用同一业务权威。
- 角色正文、工具 description、参数 description、初始化片段和动态 guidance 均使用联合提示词权威的最终正文，不只修改可见的初始化文件。共享工具存在不等于两条路径已共享正文，必须落实加载。
- 保留原角色装配、结束节点例外、恢复关联、原生批准、初始 Skill 组合与词典语义。每条消息使用同一词典快照，只替换明确类型的定义字段，不替换用户输入、文件路径或报告。
- node.input 中条件式文档指引沿用现有 NodeInput 渲染后供节点按需读取，不在后端展开业务文档，不改写 Map 副本，不向管理者注入 Map.description 或专属文档入口。
- 静态通用正文可编译嵌入，不增加运行时部署文件依赖、模板引擎、可插拔角色框架或另一套提示词入口。已批准正文之外的新业务语义须交回用户确认。

### 9. 已选「创建map」流程

- 保留概要规划、概要方案转 Map、整图优化三阶段及现有节点身份、拓扑、Bot 绑定、zone、批准与自动关闭设置。四个相关 Bot 采用已确认 when/description/input_rule/output_rule 正文，三个业务 Task 采用已确认完整 prompt，保留其 agent、model、Suite、初始 Skill 等非目标设置。
- 本次业务输入只用 runInput；参考材料可在其中说明路径与用途，不新增专门 materials 字段。删除旧 input_requirements，省略整个 map_input_rule/map_output_rule；最终配置通过界面查看，不要求公开文件成果。
- 内部材料不删除：概要规划输出 outline；转换消费 outline、输出 map；优化消费 outline/map、输出 map/handoff。最终内部 Map 文件须与优化后实际配置一致。
- 概要规划和转换节点使用最终批准的条件式交接文档指引，不能恢复早期空 input 候选。优化节点保留获准修改范围和共享对象需用户确认的要求，并读取本阶段交接标准。
- 业务文档随 Map 维护，独立 Task 与流程节点共用同一权威。迁移完整正文及所有 Markdown 链接和裸路径引用，不留下旧正文副本或兼容跳转。系统定义、接口、部署和测试说明继续归系统文档。
- 概要方案必须自包含，记录身份/修订/确认范围、目标边界、工作、真实能力选择、依赖与材料、执行条件、证据未决项和转换权限。业务绑定、材料、位置、权限及 Map 型调用管理者配置满足转换条件才正式交接；仅缺外层根 Run 启动配置可列待配置，不能沿用规划 Run 的配置。
- 能力缺口按已确认业务文档交付独立需求和稳定缺口身份，由用户另行衔接；草案和待补能力方案是中间材料，不降低交接门槛。转换者读取真实实现，不展开子图内部节点，不补建能力、不启动生成的业务。
- 优化保持已确认业务语义、身份、名称、分组、目标、拓扑、接口 ID、必需性、接线和执行配置。共享修改先列其他消费者并确认范围；超出授权或改变业务语义返回用户。
- 默认避免覆盖、写前查看、写后读回；用户可明确调整保存方式、覆盖、冲突处理及检查范围，不重复索取同一授权。代码校验、并发控制与如实反馈不因调整而取消；省略检查不表示检查通过。
- 各阶段业务检查由对应节点执行，管理者不再次验收本流程专属标准。「创建map」只交付配置创建与优化，不启动生成的业务流程。

### 10. 既有界面与所有消费者

- Bot 编辑与读取采用新四字段；scheduler 编辑 Map 的新静态规则，发起表单保留本次说明与文件绑定交互。workflow 展示冻结 Map、实际输入和公开输出，不新增页面端登记/finish 按钮或结果管理页面。
- 删除原 Map 时移除“连带删除 Run 历史”选项、deleteHistory 请求参数和相应分支。已有 Run 及副本保留，列表使用已保存信息；失效引用沿既有错误机制反馈。不取消其他独立 Run 删除能力。
- 同步后端与前端类型、验证、存储、公开请求/响应、工具 schema/预览/确认、定义创建修订脚本与材料消费者、示例和系统说明。清除旧字段和错误协议文案，不保留兼容别名。
- 创建/修订消费者读取旧 Bot 指南的实现必须适配新结构；这不授权自动决定其所属存量流程的业务迁移答案。发现未确认语义时按单流程方法回到用户，不以临时提示词补齐。
- 更新产品领域词汇中仍描述旧 Bot 指南、Map 输入和输出的部分，保留 Task、Chat、Run、zone 等既有区分。与既有 ADR 的关系见 Further Notes；不重构 Herdr App/core。

### 11. 选择性迁移清单与共享维护

- 新增 Markdown 清单，以实际服务配置定位的 Map 为入口，记录稳定身份、来源、用途、关联 Bot/Task/子 Map/script/Skill/文档、共享其他消费者、转换产物、待补项与用户实际运行结果。不是新增产品界面或持久化模型。
- 清单只使用“未开始／迁移完成／废弃”。未完整转换、存在待补项或未经用户确认仍为“未开始”，详情放备注，不新增迁移中、暂缓或待复验状态。
- “迁移完成”是当前 Map 及必要关联定义完成转换、待补解决并经用户确认，不要求实际运行已通过。“废弃”须由用户决定，仅表示不再迁移，不授权删除数据或共享依赖；未处理不等于废弃。
- 不把未关联 Task 列为独立迁移项，不默认迁移全部 Map。其他消费者须列明，但不成为当前流程的额外迁移或验收门槛；用户把关共享变化对已迁移流程的影响。
- 格式未变的 Task、Suite、脚本、Skill 和引用资料原位维护，必要提示词直接改共享原件；不长期维护多套副本。Git 承担修改历史，不建立额外变更流水。
- 复用已有单流程会话方法：选择对象、调查真实依赖和信息可达性、联合 grilling、发布已确认正文、按授权转换和交付。其他流程不照搬「创建map」业务答案，不预先穷举所有边界或承诺一会话必能完成。

### 12. 一次停机切换与历史边界

- 切换前按实际服务配置定位在线定义、Run、chief 和 Chat 存储；停止相关执行并核实在途工作及外部效果，再停服务、处理数据、更新后端/前端/工具包和所需定义。暂停不取消脚本，后端退出不证明外部效果结束，managed=false 不代表成功、失败或进程已停止。
- 旧 Map/Bot 一次性移至在线定义读取范围外的 backup，不在系统列表显示，不自动回退。转换后写入正式目录，保留 Bot ID、Map 文件名和图内引用身份；稳定引用不等于业务验证通过。
- 用户确认迁移完成后可删除该 Map/Bot 的 backup 旧副本，不能删除正式新定义。共享 Bot 完成迁移后不必等待所有消费者再移除其旧副本。未处理项和明确废弃部分不自动删除。
- 旧 Run 完整目录移至在线 Run 范围外，保留原始记录供离线查看；不直接删除，不迁回新版列表，不用当前定义补造副本或公开成果，不要求新版读取/展示/继续旧 Run。
- 清理 chief 身份账本、委派、报告和接收确认；无需归档这些 chief 运行记录。保留全部 Chat 历史目录与 agent 原生对话，包括 chief Chat，同时保留实际产出文件、zone 和无关数据，禁止整目录清理业务数据根。
- chief 原生对话可以保留，之后通过现有恢复/登记建立当前身份；旧委派和报告职责不延续。保留 Chat 不承诺恢复旧 Run 的角色、管理权或交接能力。
- 新版从新的在线 Run 集合开始，不接续旧 Run。需要继续旧业务时先核实已有结果，再按新定义重新发起，不通过恢复旧 Chat 实现跨版本 Run 接管。
- 不做热切换、新旧混跑、自动启动迁移或兼容回退。首条流程迁移完成后即可测试，无需等待全部迁移，不依据 Markdown 清单增加运行门禁。

## Testing Decisions

- 复用现有后端集成测试、前端交互测试和真实浏览器验收层级，以及独立 herdr-bot-tester 的原生接入设施；本轮不创建通用自动跑业务流程平台，不以静态 schema 检查替代真实持久化/公开交互，也不把原有分层验收一律降级。
- 已定位的先例包括独立 Chat 发起、workflow_start、命名输入与派发、输入准备、普通节点批准、nested_completion、end_node、TypeScript 脚本、chief 委派/报告/接收确认、scheduler 编辑删除与 workflow 展示。它们是复用线索，不是本 spec 已选定的 seams 或完整覆盖承诺。
- 脚本的既有验证使用隔离环境中的真实 Map 派发、Bun、HTTP 与实际文件，核实保存、revision、交接和部分效果；不以直接调用脚本函数冒充整个执行链路。不因此要求迁移所有脚本所属业务流程。
- 新旧静态字段、Run 副本、公开成果、父子交接和 chief 输出的具体 promise、测试接缝及覆盖分配由 /to-contract 决定；具体命令由实施按实际改动与项目测试指引选择。本规格不新建验收层或预先编号测试合同。
- 测试使用隔离数据、独占进程/端口/会话/构建目录，不对生产数据做破坏性验收；关机相关验证沿用安全壳，真实模型、外网、凭据及已有用户会话授权分别成立。受控 provider 证明机制，不证明真实模型自主选择或业务质量。
- 持久保存、文件可读、批准、报告、通知、显式 complete/finish 与用户业务验收分别取证；不能用通知成功证明已读、用文件存在证明质量，或用省略/过滤的检查补齐未覆盖项。
- TDD 直接使用已批准提示词和结构决策；发现遗漏向用户报告，不能临时生成业务规则来让测试通过。测试不为未批准语义制造隐含要求。
- 每条实际业务流程的开发后全流程运行验证由用户执行；“迁移完成”不要求这一结果已通过。这不取消系统代码适用的既有自动化检查，也不把缺失的既定机制验收转成用户签收。
- 独立转换试验已经确认取消；现有样例仅参考，不补做重复审批，不把其静态检查算作业务验收。
- 本次 spec 发布只做文档结构与本地引用检查，未运行产品测试、真实服务、Chat、Run 或业务流程。
