## 2. 高：优先核实并修复浏览器测试的类型检查接线

**事实：** 本轮新建的浏览器测试曾显式使用 `result: any` 和 `Awaited<ReturnType<typeof scenario>>`，依赖写入后的风格提醒才修正。早期还将公开 Run 详情误写为 `detail.snapshot`，实际接口返回 `detail.run`，直到浏览器执行才暴露。修正后最终六个测试在完整浏览器运行中全部通过。

**事实：** 本轮读取的 `frontend/package.json` 中，`build` 包含 `tsc --noEmit && vite build`，浏览器入口使用 Playwright。可见过程没有核实浏览器测试是否属于该 TypeScript 项目的检查范围，也没有查看 CI 或提交钩子。因此不能断言仓库没有现成 guardrail，或断言现有类型检查必然漏检该目录。

**建议：** 将“浏览器测试是否受类型检查”作为优先核查项：先检查 `tsconfig` 的文件集合及已有 CI/钩子接线，再决定补接现有检查还是增加独立测试 TypeScript 项目。若项目已经有相应 lint 规则，将显式 `any` 等固定语法约束交给确定性检查；不要再增加一份自然语言禁令。

对于公开 HTTP 响应，可在现有测试支撑层使用命名响应类型，或在消费处进行轻量结构校验，使错误的字段访问更早暴露。仅增加 `tsc` 并不足够：若 `response.json()` 仍将 `any` 传播到所有消费者，`detail.snapshot` 仍可能绕过检查。

**完成标准：** 对浏览器测试临时引入显式 `any` 或错误详情字段访问时，既有检查入口能够确定性报错；若暂不具备这一能力，应清楚记录当前检查边界，而不把 Playwright 转译成功视为类型安全。

**完成标准：** 正常检查结果可用少量摘要判断；遇到覆盖空洞或服务不可用时，代理能直接选择可靠替代路径，且不会把失败伪装成负面证据。
