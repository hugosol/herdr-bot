# Ticket 05：TDD 执行复盘建议

## 证据范围与结论

本复盘只使用当前可见的 ticket 05 执行对话及其工具结果，不引用父 session 或其他票据的执行情况。未另行读取宿主指定的 JSONL，因此不对当前对话之外的历史作判断。

**已观察事实：**本票新增 8 个场景，最终定向浏览器验收全部通过；时间分区检查及文档链接检查通过；提交为 `8c9031b`。生产逻辑未修改。首次构建因缺少 `tsc` 失败，安装本 worktree 的前端依赖后恢复。

主要改进机会是：让“已有行为的验收覆盖”和“修复缺陷的红绿循环”更明确地分流，减少导航及工具输出开销，并收紧运行文档中的验收记录。

## 1. 中：给“已有行为”分支增加明确的 TDD 门槛

### 事实

首次创建测试文件时，一次加入了新派发场景及两个参数化 retry 场景，然后统一运行。后续 P18、P19 切片分别添加、执行，最后运行全部 8 个场景。

行为断言首次执行均通过；缺少 `tsc` 的失败被正确归类为环境失败，没有当作行为 RED。最终报告也明确说明现有生产行为已满足要求，没有制造人为失败。

TDD 指导允许已有行为直接取得验证证据，但执行记录没有在首个测试批次前清楚区分：哪些行为已经通过代码阅读确认存在，哪些仍需要 RED 来定位缺陷。

### 推断

这里不应以“没有红灯”判定 TDD 失败。更实际的风险是：若只看到新增测试全部通过，后续执行者可能把“现状已满足”当作默认解释，跳过对测试是否能识别指定违例的检查。首批同时加入 dispatch 与 retry 两个不同入口，也弱化了单切片带来的反馈。

### 建议

在现有 TDD 技能的“criterion already satisfied”分支旁，补一个局部完成条件，而不是另建文档或给实现代理增加全局规则：

> **已有行为：**先注明已存在的行为路径及证据，再为当前一个入口补覆盖。绿色后说明指定违例会被哪项观察识别；只有无法通过检查确定敏感性时，才做定向故障注入。

将新派发与独立 retry 作为两个顺序切片；同一入口的双向配置可保留参数化。此建议属于执行判断，适合放在 TDD 技能中，不适合用机械 lint 强制。

**完成标准：**后续记录能清楚区分环境失败、行为 RED、已有行为 GREEN，并能指出绿色测试对应的具体违例检测点。

## 2. 中：为 workflow 生命周期验收提供一条分支导航指针

### 事实

本次探索读取了测试政策、领域词汇、相关 ADR，并在后端 workflow 测试、浏览器 node settings、Chat resume、workflow restart 和共享支撑设施之间寻找可复用模式。

已有 `AGENTS.md` 很短，主要承担导航职责，未出现需要拆分的大型全局规则正文。真正复用到的浏览器能力集中在 `frontend/browser-tests/support.ts`：隔离服务进程、命令记录、重启和资源清理。

### 推断

探索范围的一部分是完整验收要求决定的，不能全归为浪费；但“哪些公开入口与现成夹具能完成恢复、刷新和重启证据”缺少一个紧凑索引，导致多处示例被逐个打开。

### 建议

优先在现有 `docs/agents/testing.md` 增加一条分支导航，不扩充根 `AGENTS.md`：

> **Workflow 生命周期：**验证派发／retry、Chat Resume、页面刷新或服务重启时，先查浏览器 `support.ts` 的隔离与命令记录能力，再按入口查对应现有场景。

指针旁只列少量代表性文件及各自覆盖的入口；保留夹具 API、启动命令和字段形状在代码中的单一事实源。避免把本票的完整验收说明复制进导航文档。

**完成标准：**后续执行者能从测试政策一次定位共享夹具和入口示例，而不是先扫描整组 workflow／resume 文件。

## 3. 中：改进图索引定位与空结果后的回退路径

### 事实

本次先后调用项目列表两次，第一次返回 10 项，第二次返回 60 项才定位到 `herdr-bot`。随后对 `nodeSettings.spec.ts`、`resume.rs` 请求声明大纲，结果均为 0；同一批中的 `support.ts` 则返回了有效大纲。这些文件随后通过直接读取取得了内容。

描述式 `find` 还因区域限制而全部判定请求失败。工具输出已明确说明这不是不存在的证据，执行者随后改用其他入口，没有将失败当成文件缺失。

### 推断

图大纲为空的确切原因未验证，不能直接认定索引损坏或项目选错。不过，当前项目识别与覆盖状态没有在首次查询时解决，给探索增加了往返。

### 建议

由工具环境提供当前 worktree 对应的项目标识与覆盖状态；精确文件大纲为空时，返回明确的覆盖提示和直接读取建议。项目列表默认保留精简身份输出，并支持按根路径匹配，避免为了找到一个项目加载全部项目。

对于描述式 `find` 的区域不可用响应，保留一次明确诊断后直接引导可用的文件名／文字搜索入口，不重复消耗同一路径的判定请求。

**未验证项：**本次没有检查索引新鲜度，也没有确认 `find` 的区域失败是否为长期环境限制。

## 4. 低：让浏览器分区检查默认输出摘要，完整清单按需取用

### 事实

`npm --prefix frontend run test:browser:partition` 成功，但输出包含 full、fast、time 三份完整 manifest。后台结果显示原始输出达 8,394 行，发生了大段省略；实际交付报告只需要 `340 / 290 / 50` 的数量和分区结论。

### 建议

调整现有分区检查的输出层次，而不是新增检查：

- 默认输出数量、交集／遗漏检查结果和退出状态。
- 失败时输出相关差异项。
- 完整 manifest 通过显式详细模式或产物路径提供。

该建议保持现有验证范围与确定性，只减少成功路径的上下文负担。

**完成标准：**成功输出在一个短屏内可读；需要定位差异时仍能取得完整、稳定的清单。

## 5. 低：在独立 worktree 交付前处理依赖前提

### 事实

首次 `test:browser:build` 在 TypeScript 构建阶段因找不到 `tsc` 退出。随后执行 `npm --prefix frontend ci --ignore-scripts`，再运行同一入口，构建和测试成功。

仓库测试政策已经说明需要安装依赖，因此这不是缺少测试命令，也不能据此认定现有检查失效。

### 建议

将依赖准备放在 worktree 初始化或任务启动前提中，确保“可运行验收”与“新目录已创建”分开确认。若宿主不负责安装，则在首次验收前给出明确的依赖就绪诊断，避免用正式验收运行发现缺包。

本次只证明安装依赖后问题解除；是否应固定使用 `--ignore-scripts`，仍需按项目依赖约定决定，不能从这一轮成功推导为通用规则。

## 6. 低：运行文档只保留生命周期差异与证据边界

### 事实

本票向 `docs/workflow-runtime.md` 追加两段说明，包含生命周期语义、测试文件路径、具体运行命令、300 ms 观察窗口、gate 中断方式和受控 Herdr 证据边界。其前文已经说明 dispatch／retry 固定设置、恢复沿用执行、读取不触发关闭、不补偿等规则。

### 推断

其中部分新增内容是对已有业务规则的重复，命令和观察窗口又能直接从脚本与测试常量取得。它们会增加后续修改时需要同步维护的位置。

### 建议

将新增说明收敛为一条测试导航和必要的语义差异：

- 新派发／retry 采用当前 Map；Chat 恢复沿用原执行。
- 中断关闭后的重启没有补偿义务。
- 受控命令记录不等于真实 Herdr 外部效果；负向证据仅覆盖测试声明的观察窗口。

精确窗口、gate 参数及可执行命令留在测试和脚本中。运行文档不承载本轮通过结果，执行结果由宿主保存的验收记录承担。

## 暂不建议增加的规则

- **不新增关闭重试、补偿队列或结果字段。**本票的受控中断场景正是在验证这些行为不被引入。
- **不要求为了 RED 而改坏已满足的生产行为。**已有行为分支应提高证据清晰度，而不是制造失败仪式。
- **不据此认定仓库缺少 CI 或提交钩子。**本次对话读取了 `package.json` 和测试入口，但没有检查 CI／hook 配置，无法确认是否存在未接线的检查。
- **不新增 reviewer 风格禁令。**本次没有独立 reviewer 的执行记录，也没有观察到需要靠新增判断型编码标准处理的问题。机械规则若日后有明确证据，应优先接入确定性检查。

## 优先顺序

先明确 TDD 的已有行为分支和切片门槛，再补生命周期导航；工具侧优先压缩分区检查输出并改善索引空结果提示。依赖准备和运行文档去重作为低成本后续改进。本轮仅提出建议，未修改文件、配置、技能或代理指令，也未重跑验收。
