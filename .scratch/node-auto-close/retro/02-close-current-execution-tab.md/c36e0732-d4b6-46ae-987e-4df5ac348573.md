本次仅依据当前可见的 **02-close-current-execution-tab.md 实现轮对话及工具结果**，不引用父 session 或其他票据的执行表现。writing-for-agents 指导已由宿主加载；本轮不修改文件、不执行建议、不重跑验收。

## 1. 高：让完整后端验收入口在派发测试前检查交付产物前置条件

**事实**

- `docs/agents/testing.md` 将 `node scripts/test-backend.mjs` 列为完整后端回归和提交前检查入口。
- 本轮首次运行该入口，完成构建并执行多个测试目标后，`herdr_config` 才因当前 worktree 缺少 `backend/static/index.html` 失败；40 个 binary 未派发，doctest 未执行。该次耗时约 60 秒。
- 安装前端依赖、执行 `npm --prefix frontend run build` 后，完整后端入口重新执行并通过，耗时约 112 秒。

**判断**

这是可机械判定的验收前置条件，不宜依赖实现 agent 从较晚的测试失败反推出准备步骤。现有测试已经能发现缺失，但发现位置晚，且完整入口的使用指引没有在对应分支明确这一依赖。

**建议**

优先在现有后端测试 runner 的派发前阶段检查所需交付产物，缺失时立即给出准备命令；若项目希望该入口自足，则由它负责调用既有前端构建入口。两种方案择一，不另建一套重复的测试流程。

在现有测试指引中只保留一条面向新 worktree 的导航说明，指向该准备行为；构建命令及细节继续由现有脚本拥有。

**建议的完成标准**

在没有 `backend/static/index.html` 的隔离 worktree 中，完整后端入口在任何测试 binary 启动前完成构建，或明确失败并说明所需准备；具备产物时保持现有完整回归语义。

**未验证**

本轮没有检查 CI 或 hooks 如何准备前端产物，不能据此断言 CI 同样存在该问题，或仓库没有验收 guardrail。

## 2. 中：明确图索引的 worktree 身份与降级路径

**事实**

- 本轮工具实际工作目录为临时 worktree `hyper-ticket-ga9jSz`；列出的 `herdr-bot` 图项目指向主仓库路径。
- `get_file_outline` 对 completion 和 workflow 测试返回了声明，但与随后读取的当前源码结构、行号并不一致；对 operation、startup 和 Herdr adapter 则返回空结果，而这些文件可以直接读取。
- agent 后续依靠源码读取和 grep 继续完成了定位，没有把空图结果当成文件不存在。

**判断**

[推断] 查询的索引与当前 worktree 并非同一源码视图，或存在覆盖／刷新差异。现有结果足以证明导航证据不完整，但不足以确定唯一原因。继续逐文件请求 outline 会增加调用成本，并给错误导航留下机会。

**建议**

让图工具或任务启动上下文明确提供“当前 worktree → 对应索引项目”的绑定。图查询结果应携带足以判断根路径、快照和覆盖缺口的来源信息。

若暂不修改工具，在现有工具导航指导中增加一个分支：**worktree 身份不匹配或已知存在的文件返回空 outline 时，先核对项目根和覆盖信息，再决定建立当前 worktree 索引或直接使用源码工具。** 不要求每个文件重复试探同一个不匹配索引。

**建议的完成标准**

agent 能在首次查询前确认索引所属源码副本；遇到覆盖缺口后，后续定位有明确且可执行的降级路径。

## 3. 中：把描述性搜索服务不可用变成一次性、可降级的能力状态

**事实**

- 首次 `find` 的 26 个 judge 请求全部以 HTTP 451、区域不可用失败；没有候选完成判定。
- 工具明确提示这不是不存在的证据，并建议使用 grep。
- agent 按要求提交了工具问题记录，之后改用 grep 继续定位，没有反复调用同一失败路径。

**判断**

这是工具依赖不可用，不是搜索词不准确。单次搜索已经展开为多次必然失败的请求；agent 自己在本轮的降级处理合理。

**建议**

在 `find` 服务侧将区域拒绝等能力级错误作为本次调用的快速失败条件，停止继续展开 judge 请求；在会话工具状态中暴露可用性，让后续描述性定位直接选用可工作的工具。

保留“空结果”和“未完成判定”的明确区别，避免为了省调用而把服务失败伪装成无命中。不建议再向 AGENTS.md 增加一条要求 agent 手动记住服务故障的长期规则。

**建议的完成标准**

同类能力级拒绝只产生一次必要探测，并返回明确降级信息；搜索未判定的结果不会显示为不存在。

## 4. 中：为受控命令测试建立按业务阶段归属的断言模式

**事实**

- P15 测试初稿在关闭命令保持未返回时，成功观察到了 complete 返回和同 Run 下游派发。
- 测试随后失败，因为允许的外部命令集合遗漏了下游真实派发所需的 `workspace list`。
- agent 没有修改产品逻辑，而是分开核对“complete 自身只有精确的 tab close”和“下游派发保留正常命令”，修正后测试通过，并输出了释放前后事件顺序。

**判断**

初稿把不同业务阶段的命令混在同一个白名单里，造成无关实现细节影响验收。修正后的测试更准确地约束了承诺：完成路径不发 stop／不探测空闲，下游操作仍能正常推进。

**建议**

在现有测试示例或测试指导的外部交互分支中，采用本轮修正后的模式：**以观察点切分阶段，分别约束本动作的命令和后续动作的命令。** 这种测试设计需要判断，不适合做成针对命令名称的静态 lint，也无需为单一场景新建通用执行框架。

**建议的完成标准**

未来同类测试既能拒绝完成动作额外发送 stop 或探测命令，又不会因合法下游操作的正常命令集合而失败；非阻塞承诺仍由未释放屏障时的业务结果证明，而不是速度阈值。
