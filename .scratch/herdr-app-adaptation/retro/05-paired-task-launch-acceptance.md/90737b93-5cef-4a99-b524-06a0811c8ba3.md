**事实：** 普通 Task 启动四组合通过；但在 Herdr TUI 0.9.5 ＋ Pi 1.5.2 的三个模态格中，确认框已经可见，`herdr agent prompt` 仍返回成功，原生确认实际返回 `true`，后端随即显示已提交。原始回执记录了 `agent_status=idle` 和 `screen_detection_skipped=true`。App 同类场景实际拒绝，解除模态后在 5.125 秒重试；本地受控故障检查也通过。它们不能抵消 TUI 反例。

**建议：** 在现有测试指引的「配对 Task 发起」分支把**真实反例优先**写成步骤：构建当前产物后，先从打包页面发起一格真实 TUI 任务，保存同一 Pane 的模态画面、原始提交回执、确认回调和原生历史。完成门槛是：模态保持待答、宿主明确拒绝、无原生业务输入，然后才继续重试和全量验收。若发生误确认，保留失败证据并通知生产责任方；其余独立检查可继续，但该格保持失败。不要在验收探针中补发 `blocked` 来改变宿主行为。

**推断与边界：** 已读代码中，Toolkit 自身工具的确认会另发 `herdr:blocked`，而此次启动后出现的原生确认未走该包装层。这解释了可能的状态缺口，但未验证其他宿主版本、其他模态类型或生产修复方案。

**建议：** 复用现有命令，在配对入口的前置阶段验证锁定原生编译器可解析、所选浏览器能以独占 profile 启动、清理观察器能持有并等到所属进程退出。失败日志区分「依赖解析」「浏览器启动」「退出未确认」，不要等到业务格结束才暴露。已知 Windows 安装方式放在现有配对测试指引下，不增加常驻代理指令。
