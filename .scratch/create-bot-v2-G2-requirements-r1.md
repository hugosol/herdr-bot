## 2. 业务目标与输入

未来 Map「创建bot-V2」是 G1→G2 两个串行普通工作节点。G1 初始 grill-with-docs，只读核实已有目标并与用户对齐意图；G2 初始 writing-for-agents，依据需求决定内容归属与具体正文，经确认创建完整 Bot，Task 型另完成获准的 prompt 优化。没有空白创建、三路独立编写、独立优化或保存节点，也不嵌套旧创建bot。

### 2.1 G1→G2 共同接口

为避免独立建设 Chat 各自猜接口，双方按下列建议落实；必要变更须交回概要规划者确认，不单方切换：

- G1 输出 bot_requirements：自包含 UTF-8 Markdown「Bot 需求」。
- G2 通过同名输入 bot_requirements 直接消费该文件。
- 文件包含目标唯一身份、服务、拟建 Bot 命名、统一意图、职责／非目标、输入输出、验收、权限、资源、已有绑定和共享用途、确认依据、未决项及未验证项。
- 内含完整核实基线：Task／Map 的完整原始配置；Script 的准确相对定位、真实来源、完整原文及依赖事实。基线不是锁定快照，G2 必须重读比较。
- 文件明确未来 G2 的整体分层及创建委托；G1 只确认意图，不提前批准未知最终正文。
- 必要参考事实应完整纳入需求文档。追踪地址不能成为隐式必需输入；若有必须另传的材料，先明确额外输入／输出及映射并交回确认。不得通过同目录、固定文件名、报告或其他 Chat 发现未声明材料。
- 尚无 Bot，不存在创建后 revision；不得要求 G1 提供旧协议的空白 Bot baseline。

V2 对外仍为必需 request、可选 materials，最终 saved／handoff。request 是 JSON 委托，保留 requirements、constraints、non_goals、resource_limits、目标定位、可选 Bot 命名、真实授权与确认依据的职责；目标扩展为 Task／Map／Script，删除空白创建专属 create_blank／scope=create_blank 要求。精确表示需建设者明确交回，不改旧创建 v1 Schema，不声称旧校验器兼容。G2 不需要从原 request 隐式找参数，应完整消费 G1 的确认需求及显式材料。

### 2.2 目标核实

产品仓库：E:/Developer/myhub/herdr-bot；服务：http://127.0.0.1:18787。以当前契约、实际配置和服务返回为准，不从 cwd 推断存储位置。

- Task 型：真实存在的 normal Task，完整配置及 prompt、全部相关绑定、独立 Chat 用途与共享影响。
- Map 型：服务目录内确切 Map 文件名，完整定义、输入接口、节点目标、依赖、资源与交付；只读核实必要引用，不修改内部 Task 或节点。
- Script 型：实际 scripts 根下合法相对 .ts 路径，完整真实脚本及必要依赖／输入输出事实；只读，不 import 或执行脚本来探测行为，不编写／修改实现。

重读目标与 G1 基线比较。并发变化或职责冲突不能自动吸收成已批准的新基线；说明差异，重新核实受影响决定后再继续。Skill／文档以及真实脚本不可读时，不把其存在或名称当成已实现能力。

读取原始 Task.prompt、Bot 指南等模板字段时按当前初始化词典规则单次解析；保留原始配置供比较及保存。缺键报告字段与键，不猜测；交付材料和用户输入不插值。

## 3. 核心：先整体分层，再决定具体内容

### 3.1 必须参考的真实标准

完整读取服务中的「prompt优化者——Bot维度」：Bot bot-task-18e66273ae718d14-1，Task task-18e66273ae718d14-1，GET /api/tasks/task-18e66273ae718d14-1。

其 Task.prompt 是本能力分层设计的方法参考。建设时将适用原则落实为 G2 的稳定职责，不能只在 Bot 指南提及后假设执行 Chat 会获得它，也不能继承旧优化者「只处理既有 Task 型 Bot、禁止创建」的范围限制。原参考 Task 保持不变。

G2 不是先编写三指南，再附带整理 Task.prompt；不是把需求机械拆成三段，也不是逐份独立润色。先对整项能力的信息消费者、生效位置和到达路径作判断，再制定整体候选。

### 3.2 信息归属

| 承载位置 | 职责 |
| --- | --- |
| Skill | 可复用的方法 |
| Task.prompt | 稳定执行职责、步骤、适用分支、权限边界、缺项处理、阶段完成条件，兼容独立 Chat |
| Bot.when | 能力发现、关键结果、选用条件、易误选边界 |
| Bot.plan_guide | 影响工作划分、可行性、顺序、用户参与和交接的条件 |
| Bot.node_guide | 调用方本次须提供的目标、材料及用途、业务选择、权限、额外交付和验收 |
| 共享文档 | 共同业务契约、平台事实、操作参考 |

沿用 writing-for-agents：主流程保留共同步骤，分支细则用明确触发条件和可达章节指针承接；规则与例外集中，同一含义保留权威来源。但简化不能删除真实必要语义。

### 3.3 迁移与保持要求

- 三指南供规划者使用，不自动注入执行 Chat。执行所需约束必须由 Task.prompt、本次输入或明确可达的资料承接。
- 迁移／删除前核实承接已存在、消费者能取得、触发时机明确。不能把「应归 Skill」当成 Skill 已实现该内容。
- Skill／文档默认只读，必要修改须说明具体缺口并另获授权；无权修改或承接尚不可达，保留必要原约束，不为精简而丢失行为。
- 同一共享 Task 统筹优化，兼顾其他 Bot 绑定和独立 Chat。新共享影响须用户确认。
- 保留原需求、能力范围、权限、输入输出、验收与非目标；不以表达优化夹带新增能力。
- Task 型可将纯规划信息移入三指南，并保义调整 prompt；Map／Script 型只设计三指南，保持目标及其实现不变，不优化子 Map 内部文本。
- G1 已有效确认的意图沿用；具体歧义或新增取舍在 G2 当前 Chat 补问并记录，不重开完整访谈或自动增加返工节点。

## 4. 确认、创建及保存

### 4.1 整体候选

展示完整三指南、适用的完整 Task.prompt、归属调整说明和共享影响。记录原要求在最终配置／引用中的承接，不只给修改片段。确认业务意图、最终正文和保存授权；材料写入与 manual 报告批准另行成立。

V2 只新建 Bot，不修订已有 Bot。已有目标绑定须展示并由用户明确是否仍新建；服务不允许时报告限制。命名／ID 冲突不覆盖、随机改名或自动复用。无 Task.prompt 变化时明确说明，不做无意义 PUT。

### 4.2 保存前核实

先读 docs/scheduler.md 的定义、HTTP、revision 与路径边界；Task 型另读 docs/usage.md「仅修改 Task.prompt」；运行使用按 docs/workflow-runtime.md 核实。

- 全部候选、授权和必要联动条件齐备才写入。
- 重读完整目标、相关绑定及运行使用，与基线比较。Task API 无 Bot 式 revision，不能自造版本或声称跨进程锁。
- 当前执行者和本流程执行者配置不可修改；running／paused Run 所使用的禁写定义不可修改。暂停、节点已完成、Chat 空闲或历史未接管不自动解除禁写；无法可靠核实则阻塞，不操作运行状态绕过。
- 不直接覆盖底层 JSON 绕过合法接口或保护规则。

### 4.3 已确认保存顺序

1. 通过 Bot 合法创建接口，以 revision=null 新建三指南齐全、唯一绑定真实目标的完整 Bot；不是先建空白 Bot。请求 id 与 content 的分离及当前字段形状按真实接口契约。
2. 完整读回 Bot，取得真实 revision，核对身份、指南正文、绑定及非目标字段。
3. Task 型若有获准 prompt 变化，再重核写入条件，按 Task 合法 PUT 完整提交配置，仅改变 prompt；保留名称、模型、thinking、skill、suite、类型、group 等全部实际非目标信息，不能因接口限制静默丢字段。无法无损保存则停止并说明。
4. 完整读回 Task 与 Bot，逐字段核对最终候选及非目标保持。Map／Script 分支跳过 Task 更新，核对目标未变。

同一节点协调保存不代表事务。后一步失败时已有 Bot 保留；报告已生效／未生效／无法确认的部分，不自动删除、回滚、盲重试或重复创建，不把部分成功称为整体完成。后续如何修复由用户依据真实现场另行授权，不通过刷新基线掩盖失败。

## 5. 最终输出与完成条件

沿用旧创建bot的逻辑输出 ID：saved、handoff，分开提供真实文件，不新增 Map 顶层输出声明。

### saved

自包含 UTF-8 JSON，保留旧版完整对象组织：

- 完整已读回 Bot，含真实 id、名称、三个指南、唯一目标引用及实际非目标字段。
- 真实 Bot revision，来自服务而非时间戳、自编计数或重新序列化冒充。
- 唯一 target 及最终目标资料：Task／Map 为完整配置；Script 为准确脚本定位、核实来源、完整内容基线和必要依赖事实。不得虚构脚本 Task 配置或脚本 revision。

### handoff

自包含交接说明，格式按建设时明确的 V2 JSON 协议，记录身份、唯一绑定、需求确认／最终候选／保存授权依据、材料来源及用途、归属调整、共享影响、保存／读回检查、未验证项及部分效果。不复制完整配置和三指南正文，不承担隐式寻址。

Task 分支不再强制 target_unchanged=true；如实区分获准 prompt 变化、语义保持和其他配置不变。Map／Script 继续要求目标未变。精确字段与版本由建设者明确交回，不能误称通过旧创建 v1 Schema，也不修改旧消费者。

只有目标、全部授权修改、保存读回、非目标保持和必要交付均完成，才声明可交接。文件失败不撤销已保存配置，不交付伪成功检查。最终标注「文本／定义优化完成，行为未验证」；配置存在或服务接受不证明工具／Skill 加载、模型遵循或实际业务效果。

文件写入遵循 docs/workflow-runtime.md「统一文件交接约定」及 docs/business-materials.md「文件与独立 Chat」：明确授权和位置、检查父路径及链接安全、不覆盖其他执行产物、UTF-8 完整保存并读回比较。不得套用旧空白创建／三路保存协议中与 V2 冲突的要求。
