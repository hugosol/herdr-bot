# 从 contract 到黑盒验收：验证代码库与通用执行流程建设计划

日期：2026-11-21  
状态：讨论共识与实施方向；不是产品验收通过声明。

实施记录：黑盒验收代码已迁入独立项目 `E:/Developer/myhub/herdr-bot-tester`。该项目通过显式产品根运行，产品构建与自身回归留在产品仓。当前命令见验证项目 `README.md`；本文的后续 Wayfinder 分流与通用执行流程仍是建设计划。迁移检查不能替代真实宿主／模型验收。

## 1. 文档目的与结论

本计划补齐现有需求开发流程中，从「已经明确验收要求」到「可靠地开发验证代码、运行验证、定位并修复问题」之间的缺口。

现有 Wayfinder 流程能够产出需求、`contract.md` 和 implementation tickets。Contract 已经描述可观察承诺、验收 interface、覆盖归属与证据要求，但这些内容并不自动构成高效的验证程序开发方法。直接让 agent 一次生成大量验收脚本，再运行昂贵的完整检查，容易把环境、驱动、判定、产品和模型行为问题混在一起，形成高成本返工。

本次讨论确认三项建设工作，按用户提出的顺序逐步推进：

1. **建设独立的 Herdr 黑盒验证项目。** 从现有脚本中抽取跨仓验收场景及其设施，借鉴 pstack 重新梳理架构，以真实场景证明其可用性。
2. **更新 oh-my-wayfinder 的票据流程。** 区分产品实现票与黑盒验收票，保留 contract 的承诺和覆盖归属，使两类票进入不同的执行方式。
3. **建设通用黑盒验收开发与执行流程。** 以验收票、contract、指定版本的被测系统和项目验证能力为输入，开发验证代码、完成验证、诊断失败，并在授权范围内修复产品和复验。

Herdr-bot 是第一个实践项目，不是通用流程的隐含前提。流程既适用于一个项目，也适用于多个项目共同组成的系统。

### 1.1 共识与建议的区分

- **已达成共识**：上述目标与三项计划；黑盒验收定位；利用 pstack 已有能力补缺而非重造；验证代码需要工程化，但不能递归地为所有测试编写测试；项目专用能力与通用工作方法分离。
- **建议实现方向**：本文提出的职责划分、接入信息、执行阶段、结果表达、试点选择和交付检查。它们用于指导后续设计，不代表所有具体方案已批准或实现。
- **后续两步尚待确定**：通用技能的名称和安装位置、产品修改授权、证据留存政策。本文的示例不是当前命令或既定协议。

原调研只形成了本文。独立验证项目的后续实施见页首记录；Wayfinder 分流与通用执行流程仍待实施。

## 2. 问题定义：缺的不是更多脚本

### 2.1 已有基础

以 Node 成果批准为例，现有 [contract](../../../archive-docs/herdr-bot/node-result-approval/contract.md) 已明确：

- P1–P38 的可观察承诺及具体覆盖归属；
- S1 公开 HTTP、S2 原生工具、S3 真实页面三个验收 seam；
- 独立预期不能由被测实现计算；
- 受控机制、真实宿主、真实模型和页面证据不能互相替代；
- 缺授权、缺依赖、缺覆盖和清理失败不能冒充完整通过。

现有脚本也不是从零开始：已有 `acceptance/host` 设施、显式接收多个 worktree 的入口、来源记录、独占环境、原生观察和证据归档。

缺口主要是：如何把这些要求转成职责清晰、能够逐步开发和廉价诊断的验证软件。

### 2.2 已观察到的成本来源

用户报告的主要问题是：agent 一次生成大批脚本，随后运行完整回归；出现问题后修改，再次长时间运行，消耗时间和 token。

历史 [test.md](../../../archive-docs/herdr-bot/node-result-approval/test.md) 记录了多种不同原因，不能统一称为「测试失败」后直接改脚本：

| 问题 | 应优先定位的层次 |
| --- | --- |
| 查询路由错误、隔离索引未就绪 | 项目操作方式和环境前提 |
| Ask 返回值与标签比较错误、候选识别错误 | 验证程序的解析与判定 |
| provider 排队、流缺终帧、网络超时 | 传输与运行容量 |
| 模型没有生成材料或完成交接 | 被测业务／模型行为，或需要进一步澄清的驱动设计 |
| 已有单工具成功，但缺完整流程证据 | 覆盖与结论范围 |

这些记录证明了需要分层诊断，但不是量化性能基线；本计划不声称已经证明能够节省多少运行时间或 token。

### 2.3 避免误读原有票据

12–15 的票据要求「跳过中途完整 build／lint／test／formatter；完成后一次执行本票所需检查」。禁止的是中途完整检查，不是禁止所有小型实验。

建议后续把两种运行明确写开：

- **开发反馈**：验证当前新增或修改的最小能力与场景，快速暴露错误。
- **最终认证**：完成该票规定的完整矩阵、必需仓库检查、来源核对与清理。

窄反馈不能替代最终认证；最终认证也不应成为调试每个解析错误的唯一入口。

## 3. 术语与适用边界

### 3.1 黑盒验收

本文使用「黑盒验收」作为正式定位：从约定的外部 interface 驱动被测系统，通过独立预期和实际观察证明 contract 承诺。

可以验证 HTTP 服务、CLI、浏览器应用、原生宿主或组合系统。仓库数量、编程语言和运行进程数不是分类依据。

「集成测试」可作为宽泛称呼，但不能据此假定流程只适用于多仓联调。这里也不要求建立统一的单元／集成／端到端层级分类体系。

### 3.2 TDD 与黑盒不是对立概念

TDD 是开发方法，不等于单元测试。黑盒测试也可以先行。

本计划关注的是测试使用的 interface、预期来源和证据，而不是规定所有项目必须采用或禁止 TDD。

### 3.3 黑盒不等于禁止读取源码

执行者可以读源码来了解启动方式、查找公开 interface、诊断故障和修复产品。

但验收结论不能用下列行为替代 contract 要求的证明：

- 调用私有函数代替规定的公开路径；
- 直接写内部状态来制造应该由被测系统产生的事实；
- 复用产品算法计算期望值；
- 由驱动补写模型应生产的材料，随后声称模型完成了交接。

原则是：**诊断可以深入内部，证明必须经过约定的外部 interface。**

### 3.4 两种交付与两种结论

- **产品实现票**交付产品行为及所属开发回归。
- **黑盒验收票**交付可复跑的场景、必要的验证能力增量及针对明确版本的结论。

产品实现票不因存在独立验收流程而免除自身测试责任。

验证程序可靠与产品通过验收也是两件事：可靠的验证程序可能正确发现产品缺陷；脚本退出零也不自动证明验证程序可靠。可以交付验证代码并报告产品失败，但不能因此把要求完整通过的验收票关闭。

## 4. 总体职责划分

| 部分 | 拥有的职责 | 不应承担的职责 |
| --- | --- | --- |
| Wayfinder | 澄清承诺、生成 contract、分配覆盖及依赖、产生票据 | 不内置所有项目的启动、驱动和取证细节 |
| 通用黑盒验收流程 | 理解票据、设计场景、检查能力、开发验证代码、分类诊断、按权限修复、形成结论 | 不硬编码 Herdr、仓库数量、语言或特定模型 |
| 项目验证系统 | 项目实际的启动、检查、驱动、观察、隔离、取证和清理 | 不擅自改写 contract 或判断需求范围 |
| 产品仓库 | 产品实现、构建、交付数据及自身回归 | 不必拥有所有跨系统场景的编排实现 |

pstack 是建设和维护上述能力的方法来源，不是运行时底座。最终验证代码应能由明确的命令执行，不要求 AI agent 每次临场生成操作才能运行。

## 5. pstack 已覆盖什么，仍缺什么

### 5.1 `create-verification-skill`：能力调查与项目入口

该技能先调查仓库，而不是让用户补充可以从环境查到的事实：

| 调查维度 | 要回答的问题 |
| --- | --- |
| Surface | 用户实际接触哪个表面？ |
| Run | 怎样启动，如何确认已经可用？ |
| Drive | 已有什么 harness，缺什么自动操作能力？ |
| Observe | 能取得哪些响应、原生记录、文件、截图、日志和退出事实？ |
| Isolate | 能否隔离实例、目录、端口和会话？ |

然后形成 Launch、Doctor、Drive、Evidence、Cleanup、Helpers 及 feature map。它优先复用已有 harness，并要求实际运行一个功能、完成清理、确认清理后证据仍保留。

可直接借鉴这一调查方式。它的默认产物是项目 verification skill，不是现成的通用跨仓 runner，也不是直接消费 Wayfinder ticket 的完整开发流程。

### 5.2 `maintain-verification-skill`：漂移与缺口分类

该技能区分：

- 描述错误或缺失：文档漂移；
- 产品行为可用，但 harness 无法驱动：验证能力缺口；
- 产品行为真正损坏：产品问题，报告，不能通过改文档掩盖。

它要求源码调查和真实运行，维护范围限制在验证 skill 及其所属文件。该维护流程不直接授权产品修复；本计划第 3 步若允许修复产品，须另行规定权限。

其完整维护流程会检查功能地图并执行真实功能，不适合作为每次小修改后的默认廉价检查。

### 5.3 `architect`：共享能力的职责与调用方式

适用于多个场景反复需要相同但组织混乱的能力，例如原生确认观察、所属进程退出确认、证据身份关联。

它要求先调查受影响系统，再比较结构，选择状态所有者明确、做法单一、调用方知识负担较低的设计。

增加一个简单场景或断言不应触发全仓重新架构。

### 5.4 `build-the-lever`：把已证明的动作固化为工具

原则是先做出第一个单元，再构建工具并在该单元上重跑证明。交付应是可复跑的工具，而不只是人工操作总结。

其限制同样重要：建设能完成或证明工作的最小脚本，不先造通用框架。

### 5.5 `figure-it-out`、Feature 与小步验证原则

这些提供通用开发方法：先明确可证伪的完成条件、优先处理未知风险、按小单元实现并实测、保留决策与失败事实。

它们不是现成的「验收票执行流水线」，不能因为测试代码也是软件，就原样套用所有设计、委派和 PR 仪式。

### 5.6 `reflect`／`correct` 与后续固化

稳定出现的问题应优先通过架构、类型、运行检查或针对性测试解决，文档提醒是最后一层。

试点后再把有效做法固化成专用 skill。不能只因一个个别失败就加入长期规则，也不应在每次验收期间临时修改通用流程来迎合当前结果。

### 5.7 已知适用限制

已读文档包含 Cursor 与 Claude Code 使用方式，但本计划没有验证 pstack 在 OMP 中的完整直接执行适配。可复用其方法不等于所有命令、模型角色和外部工具已经在当前宿主可用。

跨项目通用也不等于跨操作系统。Herdr 原生窗口、焦点、声音和交互仍受真实 Windows 环境条件约束。

## 6. 第一步原计划：建设独立的 Herdr 黑盒验证项目

本节保留抽取前的目标、风险、候选试点和完成标准。它不是当前迁移任务清单，也不记录各完成标准的验收结果。

### 6.1 目标

把已有验收资产组织为长期可维护的软件，使后续新增票据主要编写场景和判据，而不是重复实现进程、配置、宿主、取证和清理。

### 6.2 迁移边界

建议迁入独立项目：

- 真正跨系统的验收场景与完整性判定；
- acceptance-only 的驱动、观察与 probes；
- 环境隔离、所属进程管理、回环服务和证据归档；
- 显式安装／来源核对与运行管理；
- 验证设施自身必要的针对性测试。

建议保留在产品仓：

- 后端、前端及产品自身浏览器回归；
- 产品构建与交付元数据；
- Toolkit 的扩展、锁文件、基线与自有 docks；
- 依赖产品编译和生产路由的安全壳、记录器等产物。

验证项目调用或消费产品仓的能力，不复制并另行维护产品实现。不能按 `scripts/` 目录边界整体搬迁。

### 6.3 已知迁移风险

前期源码调查发现：

- 部分 preflight 强制 `cwd == herdr-bot 根目录`；
- 入口通过自身文件位置推导产品根；
- 部分浏览器 driver 直接导入产品 `frontend/node_modules`；
- 共享 host 设施中仍包含 Toolkit 布局、页面和角色知识；
- 部分场景通过继承其他业务场景取得运行能力；
- 当前产品仓来源哈希包含验收代码，拆仓后这一隐含关系会消失。

因此独立运行必须显式提供被测根、产物与安装来源，并另行记录验证仓及实际执行 helper 的身份。不能通过删除来源校验来解除目录耦合。

这些是本会话调查时的事实，不是对后续工作树的永久快照。正式迁移前应对当前源码确认受影响路径；现有 MCP 索引曾对 `scripts/` 存在排除，图中缺少符号不代表代码不存在。

### 6.4 建议架构职责

| 职责 | 负责 | 禁止混入 |
| --- | --- | --- |
| 场景 | 业务前置、允许动作、Promise 对应关系与独立预期 | 通用进程管理和各类宿主解析 |
| 驱动与观察 | 操作真实系统，返回可关联的事实 | 偷补业务材料、批准、报告或通过标记 |
| 判定 | 比较实际事实与独立预期，报告违约或缺证 | 启动进程、向模型追加指令以凑成功 |
| 运行管理 | 来源、环境、资源、时限、归档和清理 | 某个业务为什么应批准的规则 |

这是职责划分，不预定四个包、四层类继承或插件系统。简单场景可以直接调用已有能力并做直白断言。

### 6.5 建设步骤

1. 按 pstack 的五个调查维度盘点现有能力及证据。
2. 给每项能力标明现有实现、调用方、已证明范围与真实缺口。
3. 选择一个完整真实场景，从独立项目启动并完成观察、判定、证据和清理。
4. 只抽取该场景实际需要的共享能力；以另一个不同类型的场景检验是否真正可复用。
5. 按依赖逐批迁移，更新 import、源码定位、命令调用方、证据清单、网络护栏和文档。
6. 避免长期双实现；具体公共命令兼容要求要显式决定，不擅自删除仍有消费者的入口。

原调研未选定试点。当时的候选包括历史 Chat 跨端恢复的单格和票 12 的工具机制场景。前者适合检验独立运行边界，后者适合检验接票方法。单格只证明试点目标，不替代原完整矩阵。

### 6.6 本步完成标准

- 可以从独立项目启动，不靠当前目录或邻居目录猜测产品位置；
- 显式绑定参与源码、产物、安装和验证代码身份；
- 至少一个完整真实场景跑通，包括清理和清理后的证据留存；
- 缺依赖、缺覆盖或清理失败不会被误判为完整通过；
- 产品自身回归仍由其原有入口维护；
- 新场景可复用已证明的能力，不要求每次重新编排底层设施。

## 7. 第二步：更新 Wayfinder 的票据流程

### 7.1 分类依据

分类依据是主要交付和证明责任，不是「文件名里含 test」，也不是是否涉及多个仓库。

产品实现票仍拥有必要回归。黑盒验收票负责指定外部承诺及真实证据。不同票之间应保持 coverage 的唯一所有者，不能重复认领或在拆票时丢失分区。

### 7.2 验收票建议提供的信息

- contract 来源与精确 coverage 分区；
- 依赖的实现能力与参与项目；
- 被测版本如何在执行时绑定；
- 必须经过的外部 interface；
- 必须是真实行为的部分，以及允许受控的部分；
- 驱动可以提供的指令、材料和确认权限；
- 完整矩阵、必需回归与通过条件；
- 授权及资源前提；
- 产品与验证代码的可修改范围；
- 证据、失败和未验证的交付要求。

不要求票据重复项目验证系统中所有安装和启动说明。票据引用能力入口，项目入口维护具体操作。

### 7.3 执行与关闭语义

- 实现能力满足前置后，验收票才可执行；不把实现票关闭当成行为正确的证据。
- 缺环境与授权应明确报告，不自动安装宿主或寻找用户凭据。
- 场景代码可以提交，产品仍可能未通过；不能用「脚本已实现」关闭要求通过的验收票。
- 发现产品问题后形成可重现的反馈，按授权修复或返回产品工作流。
- 修复后基于新的源码／产物重新判断哪些证据仍有效。

具体 ticket 类型字段、状态机、模板和路由 skill 尚未设计。此步应调查 oh-my-wayfinder 的实际实现后修改，不在本计划中假定其内部路径或接口。

### 7.4 本步完成标准

一份真实需求可以生成职责清楚的两类票；coverage 无遗漏与重复归属；验收票能被第 3 步流程消费，而不需要执行者猜测被测范围、真实程度和交付门槛。

## 8. 第三步：建设通用黑盒验收开发与执行流程

### 8.1 定位

这是要新设计的通用流程，不是声称 pstack 已有同名能力。

复用的是工作方法：读票、调查、开发、验证、诊断与修复。项目差异留在各项目的 verification skill、工具和操作说明里。

不要求所有项目使用 Python、同一个 runner、同一种输出目录、同一个宿主或多仓布局。

### 8.2 项目接入约定

pstack 的 verification skill 结构可以作为基础，但「曾使用 pstack 建设」不能自动视为可接入证明。通用流程至少应能找到：

| 信息 | 用途 |
| --- | --- |
| 验证入口与能力地图 | 知道已有能力和运行方式 |
| 来源与产物选择方式 | 确定验证的是哪个系统 |
| Launch／Doctor | 建立并检查可操作的环境 |
| Drive／Observe | 实际执行动作并取得可信事实 |
| 隔离与授权规则 | 避免操作非本轮资源 |
| 单场景与完整认证入口 | 分离开发反馈与最终交付 |
| 结果与证据位置 | 能读到具体失败、缺证和原始事实 |
| Cleanup | 确认所属资源退出与证据留存 |
| 修改权限 | 区分验证代码修复与产品修复 |

初期可以用清晰的项目文档与 skill 表达，不必立即设计统一 JSON schema。只有重复需求稳定后才固化格式。

### 8.3 通用执行阶段

#### A. 读取票据并设计证明

为每个场景明确：

- 哪项承诺由它证明；
- 如何建立并确认前置状态；
- 驱动能做什么、不能做什么；
- 独立预期是什么；
- 从哪里取得实际事实；
- 什么事实关联证明因果顺序；
- 何时继续、失败、停止或保留未验证；
- 最小反馈入口是什么。

设计应简短且可执行，不复制一份更长的 contract。若关键判据涉及业务歧义，返回澄清，而不是让运行器自行定义答案。

#### B. 绑定系统与权限

确认源码、产物、验证代码、安装版本、配置和授权。禁止回退到协调仓旧产物、正常用户会话或未声明安装。

一次执行应有明确身份。后续修复产生新的版本和执行记录，不覆盖旧失败。

#### C. 检查能力与风险最高的未知项

先复用现有能力。产品能完成但 harness 无法驱动或观察，才是验证能力缺口的证据之一。

按当前切片需要，验证关键环境假设，例如原生历史可读、确认可观察、实际 Bash 与后端处于相通环境。不把环境预检扩展成另一套全量业务验收。

#### D. 开发最小真实纵向场景

完成前置、动作、观察、判定、归档和清理的完整小闭环。先一个宿主／一个场景，再扩展矩阵。

现有能力足够时只添加场景。只有必要的共享能力缺失时才进入设施开发。

#### E. 分类失败并定向处理

| 类别 | 处理方向 |
| --- | --- |
| 环境或授权不可用 | 报告前提不足，不伪造成功、不擅自扩权 |
| 驱动／观察错误 | 修复验证能力，并用对应窄反馈及必要真实场景验证 |
| 判据与 contract 不符 | 独立修正判据，保留此前结果；不暗改通过条件 |
| 产品不满足承诺 | 保留可重现事实，在授权范围内修复产品 |
| 模型未完成被要求的自主行为 | 保留真实失败／未完成，不自动强迫顺序或重试成绿 |
| 证据不足、无法归因 | 标记未验证或不确定，不强行判断产品失败或成功 |

分类不必一次完成。无法定位时保留不确定性，并设计一个最小区分实验。

#### F. 修复与复验

产品修复和验证程序修复应分别记录动机与验证范围。通用流程不能默认拥有所有参与仓库的无限修改权限。

新增需求、改变 contract、减少覆盖、放宽真实行为要求和扩大凭据授权均不属于自动修复。

重新执行遵守业务与模型的重试政策。新的独占运行不是把旧失败改绿，也不能自动认为所有副作用都可重放。

#### G. 扩展矩阵并最终认证

逐格扩展，保留选择范围与完整需求范围。完成所需检查后才形成整票结论。

现有 12–15 票要求各自的两仓检查。若未来希望复用检查结果，需要显式修改交付约定，并设计来源、依赖和失效规则，不能以「节省时间」为由默认跳过。

### 8.4 结果必须区分的事实

结果格式尚未确定，但应能分别表达：

- 当前选中场景的结果；
- 整票覆盖是否完整；
- 被测来源及证据是否有效；
- 必需仓库检查是否满足；
- 清理是否成功；
- 验证程序是否已实现，以及产品是否通过。

当前部分入口的 `--native-only` 非零并不自动说明所选原生场景失败。执行者要读取具名结果，不能只看顶层退出码并反复「修复」一个已经通过的诊断格。

### 8.5 本步完成标准

- 同一流程能消费不同项目的黑盒验收票，而不修改流程中的业务常量；
- 能判断复用能力与真实缺口，不默认重造 harness；
- 能实现并运行场景，保留独立判据和证据；
- 能区分环境、设施、产品和缺证问题；
- 修复受授权与 contract 约束；
- 只有满足票据要求时才报告完整通过；
- 在宣称跨项目通用前，建议用第二个交互方式或技术栈不同的项目验证接入。该建议不意味着当前已选定第二个项目。

## 9. 验证代码自身需要多少测试

### 9.1 不建立无限递归

| 代码 | 推荐验证方式 |
| --- | --- |
| 简单业务断言 | 直白表达独立预期，检查观察对象和时序；通常不另写测试 |
| 完整验收场景 | 运行真实场景取得证据；通常不为每个步骤再写一层测试 |
| 复杂解析、事件关联、覆盖汇总 | 针对合理反例编写少量测试，防止假绿和误判 |
| 进程、资源、传输等共享设施 | 验证具体风险及失败处理，并通过真实场景证明接通 |

不是因为文件属于测试库就需要被测试，而是某段代码承担了复杂、可复用且容易出错的软件职责。

### 9.2 何时停止

可信度来自 contract、独立预期、真实外部观察、必要反例和代码审阅的交叉检查，不来自无限层测试。

例如复杂判定器需要确认「错 execution 的成功事件」不会放行，但不再为这条反例测试写另一层测试。

不以测试代码覆盖率为目标，不测试简单断言的语言语义，不为每个 wrapper 建立测试。验证设施测试证明工具可靠性，不代替产品真实行为通过。

### 9.3 廉价反馈的适用范围

可用去敏的真实记录检查表单解析，用独立字面事件检查错身份／缺项／乱序拒绝。它们减少对昂贵真实运行的依赖，但不能被归档为新的原生或真实模型业务成功证据。

修改驱动后仍应执行对应的真实路径；修改完整因果链时不能仅靠记录重放宣布系统通过。

## 10. 12–15 票作为方法设计的具体参照

### 10.1 票 12：工具机制、身份与时序

票 12 涉及恢复、retry 竞态、角色、持久化、并发和嵌套。后续记录明确允许逐项用户指令触发真实工具，不要求模型自主编排。

适合检验：

- 驱动、观察与判定是否分离；
- 原生确认、execution 和实际进程能否正确关联；
- 场景能否按真实回执推进，而非依靠长时间总等待；
- 一个真实在途确认是否有足够时序证据。

### 10.2 票 13：模型行为本身是被测对象

票 13 的 P20 要求真实模型自行判断成果交接并先 approve 再 report。驱动不能直接指定这个工具顺序后再声称证明了遵从。

适合检验：通用流程是否能识别驱动权限，避免把用于票 12 的逐步指令策略误用到模型决策承诺上。

### 10.3 票 14：复杂发布业务与矩阵

票 14 覆盖 V1 及其他非 V2 发布节点，需要真实材料、真实脚本、原生角色与页面事实。

适合检验：

- 单格开发反馈与完整覆盖是否分开；
- 场景是否保留发布业务职责，而不是为测试简化成另一个流程；
- 独立预期是否能检测完整对象、revision、文件和交接结果；
- 故障能否定位到环境、驱动、传输或实际业务。

### 10.4 票 15：局部成功不能替代完整链路

已有记录说明原生批准成功，不意味着材料交付、manager complete、子 Run finish、父层批准和最终页面都完成。

适合检验：证据完整性与分区结论，而不是增加重复的底层 approve 断言。

这些历史票据是设计样本，不意味着本计划要重新执行或改写已归档票据。历史文档中的状态和绝对证据路径也不能直接当成当前可用产物；部分原始证据已按用户要求删除。

## 11. 三步计划的推进与衔接

用户确认的建设顺序仍是：独立验证项目 → Wayfinder 分流 → 通用执行流程。

下表保留原计划的顺序和检查标准。能力盘点和第一步各行是历史计划，不是完成记录。当前待建设的是 Wayfinder 分流和通用执行流程，以及用实际票据检验这两步。

| 阶段 | 主要产出 | 防止偏离的检查 |
| --- | --- | --- |
| 能力盘点 | 复用清单、真实缺口、迁移依赖 | 不把所有 helper 都认定为通用能力 |
| 第一步试点 | 独立运行的真实场景与最小架构 | 从新仓启动且来源、证据、清理完整 |
| 第一步扩展 | 按依赖迁移的验收资产与操作入口 | 不复制产品实现，不长期维护双实现 |
| 第二步 | 两类票据模板、依赖与路由 | contract coverage 无遗漏、执行权限明确 |
| 第三步 | 通用执行 skill 与接入约定 | 不硬编码 Herdr；既可接单项目也可接组合系统 |
| 实践与反馈 | 真实票据执行记录、流程修正 | 改进有证据，不以文档数量或脚本行数评价 |

最终评价应关注：接到新票后需要新增多少真正的业务场景代码，失败是否容易归因，是否能用最小检查验证修复，以及结论是否保持可信。当前没有性能基线，不预设时间或 token 的节省比例，也不新增产品性能 SLA。

## 12. 安全、授权与非目标

### 12.1 持续成立的约束

- 只操作本轮拥有的进程、目录、端口、会话和窗口；
- 显式授权真实模型与凭据，不自动发现或刷新用户认证；
- 生产后端与安全关机壳不能互换；
- 普通回环测试不自动升级为真实 LAN／mDNS 验收；
- 保留原始失败与清理失败，不用重试掩盖；
- 确认所属进程退出后再清理，目录可删除不代表进程已退出；
- 证据应与秘密和运行状态分离，保留政策另行明确；
- 全自动验收不等于无限权限，也不允许将缺证偷偷转为人工通过。

### 12.2 本计划不做的事情

- 不把所有产品测试集中到一个中央仓；
- 不强制统一语言、测试框架或操作系统；
- 不先建大型 DSL、插件市场、分布式调度器或万能 runner；
- 不把受控响应冒充真实模型判断；
- 不把 pstack 的 agent 并行等同于测试资源可以并行；
- 不为每个测试再写测试；
- 不削弱 contract 来提高通过率；
- 不在这份计划中直接实现技能、迁移脚本或修改历史验收结论。

## 13. 后续阶段待定细节

原计划为第一步列出四项决策：验证仓的名称、位置、依赖和入口；首批迁移清单与试点；公共命令的消费者与切换；验证仓、产品仓和外部安装的来源记录。当前入口及证据格式见验证项目 `README.md`，不把原决策清单当作待迁移工作。

Wayfinder 分流和通用执行流程仍需明确：

1. 通用流程 skill 的归属、命名及目标 agent 环境。
2. 项目接入信息先使用文档还是已有机器可读格式。
3. 产品修复授权：可修改哪些仓库、哪些变化必须返回澄清。
4. 最终认证所需检查、证据复用及失效规则。
5. 原始日志、敏感信息、模型记录、临时状态和最终证据的留存政策。
6. 用什么第二项目检验通用性，以及何时开展该验证。

这些细节应通过当前代码、实际消费者与小型运行证据确定；不能为了做完计划而提前填写未经验证的接口。
