# Wayfinder 验收票分流与通用执行流程待决方向

状态：已确认的建设方向，尚未实施。本文保留未完成工作，不是当前产品操作说明、既定票据协议或验收通过声明。正式测试入口与安全要求见[测试指引](../agents/testing.md)。

独立黑盒验证项目 `herdr-bot-tester` 已承接跨系统场景和验证设施，通过显式产品根运行。产品构建、自身回归与交付数据仍由产品仓维护。本页不重复已经完成的拆仓计划或验证设施内部实现。

## 目标与范围

后续按依赖推进两项工作：

1. 更新 Wayfinder 的票据流程，区分产品实现票与黑盒验收票，保留 contract 的承诺、覆盖归属和依赖。
2. 建设通用黑盒验收开发与执行流程，以验收票、contract、指定版本的被测系统和项目验证能力为输入，开发验证代码、诊断失败，并在授权范围内修复产品和复验。

Herdr-bot 是实践项目，不是通用流程的隐含前提。流程应能用于单项目或组合系统，不强制仓库数量、语言、runner 或输出格式。

这两项方向已确认；下列职责、接入信息、阶段和完成标准是待设计的建议，不代表具体接口或安装位置已批准。可以复用 pstack 的调查和开发方法，但不能把它视为已经提供完整的验收票消费协议，也不假定全部技能、角色和工具在目标宿主可用。跨项目通用不等于跨操作系统。

## 票据分流

分类依据是主要交付和证明责任，不是文件名是否含 test，也不是参与仓库数量。

- 产品实现票交付产品行为及所属开发回归，不因存在独立验收流程而免除测试责任。
- 黑盒验收票交付可复跑场景、必要的验证能力增量及针对明确版本的结论。
- 每项 coverage 只有一个责任所有者，不能重复认领或在拆票时丢失。

验收票应提供以下信息，而不重复项目安装和启动手册：

- contract 来源、精确 coverage 分区、实现依赖与参与项目。
- 被测版本的绑定方式，必须经过的外部接口，以及真实行为与允许受控的边界。
- 驱动可以提供的指令、材料和确认权限。
- 完整矩阵、必需回归、通过条件、授权与资源前提。
- 产品和验证代码的可修改范围，证据、失败及未验证项的交付要求。

实现能力满足前置后才执行验收票。实现票关闭不证明产品行为正确；场景代码已交付也不等于产品通过，不能因此关闭要求完整通过的验收票。缺环境或授权须明确报告，不自动安装宿主或寻找用户凭据。修复后按新的源码与产物重新判断证据有效性。

具体 ticket 字段、状态机、模板和路由 skill 尚未设计。实施前调查 Wayfinder 的真实消费者，不预设内部路径或接口。

完成条件是一份真实需求能生成职责清楚的两类票，coverage 无遗漏或重复，验收票可被后续流程消费而不需要执行者猜测范围和门槛。

## 项目接入信息

项目专用操作由项目的验证工具和手册维护。通用流程至少需要找到下列信息。

| 信息 | 用途 |
| --- | --- |
| 验证入口与能力地图 | 复用已有能力，区分缺口 |
| 来源和产物选择方式 | 绑定实际被测系统与验证代码 |
| 启动与环境检查 | 建立可操作的环境 |
| 驱动与观察 | 执行动作，取得可关联的响应、文件、原生记录和退出事实 |
| 隔离与授权 | 只操作本轮资源 |
| 单场景与完整认证入口 | 区分开发反馈和最终交付 |
| 结果与证据位置 | 找到具体失败、缺证和原始事实 |
| 清理 | 确认所属资源退出，按政策保留证据 |
| 修改权限 | 区分验证程序修复与产品修复 |

初期可以用项目文档和已有 skill 表达，不先设计统一 JSON Schema、DSL 或插件系统。曾使用某套技能建设，不构成可接入证明。

## 建议执行流程

### 设计证明

明确每个场景证明的承诺、前置状态、允许动作、独立预期、实际观察位置、因果关联、停止条件和最小反馈入口。涉及业务歧义时返回澄清，不能让 runner 自行定义答案。

黑盒验收可以先行，也不禁止读源码诊断。证明仍须经过 contract 约定的外部接口，不能用私有函数、直接写内部状态、产品算法计算预期或代模型补写材料来替代。

### 绑定系统与权限

绑定源码、产物、验证代码、安装版本、配置和授权。不回退到旧 checkout 产物、正常用户会话或未声明安装。修复产生新的版本与执行记录，不覆盖旧失败。

### 检查能力并实现最小场景

按当前切片验证风险最高的环境假设，例如原生历史可读、确认可观察、驱动与后端环境相通。不把环境检查扩成另一套全量业务认证。

先实现前置、动作、观察、判定、证据和清理的最小真实闭环，再扩展宿主和矩阵。已有能力足够时只加场景，必要的共享能力缺失时才开发设施。场景持有业务预期，驱动返回事实，判定不启动进程或追加指令凑成功，运行管理不决定业务为何应批准。

### 分类失败与修复

| 类别 | 处理 |
| --- | --- |
| 环境或授权不可用 | 报告前提不足，不伪造成功或扩权 |
| 驱动或观察错误 | 修复验证能力，执行对应窄反馈和必要真实场景 |
| 判据与 contract 不符 | 独立修正判据，保留此前结果，不暗改通过条件 |
| 产品不满足承诺 | 保留可重现事实，仅在授权范围内修复 |
| 模型未完成要求的自主行为 | 保留失败或未完成，不强迫顺序或重试成绿 |
| 证据不足或无法归因 | 标记未验证，设计最小区分实验，不强判成功或产品失败 |

产品修复与验证程序修复分别记录动机及范围。新增需求、改变 contract、减少覆盖、放宽真实行为要求、扩大凭据权限不属于自动修复。重跑遵守业务与模型的重试政策，新建独占运行不表示旧副作用可以安全重放。

### 扩展矩阵并形成结论

窄反馈用于开发，不能替代正式覆盖。最终认证也不应成为每个解析错误的唯一诊断入口。只有满足票据要求的完整矩阵、必需检查、来源核对与清理，才报告完整通过。复用检查结果需要明确来源、依赖和失效规则，不默认跳过。

结果分别表达选中场景、整票覆盖、来源与证据有效性、必需检查、清理、验证程序交付以及产品是否通过。顶层非零可能表示缺少完整覆盖，不能只凭退出码反复修复已经通过的诊断格。

## 两类模型验收不能混用

工具机制验收可以由明确的逐步用户请求触发真实工具，核对原生确认、execution、实际进程与响应。模型自主交接验收则须由模型自行判断批准、报告和完成顺序，驱动不能先指定顺序再声称证明了自主遵从。

复杂发布业务仍须检查真实材料、完整对象、revision、脚本、角色和页面。一次原生批准成功不代表材料交付、manager complete、子 Run finish、父层批准和最终页面均已完成。通用流程须保留这些结论的区别，而不是增加重复的底层断言。

## 验证程序的验证边界

简单断言直接表达独立预期，完整场景通过真实运行证明接通，通常不再为每个步骤写测试。复杂解析、事件关联、覆盖汇总以及共享进程和传输设施需要针对实际风险的反例，防止错 execution、缺项或乱序被放行。

不建立无限递归，不以测试代码覆盖率为目标。去敏记录重放可以降低开发反馈成本，但不构成新的原生或真实模型业务成功证据。改动驱动或完整因果链后仍需执行对应真实路径。

## 完成条件与待决事项

Wayfinder 分流完成后再开展通用执行流程。该流程应能复用能力、识别真实缺口、运行场景、保留独立判据、区分失败层次，并受授权和 contract 约束。宣称跨项目通用前，应以第二个交互方式或技术栈不同的项目验证接入；尚未选定该项目，不预设时间或 token 节省比例。

仍需确定：

1. 通用流程 skill 的活跃所有者、名称、安装位置与目标 agent 环境。
2. 项目接入信息采用文档还是已有机器可读格式。
3. 可修改的产品仓库、修改范围和必须返回澄清的条件。
4. 最终认证、证据复用及失效规则。
5. 日志、敏感信息、模型记录、临时状态和最终证据的留存政策。
6. 第二个试点项目及开展时机。

持续安全规则以[测试指引](../agents/testing.md)为准。全自动执行不授权无限权限，不允许用受控响应冒充模型判断、用缺证换人工通过、为提高通过率削弱 contract，也不意味着并行 agent 的测试资源可以任意共享。本文不授权实施这些方向或改变历史验收结论。
