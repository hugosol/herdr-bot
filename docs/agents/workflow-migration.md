# 在一个会话中迁移一条流程

供 Agent 与用户共同迁移用户选定的 Map 及必要关联定义。复用的是起手问题和 grilling 方式，不是固定改动清单或工作量承诺。范围随具体流程展开；一个会话未完成时如实交接，不以压缩范围换取结束。

方法决策见[可复用迁移方法与转换规则](../../.scratch/bot-map-contract-refactor/lighthouse/05-reusable-migration.md)。范例是[关联提示词的联合设计与确认](../../.scratch/bot-map-contract-refactor/lighthouse/04-coherent-prompts.md)：它提供「创建map」的迁移设计与确认正文。从[实际 Map 清单](../workflow-migration-inventory.md)选择下一条流程；清单分别记录仓库转换、用户确认及现场效果，不是运行门禁，也不把第一个范例的业务决策推广到其他 Map。

## 1. 确定本次对象与交付边界

从用户指定的 Map 开始，核实实际定义来源、文件身份及本次目标。已有迁移票时读取 Question、Handoff、状态与 claim，按[本地 tracker](issue-tracker.md)处理认领；尊重其他会话持有的 claim。

区分本次要交付的是迁移设计与确认正文、完整转换资产，还是获准落地的实际定义。Wayfinder 默认规划；只有明确授权的工作才写入实际配置，流程迁移不自动授权生产代码重构、部署或运行目标业务。

完成条件：目标 Map 与本次交付边界明确，而不是所有影响范围都已预知。

## 2. 读取当前权威与实际输入

读取 grilling、domain-modeling 技能及[领域约定](domain.md)，使用项目术语。迁移本轮 Bot/Map 新设计时，先读这些已批准权威：

- [流程迁移清单与共享影响范围](../../.scratch/bot-map-contract-refactor/lighthouse/01-flow-inventory.md)：用户选择、共享原件、Git 历史、清单状态及完成含义。
- [Bot 与 Map node 的完整数据结构和知识归属](../../.scratch/bot-map-contract-refactor/lighthouse/02-definition-schema.md)：字段、知识分层、身份和公开接口。
- [调用上下文与系统代码改造契约](../../.scratch/bot-map-contract-refactor/lighthouse/03-call-context-design.md)：执行者实际取得什么、角色装配与运行边界。
- 若涉及「创建map」或公共角色提示词，读取上方范例的相应已确认正文；其他流程使用各自已发布的正文权威。

沿实际配置定位 Map，从 node 的 Bot 引用追踪 Task、script、子 Map，以及执行所需的 skill、文档和公共指引。调查事实由 Agent 完成，不让用户代查。按问题继续展开引用，不先要求建立整个仓库的完整依赖图。

当前代码与产品说明可能仍是旧实现：分别记录“现有行为”和“已批准目标”，不要因旧实现尚未更新而推翻设计。

完成条件：能够说明流程正常路径、必要知识的实际读取入口，并区分已决定内容、事实缺口和本轮可询问的选择。

## 3. 用以下问题开始 grilling

将目标流程代入，作为本次工作的 Question：

> 根据已定稿的数据结构与调用设计，如何与用户共同完成这条流程的迁移，使关联定义和提示词完整、职责清晰，后续接入只使用已确认内容？
>
> - 在同一讨论中联合处理有逻辑关联的 Bot、Map/node、Task、skill、实现资料与公共指引，避免按字段拆分造成重复或冲突。
> - 从目标流程及真实依赖开始，逐步明确本次需要处理的对象和修改范围。
> - 明确每段知识的唯一权威、引用位置、上下文依赖与完整正文，整体检查遗漏、重复、冲突、权限和交付语义。
> - 复用已有确认；新增候选经用户确认后才作为迁移结果。已有政策需要改变时，明确旧到新的修订并回到原权威。
> - 后续发现问题时修订原权威，不在转换资产或开发阶段另造一套业务语义。开发前不要求真实运行流程，实际业务验证与定义转换分别报告。

按 grilling 的轮次询问当前前提已满足的问题，每题给推荐答案，等待用户回答再展开下一层。既有决定直接使用，不把它们重新包装成待选问题。

字段映射、稳定 ID 与引用、共享影响、接口、保存和中断处理都是遇到时检查的方面，不是必须逐项制定新政策的固定问卷。根据实际流程发现边界；不要为了预估工作量提前穷举，也不要漏掉已经发现的必要问题。

完成条件：本次范围内的真实问题已得到用户确认；有待定内容时继续讨论或保留为明确交接项。

## 4. 联合整理并核对执行侧可达性

依据确认结果组织完整正文及必要定义变更。对每项移除、迁移或合并的知识，核实新权威及执行者的读取入口：文档存在不等于执行者会取得，Bot 摘要也不等于执行上下文。

按真实涉及的场景检查独立 Task、普通节点、嵌套 Map、管理者、chief 或脚本；公共内容变动时调查其消费者。共享对象的维护、其他消费者的记录及完成状态使用既有权威，不自行扩大为同时迁移所有消费者。

已批准正文直接取用；本次需要新增或修订的正文放在同一讨论中确认。超出本次授权的变化先交由用户决定。保留必要身份、引用与接线，变更按适用契约处理。

完成条件：获准范围内的内容有唯一权威及明确接入位置，已发现的信息缺口和冲突得到处理；未处理项不能称为完成。

## 5. 按本次边界交付

Wayfinder 会话按其发布边界使用 Lighthouse 发布确认结果，再用 Backtracer 追踪前置和缺口，更新本票 Handoff 与地图。不要仅因一轮回答获确认就不断写入政策文件。

交付确认内容的位置、涉及对象与共享影响、实际完成的修改、已做检查和未验证事项。若本次获准交付完整转换资产或修改实际定义，按相应票据及实际保存契约完成，不以几段正文冒充完整对象；选择检查前读取[测试指引](testing.md)。

迁移清单的状态沿用其权威：用户确认完整转换才是“迁移完成”，设计确认、文件保存和实际业务验证不能互相替代。Git 承担修改历史，不另造备份、状态系统或通用迁移工具。

中断时按现有票据 Handoff 保存已确认权威、尚未回答的问题、现场效果与下一步；恢复时读当前权威和实际对象，不盲目重放修改。在 Wayfinder 中按暂停流程发布并释放 claim。

完成条件：本次承诺的产物与实际效果一致，用户已确认其范围；未完成时留下可继续的准确交接，不宣称整条流程已迁移或运行成功。
