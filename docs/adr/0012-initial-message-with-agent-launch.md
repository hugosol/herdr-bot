# 启动 agent 时交付初始消息，以开始轮次确认发起成功

- 状态：accepted
- 日期：2026-10-26
- 本记录为已确认的目标行为，不表示实现已经完成。

## 决策

发起 Chat 时，将初始 Skill 调用、Bot 固定指示与本次输入合成一条初始消息，通过启动 agent 的同一条 herdr 命令交付，不再在启动后额外调用 `agent prompt`。保持现有内容合成规则、模型与思考级别、扩展配置及历史 Chat 恢复行为；对外不再将启动与提交初始消息拆成两个阶段。

初始消息非空时，以本次启动的目标 agent 触发原生 `agent_start`、进入执行轮次作为发起成功的确认，不等待首轮结束，也不承诺模型服务已接受请求。确认必须关联本次启动，并保留已经开始过轮次的事实，避免首轮很快结束后仅因当前不再是 `working` 而漏判。初始消息为空时不发送空消息，只确认 agent 已就绪、可交互。

携带初始消息的调用显式选择新的确认方式；普通、不带初始消息的启动保持等待可交互就绪的契约。启动命令已进入终端队列或进程已出现，均不足以确认非空初始消息的发起成功。

等待超时但证据不足时，报告发起结果未确认、agent 可能已执行，保留已经取得的 Tab／Pane／agent 标识及现场，不自动重试或补发；明确的启动错误如实报告，不将全部错误归为结果未知。

## 权衡

选择原生轮次开始事件，而不是把模型服务响应作为统一启动成功门槛。所查 pi／omp 源码已有部分 provider 可复用的响应钩子，限定这些路径时第四层确认未必昂贵；但钩子在不同 provider 与 HTTP／WebSocket 路径间覆盖不一致，统一确认还需处理响应错误、重试及空响应等差异。`message_start` 也可能在联网前或本地错误路径产生，不能代替远端响应证据。

第三层确认直接对应本次需要的启动交付边界，并可复用 herdr 已有的原生轮次事件集成；后续模型调用失败属于轮次执行结果，不反向否定已经确认的发起事实。即便收到 HTTP 成功响应，也不代表模型任务最终成功。

## 原生依赖前提

真实启动烟测发现，所测 OMP 18.12.6 的 CLI 初始消息直接调用 `session.prompt`，不同于交互输入的 Skill 分派路径；`/skill:<name>` 会作为普通文本进入对话。Pi 1.4.0 的原生启动 Skill 展开已通过烟测。保持本决策要求的 OMP 初始 Skill 行为，需要原生入口提供相同的 Skill 分派能力，不能以文本已交付代替 Skill 已调用；该依赖尚待确定处理范围，本记录不表示全部实现已验收。
